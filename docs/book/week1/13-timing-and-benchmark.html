Chapter 13

Timing and your first benchmark

At the end of this chapter you can measure how long a piece of your program takes, say what the number means in milliseconds per step and nanoseconds per cell, explain why the same code runs twenty to a hundred times slower in a Debug build, and write a benchmark table that another person could reproduce.

  • A first feel for whether a loop is limited by memory or by arithmetic.

Why measure

Everything you have built so far has had one question attached: does it give the right answer? The tests from chapter 12 answer that. From this chapter on there is a second question that will follow you through the whole second half of the curriculum: how long does it take?

A Game of Life grid of 1,000 by 1,000 cells has one million cells. One generation looks at every cell and its eight neighbours. If that takes 5 milliseconds, you can animate 200 generations per second. If it takes 500 milliseconds, you get two. Same program, same answer, a completely different experience. And in week 18, when the "grid" is a SmolLM2-135M weight matrix and the "step" is producing one token of text, the time per step is the product: a model that answers in 20 milliseconds per token is usable, one that needs 2 seconds per token is not.

Here is the uncomfortable truth that every experienced programmer eventually accepts: guesses about speed are usually wrong. You will be sure that a change made your code faster and the clock will say it did not. You will be sure that one loop is the slow part and the clock will point at a different one. The only defence is to measure, and to write the number down. The number is your evidence trail: a record of what you ran, on which machine, and what you saw. The BENCH.md files in this repository are that trail, one per challenge, for the full 26 weeks.

First principle

Correct first, fast second. A fast program that gives the wrong answer is worth nothing, and speeding up code you may still have to change is wasted work. In Week 1 the order is fixed: all 13 tests green, then and only then the benchmark. The benchmark program bench_life.cpp never checks the answer; it trusts the tests to have done that.

Reading a clock from C++

To measure how long something takes you do what you would do with a stopwatch: look at the time before, look at the time after, subtract. In C++ the stopwatch lives in the header <chrono>, which you met in chapter 9 when you wrote sleep_for(100ms). Now you use the other half of it.

std::chrono::steady_clock::now() is a function call. It asks the operating system for the current reading of a clock and returns it. What it returns is a time point: a value that means "this instant". On its own a time point is not useful to print; it counts from some arbitrary starting moment that the operating system chose (often the moment the computer booted). What is useful is the difference between two time points. Subtracting two time points gives a duration: an amount of elapsed time, with a unit attached. Here is the smallest complete program that does it.

#include <chrono>
#include <print>

int main() {
    const auto start = std::chrono::steady_clock::now();

    long long sum = 0;
    for (int i = 0; i < 1000000; ++i) {
        sum += i;
    }

    const auto end = std::chrono::steady_clock::now();
    const auto elapsed = end - start;

    const double ms = std::chrono::duration<double, std::milli>(elapsed).count();
    std::println("sum = {}", sum);
    std::println("the loop took {:.3f} ms", ms);
    return 0;
}

$ tools/run.sh scratch/first_timing.cpp
sum = 499999500000
the loop took 1.835 ms

Your number for the second line will differ from this one. That is expected, and most of this chapter is about why. Read the program from the top.

const auto start = std::chrono::steady_clock::now(); takes the first reading. You write auto because the real type name of a time point is long and you never need to spell it; the compiler knows it. start is const because a reading, once taken, should not change.

Then comes the work you want to time: a loop that adds up the numbers from 0 to 999,999. The result is stored in a long long, a type you have not met yet: a whole number like int, but 8 bytes wide instead of 4, so it holds values up to about 9.2 × 1018. You need it here because 499,999,500,000 does not fit in the ±2.1 billion of a 4-byte int (chapter 2); in an int the sum would overflow, which is undefined behaviour. Do not take the 8 bytes on trust; ask sizeof, as you did in chapter 2.

#include <print>

int main() {
    std::println("sizeof(int)       = {} bytes", sizeof(int));
    std::println("sizeof(long long) = {} bytes", sizeof(long long));
    return 0;
}

sizeof(int)       = 4 bytes
sizeof(long long) = 8 bytes

bench_life.cpp uses the same type when it prints its cell count. The sum is printed afterwards for a reason you will see in a moment.

const auto end = ...now(); takes the second reading, and end - start subtracts them. The result, elapsed, is a duration. On this machine its unit is the nanosecond, one billionth of a second, and its value is a whole number of them. For a benchmark report you want milliseconds with decimals, which is what the next line does.

std::chrono::duration<double, std::milli>(elapsed) builds a new duration from the old one. The shape is Type(value): make a value of this type out of that one. You have seen the same shape when you built a vector with std::vector<int> v(5, 0) in chapter 6. The two things in angle brackets say what kind of duration: the number is stored as a double, and one tick means one milli-second (std::milli is the name for one thousandth). Because the new duration has a different unit, the conversion does the division by one million for you, and because the storage is a double, the fraction is kept. Finally .count() pulls the bare number out of the duration so you can print it or do arithmetic with it. The formatting {:.3f} prints three decimals.

Analogy

A time point is a reading on a clock face: "it says 14:03:27". A duration is what you get when you subtract two readings: "4 minutes 12 seconds". You never ask what time it was when the race started in absolute terms; you only care about the gap. Where it breaks: a wall clock shows the time of day, and steady_clock does not. Its readings are meaningless on their own and only differences between them mean anything. That is on purpose, as the next section explains.

Try it

Before you touch anything, write down a prediction: if the loop in first_timing.cpp runs ten million times instead of one million, how many milliseconds will it take? Then change 1000000 to 10000000, run it with tools/run.sh three times, and compare. The sum will be 49,999,995,000,000, which is another reason it needed a long long.

What this machine showed

One million iterations took 1.5 ms on each of three runs. Ten million took 24.5 ms, then 17.9 ms, then 16.1 ms. Ten times the work took between eleven and sixteen times as long, and the first run was the slowest by a wide margin. Both of those facts are the subject of the variance section below; if your numbers also refuse to be a clean 10×, nothing is wrong.

Why steady_clock and not system_clock

There are two clocks you will see in C++ code. std::chrono::system_clock is the wall clock: the time of day, the one your menu bar shows. std::chrono::steady_clock is a stopwatch: it only ever moves forward, at a steady rate, and nobody can set it.

The wall clock gets adjusted. Your Mac quietly synchronises it with a time server, and when it does, the reading can jump forward or backward, usually by milliseconds, by much more if the clock had drifted; you can also set it by hand in System Settings. (Daylight-saving time does not move it: system_clock counts in universal time, and only the displayed local hour changes.) If you time a loop with system_clock and an adjustment happens in the middle, your "elapsed" could be too long, too short, or negative. For measurement you want the clock that is guaranteed never to go backwards. The standard library tells you which is which.

#include <chrono>
#include <print>

int main() {
    using steady = std::chrono::steady_clock;
    using system = std::chrono::system_clock;

    std::println("steady_clock is steady: {}", steady::is_steady);
    std::println("system_clock is steady: {}", system::is_steady);

    // One tick of each clock, as a fraction of a second.
    std::println("steady_clock tick: {}/{} s", steady::period::num, steady::period::den);
    std::println("system_clock tick: {}/{} s", system::period::num, system::period::den);
    return 0;
}

steady_clock is steady: true
system_clock is steady: false
steady_clock tick: 1/1000000000 s
system_clock tick: 1/1000000 s

The using steady = ... lines are the "give a long type a short name" trick from chapter 7; they save typing and nothing more. The :: after the short name means "look inside", exactly as in std::println: steady::is_steady is the thing called is_steady that lives inside the clock type. It is a built-in yes/no fact about each clock. period is another built-in fact: the length of one tick, written as a fraction of a second with a top (num, the numerator) and a bottom (den, the denominator). The last two lines print that fraction: one nanosecond for the stopwatch, one microsecond for the wall clock on this system. A nanosecond tick does not mean the clock is accurate to a nanosecond; reading it costs about 18 nanoseconds itself on this machine (timing a million calls to now() in a row shows that). It means you will never lose precision by rounding in the clock, which is all you need.

The rule is simple: for measuring elapsed time, always steady_clock. The only reason to touch system_clock is to print today's date, which you will do once, by hand, when you fill in BENCH.md.

Durations and their units

You have already used two kinds of duration without stopping to look at them: 100ms in chapter 9 and duration<double, std::milli> above. A duration is a number plus a unit, and the unit is part of its type. This is the one thing that makes <chrono> feel heavier than a plain double, and also the one thing that makes it safer: you cannot accidentally add milliseconds to seconds and get nonsense, because the library converts for you. Here is the whole set of conversions you will need this week. This program does no timing, so its output is the same on every run and on every machine, and you can check each line by hand.

#include <chrono>
#include <print>

int main() {
    using namespace std::chrono_literals;

    // A duration knows its own unit. 1500ms is "1500 ticks of one millisecond".
    std::chrono::milliseconds d = 1500ms;
    std::println("d.count() = {} (in milliseconds)", d.count());

    // Converting to a bigger unit with integers throws away the remainder...
    std::chrono::seconds whole = std::chrono::duration_cast<std::chrono::seconds>(d);
    std::println("as whole seconds: {}", whole.count());

    // ...so for reporting, convert to a duration that counts in double.
    std::chrono::duration<double> seconds = d;
    std::println("as double seconds: {}", seconds.count());

    std::chrono::duration<double, std::milli> millis = d;
    std::println("as double milliseconds: {}", millis.count());

    std::chrono::duration<double, std::micro> micros = d;
    std::println("as double microseconds: {}", micros.count());

    // Arithmetic on durations keeps the units straight for you.
    auto total = 1500ms + 2s;
    std::println("1500ms + 2s = {} ms", std::chrono::duration<double, std::milli>(total).count());
    return 0;
}

d.count() = 1500 (in milliseconds)
as whole seconds: 1
as double seconds: 1.5
as double milliseconds: 1500
as double microseconds: 1500000
1500ms + 2s = 3500 ms

Two things to take from this. First, converting to a coarser integer unit (milliseconds to whole seconds) loses information, and the library makes you say so explicitly with duration_cast; 1500 ms became 1 s, not 1.5 s. Second, converting to a double-based duration never loses anything and needs no cast, which is why the benchmark uses duration<double, std::milli>. If duration is given no second argument the unit is one second, so duration<double> means "seconds as a double". std::micro is one millionth, std::nano one billionth. That is the entire vocabulary.

Debug versus Release: the same program, two numbers

Now a measurement that matters. The program below fills a vector of ten million std::uint8_t cells, the same element type as your Life grid, with alternating 0 and 1, then times how long it takes to add them all up. The filling is outside the timed region on purpose: you are measuring the sum, not the setup. The last line uses 1e6, which is how you write one million as a double: a 1 followed by six zeros, "1 times 10 to the 6". 1e9 is a billion.

#include <chrono>
#include <cstdint>
#include <print>
#include <vector>

int main() {
    const std::size_t n = 10000000;              // ten million
    std::vector<std::uint8_t> cells(n, 0);
    for (std::size_t i = 0; i < n; ++i) {
        cells[i] = static_cast<std::uint8_t>(i % 2);   // 0 1 0 1 0 1 ...
    }

    const auto start = std::chrono::steady_clock::now();

    long long alive = 0;
    for (std::size_t i = 0; i < n; ++i) {
        alive += cells[i];
    }

    const auto end = std::chrono::steady_clock::now();
    const double ms = std::chrono::duration<double, std::milli>(end - start).count();

    std::println("alive cells: {}", alive);
    std::println("summing {} cells took {:.3f} ms", n, ms);
    std::println("that is {:.3f} ns per cell", ms * 1e6 / static_cast<double>(n));
    return 0;
}

Run it the way you have run everything so far, with tools/run.sh. Then compile it a second way, by hand, with the flag -O2 and without the sanitizers, and run that. The -o /tmp/sum_rel part puts the finished program in the /tmp folder, which is where tools/run.sh puts its programs too, so that scratch/ stays free of compiled files. -O2 rather than the -O3 CMake uses for Release is deliberate: both are "optimised", the gap between them is tiny next to the gap from Debug, and chapter 11 promised you will measure them against each other in week 6. Here are both runs on this machine (Apple M5, macOS 26, Apple clang 21):

$ tools/run.sh scratch/sum_timing.cpp
alive cells: 5000000
summing 10000000 cells took 41.187 ms
that is 4.119 ns per cell
$ clang++ -std=c++23 -Wall -Wextra -O2 scratch/sum_timing.cpp -o /tmp/sum_rel
$ /tmp/sum_rel
alive cells: 5000000
summing 10000000 cells took 0.440 ms
that is 0.044 ns per cell

Same source file. Same answer, 5,000,000. One run took 41 milliseconds and the other took less than half a millisecond. That is a factor of more than ninety. Nothing about the program changed. What changed is how the compiler translated it.

In chapter 11 you set up two build types. A Debug build is what tools/run.sh makes and what your build/ directory contains: compiled with -g so a debugger can map machine code back to your lines, with -fsanitize=address,undefined so every memory access is checked, and with no optimisation. The compiler translates your code almost line by line: every cells[i] really does compute an address, really does ask the sanitizer "is this address allowed?", really does load one byte, really does add it to alive in memory, and really does increment i and compare it against n. Ten million times.

A Release build, which is what -O2 (or CMake's -DCMAKE_BUILD_TYPE=Release, which uses -O3) gives you, lets the compiler optimise: rewrite your program into any other program that produces the same observable output. Three things happen to this loop. First, there are no sanitizer checks to pay for. Second, alive and i live in registers instead of memory. A register is one of a few dozen tiny storage slots inside the CPU itself; the CPU can read or change a register in a fraction of a nanosecond, while a trip to memory takes far longer. Third, the compiler notices that adding sixteen neighbouring bytes can be done with one wide instruction instead of sixteen narrow ones, so the loop body handles sixteen cells per iteration. That last trick is called vectorisation, and you will write it by hand in week 12. For now it is enough to know that it is why 0.04 nanoseconds per cell is possible. The CPU ticks about four billion times a second, so one tick is roughly a quarter of a nanosecond. Getting through several cells per tick is only possible when one instruction handles many cells at once.

First principle

A compiler is a translator, and a translator can be literal or fluent. Debug is the literal translation: slow, but every line of your source corresponds to machine code you can step through, and every memory access is checked. Release is the fluent translation: fast, but the correspondence is gone, which is why debugging a Release build is miserable. You develop in Debug and you measure in Release. Never the other way round.

Trap

Never compare a Debug number with a Release number and conclude anything about your code. "I changed the loop and it went from 40 ms to 2 ms" is meaningless if the first run was from tools/run.sh and the second from -O2. Same build type, same inputs, same machine, or the comparison is noise. Write the build type in every row of your table so you cannot fool yourself later.

Why print the answer?

The programs in this chapter all print the sum they computed. This is not decoration. An optimising compiler is allowed to delete any work whose result is never used. If you timed the loop and then threw alive away, -O2 could legally remove the entire loop and report 0.000 ms, and you would be timing nothing. Printing the result (or otherwise using it) forces the work to happen. One honest caveat: printing protects the answer, not your loop. Compile first_timing.cpp with -O2 and it reports 0.000 ms with the correct sum: clang recognised the sum of 0 to 999,999 as something it could work out at compile time with a formula, and no loop ran at all. That is why every program from here on sums data that only exists once the program is running, read from a vector. The Life benchmark is protected in a different way: step is defined in life.cpp, a separate source file (chapter 10), so while the compiler translates bench_life.cpp it cannot see inside step. It has to assume the call does something that matters, and it must keep every one of them.

Variance: five runs, five numbers

Run the Release version of sum_timing three times in a row. Here is what that gave on this machine. The | tail -2 after each command is a shell trick, not C++: it keeps only the last two lines of whatever the program printed, so the unchanging alive cells line is left out.

$ /tmp/sum_rel | tail -2
summing 10000000 cells took 0.440 ms
that is 0.044 ns per cell
$ /tmp/sum_rel | tail -2
summing 10000000 cells took 0.444 ms
that is 0.044 ns per cell
$ /tmp/sum_rel | tail -2
summing 10000000 cells took 0.439 ms
that is 0.044 ns per cell

Three runs, three numbers. They agree to about one percent here, which is as good as a laptop gets, but they are not identical, and on another day, or with a browser open, the spread is far larger. Nothing is broken. A measurement of time is not like a measurement of sizeof(int), which is 4 every single time. It is a measurement of a physical system that is doing many other things at the same moment. Your terminal is redrawing. A browser tab is running a timer. The operating system is deciding which of the CPU's cores your program should run on, and on an M-series chip some cores are fast and some are built to save energy. Each of those shows up as noise in the number.

Some of the noise is systematic, and the first run pays most of it. When a program touches a region of memory for the first time, the operating system has to actually hand that memory over, in chunks called pages, and that costs time the second touch does not pay. The CPU's small, fast memories (the caches; much more in week 6) start empty and fill up as the program runs. And a CPU that was idling runs slowly to save power and takes a moment to speed up. (That is the CPU's own working speed, how many instructions it executes per second; it has nothing to do with the clock you read with now(), which ticks at the same rate regardless.) All of this means the first iteration of anything is slower than the rest, and if you time only the first one you measure the warm-up, not the work.

The fix is to do the work a few times before you start the clock. That is a warm-up. Then run the timed part several times and look at the spread. The program below does both inside one run of one program, and reports every run plus the fastest.

#include <chrono>
#include <cstdint>
#include <print>
#include <vector>

int main() {
    const std::size_t n = 10000000;
    std::vector<std::uint8_t> cells(n, 0);
    for (std::size_t i = 0; i < n; ++i) {
        cells[i] = static_cast<std::uint8_t>(i % 2);
    }

    const int runs = 5;
    std::vector<double> times;              // one entry per run, in ms
    long long alive = 0;

    for (int run = 0; run < runs; ++run) {
        const auto start = std::chrono::steady_clock::now();
        alive = 0;
        for (std::size_t i = 0; i < n; ++i) {
            alive += cells[i];
        }
        const auto end = std::chrono::steady_clock::now();
        times.push_back(std::chrono::duration<double, std::milli>(end - start).count());
    }

    double fastest = times[0];
    for (double t : times) {
        std::println("run: {:.3f} ms", t);
        if (t < fastest) {
            fastest = t;
        }
    }
    std::println("alive = {}", alive);
    std::println("fastest of {} runs: {:.3f} ms", runs, fastest);
    return 0;
}

$ /tmp/variance

run: 1.028 ms
run: 0.938 ms
run: 0.944 ms
run: 0.939 ms
alive = 5000000
fastest of 5 runs: 0.938 ms

Look at the shape of that: the first two runs are the slowest, by almost 20%, and then the number settles. That is the warm-up, made visible. Two more things to notice. Between separate launches of this same program, the fastest run moved between 0.57 ms and 0.97 ms on this machine. And this loop takes about twice as long as the same loop in sum_timing.cpp. The loop is character for character the same; what changed is the program around it, and the optimiser made a different choice when translating the two. From the outside you cannot tell which choice without reading the machine code. The lesson is practical: measure the exact program you care about, not a lookalike. All of this is normal on a laptop. Which number do you write down?

Two sensible choices. The minimum is the best the machine can do: every slower run is "the real speed plus some interference", so the smallest number is closest to the truth about your code. The median, the middle value when you sort the runs, is a better picture of what a user would experience, because interference is part of real life. For a code-versus-code comparison ("is loop order B faster than loop order A?") use the minimum of several runs; it is the most stable. For "how fast is my game?" use the median. Whichever you choose, say which one it is, and never report the mean (the sum of the runs divided by their count): a single slow outlier drags a mean far from anything you actually observed. In the five runs above the mean is 0.990 ms, a value no run produced.

And keep the machine quiet. Close the browser, stop the music, let a build finish before you start, and plug the laptop in: on battery, macOS may slow the CPU down to save power. You cannot remove the noise, but you can shrink it.

Stuck? First nudge

The median of five values is the one that has exactly two values smaller than it (ignore ties for now). Loop over every times[i]; for each one, loop over every times[j] and count those strictly smaller. When the count is 2, you have found it.

What to report, and in which units

The benchmark program prints three versions of the same measurement, and you should understand all three well enough to convert between them in your head.

  • Milliseconds per step: the raw measurement divided by the number of steps timed. This is what a player feels: at 5 ms per step you could draw 200 generations a second.
  • Nanoseconds per cell: ms per step, times a million (to get nanoseconds), divided by the number of cells. This is the number you compare across grid sizes. A 2000×2000 grid has four times the cells of a 1000×1000 grid and should take about four times as long per step, so ms per step changes but ns per cell should stay flat. If it does not stay flat, something interesting is happening and you have found your first real question.
  • Cells per second: cells divided by seconds per step. The same fact as ns per cell, upside down, in the unit that people in this field like to quote ("300 million cells a second"). It is a throughput: how much work gets done per unit of time.

Here is the arithmetic done by a program, with a made-up 4.0 ms so that the output is fixed and you can check every line by hand.

#include <print>

int main() {
    const double width = 1000;
    const double height = 1000;
    const double cells = width * height;          // 1,000,000 cells
    const double ms_per_step = 4.0;               // a made-up measurement

    // 1 ms = 1,000,000 ns, so ns per cell = (ms * 1e6) / cells.
    const double ns_per_cell = ms_per_step * 1e6 / cells;

    // cells per second = cells / seconds per step.
    const double seconds_per_step = ms_per_step / 1000.0;
    const double cells_per_second = cells / seconds_per_step;

    // Bytes moved per step: about 9 reads and 1 write per cell.
    const double bytes_per_step = cells * 10;
    const double gb_per_second = bytes_per_step / seconds_per_step / 1e9;

    std::println("ms per step:      {:.3f}", ms_per_step);
    std::println("ns per cell:      {:.3f}", ns_per_cell);
    std::println("cells per second: {:.1f} million", cells_per_second / 1e6);
    std::println("steps per second: {:.1f}", 1.0 / seconds_per_step);
    std::println("bytes touched per step: {:.0f} MB", bytes_per_step / 1e6);
    std::println("memory traffic:   {:.1f} GB/s", gb_per_second);
    return 0;
}

ms per step:      4.000
ns per cell:      4.000
cells per second: 250.0 million
steps per second: 250.0
bytes touched per step: 10 MB
memory traffic:   2.5 GB/s

Notice the coincidence in the first two lines: for a grid of exactly one million cells, ms per step and ns per cell are the same number, because a millisecond is exactly a million nanoseconds. That is a handy sanity check for the 1000×1000 case and a trap for every other size; at 500×500 the ns-per-cell figure is four times the ms-per-step figure.

The unit check you should do every time is the "does it fit on a napkin" check. Steps per second times ms per step must equal 1000. Cells per second divided by cells per step must equal steps per second. If your table says 4 ms per step and 2,500 million cells per second, one of them is wrong, and it is usually a factor of a thousand in a conversion. The program above also computes two more lines you will come back to at the end of the chapter: how many bytes a step touches, and how many gigabytes per second that is.

Beyond the three numbers, a benchmark row needs the facts that make it reproducible: the machine (Apple M5, 2026), the date, the build type (Debug or Release), the grid size, and what changed since the previous row. A number with no machine and no build type is a rumour.

Inference twin

Every language model benchmark you have ever seen quotes "tokens per second". That is cells per second with a different unit: work items divided by elapsed time. Underneath it is always ms per step, where a step is producing one token. In week 18 you will measure tokens per second for your own SmolLM2-135M, and by the end of week 19 you will build this exact table (fp32, Q8_0 and int8 W8A8 rows instead of Debug and Release rows, with Q4_0 as a stretch); the arithmetic will be identical. The one new idea there is that producing a token has two phases: reading the whole prompt at once, which is limited by arithmetic, and producing each new token, which is limited by how fast weights can be read from memory. You will measure both and they will land on different lines of the same table.

Reading bench_life.cpp line by line

You did not write phase1-terminal/01-life/bench/bench_life.cpp; it was given to you. But you should be able to read every line, because in the coming weeks you will write the same kind of program for other challenges, and from week 6 you will use a benchmarking library (Google Benchmark) that automates most of it. Open the file next to this page. Here is its top half, as a fragment: the five #include lines at the top of the real file (<chrono>, <print>, <string>, <utility> for std::swap, and "life.hpp") are left out here, so this block is not a complete program on its own.

int main(int argc, char* argv[]) {
    int size = 1000;
    if (argc > 1) size = std::stoi(argv[1]);
    const int width = size;
    const int height = size;
    const int warmup_steps = 3;
    const int timed_steps = 20;

    Cells current = random_cells(width, height, 12345, 0.35);
    Cells next(current.size(), 0);

    for (int i = 0; i < warmup_steps; ++i) {
        step(current, next, width, height);
        std::swap(current, next);
    }

Arguments. The program takes one optional command-line argument, the grid size, and defaults to 1000. argc and argv and std::stoi are from chapter 8: if you ran ./life_bench 2000 then argc is 2 and argv[1] is the text "2000", which std::stoi turns into the number 2000. The grid is always square; width and height are both size. Two more constants fix the shape of the experiment: 3 warm-up steps and 20 timed steps.

Setup. random_cells is your function from milestone 2. The seed is fixed at 12345 and the fill at 0.35, so every run of the benchmark starts from the same grid. That matters: a grid that is nearly all dead could, in a cleverer implementation, be faster than a busy one, and you want to compare like with like. next is a second vector of the same size, all zeros, for step to write into.

Warm-up. Three steps are run and thrown away, for the reasons from the variance section: first-touch memory costs, cold caches, clock speed. Each step reads current and writes next, and then std::swap(current, next) exchanges the two vectors (chapter 7) so that what was just written becomes the input to the following step. This is double buffering from chapter 7, the same shape you used for the one-dimensional automaton, and the swap costs nothing measurable: it exchanges the vectors' bookkeeping, not their million bytes.

    using clock = std::chrono::steady_clock;
    const auto start = clock::now();
    for (int i = 0; i < timed_steps; ++i) {
        step(current, next, width, height);
        std::swap(current, next);
    }
    const auto end = clock::now();

    const double total_ms = std::chrono::duration<double, std::milli>(end - start).count();
    const double ms_per_step = total_ms / timed_steps;
    const double cells = static_cast<double>(width) * height;
    const double ns_per_cell = ms_per_step * 1e6 / cells;

The timed loop. It is exactly the warm-up loop again, between two clock readings. Twenty steps rather than one, because one step is a few milliseconds and the noise you saw earlier is a sizeable fraction of that; averaging over twenty steps smooths it. (A moment ago you were told never to report the mean. There is no contradiction: that advice was about separate runs of a whole measurement, where one slow run is an outlier. Here twenty steps are timed as one block, and dividing the block by twenty is simply how you get the per-step figure. If you want the minimum, run the whole benchmark several times and take the smallest result.) Note that the clock is read twice in total, not twice per step. Reading the clock is cheap but not free, and keeping it outside the loop means its cost is divided by twenty.

The arithmetic. total_ms is the conversion you know. Dividing by timed_steps gives ms per step. The number of cells is computed in double, and look at the cast: static_cast<double>(width) * height converts the first operand before the multiplication, so the product is done in floating point. For 1000×1000 this does not matter, but for a 50,000×50,000 grid the int product would overflow and you would get a nonsense cell count with no warning. Converting first is a habit worth copying. Then ns per cell is the formula from the units section.

    std::println("grid: {}x{} ({} cells)", width, height, static_cast<long long>(cells));
    std::println("steps timed: {} (after {} warm-up)", timed_steps, warmup_steps);
    std::println("ms per step:  {:.3f}", ms_per_step);
    std::println("ns per cell:  {:.3f}", ns_per_cell);
    std::println("cells per second: {:.1f} million", cells / (ms_per_step / 1000.0) / 1e6);
    return 0;
}

The prints. The first two lines restate the experiment so that the output alone, pasted into a note, is enough to know what was measured. Look at the static_cast<long long>(cells) in the first line. cells is a double, and std::println prints a large double in scientific notation: 1e+06 for a million, 4e+06 for four million. Converting it back to a whole number first makes it print as 1000000, which is what you want to read in a grid description. The last three lines are the three units. Cells per second is computed inline: cells divided by seconds per step, divided by a million to print in millions.

What the benchmark does not do: it never calls render, never prints the grid, never sleeps, and never checks the answer. Rendering a million-character string and pushing it through the terminal would take longer than the step itself and would bury the thing you want to measure. The animation loop in your main.cpp does all of that, and that is exactly why you never time the game loop to learn about step.

The loop-order experiment, on a grid that is not Life

To show you the shape of the loop-order experiment without writing your step for you, here is the same comparison on a simpler job: summing a 4096×4096 checkerboard, once with y outside and x inside, once the other way round. Both orders visit every cell exactly once and compute the same total.

#include <chrono>
#include <cstdint>
#include <print>
#include <vector>

int main() {
    const int width = 4096;
    const int height = 4096;
    std::vector<std::uint8_t> grid(static_cast<std::size_t>(width) * height, 0);

    // A checkerboard: alive where x + y is odd.
    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            grid[static_cast<std::size_t>(y * width + x)] = static_cast<std::uint8_t>((x + y) % 2);
        }
    }

    // Order A: y outer, x inner. Walks the flat vector from front to back.
    auto start = std::chrono::steady_clock::now();
    long long alive_a = 0;
    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            alive_a += grid[static_cast<std::size_t>(y * width + x)];
        }
    }
    auto end = std::chrono::steady_clock::now();
    const double ms_a = std::chrono::duration<double, std::milli>(end - start).count();

    // Order B: x outer, y inner. Same cells, same sum, jumps 4096 bytes between reads.
    start = std::chrono::steady_clock::now();
    long long alive_b = 0;
    for (int x = 0; x < width; ++x) {
        for (int y = 0; y < height; ++y) {
            alive_b += grid[static_cast<std::size_t>(y * width + x)];
        }
    }
    end = std::chrono::steady_clock::now();
    const double ms_b = std::chrono::duration<double, std::milli>(end - start).count();

    std::println("alive (y outer, x inner): {}", alive_a);
    std::println("alive (x outer, y inner): {}", alive_b);
    std::println("y outer, x inner: {:.3f} ms", ms_a);
    std::println("x outer, y inner: {:.3f} ms", ms_b);
    std::println("ratio: {:.1f}x", ms_b / ms_a);
    return 0;
}

Here start and end are not const, because they are reused for the second timing; everything else is the pattern you know. In Release, the wrong loop order is almost forty times slower (between 30× and 40× across runs on this machine) for an identical amount of arithmetic. The only difference is the sequence of addresses the CPU visits. Front to back, each byte it fetches is next to the previous one. The hardware never fetches a single byte from memory; it fetches a block of 128 bytes at a time on this chip (64 on most Intel and AMD chips) and keeps the block in a cache. So one fetch serves the next 128 reads for free. The CPU also notices the front-to-back pattern and starts fetching the following blocks before you ask for them. Now order B. One row is 4096 cells of one byte each, so moving down one row means jumping 4096 bytes. Every single read lands in a different block, so every read needs its own fetch, nothing useful is fetched ahead, and by the time the loop comes back round for the next column, the fastest cache has long since thrown those blocks out to make room. In Debug the ratio is only 1.3×, because the sanitizer overhead on every access is so large that the memory system is never the thing being waited for.

Now the surprise promised above. When the loop order of that reference step was swapped, the Release number went from 2.76 ms to between 3.1 and 3.7 ms across runs: 1.1× to 1.4× slower, not 35×. Why so little, when the sum above lost a factor of more than thirty? Because a Life step does far more work per cell than a sum. Each cell costs eight neighbour reads, sixteen wrap calls each with a %, and a couple of comparisons; that arithmetic takes about 2.7 ns per cell, and at that pace the memory system can keep up with either visiting order. In the sum, the arithmetic is a fraction of a nanosecond per cell, so memory is the only thing that matters and the order dominates. The lesson is not "loop order does not matter" (it does, and it will matter enormously in week 6). The lesson is that what bounds a loop depends on how much work it does per byte, and you cannot know which case you are in without measuring. Your prediction may well have been 10× or more. Write down what it actually was.

Is the step waiting on memory or on arithmetic?

You can get a first feel for this with the napkin arithmetic from the units program. One Life step over a million cells reads each cell about nine times (itself and its eight neighbours) and writes it once. That is about 10 bytes of memory traffic per cell, 10 megabytes per step. At 3 ns per cell a step takes 3 ms, and 10 MB in 3 ms is a little over 3 gigabytes per second.

Now compare that to what the machine can do. The memory system of an Apple M-series chip can deliver over 100 GB/s to a program that asks for memory in the friendly, front-to-back pattern, and the caches closer to the CPU are faster still. Your step is asking for 3 GB/s. It is using a few percent of the available memory bandwidth. So memory is not what the step is waiting for. It is waiting for the arithmetic: the % in wrap, the index multiplication, the eight additions, the branch that decides alive or dead. That is also why the loop-order swap barely hurt.

This kind of reasoning, compare the bytes moved per second with what the memory system can deliver, and the operations per second with what the CPU can execute, is the basis of a model you will learn properly in week 12 and use on every kernel after that. For now, take the habit: when you get a number, ask "how many bytes per second is that?" and "how many operations per second is that?", and see which one is close to a limit. Only the one that is close to a limit is worth optimising.

Inference twin

In a language model, producing one new token means reading every weight in the model once to do a small amount of arithmetic with it. For GPT-2 that is about 500 MB of weights read for roughly one multiply-add per weight, 124 million of them (for SmolLM2-135M, about 540 MB and 135 million): bytes dominate, and the step is memory-bound. Processing a long prompt in one go reuses each weight across many tokens: arithmetic dominates, and the step is compute-bound. Your Life step, at 10 bytes and perhaps 30 operations per cell, sits on the compute-bound side. Same question, same napkin, different answer.

Traps

Four mistakes that produce confident, wrong numbers. You will make at least one of them this year; the aim is to recognise it quickly.

Trap: timing the game loop

Your main.cpp loop does step, render, print, sleep. If you put the clock around that loop you measure the sleep. The program below times ten "frames" of a trivial sum with a 100 ms sleep in each; the sum itself takes well under a millisecond.

#include <chrono>
#include <cstdint>
#include <print>
#include <thread>
#include <vector>

int main() {
    using namespace std::chrono_literals;
    const std::size_t n = 1000000;
    std::vector<std::uint8_t> cells(n, 1);

    const auto start = std::chrono::steady_clock::now();
    long long alive = 0;
    for (int frame = 0; frame < 10; ++frame) {
        for (std::size_t i = 0; i < n; ++i) {
            alive += cells[i];
        }
        std::this_thread::sleep_for(100ms);     // the frame delay from your game loop
    }
    const auto end = std::chrono::steady_clock::now();

    const double ms = std::chrono::duration<double, std::milli>(end - start).count();
    std::println("alive = {}", alive);
    std::println("10 frames took {:.1f} ms, so {:.1f} ms per frame", ms, ms / 10);
    return 0;
}

The benchmark program exists precisely so that step is timed alone. Put the clock around exactly the thing you want to know about, and nothing else.

Trap: timing only the first iteration

The first iteration pays for memory being handed over page by page, for empty caches, and for a CPU that is still speeding up. On this machine the very first Life step read about 30% slower than the eighth, and the first run inside variance.cpp was almost 20% slower than the rest; with a cold machine or a grid that does not fit in the caches the gap is larger. Always warm up, always time several iterations, and divide.

Trap: optimising before the tests are green

Every change you make to go faster is a chance to break the rules of Life in a way you will not see on a random grid, because a random grid looks like noise whether or not it is right. The blinker and block tests will see it. Run ./build/life_tests after every experiment in your table, before you believe the number.

Trap: comparing across build types

Said once already, worth saying twice: a Debug number and a Release number cannot be compared to each other, and neither can two Release numbers from different machines, or from the same machine on a hot day with a video rendering in the background. Change one thing at a time, keep every other column of the table identical, and the number means something.

Check yourself

You call std::chrono::steady_clock::now() twice and subtract. What kind of value do you get, and why can you not simply print the result of a single now() as a time of day?

Answer

You get a duration: an amount of elapsed time with a unit (nanoseconds on this machine). A single now() is a time point measured from an arbitrary starting moment that the operating system chose, such as boot time, so on its own it is not a time of day. Only differences between two time points are meaningful.

Why does the benchmark use steady_clock instead of system_clock?

Answer

system_clock is the wall clock, and it gets adjusted (the operating system synchronises it with a time server, and you can set it by hand), so two readings can be a wrong distance apart or even go backwards. steady_clock only moves forward at a constant rate and is never set; is_steady is true for it and false for the wall clock.

A step on a 1000×1000 grid takes 4 ms. What is that in ns per cell, in cells per second, and in steps per second? Now the same step on a 2000×2000 grid takes 17 ms. What is the ns per cell, and is that what you would expect?

Answer

4 ms × 1,000,000 ns/ms ÷ 1,000,000 cells = 4 ns per cell; 1,000,000 cells ÷ 0.004 s = 250 million cells per second; 1000 ÷ 4 = 250 steps per second. For 2000×2000: 17 ms × 1e6 ÷ 4,000,000 cells = 4.25 ns per cell. Roughly flat, about 6% higher, which is within normal variance; a plain step should give the same ns per cell at every size.

Your Release build reports 0.000 ms per step. What has happened, and which tool tells you?

Answer

step is doing nothing: it is still the stub, or the Release build was made from a life.cpp without the implementation. The benchmark cannot detect this, because it only measures time. ./build-release/life_tests (or the Debug tests) is what checks that the work is actually done. Tests first, benchmark second.

You time the same loop five times inside one run of a program and get 1.18, 0.87, 0.47, 0.82 and 0.97 ms. Which number do you report for a code-versus-code comparison, and why not the mean?

Answer

The minimum, 0.47 ms, because every slower run is the real cost plus some interference from the rest of the machine, so the smallest value is closest to what your code itself costs and is the most stable between runs. The mean (0.86 ms here) is dragged around by outliers that have nothing to do with your code. The median is a reasonable alternative when you want "what a user experiences".

Summing a 4096×4096 grid with the wrong loop order was over 30× slower in Release, but swapping the loop order in a Life step cost well under 2×. Explain the difference in one or two sentences.

Answer

The sum does almost no arithmetic per byte, so its speed is set entirely by how fast memory can be fetched, and the visiting order changes that enormously. A Life step does dozens of operations per cell (neighbour reads, wrap calls, comparisons), so the CPU's arithmetic is the thing everything else waits for, and the memory system has slack to absorb a worse access pattern. What bounds a loop depends on work per byte.

Why does every timing program in this chapter print the sum it computed, even when nobody cares about the sum?

Answer

An optimising compiler may delete any work whose result is never used. If the sum were never printed or otherwise used, -O2 could remove the whole loop and the timing would report nearly zero. Using the result forces the work to really happen.

Why must the numbers in BENCH.md come from build-release/ and not from build/, and why is running the Debug benchmark once still worthwhile?

Answer

build/ is a Debug build: no optimisation and sanitizer checks on every memory access, so its numbers measure the sanitizers and the literal translation, not your code; on this machine the gap was about 45×. Running it once, with a prediction written down first, teaches you what those checks cost and makes you recognise a Debug number instantly when you see one by mistake.
