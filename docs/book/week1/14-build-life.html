The spec, restated

You are building life, a terminal program that plays Conway's Game of Life. The full specification is in phase1-terminal/01-life/README.md; it was frozen before the week started, and this chapter does not change it. Here is what it says, in one place.

The world. A rectangular grid of width columns and height rows. Every cell is either alive (1) or dead (0). The grid is a torus: the left edge touches the right edge and the top edge touches the bottom edge, so every cell has exactly eight neighbours and there are no corners to treat specially. The whole grid is one flat std::vector<std::uint8_t> (the type is named Cells in life.hpp) in row-major order, so the cell at column x, row y lives at index y * width + x, exactly as in chapter 7.

The rules. One generation is computed from the previous one. A live cell with 2 or 3 live neighbours stays alive. A dead cell with exactly 3 live neighbours becomes alive. Every other cell is dead in the next generation.

The program. It takes six optional arguments, each with a default:

ArgumentMeaningDefault
--width Ncolumns60
--height Nrows20
--seed Nseed for the random start; the same seed always gives the same grid1
--fill Fprobability that a cell starts alive, a number from 0.0 (nobody) to 1.0 (everybody)0.3
--fps Ngenerations drawn per second10
--steps Nhow many generations to run; 0 means forever, until Ctrl-C0

Each frame, the program moves the cursor to the top-left corner and redraws the whole grid in place with ANSI escape codes (chapter 9), a live cell as # and a dead cell as ., then sleeps so that --fps frames fit into a second. The cursor is hidden while the animation runs and shown again before the program exits, including when --steps runs out.

The proof. Thirteen doctest cases in phase1-terminal/01-life/tests/life_test.cpp must pass in a Debug build with the sanitizers on, and phase1-terminal/01-life/BENCH.md must contain real numbers from a Release build at 1000×1000.

Setup: build it and read the red

Everything is already in place. life.hpp declares the six functions, life.cpp contains a stub for each one (a body that compiles but does nothing useful: it returns a constant, or returns nothing at all), main.cpp prints one line and exits, and CMakeLists.txt builds three programs: life, life_tests and life_bench. Chapter 11 explained every line of that file. Configure once, build, run the tests:

$ cd phase1-terminal/01-life
$ cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
$ cmake --build build
$ ./build/life_tests

The test program prints a long list of failures. Do not panic and do not scroll past it; this list is your to-do list for the week. Here is the very end of it, which is the part to read first:

[doctest] assertions: 10061 | 10010 passed | 51 failed |
[doctest] Status: FAILURE!

Twelve test cases fail. That is correct and expected: you have not written anything yet. Look at the second line, though. 10,010 individual assertions passed. How can that be, when nothing works? Because one test case, random_cells: size, determinism and fill extremes, loops over 10,000 cells and checks that each one is 0 or 1, and the stub returns a vector of zeros, which are all valid cell values. The passing case is step: does not modify current. It copies a grid, calls step, and checks that the original is unchanged. The stub step does nothing at all, so of course the original is unchanged. The test is satisfied by a function that is completely useless.

This is the most important lesson of the setup, and chapter 12 already explained the mechanics: why step: does not modify current passes with a stub, and why 10,010 of the assertions pass before you have written a line. The lesson, that a passing test is not proof, is the one to carry into your own tests.

First principle

A passing test is not proof that the code is right. It is proof that the code is not wrong in the one way that test checks. That is why the test file has thirteen cases and fifty-one assertions and not one: each closes off a different way of being wrong. When all thirteen are green you still do not have proof, only a strong argument. Keep that humility; it is what the review ritual at the end of this chapter is for.

Several individual assertions pass by the same accident. index_of(0, 0, 10) == 0 passes because the stub returns 0. wrap(0, 10), wrap(10, 10) and wrap(-10, 10) all expect 0, so they pass too. random_cells with fill 0.0 is expected to be all dead, and a vector of zeros is all dead. Whenever your own tests pass later in the week, ask the same question you just asked about the stub: could a wrong function have passed this?

Milestone 1: index_of

Goal. Make int index_of(int x, int y, int width) return the position in the flat vector of the cell at column x, row y. This is the smallest function in the project and the one every other function depends on. Get it right and every later test that talks about positions is talking in your language.

Re-read. Chapter 7, the section on row-major order, and the figure with the flat index written inside each cell. Also the comment at the top of life.hpp: the contract tells you the layout in its own words.

Tests that must turn green: index_of: row-major flat index. Run only that one:

$ cmake --build build && ./build/life_tests -tc="index_of*"

The * at the end is a wildcard: every test case whose name starts with index_of. Here it matches exactly one.

Try it

Before you write the real body, do what chapter 12 had you do once: make the stub return x instead of 0, rebuild, run the filtered test. Two of the five checks pass and three fail. For each failing one, read the values: line and say out loud what the stub got wrong, for example "it ignored the row". When you can say it for all three, you know what the formula has to add. Then put the stub back to return 0; and write the real line.

Rung 1: where to look

Read the five CHECK lines in the test. Write the five inputs and expected outputs in a table on paper: (0, 0, 10) → 0, (9, 0, 10) → 9, (0, 1, 10) → 10, (3, 2, 10) → 23, (4, 4, 5) → 24. Which of the three inputs, when it goes up by one, makes the answer go up by one? Which makes it go up by width?

Rung 2: the idea in words

Rows are laid down one after another. Before row y begins, y complete rows have already been laid down, each one width cells long. Then, inside the row, you walk x cells further. The answer is "the number of cells in the rows before mine, plus how far I am into my own row".

Rung 3: the arithmetic in words

Multiply the row by the width. Add the column. Return that. There is no loop, no if, no vector; the function is one line long, and the one mistake available is multiplying the wrong one of x and y. Check your line against (3, 2, 10) → 23 by hand before you compile: 2 rows of 10 is 20, plus 3 is 23.

Common bugs. Multiplying x by width instead of y. The symptom is specific: index_of(9, 0, 10) returns 90 instead of 9, and the test prints CHECK( 90 == 9 ). Notice that (4, 4, 5) still passes with the bug, because when x == y the two formulas agree. That case is in the test precisely so you see it pass while the others fail and learn not to trust a square.

Definition of done. The filtered run says 1 passed | 0 failed; the full run says 2 passed (this one plus the accidental one). Suggested commit message: M1: index_of green.

Milestone 2: random_cells and render

Goal. Two functions that let you see a grid. random_cells(width, height, seed, fill) creates a grid of the right size in which each cell is alive with probability fill, and the same seed always gives the same grid. render(cells, width, height) turns a grid into a std::string: # for alive, . for dead, one row per line, and a '\n' after every row including the last.

Re-read. Chapter 6 for constructing a vector of a given size filled with one value, and for range-for. Chapter 8 for building a string with +=, and for std::mt19937 and std::uniform_real_distribution. Chapter 7 for the two nested loops that walk a grid row by row.

Tests that must turn green: random_cells: size, determinism and fill extremes and render: '#' alive, '.' dead, newline after every row.

$ cmake --build build && ./build/life_tests -tc="random_cells*,render*"

Two things about render that the test is strict about. First, every row ends with '\n', the last one too. The expected string for a 3×2 grid is "#..\n..#\n", eight characters, two of them newlines. If you only put a newline between rows, you are one character short and the test prints the two strings so you can compare them. Second, the characters are exactly '#' and '.', nothing else, no spaces between cells.

Here is that newline rule on a different picture: a bar chart built as one string, one bar per row. Watch the character count at the end.

#include <print>
#include <string>
#include <vector>

int main() {
    const std::vector<int> heights = {3, 1, 4};
    std::string picture;
    for (int h : heights) {
        for (int i = 0; i < h; ++i) {
            picture += '#';
        }
        picture += '\n';          // every row ends with a newline, the last one too
    }
    std::print("{}", picture);    // print, not println: the newlines are already inside
    std::println("characters in the picture: {}", picture.size());
    return 0;
}

####

Eight # characters and three newlines make eleven. When you later print a rendered grid in main, use std::print rather than std::println, for the reason in the comment.

Two things about random_cells. The first is determinism: the test calls it twice with seed 42 and demands identical vectors. A std::mt19937 seeded with the same number produces the same sequence of numbers every time, on every run, on every machine. Here are two engines with the same seed and one with a different seed, side by side:

#include <print>
#include <random>

int main() {
    std::mt19937 first(42);
    std::mt19937 second(42);
    std::mt19937 other(43);
    for (int i = 0; i < 3; ++i) {
        std::println("draw {}: seed 42 -> {}   seed 42 again -> {}   seed 43 -> {}",
                     i, first(), second(), other());
    }
    return 0;
}

draw 0: seed 42 -> 1608637542   seed 42 again -> 1608637542   seed 43 -> 494155588
draw 1: seed 42 -> 3421126067   seed 42 again -> 3421126067   seed 43 -> 2134003008
draw 2: seed 42 -> 4083286876   seed 42 again -> 4083286876   seed 43 -> 2615920895

The second thing is the fill extremes: with fill equal to 0.0 every cell must be dead, with 1.0 every cell must be alive, and with 0.5 on a 100×100 grid the test accepts anything between 4,000 and 6,000 live cells. A std::uniform_real_distribution<double>(0.0, 1.0) hands out numbers in the half-open range [0, 1): zero is possible, one never occurs. So a draw is never below 0.0, and always below 1.0. Count it:

#include <print>
#include <random>

int main() {
    std::mt19937 gen(7);
    std::uniform_real_distribution<double> unit(0.0, 1.0);   // draws are in [0, 1): 0 possible, 1 never
    int below_zero = 0;
    int below_30 = 0;
    int below_one = 0;
    for (int i = 0; i < 1000; ++i) {
        const double u = unit(gen);
        if (u < 0.0) {
            ++below_zero;
        }
        if (u < 0.3) {
            ++below_30;
        }
        if (u < 1.0) {
            ++below_one;
        }
    }
    std::println("of 1000 draws: {} below 0.0, {} below 0.3, {} below 1.0", below_zero, below_30, below_one);
    return 0;
}

of 1000 draws: 0 below 0.0, 284 below 0.3, 1000 below 1.0

About 30% of the draws are below 0.3, as you would hope; the exact number, 284, is a property of seed 7 and will be the same every time you run this program. Not one draw was below 0.0 and every draw was below 1.0, which is the half-open range in action.

Trap

< or <=? If you decide a cell is alive when its draw is strictly below fill, both extremes come out right for free: no draw is below 0.0, so fill 0.0 gives no live cells; every draw is below 1.0, so fill 1.0 gives all live cells. Decide "less than or equal" instead and fill 0.0 produces a live cell on the rare draw of exactly zero. The test would catch that only once in a very long while, which is the worst kind of bug: it passes on your machine today and fails on someone else's next month. Chapter 8's section "Alive with probability fill means r < fill" is the same rule.

Rung 1: where to look

For render: the test render: '#' alive, '.' dead, newline after every row shows the exact expected string for a 3×2 grid. Count its characters. For random_cells: the stub already returns a vector of the right size; look at how it computes that size and keep it. The chapter 8 section on randomness shows an engine, a distribution and a seed; which of those three does the seed parameter feed?

Rung 2: the shape of the loops in words

render: start with an empty string. Two nested loops, the row loop outside and the column loop inside, so you visit the cells in the same order they sit in memory. Inside the inner loop, append one character depending on the cell. After the inner loop finishes a row, append a newline. Return the string. random_cells: make the vector of the right size, all dead. Create one engine from the seed and one distribution over [0, 1). One loop over every cell; for each, take a draw and compare it with fill; set the cell to 1 if the draw is below.

Rung 3: the arithmetic in words

Inside render's inner loop you need the cell at column x, row y. You wrote the function for that in milestone 1; call it rather than repeating the formula. The index it returns is an int and the vector wants a std::size_t: chapter 6 showed the static_cast<std::size_t> that makes the compiler stop warning. In random_cells you do not even need x and y: a single loop over the whole vector, visiting each cell once, is enough, because the fill does not care where a cell is.

Rung 4: the engine and the seed

The engine must be created inside random_cells, from the seed parameter, every time the function is called. If you create it once outside the function, or seed it from the clock, the second call with seed 42 continues the sequence instead of restarting it, and a == b fails even though both grids look random. The seed is the only thing the caller controls; honour it.

Common bugs and their symptoms.

  • Missing final newline. The test prints CHECK( #..\n..# == #..\n..#\n ), but with each \n shown as a real line break, so the two strings are spread over several lines. Look for the empty line at the end of the expected one; your string does not have it.
  • Rows and columns swapped in render. If the loops are swapped, the 3×2 test grid comes out as 2 rows of 3 turned on its side. If the index formula is swapped, you read past the end of the vector and the sanitizer reports a heap-buffer-overflow (see the debugging playbook).
  • All 32 alive for fill 0.0 and none for fill 1.0. You compared the wrong way round: "alive when the draw is above fill". fill 0.5 cannot catch that, because half is half either way; the extremes can.
  • Live count exactly 0 or 10,000 for fill 0.5. Either you compared the draw with something other than fill, or every cell got the same draw because the engine is created inside the loop, so each pass starts the sequence again from the seed and takes the same first number. (Creating the distribution inside the loop is harmless, if wasteful: it has no memory of its own.)

Definition of done. Both filtered cases pass; the full run shows 4 passed, 9 failed. You can now also test render by eye in a scratch program: render a random_cells(10, 4, 1, 0.3) grid and look at it. Commit: M2: random_cells and render green.

Milestone 3: wrap and count_neighbours

Goal. wrap(v, n) brings any integer v, including a negative one, into the range 0 to n - 1, like the hour hand of a clock: three hours before 2 o'clock is 11, not -1. The analogy breaks in one place: a clock face runs from 1 to 12 and has no 0, while wrap runs from 0 to n - 1 and works for any n, not only 12. count_neighbours(cells, width, height, x, y) returns how many of the eight cells around (x, y) are alive, on a torus, never counting the cell itself. This is the heart of Life and the place where most bugs in this project live.

Re-read. Chapter 7: the clock-face section on wrapping in one dimension, the negative-modulo trap, the "neighbours on a ring" section, and the section about the bug that only a non-square grid catches.

Tests that must turn green: wrap: like a clock face, count_neighbours: interior cell, count_neighbours: does not count the cell itself, count_neighbours: edges wrap around (torus). Do wrap first and run its case alone, then the three others:

$ cmake --build build && ./build/life_tests -tc="wrap*"
$ cmake --build build && ./build/life_tests -tc="count_neighbours*"

Before you write wrap, see the trap once more with your own eyes. In C++, the remainder of a negative number is negative:

#include <print>

int main() {
    std::println("10 % 10 = {}", 10 % 10);
    std::println("11 % 10 = {}", 11 % 10);
    std::println("-1 % 10 = {}", -1 % 10);
    std::println("-11 % 10 = {}", -11 % 10);
    std::println("-1 / 10 = {}", -1 / 10);
    return 0;
}

10 % 10 = 0
11 % 10 = 1
-1 % 10 = -1
-11 % 10 = -1
-1 / 10 = 0

The test asks for wrap(-1, 10) == 9 and wrap(-11, 10) == 9. Plain % gives -1 for both. A clock does not have an hour called -1; one hour before 0 is 9. The last line, -1 / 10 = 0, is the reason: C++ rounds a division towards zero, and the remainder is whatever is left over after that, so it carries the sign of v.

Trap

Three fixes that are almost right. The seven test cases are chosen to catch each of them.

  • "If v is negative, add n." Gets -1 right (9) but turns -11 into -1.
  • "Take the remainder, then always add n." Gets -1 right but turns 0 into 10 and 7 into 17.
  • "Add n first, then take the remainder." Gets -1 and -10 right but turns -11 into -1 again.

Each of those fails at least one of the seven. Check all seven cases by hand against your formula before you compile.

Try it

Copy neg_mod.cpp into scratch/ and add one std::println per test value (0, 7, 10, 11, -1, -10, -11) that prints your candidate formula's result next to the expected answer. Run it with tools/run.sh. Only when all seven lines agree, move the formula into life.cpp. This is the smallest possible experiment, and it is faster than rebuilding the whole project to find out.

Now the neighbours. A cell at (x, y) has eight neighbours, found by adding an offset between -1 and 1 to each coordinate and skipping the one offset pair that is (0, 0), the cell itself:

  dx:      -1       0       +1
        +-------+-------+-------+
 dy=-1  |(-1,-1)|( 0,-1)|(+1,-1)|     the row above
        +-------+-------+-------+
 dy= 0  |(-1, 0)| SKIP  |(+1, 0)|     left and right
        +-------+-------+-------+
 dy=+1  |(-1,+1)|( 0,+1)|(+1,+1)|     the row below
        +-------+-------+-------+

On a torus, x - 1 for x = 0 is not -1 but width - 1, and y + 1 for the bottom row is 0. That is exactly what wrap is for: wrap the column with width, and wrap the row with height. Both. Separately. The test edges wrap around (torus) uses a 5×3 grid, not a square, so that wrapping the row with width by mistake gives a wrong answer instead of a lucky one. Chapter 7's wrong_formula.cpp showed why: on a 7×3 grid the swapped formula draws the wrong picture, and when height is larger than width it indexes past the vector, so the sanitizer stops you. The 5×3 torus test exists for the same reason.

Rung 1: where to look

wrap: the comment above it in life.hpp says "like the hands of a clock". Which of the seven test cases does plain % get wrong? Exactly the negative ones. count_neighbours: the test interior cell draws a ring of eight live cells around the centre of a 5×5 grid and also asks about the corner (0, 0), which touches only (1, 1) of that ring directly. Draw the 5×5 grid on paper and count the corner's neighbours by hand, remembering that the corner's other neighbours wrap to the far side.

Rung 2: the idea in words

wrap: take the remainder of v by n. If that remainder is negative, it is n too small; add n. Alternatively, take the remainder, add n (the number is now certainly positive), and take the remainder once more to bring it back under n. Either way, test it against all seven cases on paper, -11 included. count_neighbours: for each of the eight offsets, compute the neighbour's column by wrapping x plus the horizontal offset with width, and its row by wrapping y plus the vertical offset with height. Look up that cell. Add its value to a running total. Return the total.

Rung 3: the shape of the loops in words

Two tiny nested loops, one for the vertical offset from -1 to 1, inside it one for the horizontal offset from -1 to 1. At the top of the inner body, if both offsets are zero, continue: that is the cell itself. Otherwise wrap, index, add. The running total starts at 0 before the loops and is returned after them. A cell's value is a std::uint8_t, which is a small integer, so adding it to an int total works directly; alive is 1, dead is 0, so the sum is the count.

Rung 4: the arithmetic, and the one line to get right

The lookup is the same as in render: your index_of with the wrapped column and the wrapped row, cast to std::size_t for the vector. The classic mistake is to wrap one coordinate and not the other, or to wrap the row with width. Say the line out loud as you type it: "column wrapped by width, row wrapped by height". If you have eight nearly identical lines instead of two loops, that is allowed, but the review will ask why.

Common bugs and their symptoms.

  • Counting the cell itself. The does not count the cell itself case reports CHECK( 1 == 0 ) for the lone centre cell. The interior cell case stays green with this bug, because every cell it asks about is dead; that is exactly why the second case exists.
  • Forgetting to wrap. The edges wrap around (torus) case fails with 0 == 1. If you also index without wrapping, the sanitizer stops the run with a heap-buffer-overflow, because x - 1 became -1 and there is no cell -1.
  • Wrapping the row with width. The two square-grid cases pass. The 5×3 case stops with a sanitizer report on its very first check, count_neighbours(g, 5, 3, 0, 0). The first neighbour it looks at is offset (-1, -1): column -1 wraps to 4, and row -1 wrapped by 5 instead of 3 is row 4. A 3-row grid has no row 4. Index 4 × 5 + 4 = 24 in a 15-cell vector, so the report says 9 bytes after 15-byte region, with count_neighbours and its line number in the first stack frame.
  • Negative modulo in wrap. wrap(-1, 10) returns -1, and later every negative index makes the sanitizer shout.

Definition of done. All four cases pass; the full run shows 8 passed, 5 failed, and the five remaining failures all begin with step:. Commit: M3: wrap and count_neighbours green.

Milestone 4: step

Goal. step(current, next, width, height) computes one generation. It reads only from current, writes every cell of next, and never modifies current. The two vectors already have width * height cells each when the function is called.

Re-read. Chapter 5 on const Cells& versus Cells&: the signature tells you which one you may write to. Chapter 7, the Rule 90 section: the one-dimensional automaton that goes wrong when updated in place and right with two buffers. step is that program with one more dimension and eight neighbours instead of two.

Tests that must turn green: all six step: cases.

$ cmake --build build && ./build/life_tests -tc="step*"

The rules, as a table. Read the row for the cell's current state, then the column for its neighbour count:

Cell now0 or 1 live neighbours234 to 8
alivedies (loneliness)stays alivestays alivedies (crowding)

Only two cells in that table come out alive: a live cell with 2 or 3, and a dead cell with 3. Everything else is dead. Notice what that means for how you write next: it is not enough to set the cells that become alive. Every cell of next must be written, dead ones included, because the test a lone cell dies hands you a next that is deliberately full of 1s and expects every one of them to become 0. A function that only writes births leaves that garbage in place.

The test to believe first is the blinker, a row of three live cells. It is the smallest pattern that changes and comes back, and if it works, the rules, the neighbour count and the double buffering (two vectors: read from one, write into the other, then swap, as in chapter 7) are all right at once:

 generation 0      generation 1      generation 2
  .....             .....             .....
  .....             ..#..             .....
  .###.     -->     ..#..     -->     .###.
  .....             ..#..             .....
  .....             .....             .....

Why does it do that? Count by hand. The middle cell (2, 2) has two live neighbours (left and right): it survives. Each end cell has one live neighbour (the middle): it dies. The cell above the middle, (2, 1), is dead and sees exactly three live cells below it: it is born. So does (2, 3). Everything else sees at most two and stays dead. The result is the vertical bar, and by the same argument the vertical bar becomes the horizontal one again. The test blinker oscillates with period 2 checks both halves of that argument.

Rung 1: where to look

Look at the signature. current is a const Cells&: you can read it but the compiler will refuse an assignment into it. next is a Cells&: the caller's vector, which you are meant to fill. Now look at the six tests and sort them: which ones test the rules, which one tests that next is fully overwritten, which one tests the torus, which one tests that current is left alone?

Rung 2: the shape of the loops in words

Two nested loops over the grid, row outside and column inside, the same walk as in render. For each cell: count its live neighbours in current with the function from milestone 3; read whether the cell itself is alive in current; decide, from the table, whether it is alive in the next generation; write that 0 or 1 into next at the same position. Nothing is read from next and nothing is written to current, ever.

Rung 3: the decision in words

The new value is 1 when either "the cell is alive and the count is 2 or 3" or "the cell is dead and the count is exactly 3", and 0 otherwise. That is one if with two conditions joined by or, or two ifs, or a comparison whose result you store. Whichever you choose, the otherwise branch must actually write a 0, not do nothing.

Rung 4: the arithmetic in words

The position where you write into next is the position of the cell you are looking at: the same index_of you used to read it, cast to std::size_t. There is no wrapping in step itself: the loops only visit valid cells, and all the wrapping happens inside count_neighbours. If you find yourself calling wrap in step, stop and ask what for.

Common bugs and their symptoms.

  • Updating in place. That is: copying current into next and then reading neighbours from next, so that you read cells you already overwrote this generation. The lone cell and the block still pass, because for them the new values happen to equal the old ones. blinker oscillates with period 2 and wraps across the edges fail. The first CHECK( next == vertical ) prints both vectors as lists of 25 numbers. Yours has four live cells in a lopsided shape where the vertical bar should be. Here is why: the cell above the middle is born first (correctly); its right-hand neighbour then sees that newborn plus two cells of the bar, counts three and is born too; the middle cell then counts four and dies. The Rule 90 section of chapter 7 shows exactly this corruption in one dimension.
  • Only writing births. a lone cell dies reports twenty-five CHECK( 1 == 0 ) failures, one per leftover 1.
  • Writing to current. It will not compile. clang says cannot assign to return value because function 'operator[]' returns a const value. That is the compiler saving you: the const in the signature is a promise, and it is enforced.
  • Off-by-one in a loop bound. Either the last row is never written, and the test shows stale values in the last five positions, or you step past the end and the sanitizer reports it.

#include <print>
#include <string>

int main(int argc, char* argv[]) {
    // Defaults first: a flag that is not given keeps these.
    int times = 2;
    std::string word = "hello";

    // Walk the arguments two at a time: a flag, then its value.
    for (int i = 1; i + 1 < argc; i += 2) {
        const std::string flag = argv[i];
        const std::string value = argv[i + 1];
        if (flag == "--times") {
            times = std::stoi(value);
        } else if (flag == "--word") {
            word = value;
        } else {
            std::println("unknown flag: {}", flag);
            return 1;
        }
    }

    for (int i = 0; i < times; ++i) {
        std::println("{}", word);
    }
    return 0;
}

The loop condition i + 1 < argc matters: it guarantees that argv[i + 1] exists before you read it, so ./life --width with no number does not read past the end of the arguments. The seed parameter of random_cells is an unsigned int while std::stoi gives an int. The compiler converts silently here (-Wall -Wextra does not warn about this one), but a static_cast<unsigned int> (chapter 2) makes the conversion visible, which matters because --seed -1 quietly becomes 4294967295.

The second non-integer flag is --fill, and it is the one that bites. argv holds text, and std::stoi reads an integer from the front of the text and stops at the first character that is not part of one. For "0.3" that is the dot:

#include <print>
#include <string>

int main() {
    const std::string text = "0.3";          // what argv holds after --fill 0.3
    const int as_int = std::stoi(text);      // reads "0", stops at the '.'
    const double as_double = std::stod(text);
    std::println("std::stoi(\"{}\") = {}", text, as_int);
    std::println("std::stod(\"{}\") = {}", text, as_double);
    return 0;
}

std::stoi("0.3") = 0
std::stod("0.3") = 0.3

No error, no warning, only a 0 where 0.3 should be. A fill of 0 means every cell is dead, so the symptom is a grid of dots for every seed. std::stod, "string to double" from chapter 8, is the one you want for --fill.

Milestone 6: the animated loop

Goal. Turn the one-frame print into an animation. The shape of the loop, from the comment in the old main.cpp and from chapter 9, is this:

  1. Hide the cursor. Clear the screen, once.
  2. For each frame: move the cursor home; print the frame; flush; compute the next generation into the second vector; swap the two vectors; sleep for one frame's worth of time.
  3. Stop after --steps generations if that is not zero; otherwise run until Ctrl-C.
  4. Show the cursor again before exiting.

Tests that must turn green: none; checked by eye, as in milestone 5.

Re-read. Chapter 9, all of it: escape sequences, buffering and flushing, sleep_for and the ms literal, the bouncing #, the countdown that redraws a whole frame, frame timing, flicker, and the section on Ctrl-C and the lost cursor. Chapter 7 for std::swap on two vectors.

Here is the loop skeleton on a different picture, a progress bar that fills over twenty frames. Every structural line of your Life loop has a counterpart here, and only the picture is different.

#include <chrono>
#include <cstdio>
#include <print>
#include <string>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    const int frames = 20;

    std::print("\x1b[?25l");          // hide the cursor
    std::print("\x1b[2J");            // clear the screen ONCE
    for (int f = 1; f <= frames; ++f) {
        std::print("\x1b[H");         // cursor home: top-left, every frame
        std::string bar;
        for (int i = 0; i < f; ++i) {
            bar += '#';
        }
        for (int i = f; i < frames; ++i) {
            bar += '.';
        }
        std::print("[{}] frame {:2} of {}\n", bar, f, frames);
        std::fflush(stdout);          // push the frame to the terminal now
        std::this_thread::sleep_for(100ms);
    }
    std::print("\x1b[?25h");          // show the cursor again, always
    std::println("done");
    return 0;
}

Run it and watch the bar fill in place without scrolling. Then run it with the output piped through cat -v, which shows the escape characters as ^[ instead of obeying them (if your shell has replaced cat with a fancier tool such as bat, write /bin/cat -v), and you can see the structure: hide, clear, then ^[[H before every frame, nothing else. (head -3 keeps only the first three lines, so the terminal is not flooded with twenty.)

$ clang++ -std=c++23 -Wall -Wextra bar_anim.cpp -o bar_anim
$ ./bar_anim | cat -v | head -3
^[[?25l^[[2J^[[H[#...................] frame  1 of 20
^[[H[##..................] frame  2 of 20
^[[H[###.................] frame  3 of 20

Why clear only once? Chapter 9's flicker section explains it: clearing erases everything and the terminal shows a blank for an instant before the new frame arrives. Since every Life frame has exactly the same size as the previous one and overwrites every character, moving the cursor home and printing on top is enough. The sleep for a frame rate of fps is 1000 / fps milliseconds, as in chapter 9's frame timing section; with --fps 10 that is 100 milliseconds, which is what the bar above uses.

Rung 1: where to look

The bouncing # and the countdown in chapter 9 are both "frame loops"; the countdown is the closer one because it redraws a whole block of text. Which of its lines moves the cursor, which one makes the output appear, and which one waits? Those three lines, in that order, are the body of your loop too, with "compute the next generation and swap" inserted after the frame is on screen.

Rung 2: the shape in words

After parsing, you have current from random_cells; make a second vector next of the same size, all zero. Hide the cursor; clear. A counter of generations. A loop that runs while steps is zero or the counter is below steps. In the body: home, print render(current, ...), flush, step(current, next, ...), std::swap(current, next), increase the counter, sleep. After the loop: show the cursor. Return 0.

Rung 3: the arithmetic and the types

The sleep length is a duration, not an int: chapter 9 showed how to make std::chrono::milliseconds from a computed number. 1000 / fps is integer division, which is fine here (1000 / 10 = 100, 1000 / 30 = 33). Guard against fps of zero before you divide. Dividing an integer by zero is undefined behaviour. In the Debug build UBSan prints runtime error: division by zero and carries on with a nonsense value. In a Release build there is no message at all: on this Mac the result happens to be 0, and on an Intel machine the same line kills the program. The stretch section below gives --fps 0 a meaning; for now a sensible choice is to treat it as "do not sleep".

Rung 4: the swap

After step has filled next, the newest generation is in next and the old one is in current. You want to draw the newest one next time round and reuse the old vector as the scratch space. std::swap(current, next) does exactly that in constant time (chapter 6's term: the same handful of instructions whether the vectors hold 25 cells or a million), by exchanging the two vectors' insides rather than copying a million bytes (chapter 7). If you copy instead, the program still works, but your benchmark in milestone 7 will show the cost.

Common bugs and their symptoms.

  • The grid scrolls down the screen instead of staying put. The cursor-home sequence is missing, or is printed after the frame instead of before it.
  • The grid appears only when the program ends, or in bursts. No flush after the print; chapter 9's buffering section is the explanation.
  • The picture never changes. You stepped but did not swap, or you swapped but drew next instead of current.
  • The cursor is gone after the program ends. The show-cursor sequence is missing, or the --steps exit path skipped it. Type tput cnorm to get it back.
  • A doubled picture after resizing the terminal. Clearing once more when that happens is a stretch goal; for now, do not resize while it runs.
Trap

Ctrl-C and the invisible cursor. When you press Ctrl-C, the operating system stops your program immediately, between two of your lines, and the "show the cursor" line at the bottom of main never runs. Your terminal is left with an invisible cursor. Chapter 9's last section shows the terminal command that fixes it, tput cnorm (or reset, which also clears the screen), and explains why a real fix needs something from week 3: clean-up tied to a variable that runs no matter how the program leaves, which is called RAII. For this week: --steps is your clean exit. Test with --steps 50, and keep tput cnorm in your fingers.

The debugging playbook

A test fails and the message does not make it obvious why. Work through these in order; stop as soon as you understand the bug.

1. Print the grid inside the test. You can. The test file is yours to edit for debugging (put it back afterwards), and it already includes life.hpp, so render is available. Add a print just before the failing CHECK:

// inside a TEST_CASE, before the CHECK that fails:
std::print("current:\n{}", render(cur, 5, 5));
std::print("next:\n{}", render(next, 5, 5));

A picture of five rows tells you more than a vector of twenty-five numbers. You see at once whether a bar is one cell too far to the right, whether a whole row is missing, whether the edge wrapped. You will need #include <print> at the top of the test file for this.

2. Shrink to 3×3. If a 5×5 case fails, write a scratch program with a 3×3 grid and one live cell, and call the failing function by hand on each position, printing the result. Nine cells is few enough to check every one on paper. Bugs that hide in a big grid stand naked in a small one.

3. Check x/y order with a non-square grid. Make the scratch grid 4×2, not 3×3. Any place where you multiplied x by width, wrapped y by width, or swapped the two loop bounds now produces an index outside the vector or a visibly wrong picture. You saw the table in milestone 3.

4. A sanitizer report means an index is wrong. When the test output contains AddressSanitizer: heap-buffer-overflow, do not read the rest of the test output; read the report. Here is what it looks like, produced by a one-dimensional program that forgets to wrap the right-hand neighbour of the last cell in a ring of eight:

#include <cstdint>
#include <print>
#include <vector>

int main() {
    const int n = 8;
    std::vector<std::uint8_t> ring(n, 0);
    ring[7] = 1;
    // Count how many of the two neighbours of cell 7 are alive, forgetting to wrap:
    const int left = 7 - 1;
    const int right = 7 + 1;          // 8: there is no cell 8
    int alive = ring[static_cast<std::size_t>(left)] + ring[static_cast<std::size_t>(right)];
    std::println("alive neighbours: {}", alive);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra -g -fsanitize=address,undefined asan_demo.cpp -o asan_demo
$ ./asan_demo
=================================================================
==68040==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x6020000000d8 at pc 0x000104cecc30 bp 0x00016b111c30 sp 0x00016b111c28
READ of size 1 at 0x6020000000d8 thread T0
    #0 0x000104cecc2c in main asan_demo.cpp:12
    #1 0x000186c214e0 in start+0x1b4c (dyld:arm64e+0x204e0)

0x6020000000d8 is located 0 bytes after 8-byte region [0x6020000000d0,0x6020000000d8)
allocated by thread T0 here:

Three facts in that report are the whole diagnosis. READ of size 1: a read of one byte, so a std::uint8_t cell. in main asan_demo.cpp:12: the file and line of the read, which is the line with the index. 0 bytes after 8-byte region: the vector has 8 bytes and you read the byte just past its end, so the index was exactly n. In your project the line will be inside count_neighbours or step, and the question is always the same: which coordinate was not wrapped, or which formula was swapped? The process number between the == signs (68040 here) and the long hexadecimal addresses such as 0x6020000000d8 will differ between runs and between machines; the three facts will not.

5. "It looks alive but wrong." The animation runs, patterns move, but blinkers smear and blocks dissolve. Nearly always one of two things: in-place update (you read a neighbour that this generation already overwrote, which the Rule 90 program in chapter 7 demonstrates) or self-counting (the cell counts itself as a neighbour, so every count is one too high). The step tests catch both, so if the tests are green and the animation is wrong, the bug is in main: are you drawing current after the swap?

6. Read the test, not just its name. Open life_test.cpp at the failing line. The helper grid_with at the top builds a grid from a list of (x, y) pairs; draw the grid it builds on paper, then do by hand what the function should do, then compare with what yours did. Fifteen minutes with paper beats an hour of guessing.

The review ritual

After each milestone, with the tests green and the commit made, ask Claude for a review according to CLAUDE.md. Make the request narrow and name the function:

Review life.cpp index_of for correctness and style; do not rewrite it.

The "do not rewrite it" is not politeness; it is the rule, and saying it keeps both of you honest. A good review does not produce code. It asks questions and makes observations in six parts, in the order CLAUDE.md lists: correctness, clarity and style, idioms, performance ideas, the inference twin, and three questions you should be able to answer without looking at the code. Here is what a good review of this week's functions tends to ask about, so you can pre-empt it:

  • const. Is every variable that never changes after it is set marked const? Is every reference parameter you only read a const T&? Chapter 5 made the case; the review checks you took it.
  • size_t casts. The vector index is a std::size_t and your coordinates are ints. Every [] needs a static_cast<std::size_t>, and the review will ask whether it belongs at each call site or in one place. There is no single right answer; there is a right answer for your code, and you should be able to say why.
  • Naming. Is the horizontal offset called something a reader recognises (dx is the convention)? Is the neighbour count called count, alive, n? Does neighbour keep its British spelling everywhere, to match count_neighbours?
  • Off-by-one. Every loop bound: < or <=? Every offset range: does it include both -1 and 1? The review will name a concrete input (a 1×1 grid, a 2×2 grid, width 1) and ask what your code does with it. A 1×1 torus is a wonderful edge case: the single cell is its own neighbour eight times over, and the spec says to count the eight neighbours, so the right answer is eight times its own value. Does yours do that?
  • Repetition. If the index formula appears in three functions as arithmetic instead of as a call to index_of, the review will ask what happens if the layout ever changes (week 4's Tetris has you write transpose and flip, which is where that question stops being theoretical).

The inference twin, in depth

The README says this week secretly teaches tensors. Here is the whole correspondence, now that you have built the thing. Keep this section; you will reread it in week 15 with a different kind of recognition.

Flat array plus shape equals tensor. Your grid is one std::vector<std::uint8_t> of width * height bytes, plus two integers that say how to read it. The vector alone is meaningless: a million bytes could be a 1000×1000 grid or a 500×2000 one. The shape, carried alongside, gives it meaning. A tensor in PyTorch, in ggml, in every inference engine, is exactly this: one unbroken block of numbers plus a shape and a stride per dimension, where the stride is how many elements you skip to move by one along that dimension. Your index_of is a stride computation: the stride of y is width, the stride of x is 1. A tensor with three dimensions (a rank-3 tensor) adds one more term to the formula; a transposed view changes the strides without touching the bytes. When you write the Tensor class in week 15, index_of grows to any number of dimensions, and nothing else about it changes.

The 3×3 stencil is a convolution kernel. count_neighbours reads a small window around a cell and combines the values; step does that for every cell and writes one output per input position. That shape, "each output depends on a fixed small neighbourhood of the input", is a stencil, and a convolution layer in a neural network is a stencil whose combining function is a weighted sum instead of a count. Even the elementwise operations in a transformer, where each output depends only on the matching input (a 1×1 stencil), have the same loop structure: walk every position, read a neighbourhood, write one value. The CUDA kernel you write in week 22 for Life is, line for line, the shape of every elementwise and stencil kernel in ggml-cuda, with a different body.

Current and next are ping-pong buffers. You cannot compute generation t + 1 into the same memory that holds generation t, because the cell to your right still needs the old value of the cell you just overwrote. So you have two buffers and swap them. An inference engine running one layer of a language model (a transformer layer: one of the repeated stages the numbers pass through) has the same problem: the layer's output is computed from the layer's input, and the input must stay intact until every output is written. Engines keep two buffers for those numbers (the activations) and ping-pong between them exactly as you did. The KV cache in week 18, a store of earlier results that later tokens read, is a bigger version of the same discipline: never let a reader see a half-written result.

The step loop cost is tokens times dimension. One step visits width * height cells and does a fixed amount of work (about nine reads and one write) per cell, so the cost is proportional to the number of cells. One token through one transformer layer visits every element of an activation vector of size dim and does a fixed amount of work per element; generating N tokens is N steps of that. Your ms per step at 1000×1000 and a model's ms per token are the same kind of number from the same kind of loop, and the benchmark you ran is the same experiment: fixed work per element, measured many times, divided.

The test suite is a numerical reference test. The blinker test says: given this exact input, the output must be this exact grid. Week 15 tests your matmul the same way, except that the "exact grid" comes from PyTorch, dumped to a file by a Python script, and the comparison allows a tolerance because floating-point arithmetic rounds. The habit is identical: a known input, a reference output computed some other way, a check. Your grid_with helper is the ancestor of the load_reference_tensor helper you will write then.

BENCH.md is the tokens-per-second table. The phase 4 gate asks for tokens per second at fp32, Q8_0 and Q4_0 at 1, 4 and 8 threads. That table is BENCH.md with more columns: the same machine line, the same build type, the same "ms per unit of work", the same note on what you expected. Start writing that table well now, with the date and the machine every time, and the week-17 version will take you ten minutes.

Analogy

Life is to an inference engine what a scale model is to a building. Every structural element is present: the flat storage, the stride arithmetic, the stencil loop, the two buffers, the reference tests, the benchmark. The proportions are right and you can walk through it in a week. Where the analogy breaks: a scale model does not have to stand up. Your Life has to actually run, and it has to be correct, and the sanitizer and the tests enforce that. The model is load-bearing.

Check yourself

Why does step take two vectors, current and next, instead of updating one grid in place? Describe what you would see on the blinker if it updated in place.

Answer

Every cell's new value depends on the old values of its eight neighbours. If you overwrite a cell as you go, the cells to its right and below read the new value instead of the old one, and the rules are applied to a mixture of two generations. On the blinker, walking row by row, the cell above the middle is born first (correctly), but then the cell to its right sees that newborn plus two cells of the bar, counts three and is wrongly born too; the middle cell then counts four and wrongly dies. The vertical bar never forms; after one more generation the pattern has settled into a 2×2 block that never changes again. Two buffers keep one generation fully intact while the other is written, and std::swap exchanges them in constant time.

The torus test uses a 5×3 grid and the index test uses (4, 4, 5) among its cases. Why are non-square grids and an x == y case both in the test file?

Answer

On a square grid, swapping x and y in the index formula, or wrapping the row with width instead of height, still produces valid indices and symmetric patterns look right, so the bug hides. On a 5×3 grid the wrong formula points outside the vector or at the wrong cell and the test fails. The (4, 4, 5) case is the opposite lesson: it passes with the swapped formula, so you see one green assertion next to four red ones and learn that a passing case on a square is not evidence.

What does the seed guarantee about random_cells, and what does it not guarantee?

Answer

It guarantees that the same seed, same width, same height and same fill produce an identical grid every run, on the same machine with the same compiler and standard library, because std::mt19937 is a fixed arithmetic sequence and the standard specifies its output exactly. It does not guarantee a particular number of live cells (only a probability per cell), and it does not guarantee the same grid across different standard libraries, because std::uniform_real_distribution may turn the engine's integers into doubles differently. The test therefore checks "same seed twice gives equal grids" and "fill 0.5 gives roughly half", never an exact live count for a non-extreme fill.

The stub step does nothing and the test step: does not modify current passes. What does that tell you about tests in general, and what does the test a lone cell dies do about it?

Answer

A test can only prove the absence of the specific bug it looks for; a useless function can pass a test that happens to accept "nothing happened". That is why there are thirteen cases, each closing off a different wrong behaviour. a lone cell dies defends against the opposite laziness: it fills next with 1s before calling step, so a step that only writes births and leaves everything else alone fails on all twenty-five cells. Together, the two tests force step to write every cell of next and to leave current alone.

Why does the animation clear the screen once, before the loop, and then only move the cursor home for each frame?

Answer

Clearing wipes the whole screen, and for an instant the terminal shows blank space before the new frame arrives, which you see as flicker. Every Life frame has exactly the same size as the one before and overwrites every character, so moving the cursor to the top-left and printing on top replaces the old frame completely with no blank instant. Clearing is only needed once, to remove whatever was on the screen before the program started.

Your main computes the sleep as 1000 / fps. What happens when someone passes --fps 0, in Debug and in Release, and what should the program do instead?

Answer

Dividing an integer by zero is undefined behaviour. In the Debug build UBSan prints runtime error: division by zero and continues with a nonsense value; in Release there is no message, and the result depends on the machine (0 on this Mac, a crash on Intel). The program must check fps before dividing: either refuse it with a usage message and return 1, or give 0 a meaning such as "do not sleep", which the stretch goals use for timing a 1000×1000 run from the game itself.

In the sanitizer report, what do READ of size 1 and 0 bytes after 8-byte region tell you, and what is the first thing to check in your code?

Answer

READ of size 1 says a one-byte value was read, which is a std::uint8_t cell. 0 bytes after 8-byte region says the vector is 8 bytes long and the read was at index 8, exactly one past the end. So an index equal to the size was used, which on a grid means a coordinate that should have been wrapped back to 0 was not, or a loop bound used <= instead of <. Check the line the report names, and in it the coordinate that was not passed through wrap.
