Chapter 09

The terminal: drawing with bytes

At the end of this chapter you will be able to make a program that clears the screen, draws a picture, waits a tenth of a second, and draws the next picture in the same place, so that a grid of characters appears to move. That is all an animation is, and it is all the Life game loop needs.

In this chapter
  • What a terminal is: a program that reads bytes from yours and paints characters in a grid.
  • Printable bytes and control bytes: '\n', '\r', '\t', and byte 27, the escape.
  • Escape sequences: clear the screen, move the cursor, hide it, show it, colour the text.
  • Buffering: why a program that prints without newlines can show nothing until it exits, and std::fflush.

What a terminal actually is

Every program you have written so far ends with text appearing in a window. It is worth asking, once, how that happens, because the answer is simpler than it looks and you are about to exploit it.

When your program calls std::println("Hello"), it does not draw anything. It cannot: it has no idea what a window is. What it does is hand six bytes (the five letters and a newline) to the operating system and say "this is for output". (Strictly, the bytes wait in a buffer first and are handed over in batches; the section on buffering below is about exactly that.) The operating system passes those bytes to whatever program is listening on the other end of the output. Normally that program is the terminal: Terminal.app, iTerm, the terminal pane in your editor. The terminal is an ordinary program. Its one job is to read a stream of bytes and paint characters into a grid of cells, one character per cell, moving a cursor (the position where the next character goes) one cell to the right after each one.

The third program in the picture is the shell: zsh on your Mac. The shell is the program that shows you a prompt, reads ./hello when you type it, and starts your program with its output connected to the same terminal. When your program ends, the shell prints the next prompt. So there are three programs: the shell, which started yours; your program, which produces bytes; and the terminal, which turns bytes into pixels.

The stream of bytes your program writes has a name: standard output, or stdout. std::println and std::print write to it. Nothing else happens. If you see pixels, that is the terminal's doing.

First principle

Your program never draws. It writes bytes to stdout. The terminal, a separate program, reads those bytes and decides what to paint. Everything in this chapter is about choosing the bytes that make the terminal paint what you want.

Here is a program that shows the bytes behind a piece of text. Each char is a one-byte number; static_cast<int> lets you print it as a number instead of a letter (chapter 2).

#include <print>
#include <string>

int main() {
    std::string text = "ab\ncd";
    std::println("the text has {} bytes", text.size());
    for (char c : text) {
        std::println("byte value {}", static_cast<int>(c));
    }
    return 0;
}

the text has 5 bytes
byte value 97
byte value 98
byte value 10
byte value 99
byte value 100

Five bytes. a is 97, b is 98, c is 99, d is 100. Those are printable bytes: when the terminal reads one, it paints the matching character in the cell under the cursor and moves the cursor right. In the middle sits byte 10, which is '\n'. The terminal does not paint a "10". Byte 10 is a control byte: a byte that commands the terminal instead of drawing. Byte 10 means "move the cursor to the start of the next line".

So the rule for the whole stream is: printable bytes draw, control bytes command. There are only a few control bytes you need, and you have been using one of them since chapter 1.

Analogy

A terminal is a typewriter with a very obedient typist. Each letter you send, the typist types, and the carriage moves one space right. Some keys do not type a letter: the carriage-return lever slides the carriage back to the left margin, the line-feed knob rolls the paper up one line, the tab key jumps the carriage to the next tab stop. The terminal's control bytes are those levers. Where the analogy breaks: paper cannot be erased, but a terminal cell can be repainted as often as you like, and the typist can be told to jump to any row and column directly. That difference is what makes animation possible.

Three control bytes you already own

'\n' is byte 10, newline (also called line feed). The cursor goes to column 0 of the next line. std::println adds one for you after your text; std::print does not, which is exactly why std::print exists. (A purist's footnote: on its own, byte 10 only moves the cursor down. The operating system's terminal driver quietly adds a carriage return in front of every newline your program writes, so that "next line" also means "column 0". In week 3, Snake puts the terminal into raw mode, which switches that favour off, and you will see the staircase that results.)

'\t' is byte 9, tab. The cursor jumps right to the next tab stop, which in every terminal you will meet is the next column that is a multiple of 8. It is a cheap way to line up columns.

#include <print>

int main() {
    std::println("x\ty\tsum");
    std::println("1\t2\t3");
    std::println("10\t20\t30");
    return 0;
}

x	y	sum
1	2	3
10	20	30

The output block above holds the raw tab bytes, so the browser shows them its own way. In the terminal you see x in column 0, y in column 8 and sum in column 16, with the numbers lined up under them. 10 takes two cells, but the tab after it still jumps to column 8, which is why the second column does not shift.

'\r' is byte 13, carriage return. The cursor goes back to column 0 of the same line, without moving down. Whatever you print next lands on top of what is already there. Try to predict what this shows before you run it.

#include <print>

int main() {
    std::print("12345");
    std::print("\r");      // back to column 0 of the SAME line
    std::print("AB");
    std::print("\n");
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra carriage_return.cpp -o carriage_return
$ ./carriage_return
AB345

The program wrote nine bytes: 1 2 3 4 5 CR A B LF. The terminal painted 12345, slid the cursor back to the start, painted A over the 1 and B over the 2, and the 345 stayed because nothing was written on top of it. You have just drawn two frames of an animation on one line. The rest of this chapter is more of the same, with better tools.

Why the book cannot show that as an output block

The book's checker compares the raw bytes a program writes, not what a terminal paints. For carriage_return.cpp the raw bytes are 12345\rAB\n, which no text block can show honestly. So programs whose point is what the terminal does with the bytes are marked compile and the result is described in a shell block. Run them yourself; the whole chapter is meant to be watched.

Escape sequences: commands to the terminal

Newline, tab and carriage return were enough in 1970. People soon wanted more: clear the screen, move the cursor anywhere, change the colour. There are not enough spare byte values for all of that, so a scheme was agreed that is still what every terminal understands today. One control byte, byte 27, called escape (ESC), means "the next few bytes are a command, not text". The command's bytes follow, and the terminal performs it without painting any of them. The whole group is an escape sequence. The particular set of commands is the ANSI set, after the standards body that wrote them down.

You cannot type byte 27 into a string literal (pressing the Escape key in an editor does something else entirely), so C++ lets you write it as a hex escape: \x1b. The \x says "a byte written in hexadecimal follows". Hexadecimal is counting in sixteens instead of tens: the digits are 0 to 9 and then a to f for ten to fifteen, so 1b means one sixteen plus eleven, which is 27. (The sanitizer report in chapter 6 was full of hexadecimal numbers; this is the first one you write yourself.) Almost every command you need then continues with [, zero or more ordinary decimal digits (separated by ; when there are several), and one letter that says which command it is. Here is proof that "\x1b[2J" is just four bytes.

#include <print>
#include <string>

int main() {
    std::string clear = "\x1b[2J";
    std::println("the clear-screen command is {} bytes:", clear.size());
    for (char c : clear) {
        std::println("  byte {}", static_cast<int>(c));
    }
    return 0;
}

the clear-screen command is 4 bytes:
  byte 27
  byte 91
  byte 50
  byte 74

27 is ESC, 91 is [, 50 is the digit 2, 74 is J. When the terminal sees them in a row it clears every cell on the screen. These are the sequences this week needs:

Bytes you writeWhat the terminal does
"\x1b[2J"Clear the whole screen (every cell becomes a space). The cursor does not move.
"\x1b[H"Move the cursor to the top-left corner: row 1, column 1. ("Home".)
"\x1b[{row};{col}H"Move the cursor to a given row and column. Both count from 1, not 0. "\x1b[H" is the short form of "\x1b[1;1H".
"\x1b[?25l"Hide the cursor. (The last character is a lower-case L.)
"\x1b[?25h"Show the cursor again.
"\x1b[31m"From here on, paint text in red. 30 to 37 are black, red, green, yellow, blue, magenta, cyan, white. 1; in front means bold.
"\x1b[0m"Reset: back to the terminal's normal colour and weight.

The first two together are the heart of every terminal animation. Clear, go home, draw the picture. Clear, go home, draw the next picture. Because every frame starts at the same cell, each frame lands exactly on top of the one before, and the eye sees motion.

#include <print>

int main() {
    std::println("This line was here before.");
    std::println("So was this one.");

    std::print("\x1b[2J");      // clear the whole screen
    std::print("\x1b[H");       // cursor to row 1, column 1

    std::println("#####");
    std::println("#...#");
    std::println("#####");
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra clear_and_home.cpp -o clear_and_home
$ ./clear_and_home
#####
#...#
#####

When you run it, the two "before" lines appear for a fraction of a second, too fast to see, and then the screen is wiped and the box sits alone in the top-left corner, with your shell prompt right under it. Everything that was in the window, including your earlier commands, is gone (most terminals keep it in the scrollback, the history of lines that have left the window; scroll up and it is still there). That is what "\x1b[2J\x1b[H" does, and from now on you will usually write the two commands as one string.

Moving the cursor to a chosen cell uses the row-and-column form. Since std::print fills {} with values, you can put the row and column in with the usual braces.

#include <print>

int main() {
    std::print("\x1b[2J\x1b[H");           // clean slate, cursor top-left
    std::print("\x1b[3;10H");              // row 3, column 10
    std::print("A");
    std::print("\x1b[5;20H");              // row 5, column 20
    std::print("B");
    std::print("\x1b[1;1H");               // back to the top-left corner
    std::print("C");
    std::print("\x1b[8;1H");               // row 8, so the shell prompt lands below
    std::print("\n");
    return 0;
}

$ ./move_cursor
C

         A

                   B

You see a C in the corner, an A on the third row nine cells in, a B on the fifth row nineteen cells in, and the prompt further down. Notice that the program printed them in the order A, B, C and the terminal does not care: the cursor was moved before each one. For Life you will not need this form, because printing the grid row by row from the home position is simpler, but it is good to know that any cell is reachable.

Trap

Two things about "\x1b[{row};{col}H" fight the habits you built in chapter 7. The terminal counts from 1, not 0: the top-left cell is row 1, column 1, and "\x1b[0;0H" is quietly treated as "\x1b[1;1H", so an off-by-one here produces no error, only a picture one cell out of place. And the row comes first, then the column, which is the opposite order from (x, y). If you ever want to place a cell that your code calls (x, y) in a 0-based grid, the sequence is row y + 1, column x + 1. Life does not need this form; Snake in week 3 does.

Colour is optional and fun. A colour sequence changes a setting in the terminal that stays on until you reset it, so always pair a colour with "\x1b[0m".

#include <print>

int main() {
    std::println("\x1b[31mred\x1b[0m plain");
    std::println("\x1b[32mgreen\x1b[0m plain");
    std::println("\x1b[1;34mbold blue\x1b[0m plain");
    return 0;
}

$ ./colours
red plain
green plain
bold blue plain

In your terminal the first word of each line is coloured and the word plain is not. If you forget the reset, everything the shell prints afterwards is red too, prompt included. Typing reset at the prompt fixes it.

Trap

The \x escape is greedy: it keeps eating hexadecimal digits for as long as they continue. [ is not a hex digit, so "\x1b[" is safe. But the letters a to f and A to F are hex digits. If you ever write "\x1bA", the compiler reads 1bA as one three-digit number, which does not fit in a byte:

#include <print>

int main() {
    std::print("\x1bAB\n");
    return 0;
}

hex_trap.cpp:4:17: error: hex escape sequence out of range
    4 |     std::print("\x1bAB\n");
      |                 ^~~~~~
1 error generated.

Every sequence in the table starts with \x1b[, so you will not hit this in Life. If you ever need ESC followed by a letter, split the string: "\x1b" "A"; two string literals side by side are glued into one.

The shell knows these bytes too

The shell command tput prints the escape sequence for a named action. tput clear writes \x1b[H\x1b[2J, tput civis writes \x1b[?25l (cursor invisible), tput cnorm writes \x1b[?12l\x1b[?25h (cursor normal: "stop blinking" followed by "show"). To see the bytes, feed one into od -c, a shell tool that prints every byte it receives: tput civis | od -c shows 033 [ ? 2 5 l, where 033 is how od writes byte 27. (The | is a pipe: the shell connects the output of the program on its left to the input of the program on its right. You will use it again in the next section.) The shell's clear command writes \x1b[3J (wipe the scrollback too) and then the same two commands as tput clear. Your program and these commands are doing the exact same thing: writing bytes that the terminal obeys.

Next, change move_cursor.cpp to draw a box of # three rows high and five wide with its top-left corner at row 4, column 6, using one cursor move per row. Finally run colours.cpp with the three \x1b[0m resets deleted and look at your prompt; type reset to recover.

Buffering: why nothing shows up

Here is a program that prints a dot every half second. Compile it and watch.

#include <chrono>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    for (int i = 0; i < 5; ++i) {
        std::print(".");                            // no '\n': may sit in the buffer
        std::this_thread::sleep_for(500ms);
    }
    std::println(" done");
    return 0;
}

(The two new lines, using namespace std::chrono_literals; and sleep_for(500ms), are explained in the next section; for now read them as "wait half a second".) Watch closely. You would expect the first dot at once, because it is printed before the first sleep. On a terminal the dots do arrive one by one, but the first one shows up only after half a second, and the fifth dot appears together with done at the very end. Each dot is one sleep late. Now run it with its output going somewhere else: ./no_newline | cat. That is the pipe from the tput note: your program's stdout now goes to cat, a program that copies whatever it reads to the terminal, so your program itself is no longer writing to a terminal. This time you see nothing at all for two and a half seconds, then ..... done in one go. Same program, same bytes, different timing. Why?

Writing to the operating system is slow compared with writing to memory, so std::print does not hand over each byte as you produce it. It appends your bytes to a buffer: a block of memory it owns. On this Mac, when the output is a pipe, the buffer holds 65,536 bytes. You can see the number: print 70,000 xs with no newline, sleep two seconds, then print " end", and run it through | cat. Exactly 65,536 arrive at once, and the last 4,464 wait for the sleep. Only when the buffer is flushed are its contents actually sent on. The library flushes when the buffer fills up, when the program exits normally, and, if the output is a terminal, whenever a '\n' goes through. That last rule is called line buffering, and it is why std::println has always seemed instant: every line ends in a newline, and every newline flushes. When the output is a pipe or a file there is no line-buffering rule, only "full or exit", which is what you saw with | cat.

Analogy

The buffer is a post bag. Dropping a letter into the bag is cheap; the walk to the post office is the expensive part, so the carrier goes when the bag is full or the day ends, not once per letter. A flush is you telling the carrier "go now". Where the analogy breaks: a real post bag does not care what the letters say, but this one does. When the other end is a terminal, a newline in the text sends the carrier off at once, and so does the next std::print; when the other end is a pipe, neither does.

There is one more rule, and it explains the late dots. When the output is a terminal, every call to std::print or std::println first flushes whatever is already waiting in the buffer, and then adds its own text to the buffer. So the first dot sat in the buffer during the first sleep and was pushed out by the second std::print; the fifth dot was pushed out by the std::println(" done"). Each frame of an animation written this way would show up one sleep late. (You can check this against the library's own source: the <print> header on your Mac has a function __vprint_unicode_posix whose first lines are "if this is a terminal, fflush".)

An animation frame is a block of text that you want on screen now, before the sleep. Relying on those rules is fragile, for three reasons. The rules change with where the output goes, as you just saw. The last line of a frame may not end in a newline. And "flushed by the next print" means the frame shows up one sleep late, so what is on screen is always the previous frame. The fix is to flush yourself. std::fflush(stdout), from the header <cstdio>, means "send everything in the buffer right now". stdout is the name of the standard output stream in that header.

#include <chrono>
#include <cstdio>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    for (int i = 0; i < 5; ++i) {
        std::print(".");
        std::fflush(stdout);                        // push the buffer out NOW
        std::this_thread::sleep_for(500ms);
    }
    std::println(" done");
    return 0;
}

$ ./flush_each_dot | cat
..... done

The final text is identical; the difference is that now each dot appears when it is printed, terminal or not. (You may meet std::cout.flush() in other books; it flushes the <iostream> output object, which this book does not use. std::fflush(stdout) is the one that pairs with std::print.)

First principle

Output is batched. Bytes you print sit in a buffer until something flushes it. After each complete frame, call std::fflush(stdout) so the frame is on screen before you sleep. Do it once per frame, not once per character.

Time: durations and sleeping

Animation needs two things from the clock: a way to wait, and a way to measure. Both live in the header <chrono>, and both are built on one idea, the duration: an amount of time with its unit built into the type. std::chrono::milliseconds is a type whose values are whole numbers of milliseconds. std::chrono::seconds is whole seconds. You cannot accidentally add a seconds value to a milliseconds value and get nonsense, because the compiler knows the units and converts.

Writing std::chrono::milliseconds(100) every time is tiresome, so the library offers duration literals: after the line using namespace std::chrono_literals; you can write 100ms, 2s, 500us (microseconds) and they mean the same as the long form. The using namespace line is written inside main so the short names are only visible there. To get the plain number back out of a duration, call .count().

#include <chrono>
#include <print>

int main() {
    using namespace std::chrono_literals;

    std::chrono::milliseconds a(100);          // the long way
    std::chrono::milliseconds b = 100ms;       // the literal: the same value
    std::println("a = {} ms, b = {} ms", a.count(), b.count());

    std::chrono::milliseconds one_second = 1s; // seconds convert to ms exactly
    std::println("1s is {} ms", one_second.count());

    std::chrono::milliseconds frame = 1000ms / 60;
    std::println("one frame at 60 fps is {} ms", frame.count());

    auto total = 100ms + 250ms + 1s;
    std::println("100ms + 250ms + 1s = {} ms", total.count());
    return 0;
}

a = 100 ms, b = 100 ms
1s is 1000 ms
one frame at 60 fps is 16 ms
100ms + 250ms + 1s = 1350 ms

Three details. 1s was assigned to a milliseconds variable and became 1000; the compiler did the conversion because seconds to milliseconds is exact. Going the other way, milliseconds to seconds, would lose information, and the compiler refuses to do it silently. 1000ms / 60 is 16, not 16.67: the duration holds whole milliseconds and the division is integer division (chapter 2). And auto on the sum let the compiler pick the finest unit involved, milliseconds, so nothing was lost.

Here is the refusal. 1500 milliseconds is one and a half seconds, and a seconds value can only hold whole seconds, so the half would have to vanish:

#include <chrono>
#include <print>

int main() {
    using namespace std::chrono_literals;
    std::chrono::seconds s = 1500ms;    // 1.5 seconds does not fit in whole seconds
    std::println("{} s", s.count());
    return 0;
}

      |                          ^   ~~~~~~

Read the first line only. ratio<[...], 1000> is the library's spelling of "thousandths of a second" and ratio<[...], 1> is "whole seconds"; "no viable conversion" between them means the compiler will not drop the fraction behind your back. When you do want to round down on purpose, there is a tool for saying so, duration_cast; it appears in the section on measuring time below.

To wait, call std::this_thread::sleep_for with a duration. It comes from the header <thread>. A thread is one sequence of instructions being run by the CPU. Your program is exactly one thread, so "this thread" means the running program itself (programs with several threads are week 11). It pauses your program for at least the duration asked; the operating system runs other programs meanwhile and wakes yours up when the time is up.

#include <chrono>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    std::println("tick");
    std::this_thread::sleep_for(500ms);
    std::println("tock");
    std::this_thread::sleep_for(500ms);
    std::println("tick");
    std::this_thread::sleep_for(std::chrono::milliseconds(500));
    std::println("tock");
    return 0;
}

First principle

Your first animation: a bouncing #

You now have every piece. Put a # somewhere on a 40-column line, print the line, wait, move the # one cell, print the line again on top of the old one. Each printing is a frame; the wait between frames sets the speed. The line is a std::string of 40 dots, built with the (n, value) construction you saw for vectors in chapter 6 and for a string of a million xs in chapter 5. Because it is one line, '\r' is all the cursor movement needed. One small new thing: std::println() with nothing between the brackets prints just a newline. That is how the program leaves the finished line on screen and puts the prompt below it.

#include <chrono>
#include <cstdio>
#include <print>
#include <string>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    const int columns = 40;
    int x = 0;          // where the # is
    int dx = 1;         // +1 moving right, -1 moving left

    for (int frame = 0; frame < 60; ++frame) {
        std::string line(static_cast<std::size_t>(columns), '.');
        line[static_cast<std::size_t>(x)] = '#';

        std::print("\r{}", line);        // '\r' = back to column 0, then overwrite
        std::fflush(stdout);
        std::this_thread::sleep_for(50ms);

        x += dx;
        if (x == columns - 1 || x == 0) {
            dx = -dx;                    // hit a wall: turn around
        }
    }
    std::println();
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra bounce.cpp -o bounce
$ ./bounce
...................#....................

For three seconds (60 frames of 50 ms) a # slides from the left edge to the right edge, turns, and slides back; the line above is where it stopped after sixty frames. Read the loop as the terminal sees it. Every frame's std::print begins with '\r', so the cursor goes to column 0 first, and then forty printable bytes land on top of the forty from the frame before. Nothing is ever cleared; it is all overwriting. std::fflush makes sure the forty bytes are out before the sleep. The dx variable is a trick worth remembering: velocity as a signed number, and bouncing is nothing more than dx = -dx.

Walk the first frames by hand to see the turn happen. Frame 0 draws x = 0, then x becomes 1. Frame 38 draws x = 38, then x becomes 39, which is columns - 1, so dx flips to -1. Frame 39 draws x = 39, the right edge, then x becomes 38. From there x falls by one per frame, so frame 59, the last, draws x = 39 - 20 = 19: nineteen dots, the #, twenty dots. Count the line above.

A detail: std::print("\r{}", line) rather than std::print(line). The first argument of std::print must be a pattern the compiler can check while compiling, which a std::string variable is not. To print a string you built at run time, pass it as the value for a {}. If you forget, the error is long and starts like this:

Redrawing a whole frame: a countdown

One line was enough for '\r'. Life needs a block of rows, so the frame must start at the top-left corner every time: that is "\x1b[2J\x1b[H". Here is a countdown clock that redraws a little box once a second. It also hides the cursor while it runs, because a blinking cursor sitting in the middle of a picture is distracting, and shows it again at the end.

#include <chrono>
#include <cstdio>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    std::print("\x1b[?25l");                // hide the cursor
    for (int seconds = 10; seconds >= 0; --seconds) {
        std::print("\x1b[2J\x1b[H");        // clear, cursor home
        std::println("+------------+");
        std::println("|  T minus   |");
        std::println("|     {:2}     |", seconds);
        std::println("+------------+");
        std::fflush(stdout);
        if (seconds > 0) {
            std::this_thread::sleep_for(1s);
        }
    }
    std::println("Lift-off.");
    std::print("\x1b[?25h");                // show the cursor again
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra countdown.cpp -o countdown
$ ./countdown
+------------+
|  T minus   |
|      0     |
+------------+
Lift-off.

The number in the box ticks from 10 to 0 while the box stays put. {:2} is {} with a width, the code from chapter 2's formatting table: "at least two characters, padded with spaces on the left", so the single digit 0 takes the same room as 10 and the box's right edge does not jump. Every frame is the same four lines written to the same four rows, so to the eye only the digits change.

This is the shape of the Life game loop in phase1-terminal/01-life/src/main.cpp: home, print the grid, flush, compute the next generation and swap, sleep, repeat (chapter 14 explains why the clear happens only once, before the loop). You will put the Life pieces into it in chapter 14.

Hint for the last one

Every frame writes exactly the same cells, so painting over them without clearing leaves no leftovers. If a frame were ever shorter or narrower than the one before, the old cells outside it would stay on screen. Life's frames are always the same size, so for Life "home" alone works too, and it is one thing less for the terminal to do each frame.

Frame timing

Speed is normally stated as frames per second (fps). The sleep you need is the length of one frame, which is 1000 / fps milliseconds:

#include <print>
#include <vector>

int main() {
    std::vector<int> fps_values = {1, 5, 10, 24, 30, 60, 120};
    for (int fps : fps_values) {
        int ms_per_frame = 1000 / fps;
        std::println("{:3} fps  ->  {:4} ms per frame", fps, ms_per_frame);
    }
    return 0;
}

  1 fps  ->  1000 ms per frame
  5 fps  ->   200 ms per frame
 10 fps  ->   100 ms per frame
 24 fps  ->    41 ms per frame
 30 fps  ->    33 ms per frame
 60 fps  ->    16 ms per frame
120 fps  ->     8 ms per frame

({:3} and {:4} are the same width trick as {:2} in the countdown. And 1000 / 24 printed 41, not 41.67: integer division, as in chapter 2.) Call that number the frame budget: the time one frame is allowed to take, from the start of one draw to the start of the next. Life's --fps argument will turn into exactly this division.

Why a fixed sleep drifts

The bouncing # slept 50 ms per frame. But a frame is not only the sleep: building the string, printing it and flushing it also take time. Call that the draw time. If you always sleep the full budget, every frame takes draw time plus budget, and the extra adds up. Here is the arithmetic for one minute at 10 fps with a 7 ms draw:

#include <print>

int main() {
    const int frames = 600;          // one minute at 10 fps
    const int budget_ms = 100;       // what you WANT each frame to take
    const int draw_ms = 7;           // what drawing actually costs

    // Plan A: draw, then always sleep the full budget.
    const int plan_a_total = frames * (draw_ms + budget_ms);

    // Plan B: draw, then sleep only what is left of the budget.
    const int plan_b_total = frames * (draw_ms + (budget_ms - draw_ms));

    std::println("wanted:  {} ms", frames * budget_ms);
    std::println("plan A:  {} ms  (late by {} ms)", plan_a_total, plan_a_total - frames * budget_ms);
    std::println("plan B:  {} ms  (late by {} ms)", plan_b_total, plan_b_total - frames * budget_ms);
    return 0;
}

wanted:  60000 ms
plan A:  64200 ms  (late by 4200 ms)
plan B:  60000 ms  (late by 0 ms)

Plan A is more than four seconds late after a minute. For a 1000×1000 Life grid the draw time would be far more than 7 ms: the next section shows that merely building a one-million-character string, the size of such a frame, takes about 5 ms before a single byte has reached the terminal, and painting a million cells takes the terminal far longer still. The drift would be far worse. Plan B is the fix: measure how long the draw took, and sleep only for what is left of the budget.

Measuring time with steady_clock

Measuring needs a clock. std::chrono::steady_clock is a clock that only ever moves forward at a constant rate; it is not the wall clock, which can jump when the system adjusts the time. steady_clock::now() returns a time point, a moment. You cannot print a time point with {} (the compiler refuses: a moment on the steady clock is not a date or a time of day), but you can subtract two of them, and the result is a duration. duration_cast<milliseconds> converts a duration to the unit you want to print, rounding down.

#include <chrono>
#include <print>
#include <string>

int main() {
    using clock = std::chrono::steady_clock;

    const auto start = clock::now();

    std::string frame;
    for (int i = 0; i < 1000000; ++i) {
        frame += '#';
    }

    const auto end = clock::now();
    const auto elapsed = std::chrono::duration_cast<std::chrono::microseconds>(end - start);

    std::println("built {} bytes in {} microseconds", frame.size(), elapsed.count());
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra measure.cpp -o measure
$ ./measure
built 1000000 bytes in 4868 microseconds
$ ./measure
built 1000000 bytes in 5225 microseconds

The number differs on every run and on every machine, which is why this program has no exact output block. The using clock = ...; line gives the long type a short name, the way using Cells = ...; does in life.hpp (chapter 7). The pattern start = now(); work; end = now(); end - start is the whole of chapter 13, where you will point it at the Life step and get your first benchmark number. Here you point it at a frame.

A paced loop

Now combine the two: take the time at the start of the frame, draw, take the time again, and sleep for budget - spent. If the draw took longer than the whole budget, there is nothing left to sleep; the if guards that, because asking to sleep for a negative duration is meaningless (it returns at once, but it is clearer to skip it).

#include <chrono>
#include <cstdio>
#include <print>
#include <string>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    using clock = std::chrono::steady_clock;

    const int fps = 10;
    const std::chrono::milliseconds budget(1000 / fps);
    const auto run_start = clock::now();

    std::print("\x1b[?25l");
    for (int frame = 0; frame < 30; ++frame) {
        const auto frame_start = clock::now();

        // ---- draw: build the whole frame, print it once ----
        std::string screen = "\x1b[2J\x1b[H";
        for (int row = 0; row < 8; ++row) {
            for (int col = 0; col < 32; ++col) {
                char cell = '.';
                if ((row + col + frame) % 4 == 0) {
                    cell = '#';
                }
                screen += cell;
            }
            screen += '\n';
        }
        screen += "frame " + std::to_string(frame) + "\n";
        std::print("{}", screen);
        std::fflush(stdout);

        // ---- pace: sleep only for what is left of the budget ----
        const auto spent = clock::now() - frame_start;
        if (spent < budget) {
            std::this_thread::sleep_for(budget - spent);
        }
    }
    std::print("\x1b[?25h");

    const auto total = std::chrono::duration_cast<std::chrono::milliseconds>(clock::now() - run_start);
    std::println("30 frames took {} ms (wanted {} ms)", total.count(), 30 * budget.count());
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra paced_loop.cpp -o paced_loop
$ ./paced_loop
30 frames took 3130 ms (wanted 3000 ms)

Diagonal stripes scroll across an 8-by-32 box for three seconds. The last line is the honest part: 3130 ms, not 3000 (three runs on this Mac gave 3128, 3130 and 3136 ms; yours will differ a little). The draw time was subtracted correctly, so where did the extra 130 ms come from? From sleep_for itself. It promises to sleep at least as long as you ask; the operating system wakes your program up when it gets round to it, a few milliseconds late. Thirty frames, a little over four milliseconds late each here. For a game that is invisible. For a benchmark it is why chapter 13 never times a sleep.

Two other things to notice in that program. The spent < budget comparison works directly on durations; the compiler converts the units. And budget is declared as const std::chrono::milliseconds budget(1000 / fps), an int turned into a typed duration once, at the top, so that the rest of the loop never sees a bare number.

Try it

Set fps to 30 and then to 2, and compare the "took" line with the "wanted" line each time. Then add an int overran = 0; before the loop, give the if an else branch that does ++overran;, and print overran at the end; with fps = 10 it should stay 0. Now set fps to 2000, so the budget is 1000 / 2000 = 0 ms, and run again: overran is 30 and the loop runs as fast as the terminal allows. That is the "draw took longer than the whole budget" case, and it is what a 1000×1000 Life grid would do to any sensible budget.

Inference twin

When a language model streams its answer into a terminal, token by token, the tokens travel down this same stdout stream, through the same buffer, into the same grid of cells. The frame budget you just computed is the per-token latency budget an inference engine lives by: at 20 tokens per second, each token has 50 ms, and whatever the model's step takes is subtracted from it. A frame that overran its budget is a dropped frame in a game and a latency spike in a chat window; the user experiences both as a stutter. In week 18 you will measure your own SmolLM2-135M engine's tokens per second with exactly the steady_clock pattern from measure.cpp.

Flicker

There is one more thing paced_loop.cpp did on purpose: it built the whole frame, including the clear-and-home command, into one std::string and printed it with a single std::print. Here is what happens if you do not.

#include <chrono>
#include <cstdio>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    for (int frame = 0; frame < 20; ++frame) {
        std::print("\x1b[2J\x1b[H");
        std::fflush(stdout);                 // the screen is now EMPTY ...
        for (int row = 0; row < 10; ++row) {
            for (int col = 0; col < 30; ++col) {
                char cell = '.';
                if ((row + col + frame) % 3 == 0) {
                    cell = '#';
                }
                std::print("{}", cell);
                std::fflush(stdout);         // ... and refills one cell at a time
            }
            std::println();
        }
        std::this_thread::sleep_for(100ms);
    }
    return 0;
}

Run it and the picture shimmers, or shows a bright flash each frame, or paints visibly from top to bottom, depending on how fast your terminal is. The reason is in the comments. The clear command is sent and flushed on its own, so for a moment the terminal shows an empty screen. Then three hundred separate one-byte writes arrive, each one a round trip to the operating system and the terminal, and the terminal repaints after some of them. Your eye catches the blank screen and the half-drawn frames in between. That is flicker.

The fix is to never let the terminal see a half-finished frame: build it all first, then hand it over in one go.

#include <chrono>
#include <cstdio>
#include <print>
#include <string>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    for (int frame = 0; frame < 20; ++frame) {
        std::string screen = "\x1b[2J\x1b[H";          // the command is part of the frame
        for (int row = 0; row < 10; ++row) {
            for (int col = 0; col < 30; ++col) {
                char cell = '.';
                if ((row + col + frame) % 3 == 0) {
                    cell = '#';
                }
                screen += cell;
            }
            screen += '\n';
        }
        std::print("{}", screen);                      // ONE write for the whole frame
        std::fflush(stdout);
        std::this_thread::sleep_for(100ms);
    }
    return 0;
}

Same picture, same speed, and now it is rock steady. The clear command and the 310 bytes of picture reach the terminal in a single write, so the terminal clears and repaints in one pass with no blank moment in between. This is also why render in life.hpp returns a std::string rather than printing: the string is the frame, and main prints it once.

Trap

Never put a sleep_for or a fflush inside the loop that draws cells. One flush per frame, one sleep per frame, after the whole frame is out. A sleep inside the drawing loop is the most common cause of "my animation is slow and flickery" and it is a one-line fix.

Ctrl-C and the lost cursor

Every animation in this chapter runs for a fixed number of frames. Life will run until you stop it, and the way you stop a terminal program is Ctrl-C. Hold Control and press C, and the operating system's terminal driver sends your program an interrupt signal; a program that has made no arrangements for it (yours) is killed on the spot. "On the spot" is the problem: the program does not reach its last lines. If one of those lines was std::print("\x1b[?25h"), the cursor stays hidden, and your prompt comes back without a cursor.

#include <chrono>
#include <cstdio>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    std::print("\x1b[?25l");                  // hide
    std::fflush(stdout);
    std::println("cursor hidden for three seconds; try pressing Ctrl-C now");
    std::this_thread::sleep_for(3s);
    std::print("\x1b[?25h");                  // show: this line is skipped if you Ctrl-C
    std::fflush(stdout);
    std::println("cursor restored, exiting normally");
    return 0;
}

$ ./cursor_guard
cursor hidden for three seconds; try pressing Ctrl-C now
^C
$ tput cnorm

Let it run to the end and the cursor comes back by itself. Interrupt it and the cursor is gone until you type tput cnorm (which, as you saw, writes the show-cursor sequence for you) or reset, which puts the whole terminal back to its starting state and clears the screen. Neither hurts anything; keep them in mind for the week.

The proper fix has two halves, and both are week 3 material. First, C++ has a mechanism that ties a piece of clean-up to a variable. The clean-up runs by itself when the variable's scope ends, and it does not matter how the scope is left: a normal return, an early return, or a break out of the loop. This is RAII, which chapter 6 named when the vector freed its own memory; week 3's Snake builds a terminal guard on it, where you will also have to restore the keyboard mode. Second, RAII alone does not survive Ctrl-C: a program killed by the interrupt signal runs no more of your code, clean-up included. So Snake also asks the operating system to deliver the signal to a small function of yours instead of killing the program; that function sets a flag, the game loop sees the flag and ends normally, and the RAII clean-up runs. For this week: hide the cursor at the start of the loop, print "\x1b[?25h" before the normal return 0, and when you Ctrl-C, type tput cnorm. Also consider a --steps argument so that the program can end normally after a given number of generations, which is both friendlier and easier to test.

How big is the terminal?

Your program draws into a grid it cannot see. If a frame has more rows than the terminal window, the top rows scroll off before you see them and the next frame's clear-and-home no longer lands where the previous one did; the picture jitters. If a row is wider than the window, the terminal wraps it onto the next line and every row after it is shifted. Both look like bugs in your code and neither is.

The shell can tell you the size:

$ tput cols
120
$ tput lines
40

Those numbers are for one particular window; yours will differ, and they change when you resize. The rule for this week is simple: choose a grid that is smaller than the terminal. Life takes --width and --height on the command line (chapter 8), so leave at least two rows for the shell prompt and any status line you print, and a few columns of margin. A 1000×1000 grid is for the benchmark in chapter 13, not for drawing; nothing on your screen can show it, and at 1000 bytes per row the frame would be a megabyte.

Deferred

A program can also ask the operating system for the terminal size itself, and be told when the window is resized. That needs a system call and a signal handler, which are week 3 and later. For now, tput and sensible defaults are enough.

Check yourself

Your program calls std::println("hi"). Name the three programs involved in the letters appearing on screen, and say what each one does.

Answer

Your program writes three bytes (h, i, newline) to stdout. The terminal reads those bytes and paints h and i into cells, then moves the cursor to the next line for the newline. The shell is the program that started yours with its output connected to that terminal, and prints the next prompt when yours ends. Your program draws nothing itself.

What does the terminal show after std::print("hello\rJ\n")? And how many bytes did the program write?

Answer

It shows Jello. The \r moves the cursor back to column 0 of the same line, J overwrites the h, and the rest stays. The program wrote 8 bytes: five letters, carriage return (13), J, newline (10).

Which bytes make up "\x1b[H", and what does the terminal do with them? Why does it not paint a [ and an H?

Answer

Three bytes: 27 (escape), 91 ([), 72 (H). The terminal moves the cursor to row 1, column 1. Byte 27 tells the terminal that what follows is a command, so it reads the [ and H as the name of the command, not as text, and paints nothing.

A program prints a frame with std::print (no trailing newline), then sleeps for a second, in a loop. On the terminal it looks fine. Run as ./prog | cat it shows nothing until it exits. Explain, and give the one-line fix.

Answer

Output goes into a buffer. On a terminal the library flushes at every newline, and each std::print first flushes what the previous one left behind, so the frame gets out (at worst one frame late); through a pipe it flushes only when the buffer is full or the program exits, so everything waits. Add std::fflush(stdout); (header <cstdio>) right after printing each frame, before the sleep.

Why does std::this_thread::sleep_for(100) fail to compile, and what should you write instead?

Answer

sleep_for takes a duration, a value whose type carries its unit. A bare 100 is an int with no unit, and the library refuses to guess whether it means seconds or milliseconds. Write std::this_thread::sleep_for(100ms) after using namespace std::chrono_literals;, or std::this_thread::sleep_for(std::chrono::milliseconds(100)).

You want 25 frames per second. Drawing a frame takes 12 ms. How long should you sleep after each frame, and what happens over 1000 frames if you simply sleep 40 ms every time?

Answer

The budget is 1000 / 25 = 40 ms per frame, so sleep 40 - 12 = 28 ms. Sleeping the full 40 ms makes each frame take 52 ms; over 1000 frames that is 52 s instead of 40 s, 12 seconds of drift. Measure the draw with steady_clock::now() before and after, and sleep for budget - spent only if spent < budget.

Two programs draw the same 20×60 picture at the same speed. One flickers and one does not. What is the likely difference in their code?

Answer

The flickering one sends the clear command and then prints cell by cell (and probably flushes or sleeps inside the drawing loop), so the terminal shows a blank screen and partial frames between writes. The steady one builds the whole frame, clear command included, into one std::string and prints it with a single std::print("{}", screen) followed by one std::fflush(stdout).

You pressed Ctrl-C during an animation and your prompt has no cursor. What happened, and what do you type?

Answer

The program had sent \x1b[?25l (hide cursor) and was killed before it reached the line that sends \x1b[?25h (show cursor). Type tput cnorm, which sends the show-cursor sequence for you, or reset, which restores the whole terminal. The permanent fix is week 3's: an RAII guard that restores the cursor whenever its scope ends, plus a signal handler that turns Ctrl-C into "end the loop normally" so that the scope does end.
