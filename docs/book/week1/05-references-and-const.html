Chapter 05

References and const

At the end of this chapter you will be able to hand a function a variable instead of a copy of it, let the function change that variable when you want it to, and forbid the change when you do not. You will also be able to read the two most important function signatures in life.hpp and know exactly what they promise.

The problem: a parameter is a copy

In chapter 4 you learned that a function's parameter is a brand new box. When you called try_to_double(count), the machine made a fresh int box called n, copied the 4 bytes of count into it, and ran the function on n. The function never touched count. That is why n = n * 2 inside try_to_double changed nothing the caller could see: count was still 21 afterwards.

For an int the copy is harmless: 4 bytes, a single machine instruction. Now think about something bigger. You have not met std::string properly yet (that is chapter 8); for now take it as a piece of text: a variable that holds any number of characters. It lives in the <string> header, so a program that uses it needs #include <string> at the top, the same way std::println needs #include <print>. The line

std::string big(1000000, 'x');   // one million copies of the letter x

makes a text of exactly one million x characters, one byte each. The shape of this line is new. Until now you gave a variable its starting value with =, as in int count = 21;. Parentheses straight after the name are a second way to do the same job, and they can take more than one value. For a std::string, two values in the parentheses mean "this many copies of this character". Take the shape on trust for now; chapter 6 uses exactly the same shape to build a std::vector of a given size.

Those million bytes live in memory. If you hand big to a function the way chapter 4 taught, the parameter is a copy of the whole thing: the machine has to find a million fresh bytes and copy every one of them over before the first line of the function even runs.

Here is a program that proves the copy really happens. The function changes its parameter completely, and the caller's text is untouched afterwards. (You also need one small thing on trust: big.size() means "how many characters are in big". Chapter 6 explains .size() properly.)

#include <print>
#include <string>

// `text` is a COPY of whatever the caller passed in.
void shout(std::string text) {
    text = "changed inside shout";
    std::println("inside shout:  {}", text);
}

int main() {
    std::string big(1000000, 'x');   // one million copies of the letter x
    std::println("before:        {} characters", big.size());
    shout(big);
    std::println("after:         {} characters", big.size());
    return 0;
}

before:        1000000 characters
inside shout:  changed inside shout
after:         1000000 characters

Inside shout, text became a short sentence. Outside, big still has its million characters. Two separate boxes; the second one was filled by copying the first.

That copy has two costs. Time: the processor moves a million bytes from one place in memory to another, and if you call the function a thousand times, it does that a thousand times. Memory: while the function runs, two million bytes are in use instead of one million.

Now scale that to the Life grid. The benchmark at the end of this week is a 1000×1000 grid: one million cells, one byte each. If the grid were passed by value, every call that asks "how many neighbours does this one cell have?" would first copy all one million cells. You ask that question once per cell, so one generation would copy a million cells a million times. That is 1012 bytes, a trillion, moved to compute a single frame. The program would be unusably slow, and every byte of it would be waste, because the function only wanted to look.

First principle

Passing by value means: make a new box, copy the bytes in. The cost is proportional to the number of bytes. A 4-byte int is free. A million-byte text is not. Nothing about the function changes this; it is the act of calling that pays.

What you want is a way to say to the function: "do not take a copy; work on my box." C++ has exactly that. It is called a reference.

A reference is another name for an existing box

A reference is a second name for a variable that already exists. You declare one by putting & after the type:

int x = 5;
int& r = x;      // read it as: "r is a reference to int, and it refers to x"

After this line there is still only one box, the one made by int x = 5. The name r is glued to that same box. Reading r reads the box. Writing r writes the box. Watch:

#include <print>

int main() {
    int x = 5;
    int& r = x;        // r is another name for x

    std::println("x = {}, r = {}", x, r);

    r = 10;            // write through the nickname...
    std::println("x = {}, r = {}", x, r);

    x = 42;            // ...or through the original name
    std::println("x = {}, r = {}", x, r);
    return 0;
}

x = 5, r = 5
x = 10, r = 10
x = 42, r = 42

Every line shows the same number twice, because there is only one number. r = 10 did not "copy 10 into r and then into x". It wrote 10 into the one box that both names point at.

Analogy

A reference is a nickname. If your friend is called Alexander and everyone calls him Alex, there is still one person. Give Alex a haircut and Alexander has a haircut. Tell Alexander a secret and Alex knows it. The nickname is not a second person; it is a second way to point at the first one.

Where it breaks: you can give a nickname to somebody later in life, you can stop using it, and you can move it to a different person. A C++ reference can do none of that. It must be attached to a variable the moment it is declared, and from then until it goes out of scope it refers to that one variable and nothing else. It is a nickname written in permanent ink at birth.

A reference must be bound at birth

Because a reference is only a name, a reference without a variable makes no sense: a name for nothing. The compiler refuses:

#include <print>

int main() {
    int& r;            // a nickname for... nobody?
    r = 5;
    std::println("{}", r);
    return 0;
}

unbound.cpp:4:10: error: declaration of reference variable 'r' requires an initializer
    4 |     int& r;            // a nickname for... nobody?
      |          ^
1 error generated.

"Requires an initializer" is the compiler's way of saying: tell me what this is a name for. Compare this with a plain int r;, which the compiler allows (it makes a box with garbage in it). A reference has no box of its own to leave empty.

A reference cannot be re-pointed

Here is the mistake every beginner makes once. You have a reference to x. You write r = y; and expect r to now be a name for y. It is not. Assignment through a reference is assignment to the box it refers to. So r = y copies y's value into x:

#include <print>

int main() {
    int x = 1;
    int y = 2;
    int& r = x;        // r is bound to x, for ever

    r = y;             // this does NOT make r a name for y

    std::println("x = {}, y = {}, r = {}", x, y, r);

    r = 99;            // still writes into x
    std::println("x = {}, y = {}, r = {}", x, y, r);
    return 0;
}

x = 2, y = 2, r = 2
x = 99, y = 2, r = 99

After r = y, x is 2 (it received y's value) and y is still 2. After r = 99, x is 99 and y is untouched: r never stopped being a name for x. There is no syntax at all for re-pointing a reference. Once you accept that, references become very simple: every use of r is just a use of x.

First principle

A variable is a named box in memory. A reference adds a name without adding a box. The only line where the & does something special is the declaration int& r = x;, which binds the name. On every other line, r behaves exactly like x.

References on their own, inside one function, are rarely useful: you already have the name x, why would you want a second one? Their real job is in function parameters. That is where they fix the copy problem.

Pass by reference: let a function change your variable

If a parameter is declared as a reference, the parameter becomes another name for the caller's variable instead of a copy of it. No new box, no copy, and whatever the function writes lands in the caller's variable. Here is chapter 4's pass-by-value next to the reference version, both trying to add one to the caller's variable:

#include <print>

// Chapter 4 version: v is a copy. Changing it changes nothing outside.
void add_one_to_copy(int v) {
    v = v + 1;
    std::println("  inside add_one_to_copy: v = {}", v);
}

// Reference version: v is another name for the caller's variable.
void add_one(int& v) {
    v = v + 1;
    std::println("  inside add_one:         v = {}", v);
}

int main() {
    int counter = 10;

    add_one_to_copy(counter);
    std::println("after add_one_to_copy: counter = {}", counter);

    add_one(counter);
    std::println("after add_one:         counter = {}", counter);
    return 0;
}

  inside add_one_to_copy: v = 11
after add_one_to_copy: counter = 10
  inside add_one:         v = 11
after add_one:         counter = 11

The two function bodies do the same work: add one to v, then print it. The only difference that matters is one & in the parameter list, and that one character decides whether the caller's counter changes. Inside add_one, the name v and the caller's name counter are two names for one box. The call add_one(counter) is the "birth" moment: it binds v to counter, the same way int& r = x; bound r to x.

Notice how the call looks the same in both cases: add_one_to_copy(counter) and add_one(counter). You cannot tell from the call site whether the function takes a copy or a reference. You have to read the signature. This is why the declarations in a header file like life.hpp matter so much: the & in the declaration is a promise about what the function may do to your variables.

Swapping two variables

The classic reason to pass by reference is a function that must change two things at once. A function can only return one value, but it can write through as many references as it likes:

#include <print>

void swap_values(int& a, int& b) {
    int temp = a;      // remember a's value
    a = b;             // overwrite a with b's value
    b = temp;          // put the remembered value into b
}

int main() {
    int left = 1;
    int right = 2;
    std::println("before: left = {}, right = {}", left, right);

    swap_values(left, right);
    std::println("after:  left = {}, right = {}", left, right);
    return 0;
}

before: left = 1, right = 2
after:  left = 2, right = 1

Walk through it with the box picture. When swap_values(left, right) runs, a is a name for left's box and b is a name for right's box. temp is a real, new box (it is a plain int, not a reference) holding a copy of 1. a = b writes 2 into left's box. b = temp writes 1 into right's box. Done.

Try it

Make two changes to swap_values.cpp, one at a time, and predict the "after" line before you run each. First: remove both & signs. Second: put them back, then remove only the & on b, so the signature reads void swap_values(int& a, int b). Walk the box picture for each before running.

Show the answer

With no & at all, the function swaps two private copies and main sees nothing: after: left = 1, right = 2, identical to "before". With only a by reference, a = b still writes into left's box (so left becomes 2), but b = temp writes into a private copy, so right stays 2: after: left = 2, right = 2. The value 1 is lost. One missing & is enough to break the function, and the compiler says nothing, because both versions are legal C++.

Keep swap_values in mind. In chapter 7 you will meet std::swap, which does exactly this for any type, including two whole grids, and it is the heart of the Life game loop.

Returning more than one result

The same trick lets a function hand back two answers. Integer division has a quotient and a remainder; here is a function that produces both:

#include <print>

// Two results from one function: both are written through references.
void divide(int a, int b, int& quotient, int& remainder) {
    quotient = a / b;
    remainder = a % b;
}

int main() {
    int q = 0;
    int r = 0;
    divide(17, 5, q, r);
    std::println("17 / 5 = {} remainder {}", q, r);

    divide(100, 7, q, r);
    std::println("100 / 7 = {} remainder {}", q, r);
    return 0;
}

17 / 5 = 3 remainder 2
100 / 7 = 14 remainder 2

Look at the mix of parameters. a and b are inputs: small, and the function has no reason to change them, so they go by value. quotient and remainder are outputs: the function's whole purpose is to write into them, so they go by reference. Reading the signature tells you the story before you read a single line of the body. (You met %, "remainder after division", in chapter 2. Chapter 7 puts it to work wrapping around the edges of the grid.)

One detail in main: q and r are initialised to 0 even though divide overwrites them on every call. Why bother? Because chapter 2's rule still stands: a variable that is declared without a value holds whatever bytes were left in that memory. Giving q and r a value costs nothing and means that if you ever forget to call divide, you print a harmless 0 instead of nonsense. Notice also that the two calls reuse the same two boxes: the second divide simply writes new values over the old ones.

Try it

Write void min_max(int a, int b, int c, int& smallest, int& largest) that finds the smallest and the largest of three numbers and writes them through the two references. Call it with 7, 2, 9 and print the results. Then make a deliberate mistake: remove the & from smallest only, and predict the output before you run it.

Stuck? First nudge

Start by writing smallest = a; largest = a;, then use if to replace them with b or c when those are smaller or larger. With the & removed from smallest, the function writes into a private copy and the caller's variable keeps whatever you initialised it to.

Pass by const reference: read a big thing without copying it

Back to the million-character text. You want a function, call it print_text, that looks at the text without paying for a copy. Pass by reference solves the copy. But a plain std::string& parameter also hands the function permission to change the caller's text, and a function that only prints has no business doing that. You want a reference that is read-only.

That is what const in front of the type does. A const reference is another name for an existing box through which you may read but not write. In this book it is written const T&, where T is a placeholder for whatever type you have in mind: const int&, const std::string&, and later const Cells&. It is the single most common parameter type in real C++ code, so read the next program slowly:

#include <print>
#include <string>

// Reads `s` without copying it, and promises not to change it.
void print_text(const std::string& s) {
    std::println("{} characters", s.size());
}

int main() {
    std::string small = "hello";
    std::string big(1000000, 'x');

    print_text(small);
    print_text(big);
    print_text("a literal works too");
    return 0;
}

5 characters
1000000 characters
19 characters

Read the parameter from right to left: s is a reference (&) to a std::string that is const, meaning "treated as unchangeable in here". The call print_text(big) binds s to big. Not one of the million bytes is copied. The function reads the size through the reference and returns.

The third call needs a closer look, because there is no variable in it at all: print_text("a literal works too"). The parameter wants a std::string, and a string literal is not one. So the machine builds a nameless std::string from the literal, binds s to it, runs the function, and throws the nameless string away at the end of the statement. A value like that, which has no name and lives only for the length of one statement, is called a temporary. The output 19 characters is the length of the literal: "a literal works too" is 19 characters including the spaces. Count them. The temporary is gone by the time the next line of main runs.

What happens if the function breaks its promise? Here is the smallest possible example, using int so the message is short. The function says const and then tries to write:

#include <print>

void add_one(const int& v) {
    v = v + 1;         // trying to write through a read-only name
}

int main() {
    int counter = 10;
    add_one(counter);
    std::println("{}", counter);
    return 0;
}

const_ref_write.cpp:4:7: error: cannot assign to variable 'v' with const-qualified type 'const int &'
    4 |     v = v + 1;         // trying to write through a read-only name
      |     ~ ^
const_ref_write.cpp:3:25: note: variable 'v' declared const here
    3 | void add_one(const int& v) {
      |              ~~~~~~~~~~~^
1 error generated.

Two things to notice. First, the error points at the write, not at the declaration: "cannot assign to variable 'v'". Second, the note underneath tells you where the promise was made. Clang almost always pairs an error with a note like this; read both.

This error is a feature. You wrote const because the function should not modify its input. Months later, somebody (perhaps you) adds a line that modifies it. Instead of a silent bug where the caller's text quietly changes, the build fails at the exact line. const turns a category of runtime mistake into a compile-time message.

Write void describe(const int& n) that prints zero when n == 0 and otherwise prints the value. Call it three times: with 0 (a literal), with 42, and with an int variable holding your age. Stuck? First nudge

You need an if/else from chapter 3 and two std::println calls. The first two calls bind n to a temporary holding the literal; the third binds it to your variable. The error will say "cannot assign to variable 'n' with const-qualified type 'const int &'", and the note will point at the parameter list.

Why const& and not plain & for read-only parameters

You might think: if the function does not write to the parameter anyway, why bother with const? A plain std::string& also avoids the copy. There are two answers. The first you have just seen: the promise is checked. The second is more practical. A plain reference can only be bound to a real, named variable. A const reference can also be bound to a temporary, like the nameless string the machine built from "a literal works too" in the program above. Watch what happens when you drop the const and pass a literal:

#include <print>
#include <string>

void print_text(std::string& s) {
    std::println("{} characters", s.size());
}

int main() {
    print_text("a literal");
    return 0;
}

literal_nonconst.cpp:9:5: error: no matching function for call to 'print_text'
    9 |     print_text("a literal");
      |     ^~~~~~~~~~
literal_nonconst.cpp:4:6: note: candidate function not viable: no known conversion from 'const char[10]' to 'std::string &' (aka 'basic_string<char> &') for 1st argument
    4 | void print_text(std::string& s) {
      |      ^          ~~~~~~~~~~~~~~
1 error generated.

The message is long, so take it in pieces. The error line says the call does not match any print_text the compiler knows about. The note explains why the one candidate was rejected: it could not convert the argument to std::string &. Two bits of the note look alarming and are not. const char[10] is the compiler's name for the literal "a literal" itself: nine characters plus a hidden end marker, ten in all, none of them changeable. And basic_string<char> is the full internal name of std::string; the aka ("also known as") just tells you the two are the same thing. Take both on trust; you will meet them properly in chapter 8.

The logic behind the refusal is sound. A plain reference means "I might write into this". Writing into a temporary that vanishes at the end of the statement is nonsense, so the compiler refuses to bind one. A const& means "I will only read", and reading a temporary is fine. So const T& parameters accept everything you could want to pass: named variables, literals, and the result of a calculation such as a + b. That flexibility is the second reason it is the default for read-only inputs.

Reading a signature aloud

Get into the habit of translating parameter types into plain sentences:

  • int v: "give me a copy of an int; I will do what I like with my copy."
  • int& v: "give me your int itself; I will probably change it."
  • const int& v: "give me your int itself; I promise only to look."

Every function in life.hpp can be read this way, and should be.

Rules of thumb: value, reference, or const reference?

You now have three ways to declare a parameter. Here is how to choose. The table is not a law of the language; it is what experienced C++ programmers do by default, and it is what the Week 1 code does.

The parameter is...Declare it asWhy
Small and read-only: int, double, bool, char, std::size_t, std::uint8_tT (by value)Copying 1 to 8 bytes is as cheap as anything the machine does. A reference would be no faster and is one more thing to read.
Big and read-only: a std::string, a std::vector (chapter 6), any gridconst T&No copy, and the compiler guarantees the function does not change it.
Something the function must change for the callerT&The whole point: writes go to the caller's variable.
A result the function producesreturn it by valueReturning even a big object by value is fine; the compiler is allowed to build the result directly in the caller's box, so there is usually no copy at all. Prefer return to an output reference when there is only one result.

Two of the rows deserve a word more.

Small things by value. It is tempting, once you learn const&, to write it everywhere. Do not. A reference has to be set up by the machine too. Under the hood it is an address, the number of the byte where the box starts, which you met in chapter 2; week 7 of the curriculum says much more about this. On this Mac an address is 8 bytes, so handing over a reference to a 4-byte int moves more bytes than copying the int would. More importantly, int v is simply easier to read than const int& v. Reserve const& for things whose copy would actually hurt.

Returning by value is fine. A beginner who has just learned that copies are expensive may try to avoid return big_thing; and instead pass an output reference. In modern C++ that is backwards. When a function returns an object by value, the compiler builds that object straight into the place the caller will keep it. The function random_cells in life.hpp returns a whole grid by value, and that is the right design: one result, so return it. You will see how in chapter 8.

Trap

Reading void f(int& v) from the call site is impossible: f(x) looks the same whether f takes a copy or a reference. If a variable mysteriously changes after a function call, open the declaration and look for the &. The reverse trap is just as common: you pass x to a function expecting it to be changed, nothing happens, and the cause is a missing & in the signature.

const correctness ripples

A function that takes const int& v has promised not to change v. The compiler holds it to that promise everywhere inside the function, including when it calls other functions. If it passes v to a function that takes a plain int&, that function might write to v. The first function would not have written anything itself, but it would have handed a writable name to someone who could, and that breaks the promise just the same. The compiler refuses:

#include <print>

void bump(int& v) {
    v = v + 1;
}

// Promises not to change v...
void inspect(const int& v) {
    bump(v);           // ...then hands v to a function that might
    std::println("{}", v);
}

int main() {
    int n = 1;
    inspect(n);
    return 0;
}

ripple.cpp:9:5: error: no matching function for call to 'bump'
    9 |     bump(v);           // ...then hands v to a function that might
      |     ^~~~
ripple.cpp:3:6: note: candidate function not viable: 1st argument ('const int') would lose const qualifier
    3 | void bump(int& v) {
      |      ^    ~~~~~~
1 error generated.

"Would lose const qualifier" is the key phrase. The compiler is not saying bump is wrong. It is saying: you cannot hand a read-only name to a function that wants a writable one. This is what people mean by const correctness: once you mark something const, everything it is passed to must also accept const. The property ripples outwards through the call chain.

The fix is almost always the right fix anyway: if the helper only reads, make its parameter const& too (or by value, if it is small):

#include <print>

// Reads only: safe to call with a const reference.
int doubled(const int& v) {
    return v * 2;
}

// Promises not to change v, and only calls functions that promise the same.
void inspect(const int& v) {
    std::println("v = {}, doubled = {}", v, doubled(v));
}

int main() {
    int n = 21;
    inspect(n);
    return 0;
}

v = 21, doubled = 42

(By the rules of thumb, doubled should really take int v by value, since an int is small. It takes const int& here only to show that const-to-const binding is allowed. Passing a const int& on to an int by-value parameter is also fine: making a copy of something is not changing it.)

The practical consequence for your week: when you write count_neighbours, which receives the grid as const Cells&, every helper you call on that grid must also take it as const Cells&. Start with const and you will never have to go back and add it; start without and you will spend an afternoon adding it everywhere.

Try it

Go back to ripple.cpp, the one that failed, and fix it the other way: leave bump alone and change inspect's parameter to a plain int&. Add std::println("n = {}", n); after the call in main. Predict both lines of output before you run. Then ask yourself which of the two fixes you would want if inspect were called count_neighbours.

Show the answer

It compiles and prints 2 then n = 2. inspect no longer promises anything, so bump is free to write, and the write reaches main's n. That is the honest signature if the function really must change its argument. For count_neighbours it would be the wrong fix: a counting function that is allowed to alter the grid is a bug waiting to happen, so the right move is to keep const and fix the helper.

Reading the life.hpp signatures

You now know enough to read the two most important lines in phase1-terminal/01-life/src/life.hpp. Do not implement anything yet; the point is to understand the contract. Here are the declarations, copied exactly (a Cells is the grid: a flat list of cells, one byte each, 1 for alive and 0 for dead; chapter 6 and chapter 7 build it up):

// How many of the 8 neighbours of (x, y) are alive.
int count_neighbours(const Cells& cells, int width, int height, int x, int y);

// One generation of Life. Reads `current`, writes the result into `next`.
void step(const Cells& current, Cells& next, int width, int height);

Read count_neighbours aloud using the habit from earlier. "Give me the grid itself, I promise only to look (const Cells&). Give me copies of the width, the height, and the coordinates (four ints by value)." It returns one small answer, an int between 0 and 8, so that comes back by return. Every rule of thumb in the table is visible in one line. The grid is the big thing, so it is a const reference. The four numbers are small, so they are copies. The result is single, so it is returned.

Now step. "Give me the grid current, I promise only to look. Give me the grid next, and I will write into it. Width and height by copy." Two grids, one read-only, one writable. That split is not a style choice; it is the entire algorithm.

Why two grids? Every new cell depends on the old values of its neighbours, so writing into the grid you are reading would mix two generations. Chapter 7 shows this going wrong on a one-dimensional automaton and names the fix, double buffering.

The const on current is what lets the compiler check that your step never breaks the rule. If you accidentally write into current, you will get a "cannot assign" error from the same family as the one earlier, instead of a flickering, wrong simulation. (For a grid the exact wording is cannot assign to return value because function 'operator[]' returns a const value; the operator[] part is chapter 6's business. The meaning is the same: you tried to write through a read-only name.) The test named "step: does not modify current" in tests/life_test.cpp checks the same thing at run time; the const checks it at compile time, which is earlier and cheaper.

Inference twin

A weight matrix in a language model is a few hundred megabytes to several gigabytes of numbers. Nobody ever copies one to look at it. Every function that computes with weights receives a view: in C++ that is std::span or std::mdspan (week 15), and in llama.cpp it is a tensor struct that records where the data lives and how it is shaped. A view is a reference with extra information attached: "the bytes are over there, and here is how to read them as a 768×768 grid". Your const Cells& cells is the simplest possible view: a reference to the data plus width and height carried alongside. The forward pass of SmolLM2-135M is a chain of functions that all take const views of the weights and write into a separate output buffer, exactly the shape of step(const Cells&, Cells&). In the KV cache (week 18), the ping-pong between a read buffer and a write buffer is the same double-buffering idea at a larger scale.

const for local variables, and constexpr in one line

const is not only for parameters. Chapter 2 introduced it for ordinary variables, and it means the same thing: this box is filled once and never written again. The compiler enforces it exactly as it did for the parameter:

#include <print>

int main() {
    const int width = 10;
    width = 20;        // width promised never to change
    std::println("{}", width);
    return 0;
}

const_local.cpp:5:11: error: cannot assign to variable 'width' with const-qualified type 'const int'
    5 |     width = 20;        // width promised never to change
      |     ~~~~~ ^
const_local.cpp:4:15: note: variable 'width' declared const here
    4 |     const int width = 10;
      |     ~~~~~~~~~~^~~~~~~~~~
1 error generated.

Same message shape as before: the error at the write, the note at the promise. Make locals const whenever you can. In bench_life.cpp you can see this habit already: const int width = size;, const int warmup_steps = 3;, const auto start = clock::now();. A reader who sees const knows they can stop tracking that variable: its value on line 10 is its value on line 90. In a loop-heavy program like Life, every variable you can mark const is one less thing that can go wrong.

You will also see constexpr in other people's code. In one line: read it as "a const the compiler can compute while compiling", and move on until week 9, where lookup tables give it a real job. For Week 1, const is all you need, and this book does not use constexpr again.

Two traps

Trap one: returning a reference to a local variable

A reference is a name for a box. Local variables live in boxes that are thrown away when the function returns (chapter 4 called this scope). So a function that returns a reference to one of its own locals is handing you a name for a box that no longer exists. The program below does exactly that. One new thing in it: the return type is int&, not int. A function can have a reference as its return type, which means "I hand back a name for a box, not a copy of a value". You will not write such a function this week; it is here only to show the trap.

#include <print>

int& make_number() {
    int local = 7;     // lives only while make_number runs
    int& name = local;
    return name;       // a nickname for a box that is about to vanish
}

int main() {
    int& r = make_number();
    std::println("{}", r);
    return 0;
}

Clang spots this one and warns. With the book's flags (-Wall -Wextra, which tools/run.sh uses) you see:

dangling.cpp:6:12: warning: reference to stack memory associated with local variable 'local' returned [-Wreturn-stack-address]
    6 |     return name;       // a nickname for a box that is about to vanish
      |            ^~~~
dangling.cpp:5:10: note: binding reference variable 'name' here
    5 |     int& name = local;
      |          ^      ~~~~~
1 warning generated.

A warning does not stop the build: the program is still produced and still runs. On this machine it printed 1 when compiled with plain clang++ -std=c++23 -Wall -Wextra. Run through tools/run.sh it printed a large meaningless number instead (44783712 on one run), and that number changed from build to build. Neither is 7, and neither is promised. The box that held 7 was recycled the moment make_number returned, and whatever happened to be written there next is what you read. This is undefined behaviour, the term from chapter 2: the language gives no rules for what happens, so anything can, including appearing to work until the day it does not.

Two more things to notice. The sanitizers in tools/run.sh, which catch many memory bugs, did not catch this one. And the compiler will not always manage the warning either, especially when the reference travels through two or three functions before it is used. So the warning is your only safety net here, and it has holes. Treat -Wreturn-stack-address as an error whenever you see it.

Trap

Never return a reference to a local variable. For Week 1 the rule is even simpler: do not return references at all. Return by value. The functions in life.hpp that produce something, random_cells and render, both return by value, and that is the right call. Week 7 of the curriculum covers lifetimes properly, and then you will learn the few cases where returning a reference is correct.

Trap two: auto drops the reference

Chapter 2 introduced auto as "work out the type from the right-hand side". It has one rule you must know now: auto on its own never deduces a reference. If the right-hand side is a reference, auto gives you a copy of the thing it refers to.

#include <print>

int main() {
    int x = 1;
    int& r = x;

    auto y = r;        // auto deduces int, NOT int&: y is a copy
    y = 99;
    std::println("after y = 99:  x = {}, y = {}", x, y);

    auto& z = r;       // auto& keeps the reference: z is another name for x
    z = 99;
    std::println("after z = 99:  x = {}, z = {}", x, z);

    const int limit = 7;
    auto c = limit;    // auto deduces int, NOT const int: c is a writable copy
    c = 8;
    std::println("limit = {}, c = {}", limit, c);
    return 0;
}

after y = 99:  x = 1, y = 99
after z = 99:  x = 99, z = 99
limit = 7, c = 8

auto y = r; made a brand new int box and copied 1 into it. Writing 99 into y left x alone. auto& z = r; made a reference, and writing through z changed x. The last three lines show that auto drops const in the same way: limit is const, but auto c = limit; deduces plain int, so c is a writable copy and c = 8 compiles without complaint. The rule in one sentence: auto gives you a fresh, writable copy of the value, and forgets both the & and the const of whatever was on the right. If you want to keep them, you write them yourself: auto& or const auto&.

This bites hardest with big things. auto grid = current; where current is a const Cells& silently copies a million cells. Write const auto& grid = current; if you want another read-only name, or just use current directly. When in doubt, write the type out in full. auto saves typing; it should never cost you a copy you did not see.

Check yourself

After int a = 3; int& b = a; b = 8;, what is a? How many int boxes exist?

Answer

a is 8. Exactly one box exists; b is a second name for it, not a second box.

You have int x = 1; int y = 2; int& r = x; and then r = y;. What are x, y and r afterwards?

Answer

x is 2, y is 2, r is 2. Assignment through a reference writes into the box it refers to; it does not re-point the reference. r is still a name for x.

Why does int& r; fail to compile while int n; compiles?

Answer

int n; creates a box (with an unspecified value in it). int& r; would create a name with no box to name, which is meaningless, so the compiler demands an initialiser: int& r = something;.

A function is declared void grow(std::string& s); and another void show(const std::string& s);. Which one may change the caller's text? Which one can you call with a literal like show("hi")?

Answer

grow may change the caller's text; show promises not to. Only show accepts a literal, because a const& can bind to a temporary value and a plain & cannot.

Which parameter type would you choose for each: a double probability that is only read; a std::string that is only read; an int that the function must increase for the caller?

Answer

double fill by value (small, read-only). const std::string& text (big, read-only). int& count (must be changed for the caller).

void f(const int& v) { g(v); } fails to compile with "would lose const qualifier". What does g's signature look like, and what are the two ways to fix the problem?

Answer

g takes a plain int&. Either change g to take const int& (or int by value) if it only reads, or, if g genuinely must write, then f cannot honestly promise const and its own parameter should become int&. The first fix is almost always the right one.

In void step(const Cells& current, Cells& next, int width, int height);, why is one grid const and the other not? What would go wrong if there were only one grid?

Answer

current is read-only: it is the generation being counted. next is written: it receives the new generation. With one grid, cells updated early in the pass would be seen in their new state by cells counted later in the pass, mixing present and future and giving wrong, order-dependent results. Two grids (double buffering) keep reads and writes separate.

int& r = x; auto y = r; y = 5; Does x change? What would you write instead to get another name for x?

Answer

No. auto drops the reference, so y is an independent copy. Write auto& y = r; (or int& y = r;) to get a reference.

  • Declare a reference, bind it at birth, and predict what every read and write through it does to the original.
  • Write functions that change the caller's variables through T& parameters, including a swap and a function with two results.
  • Write functions that read big things through const T& without copying, and recognise the compiler message when a promise is broken.
  • Choose by value, & or const& for a parameter using the rules of thumb, and read a signature aloud as a sentence of promises.
  • Read count_neighbours and step in life.hpp and say why one grid is const and the other is not.
  • Avoid the two traps: never return a reference to a local, and remember that auto drops & and const.
