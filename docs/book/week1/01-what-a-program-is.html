The machine underneath

Before you write a line of C++, it is worth being precise about what a computer is, because everything in this book is a way of telling that machine what to do. Strip away the case, the screen and the operating system, and three things remain.

The first is the CPU (central processing unit). It does one tiny thing at a time: add two numbers, copy a number from one place to another, compare two numbers, jump to a different instruction. Each of these is an instruction. A single instruction is almost useless. The usefulness comes from the sheer number and from the order they are carried out in. The M5 chip in your Mac ticks roughly four billion times every second, and each tick finishes one or more instructions. So "a few billion instructions per second" is the right order of magnitude to keep in your head; it will matter when you time your first benchmark in chapter 13.

The second is memory (RAM). Picture one enormous row of boxes, numbered 0, 1, 2, 3, and so on up into the billions. Each box is a byte. A byte is eight tiny switches, each of which is either off or on. Eight switches that can each be in two positions give 2 × 2 × 2 × 2 × 2 × 2 × 2 × 2 = 256 possible patterns. So a byte can hold one of 256 different values, and nothing more. Anything larger, such as a big number, a word, or a picture, is stored as several bytes side by side. The number of a box is its address. The CPU reads a byte by asking for its address, and writes one by sending an address and a new pattern.

address:   0     1     2     3     4     5     6     7     8   ...
         +-----+-----+-----+-----+-----+-----+-----+-----+-----+
byte:    | 72  | 101 | 108 | 108 | 111 |  0  | 42  | 0   | 0   | ...
         +-----+-----+-----+-----+-----+-----+-----+-----+-----+
one byte = 8 switches:   0 1 0 0 1 0 0 0   = 72

Two things in that figure need saying. First, the switches are read as a number the way a car's odometer is read, except that each position can only show 0 or 1, so each position is worth twice the one to its right: 128, 64, 32, 16, 8, 4, 2, 1. The pattern 0 1 0 0 1 0 0 0 has the 64 switch and the 8 switch on, and 64 + 8 = 72. Second, the five bytes 72, 101, 108, 108, 111 are not random: they are the word Hello. Every letter has an agreed number (72 is H, 101 is e, 108 is l, 111 is o), and text in memory is nothing but a row of those numbers. Chapter 2 shows you some of those codes. The 0 after the word and the 42 two boxes later are simply other values that happen to be stored next to it. Memory does not know which bytes are text and which are numbers; only the program does.

The third is everything else: the devices. The keyboard sends bytes in when you press keys. The screen receives bytes and turns them into light. The disk (the SSD in your Mac) keeps bytes when the power is off. The CPU talks to all of these by reading and writing bytes.

One more name before the central idea. The operating system (macOS on your Mac) is itself a program, one that is always running. It owns the devices and the memory, and it starts and stops every other program on your behalf. When you type a command in the terminal, it is the operating system that finds the file and starts it.

Now the central idea of the chapter. A program is a list of instructions sitting in memory. When you run a program, the operating system copies its instructions from disk into memory, points the CPU at the first one, and steps back. The CPU reads an instruction, carries it out, moves to the next, and keeps going until it reaches an instruction that says "stop". That is all that running a program is. There is no understanding, no intention, no common sense anywhere in the machine. There is only the next instruction.

First principle

A computer is a CPU that executes one small instruction at a time, a numbered row of bytes it can read and write, and devices that move bytes in and out. A program is a list of those instructions. Every C++ construct in this book is, in the end, a way of producing such a list.

Analogy

Think of a recipe followed by a cook who is astonishingly fast and completely literal. The cook reads one line, does exactly what it says, and moves to the next. If the recipe says "add salt" but never says how much, the cook does not guess; the cook stops and complains. If the recipe says "add the eggs" before "crack the eggs", the cook adds whole eggs, shell and all. The cook never gets bored, never skips a step, and never notices that the result is nonsense.

Where the analogy breaks: a human cook has at least a little understanding of food and can fill small gaps. The CPU has none. Also, a real cook can take a vague instruction and do something sensible; the CPU can only perform the handful of instruction kinds it was built with, so every vague human wish has to be broken down into those instructions before it can run at all. That breaking-down is your job, and the compiler's. And one correction to the recipe itself: the part of the story where the cook "stops and complains" about a missing amount is really the compiler's job, which you will see in a moment. The CPU itself never complains. Give it a nonsensical instruction and it carries it out anyway, and the nonsense shows up later as wrong output or a crash.

Source code and machine code

The instructions the CPU understands are patterns of bytes called machine code. Nobody writes machine code by hand any more. It is unreadable, and it is different for every kind of CPU. Instead you write source code: ordinary text, in a language such as C++, that a human can read.

Something has to turn the one into the other. A program called a compiler reads your text and translates it into machine code. Your program is not the only code involved, though: when you print, you use ready-made code that somebody else wrote. That ready-made code is the standard library, and it ships with the compiler. A second program called the linker glues your translated code together with the pieces of the standard library you used and writes one file, the executable, that the operating system can load and run. "Executable" is the noun for "a file the operating system can run".

The compiler used in this book is clang. It comes with Apple's command line tools. The same compiler has two names on your machine: clang compiles the older C language, and clang++ is the same program told to speak C++. You always type clang++; the book says "clang" when it means the compiler in general. Chapter 10 and chapter 11 go much deeper into compiling and linking. For now, all you need is this picture: text in, executable out.

  hello.cpp          clang++            hello
 (your text)  --> compiler + linker -->  (machine code the CPU can run)
   81 bytes                             301,992 bytes

The two byte counts are real; a few pages from here you will measure both of them yourself.

Your first program

Here is a complete C++ program: the same six lines you typed into scratch/hello.cpp in chapter 0. It prints one line of text and stops. You will take a few parts of it on trust for a chapter or two, but by the end of this section you will know what every character is for.

#include <print>

int main() {
    std::println("Hello, Life.");
    return 0;
}

Hello, Life.

Six lines, one of them blank. Take them one at a time.

#include <print>

C++ by itself does not know how to print anything. Printing is done by code in the standard library, and the library is organised into named parts. Each part is a file called a header. #include <print> tells the compiler: "before you read the rest of this file, bring in the header called print". The angle brackets < and > around the name mean "look for this among the standard headers that came with the compiler", as opposed to a file of your own; you will meet the other spelling, with double quotes, in chapter 10. The line begins with #, which marks it as an instruction to the compiler itself rather than an instruction for the program to carry out. Note that it has no semicolon at the end; lines beginning with # never do.

Analogy

Think of #include as borrowing the printing toolbox and putting it on the bench before you start work. Where it breaks: nothing is moved or borrowed. The compiler literally reads the text of the header file at that point, as if you had typed all of it into your own file. That is why the line must come before the first use of std::println: the compiler reads top to bottom and cannot use a name it has not yet seen. Chapter 10 shows you this happening.

int main()

When the operating system has loaded your program, it needs to know where to begin. In C++ it always begins at a function named main. A function is a named, self-contained piece of a program; chapter 4 is all about them, so for now take main on trust as "the starting point". The int before the name says that when main finishes, it hands back a whole number (int is short for integer) to whoever called it, which is the operating system. The empty parentheses () say that main takes no inputs. Every program has exactly one main.

The braces { and }

The opening brace { after main() and the closing brace } on the last line mark the beginning and end of the body of main: the list of things to do. Braces always come in pairs and they group. Everything between them belongs to main. You will see braces used to group things all through C++.

std::println("Hello, Life.");

This is the one line that does something you can see. Read it from the inside out.

  • "Hello, Life." is a string literal: a piece of text, written between double quotes, exactly as it should appear. The quotes are not printed; they tell the compiler where the text starts and stops.
  • println is the name of a function in the standard library that prints its text and then moves to the next line. (The ln at the end stands for "line".)
  • std is the name of the namespace that the whole standard library lives in. A namespace is like a labelled drawer of names; it stops a library name from clashing with one of yours. std is short for "standard". (Where the drawer picture breaks: a drawer holds things, but a namespace holds only names, and you never have to "open" it. Writing std:: in front of a name is the whole act.)
  • :: means "look inside". So std::println reads as "the println that is inside std".
  • The parentheses after println hold what you hand to it. Each thing you hand to a function is called an argument; here there is one argument, the string literal. Handing the arguments over and letting the function work is called calling the function. Remember the word "argument": the compiler uses it in its messages.
  • The semicolon ; at the very end marks the end of a statement. A statement is one complete instruction in C++, the way a sentence is one complete thought. The compiler needs the semicolon to know where one statement stops and the next begins. Forgetting it is the single most common beginner error, and later in this chapter you will forget it on purpose to see what happens.

return 0;

Remember that main promised to hand back an int. This statement is where it does so. return ends the function and sends a value back; 0 is the value. By a convention older than C++, a program that returns 0 is saying "everything went fine", and any other number means "something went wrong". In a moment you will see the operating system receive this number.

Whitespace and indentation

The blank line after #include, the four spaces before std::println, the line breaks: none of these mean anything to the compiler. They are entirely for human readers. To prove it, here is the same program with the whitespace squashed out. It compiles and behaves identically.

#include <print>
int main(){std::println("Hello, Life.");return 0;}

Hello, Life.

Please never write it like that. Indent the body of every pair of braces by four spaces, one statement per line. Your future self reading this code at midnight will thank you. The one place whitespace does matter is inside a string literal: "Hello, Life." with two spaces prints two spaces.

Statements run top to bottom

The body of main can hold as many statements as you like. The CPU performs them in order, first to last, exactly like the cook working down the recipe.

#include <print>

int main() {
    std::println("First this line is printed.");
    std::println("Then this one.");
    std::println("The cook never skips a step and never reorders them.");
    return 0;
}

First this line is printed.
Then this one.
The cook never skips a step and never reorders them.
Try it

Before you go on, add a fourth std::println line to two_lines.cpp, somewhere between the existing three. Write down, on paper, exactly what the four lines of output will be and in what order. Then run it (the next section shows you how) and compare. Being able to predict the output before running is the skill this whole book trains; start now, while the programs are small enough that you will always be right.

Compile and run

You already have the first program saved as scratch/hello.cpp from chapter 0. The .cpp ending is the convention for C++ source files. In chapter 0 you ran it through tools/run.sh; this time you will do by hand what the script did for you, so that you see each step. Open a terminal at the repo root, move into the scratch folder, and type the two commands.

$ cd scratch
$ clang++ -std=c++23 -Wall -Wextra hello.cpp -o hello
$ ./hello
Hello, Life.

The first command is the compiler. Each part of it means one thing.

  • clang++: the C++ compiler itself (and, behind the scenes, the linker).
  • -std=c++23: speak the 2023 edition of C++. Without it you may get an older edition that lacks <print>.
  • -Wall: turn on all the common warnings. A warning is the compiler saying "this is legal, but it looks like a mistake". Treat every warning as a bug to fix.
  • -Wextra: turn on a second set of warnings that -Wall leaves out (for example, a function input that is never used, which you will care about from chapter 4). The two flags together are the Week 1 standard; type both every time.
  • hello.cpp: the source file to translate.
  • -o hello: name the output file hello. Without it you get a file called a.out.

If the compiler is happy it prints nothing at all. Silence is good news. You now have a new file in the folder, hello, and it is a real executable. Ask the system what it is, using two small shell tools: wc -c counts the bytes in a file (wc is "word count", and -c asks for characters, which for these files means bytes), and file looks inside a file and reports what kind of thing it is.

$ wc -c hello.cpp
      81 hello.cpp
$ file hello
hello: Mach-O 64-bit executable arm64
$ wc -c hello
  301992 hello

Your 81 bytes of text became 301,992 bytes of machine code. Mach-O is the name of the file layout macOS uses for executables, and arm64 is the CPU family that Apple Silicon belongs to, so the file is machine code for exactly the kind of CPU in your Mac; it would not run on an Intel machine. The exact byte count depends on your version of the command line tools, so yours may differ a little. Most of those bytes are the printing machinery from the standard library that the linker glued in. That is the compiler and linker doing their job: text in, executable out.

The second command, ./hello, runs it. The ./ means "in this folder". The shell does not look in the current folder for programs unless you tell it to, so plain hello would say "command not found" even though the file is right there.

Trap

Editing hello.cpp does nothing to hello. The executable is a separate file, made from the source at the moment you compiled. If you change the source and run ./hello again without recompiling, you get the old behaviour and wonder why your change "did not work". Always edit, then compile, then run, in that order.

Where does the text go?

When you run a program from the terminal, the text that std::println produces is sent to a channel called standard output, and the terminal displays whatever arrives there. The program does not know it is talking to a terminal; it only writes bytes. You can prove that right now: the shell can send standard output into a file instead, without changing one line of the program. The > after a command tells the shell "put this command's standard output into the named file instead of on the screen".

$ ./hello > out.txt
$ cat out.txt
Hello, Life.

Nothing appeared on screen after the first command, because the bytes went into out.txt; cat shows the file's contents. Delete out.txt afterwards if you like; it is only a demonstration.

The exit code: where return 0 goes

The 0 that main returned did not vanish. The operating system received it and passed it to the shell, which remembers it under the special name $?. This number is the exit code (also called the exit status) of the last command. The shell command echo prints whatever you write after it, so echo $? prints the exit code:

$ ./hello
Hello, Life.
$ echo $?
0

Now change the program so that main returns 3 instead:

#include <print>

int main() {
    std::println("I am about to report a problem to the shell.");
    return 3;
}

$ clang++ -std=c++23 -Wall -Wextra return3.cpp -o return3
$ ./return3
I am about to report a problem to the shell.
$ echo $?
3

The program printed its line as before, and then the shell reports 3. Nothing on screen looked different, but the number travelled from your return statement, through the operating system, to the shell. Scripts and build tools read this number to decide whether a step succeeded, so it matters: tests, for example, exit with 0 when they all pass and with something else when one fails. In this book every program returns 0 unless it has a reason not to.

A detail you can ignore for now

C++ makes one exception for main: if you leave the return out entirely, the compiler behaves as if you had written return 0;. You will see other people's code rely on this. This book always writes it, because being explicit costs one line and removes a question.

The shortcut: tools/run.sh

Typing the full compiler command every time gets old. The repository has a small script, tools/run.sh, that compiles one file with the Week 1 flags and runs it in one step. It expects to be run from the repository root, so first step back up out of scratch (cd .. means "go to the folder above this one"):

$ cd ..
$ tools/run.sh scratch/hello.cpp
Hello, Life.

Two things to know about it. First, it adds flags you have not met yet, the sanitizers, which make certain memory mistakes announce themselves loudly instead of corrupting things silently; chapter 2 shows the first one speaking and chapter 11 explains the flags. Second, it puts the executable in a temporary folder and deletes it afterwards, so your source folders stay clean. Keep your experiments in scratch/ at the repository root; it is ignored by git. From here on, the book shows the full clang++ command when the flags matter and tools/run.sh when they do not.

Placeholders: putting values into a sentence

Printing fixed text is only half of printing. Most of the time you want to print a value: a count, a result, a size. std::println handles this with placeholders. Inside the string you write a pair of braces {} wherever a value should appear, and after the string you list the values as further arguments, separated by commas. The first value fills the first {}, the second fills the second, and so on. These are the same two characters as the braces around the body of main, but inside a string literal they have nothing to do with grouping; println looks for them and treats each pair as "a value goes here".

#include <print>

int main() {
    std::println("{} plus {} is {}", 2, 3, 5);
    std::println("A byte has {} switches and {} patterns.", 8, 256);
    std::println("Words work too: {} and {}.", "left", "right");
    std::println("{} {} {}", 1, 2.5, "three");
    return 0;
}

2 plus 3 is 5
A byte has 8 switches and 256 patterns.
Words work too: left and right.
1 2.5 three

Look closely at the first line of output. The program did not add 2 and 3. You typed the 5. The placeholders only insert what you give them. In chapter 2 you will let the program do the arithmetic itself. Notice also that the values can be whole numbers, numbers with a decimal point, or text; println turns each into characters in the sensible way. Chapter 2 names these kinds of value properly.

What if you want an actual brace to appear in the output? Double it: {{ prints { and }} prints }.

#include <print>

int main() {
    std::println("A placeholder looks like {{}} in the source.");
    std::println("Braces that print as braces: {{ and }}");
    return 0;
}

A placeholder looks like {} in the source.
Braces that print as braces: { and }
Try it

Go back to the memory figure at the top of the chapter. Write a program that prints the first three boxes as sentences, one per line, using two placeholders in each: Address 0 holds 72., Address 1 holds 101., Address 2 holds 108. Use one string with two {} and change only the values. Predict the output before you run it.

Show the answer 
#include <print>

int main() {
    std::println("Address {} holds {}.", 0, 72);
    std::println("Address {} holds {}.", 1, 101);
    std::println("Address {} holds {}.", 2, 108);
    return 0;
}

Address 0 holds 72.
Address 1 holds 101.
Address 2 holds 108.
Trap

The number of {} in the string must match the number of values after it. Three placeholders and two values is an error. Two moments matter here, and they get names now because you will use them all week: compile time is while clang++ is translating your text, and run time is later, while the finished executable is running. std::println checks the string at compile time, so you find out about the mismatch from the compiler, before the program ever runs. That is the good kind of error: it cannot reach a user. The message is long and ugly; you will meet it a few pages from here and learn how to read it.

The edit-compile-run loop

Programming has a rhythm, and you have already done it several times in this chapter without naming it. You edit a source file. You compile it. Either the compiler complains, and you go back to editing, or it stays silent and you run the result. Then you look at the output, decide what to change, and go around again. Professionals go around this loop hundreds of times a day. Getting fast and calm at it is most of what "being good at programming" feels like from the inside.

   +--------+      +-----------+  errors?  yes
   |  edit  | ---> |  compile  | -------------> back to edit
   +--------+      +-----------+
       ^                 | no
       |                 v
       |           +-----------+
       +---------- |    run    |   look at the output, decide, repeat
                   +-----------+

The compile step is where beginners get stuck, because the compiler's complaints look frightening. They are not. They are the most helpful text you will read all day, once you know their shape. Now deliberately break the hello program four different ways and read what clang says each time. Every message below is the real output from Apple clang 21; nothing is paraphrased. You can check which version you have; the first line is the one that matters, and the arm64 on the second line is the same CPU family that file reported earlier.

$ clang++ --version
Apple clang version 21.0.0 (clang-2100.1.1.101)
Target: arm64-apple-darwin25.6.0
Thread model: posix
InstalledDir: /Library/Developer/CommandLineTools/usr/bin

If your version is newer, a message may differ in a word or two. The shape, which is what you are learning to read, does not change.

Error one: the missing semicolon

Delete the semicolon after the println call.

#include <print>

int main() {
    std::println("Hello, Life.")
    return 0;
}

missing_semicolon.cpp:4:33: error: expected ';' after expression
    4 |     std::println("Hello, Life.")
      |                                 ^
      |                                 ;
1 error generated.

Read the first line left to right. missing_semicolon.cpp is the file. 4 is the line number. 33 is the column, counting characters from the left. Then comes the word error:, and then a sentence saying what is wrong: it expected a ; after the expression. An expression is any piece of code that works out to a value or does one thing; the whole call std::println("Hello, Life.") is one expression, and a statement is usually an expression followed by a semicolon. Below that, clang shows you the offending line, puts a ^ under the exact spot, and here even suggests the fix by printing a ; where one should go. Finally it counts: 1 error generated. No executable was produced; if an old hello is lying around it is unchanged.

The format file:line:column is universal. Every compiler, and every editor, understands it. In most editors (Zed included) you can hold the command key and click a file:line:column to jump straight to the spot.

Error two: a misspelled name

Put the semicolon back and misspell println as printn.

#include <print>

int main() {
    std::printn("Hello, Life.");
    return 0;
}

typo.cpp:4:10: error: no member named 'printn' in namespace 'std'
    4 |     std::printn("Hello, Life.");
      |          ^~~~~~
1 error generated.

Same shape: file, line 4, column 10, error:, then the sentence. "No member named printn in namespace std" is clang telling you that it looked inside the std drawer and found nothing by that name. (A member of a namespace is simply a name that lives inside it; println is a member of std, printn is not.) The ^~~~~~ underlines the whole misspelt word. The compiler does not guess what you meant; it reports precisely what it could not find and leaves the fix to you. Remember the literal cook.

Error three: the missing #include

Fix the spelling and remove the #include line entirely.

int main() {
    std::println("Hello, Life.");
    return 0;
}

no_include.cpp:2:5: error: use of undeclared identifier 'std'
    2 |     std::println("Hello, Life.");
      |     ^
1 error generated.

This one is instructive because the message does not mention #include at all. It says it has never heard of std. An identifier is any name in a program: main, std, println, and later the names you invent yourself. "Undeclared" means no line before this one has introduced that name to the compiler. That is exactly true here: the std namespace and everything in it only come into existence in your file when you include a standard library header. Without the include, the very first mention of std is a mystery word. When you see "undeclared identifier" for a name you are sure exists, the first question to ask is: did I include the header that provides it? The usual culprits are <print> for printing, <vector> from chapter 6 on, and <string> from chapter 8 on.

Error four: a wall of text

Now the ugly one, so that it does not frighten you when it happens by accident. Give println three placeholders but only two values.

#include <print>

int main() {
    std::println("{} plus {} is {}", 2, 3);
    return 0;
}

too_few.cpp:4:18: error: call to consteval function 'std::basic_format_string<char, int, int>::basic_format_string<char[17]>' is not a constant expression
    4 |     std::println("{} plus {} is {}", 2, 3);
      |                  ^
/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/c++/v1/__format/format_parse_context.h:64:7: note: non-constexpr function '__throw_format_error' cannot be used in a constant expression
   64 |       std::__throw_format_error("Argument index outside the valid range");
      |       ^
/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/c++/v1/__format/format_string.h:67:20: note: in call to '__parse_ctx.next_arg_id()'
   67 |   size_t __value = __parse_ctx.next_arg_id();
      |                    ^~~~~~~~~~~~~~~~~~~~~~~~~
    (… four more notes, thirteen lines in all, each pointing into the standard library …)
too_few.cpp:4:18: note: in call to 'basic_format_string<char[17]>("{} plus {} is {}")'
    4 |     std::println("{} plus {} is {}", 2, 3);
      |                  ^~~~~~~~~~~~~~~~~~
/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/c++/v1/__format/format_error.h:38:48: note: declared here
   38 | [[noreturn]] inline _LIBCPP_HIDE_FROM_ABI void __throw_format_error(const char* __s) {
      |                                                ^
1 error generated.

Thirty lines, most of them pointing into files you have never opened, deep inside the standard library. Here is how to read it, and this method works for every long compiler message you will ever see.

  1. Find the lines that say error:. There is exactly one here, at the top, and it points at your file, line 4, column 18, the start of the string. The lines that say note: are not separate problems. A note is the compiler explaining the error in more detail, usually by showing the chain of calls that led there. You can skip every note that points into /Library/Developer/...; that is library code and it is not where the mistake is.
  2. Look for a plain-English clue in the first note or two. Here the first note contains the words "Argument index outside the valid range": the string asked for a third argument and there was none. Once you have seen this message once, you will recognise it instantly. The error: line itself is full of words you do not know (consteval, constant expression, basic_format_string). You do not need them. They are the compiler's way of saying "I tried to check this string while compiling and the check failed"; the reason it failed is in the note.
  3. Fix the first error first, then recompile. Never try to fix the second, third and fourth error before re-running the compiler. Errors cascade: one missing semicolon can confuse the compiler about everything that follows, producing twenty messages that all vanish when the one real mistake is fixed. Fix the top one, compile again, read again.

The counting line at the bottom, 1 error generated., confirms that all that text was about one mistake.

First principle

A compiler message is a precise report of the first point at which the text stopped making sense to a very literal reader. It names the file, the line and the column. Go there, look at that spot and a line or two before it, fix one thing, and compile again.

Errors versus warnings

A line beginning error: means no executable will be produced; you must fix it. A line beginning warning: means the compiler produced an executable but noticed something suspicious. With -Wall -Wextra you will see warnings about, for example, a value you computed and never used. You will see your first real one, with its text, in the next section. In this book, and in the Week 1 project, a warning counts as a bug: fix it before moving on.

Comments

Source code is read by two audiences: the compiler and people. A comment is text in a source file that the compiler ignores entirely and that exists only for people. C++ has two kinds.

  • A line comment starts with // and runs to the end of that line.
  • A block comment starts with /* and ends with */, and can span many lines.
// comments.cpp — shows the two kinds of comment.
// A line comment runs from the two slashes to the end of the line.

#include <print>

/* A block comment starts with slash-star and ends with star-slash.
   It can span several lines. The compiler skips everything in between. */

int main() {
    // Greet first, because the greeting must appear before any numbers.
    std::println("Hello, Life.");

    std::println("Count: {}", 42);  // a comment can share a line with code

    /* std::println("This line is switched off."); */

    return 0;  // 0 tells the shell: no problems
}

Hello, Life.
Count: 42

Notice that the line wrapped in /* */ did not print. Wrapping code in a comment to switch it off temporarily is called commenting out, and you will do it constantly while experimenting. Line comments are the everyday kind; block comments are handy for commenting out several lines at once.

Trap

Block comments do not nest. The compiler does not count how many /* it has seen; it ends the comment at the very first */. So if you wrap a block comment around code that already contains one, the inner */ closes your outer comment early, and the lines after it are suddenly live code again, followed by a stray */. Here it is happening.

#include <print>

int main() {
    /* Switched off while experimenting:
       std::println("one");
       /* an inner block comment: this is the mistake */
       std::println("two");
    */
    std::println("Hello, Life.");
    return 0;
}

nested_comment.cpp:6:8: warning: '/*' within block comment [-Wcomment]
    6 |        /* an inner block comment: this is the mistake */
      |        ^
nested_comment.cpp:8:6: error: expected expression
    8 |     */
      |      ^
1 warning and 1 error generated.

This is your first real warning: line, and it shows how warnings and errors work together. Trace it with the rule above. The outer comment starts on line 4. The */ at the end of line 6 ends it, because it is the first one. Line 7, std::println("two");, is therefore ordinary code and compiles fine. Line 8 is a bare */, which is not C++ at all, so the compiler reports expected expression there. The warning on line 6 is clang being helpful: with -Wall it noticed the inner /*, guessed what you meant, and pointed at the cause rather than the symptom. The last line counts both: 1 warning and 1 error generated. When you need to switch off a block that already contains a block comment, use line comments on each line instead; // has no closing mark, so nothing can end it early.

Comment the why, not the what

A comment that repeats what the code plainly says is noise: return 0; // return zero tells a reader nothing. The code already says what happens. A comment earns its place when it says why: a decision, a constraint, a reason that is not visible in the code itself. Look at the Week 1 contract in phase1-terminal/01-life/src/life.hpp. Its comments do not describe the C++; they describe the rule each function must obey (wrap(-1, 10) == 9, "like the hands of a clock") and the one layout idea the week is built on. That is what good comments look like. The file is also the first real C++ header you will read, and after this chapter you can already recognise its // comments, its #include lines and its semicolons; the rest arrives over the next few chapters.

Five near-identical lines is obviously the wrong way to do this. If the grid were 80 by 24 you would need 24 lines of source, and if its size could change while the program runs, no fixed list of statements could cope at all. Chapter 3 gives you loops, which let you say "do this five times" once; chapter 6 gives you a way to hold the cells themselves in memory instead of in the text of the program; chapter 7 shows how a 2D grid lives in the one-dimensional row of bytes you met at the top of this chapter. The render function in life.hpp, which you will write this week, produces exactly this kind of text: one line per row, dots and hashes, a line break after every row.

Inference twin

llama.cpp, the program that runs large language models on ordinary computers, is also a program in the sense of this chapter, and nothing more than that. It has a main. The operating system loads its instructions into memory and the CPU walks through them. It reads bytes from a file on disk (the model's weights: billions of numbers, stored a few bytes each), does an enormous amount of arithmetic on them, and writes bytes to standard output (the text you see appear). There is no step in that description that is not "read bytes, do arithmetic, write bytes". The arithmetic is cleverer and there is vastly more of it, but your five-line grid and a running language model are the same kind of object: a list of instructions that a literal machine performs in order.

Hint for 2: where do the values go?

The string comes first, with one {} for each thing you want inserted; the values come after it, separated by commas, in the same order. A name is text, so it goes in double quotes, just like "left" did.

Hint for 4: what the missing closing brace looks like

Delete the final } of hello.cpp and compile. You get an error and a note, and this time the note is useful: it points back at the { that was never closed.

no_brace.cpp:5:14: error: expected '}'
    5 |     return 0;
      |              ^
no_brace.cpp:3:12: note: to match this '{'
    3 | int main() {
      |            ^
1 error generated.

Notice the error points at the end of line 5, the last place the compiler could still hope to find a }, not at the missing character itself, because a missing character has no position. Reading "a line or two before" the reported spot is normal.

Hint for 3: why does the second echo show 0?

$? always holds the exit code of the most recent command. After ./hello runs and returns 0, the 7 from your other program is gone. Even the echo itself sets $? to 0, so typing echo $? twice in a row prints the real status and then 0.

Check yourself

How many different values can one byte hold, and why that number?

Answer

256. A byte is eight switches, each off or on, so there are 2 × 2 × 2 × 2 × 2 × 2 × 2 × 2 = 28 = 256 possible patterns.

In std::println, what does std name, and what does :: mean?

Answer

std is the namespace that holds the whole standard library; :: means "look inside". So std::println is "the println inside std".

What happens if you delete the line #include <print> and compile?

Answer

Compilation fails with error: use of undeclared identifier 'std'. The std namespace and println only become known to your file through the header, so without the include the compiler has never heard of either.

A program ends with return 3;. What prints if you run it and then type echo $??

Answer

3. The value returned from main becomes the program's exit code, which the shell stores in $?. By convention 0 means success and anything else means a problem.

The compiler prints one error: line followed by twelve note: lines. How many mistakes do you need to fix?

Answer

One. Notes are extra detail about the error above them, not separate problems. Find the error: line, go to its file:line:column, fix that, and recompile before reading anything else.

What does std::println("{} and {}", 1, 2, 3); do?

Answer

Two placeholders with three values is a mismatch. The 3 has no placeholder. Apple clang's standard library (it is called libc++) accepts this particular direction: extra values are ignored, and it prints 1 and 2. The other direction, more placeholders than values, is a compile error. Keep them equal and the question never arises.

You edit hello.cpp, run ./hello, and see the old text. What did you forget?

Answer

To compile. hello is a separate file made from the source at the moment you last ran clang++; editing the source does not touch it.

Which of these is a good comment: return 0; // return zero or return 0; // 0 tells the shell: no problems?

Answer

The second. The first repeats what the code already says (the what). The second adds something the code does not show: why 0 is the right value to return.
