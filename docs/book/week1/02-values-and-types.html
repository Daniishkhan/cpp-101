Chapter 02

Values and types

At the end of this chapter you can store a number, a yes/no answer or a character in a named place in memory, do arithmetic with it, print it neatly, and explain exactly which bytes the computer is using and what it thinks they mean.

Bytes have no meaning

In chapter 1 you printed text. Behind that text, the machine was shuffling bytes: groups of 8 bits, each bit a 0 or a 1. A byte can hold one of 256 patterns (2 multiplied by itself 8 times). Memory is nothing more than a very long row of these bytes, each with a position number called its address.

Here is the fact that this whole chapter rests on: a byte does not know what it is. Take four bytes in a row: three of them all zeros, one with the pattern 01000001. Are they the whole number 65? Are they the letter A and three empty characters? Are they a very small fraction? Are they part of a longer number? The bytes themselves cannot tell you. They are the same bytes in every case.

Something has to decide. In C++ that something is the type. A type is a label that tells the compiler two things about a stretch of memory:

  • How to interpret the bytes. How many bytes belong together, and what rule turns those bit patterns into a value (a whole number? a fraction? a character? yes or no?).
  • Which operations are allowed. You can divide two numbers; you cannot divide two characters. You can ask whether a yes/no value is true; you cannot ask that of a fraction without saying what you mean.

The compiler uses the type every time you touch the memory. If it knows four bytes are an int, it produces the CPU instruction for adding whole numbers. If it knows eight bytes are a double, it produces the quite different instruction for adding fractions. The bytes do not carry the type at run time. The type exists only in the compiler's head, while it is translating your program.

You can see this with one program. The same value, 65, is stored twice: once in a one-byte box labelled "character", once in a four-byte box labelled "whole number". The byte that holds 65 has the same bit pattern, 01000001, in both; the int simply has three more bytes of zeros beside it. Only the label differs, and the label decides what gets printed.

#include <print>

int main() {
    char as_character = 65;   // one byte holding the value 65
    int  as_number    = 65;   // four bytes holding the value 65

    std::println("as a char: {}", as_character);
    std::println("as an int: {}", as_number);
    return 0;
}

as a char: A
as an int: 65

Take the two new words char and int on trust for a few minutes; both get their own section below. The point is the pair of lines at the bottom: same number in, different thing out, because the type told std::println how to read the box.

First principle

Memory is bytes. Bytes have no meaning. A type is the rule the compiler uses to give a stretch of bytes a meaning and a set of allowed operations. Every variable you will ever write is "some bytes plus a type".

Analogy

Think of a variable as a labelled box on a shelf. The label is the type: "whole number, 4 bytes". The contents are the value: 65. The name written on the box is the variable name: as_number. You can replace the contents as often as you like, but you can never change the label; a box labelled "whole number" holds whole numbers for its entire life.

Where the analogy breaks: a real box can be empty. A C++ variable cannot. The bytes are always there, and they always contain some pattern, even before you put anything in. That difference causes a real bug, and it comes up in the next section.

Variables: declare, initialise, assign

A variable is a named region of memory with a type. You bring one into existence with a declaration: the type, then the name. You give it a first value with an initialisation: an = and a value on the same line. Later you can replace the value with an assignment, which is also written with =.

#include <print>

int main() {
    int apples = 5;              // declare a box called apples, put 5 in it
    std::println("apples: {}", apples);

    apples = 8;                  // replace the contents
    std::println("apples: {}", apples);

    apples = apples + 2;         // read, add 2, store back
    std::println("apples: {}", apples);
    return 0;
}

apples: 5
apples: 8
apples: 10

Read the first line of main as three steps the compiler takes: reserve four bytes somewhere in memory; remember that they are called apples and are to be read as an int; write the bit pattern for 5 into them. From then on, whenever you write apples, the compiler substitutes "the four bytes at that address, read as an int".

The line apples = apples + 2; looks like a false equation if you read = as "equals". It is not an equation. In C++, = means store: compute whatever is on the right, then put the result into the box named on the left. The right side runs first, reading 8 out of the box; the addition makes 10; then 10 is written back into the same box. The old 8 is gone.

"Read, change, store back" is so common that C++ has a shorthand for it. apples += 2; means exactly the same as apples = apples + 2;: add 2 to what is in the box and store the result in the same box. The operator is called compound assignment, and every arithmetic operator has one: apples -= 3; subtracts 3, apples *= 2; doubles, apples /= 2; halves (with integer division, which has its own section below). The book uses += freely from here on, mostly to add things up: total += x; reads "add x to total".

The {} in the text given to std::println is a placeholder: the value after the comma is printed in its place, and std::println uses that value's type to decide how to turn the bytes into characters.

Always initialise

A declaration without an = is legal. The box is reserved, but nothing is written into it. Remember the broken part of the analogy: the bytes are there anyway, holding whatever pattern the previous user of that memory left behind. Reading them gives you a nonsense value, and a different nonsense value on another run or another machine.

#include <print>

int main() {
    int count;                   // declared, but nothing was put in the box
    int doubled = count * 2;     // reads whatever bytes happened to be there
    std::println("doubled: {}", doubled);
    return 0;
}

This program compiles. With -Wall the compiler does what it can, which is to warn you:

uninit.cpp:5:19: warning: variable 'count' is uninitialized when used here [-Wuninitialized]
    5 |     int doubled = count * 2;     // reads whatever bytes happened to be there
      |                   ^~~~~
uninit.cpp:4:14: note: initialize the variable 'count' to silence this warning
    4 |     int count;                   // declared, but nothing was put in the box
      |              ^
      |               = 0
1 warning generated.

On the run that produced the text for this chapter, it printed doubled: -420151120. On your machine it will print something else. Reading an uninitialised variable is one example of undefined behaviour, which has its own section below. Be warned: the sanitizers you will meet there do not catch this one. The same program compiled with -fsanitize=address,undefined printed doubled: 0 and no message at all. That looks perfectly healthy and is not. The compiler warning is your only guard. The rule that avoids the problem is short:

Trap

Never write int x;. Always write int x = 0; (or whatever the right first value is). An uninitialised variable is not empty, it is random, and a program that reads it is broken even on the days it seems to work. The compiler's warning is your friend here: read every warning and fix it.

Try it

Save the program above as scratch/uninit.cpp. Compile it twice: once with clang++ -std=c++23 uninit.cpp -o uninit and once with -Wall -Wextra added. Only the second compile warns; the first hands you a broken program in silence, which is why the project never compiles without those two flags. Run the program a few times and watch the number. Then add = 0 to the declaration, recompile with the warnings on, and confirm that both the warning and the nonsense are gone.

int: whole numbers in four bytes

int is the type for whole numbers: counts, positions, indices. On your Mac an int is 4 bytes, which is 32 bits. The operator sizeof asks the compiler how many bytes a type takes, and you can print the answer.

Thirty-two bits give 232 patterns, a little over 4.29 billion. An int is a signed type: one of its 32 bits, the sign bit, records whether the number is negative. That spends half of the patterns on negative numbers, so the range runs from −2,147,483,648 up to 2,147,483,647: roughly plus or minus 2.1 billion. The opposite kind, an unsigned type, has no sign bit and uses every pattern for zero and the positive numbers. You meet two unsigned types later in this chapter.

#include <print>

int main() {
    int biggest  = 2147483647;
    int smallest = -2147483648;
    std::println("biggest int:  {}", biggest);
    std::println("smallest int: {}", smallest);
    std::println("sizeof(int):  {} bytes = {} bits", sizeof(int), sizeof(int) * 8);
    return 0;
}

biggest int:  2147483647
smallest int: -2147483648
sizeof(int):  4 bytes = 32 bits

Two point one billion is plenty for a Life grid: a 1000 by 1000 grid has a million cells. But think about what happens one step past the top.

Overflow

What is 2,147,483,647 plus 1? In mathematics, 2,147,483,648. In a 4-byte int there is no bit pattern for that number. The language does not say what happens. To see what your machine does, compile the program below with a sanitizer switched on. A sanitizer is extra checking code that the compiler weaves into your program when you pass a -fsanitize= flag. While the program runs, those checks watch the risky operations and print a message the moment one goes wrong. Chapter 0 mentioned sanitizers in passing; this is the first time you hear one speak. The one used here is the UndefinedBehaviorSanitizer, one of the two that tools/run.sh and the project's Debug build (take that name on trust until chapter 11) always switch on:

#include <print>

int main() {
    int biggest = 2147483647;
    int one = 1;
    int beyond = biggest + one;      // there is no int this big
    std::println("beyond: {}", beyond);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra -fsanitize=undefined overflow.cpp -o overflow
$ ./overflow

overflow.cpp:6:26: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior overflow.cpp:6:26
beyond: -2147483648

Read the first line carefully. It names the file, the line and the column, says what went wrong (signed integer overflow), and gives the exact numbers. Then the program carried on and printed −2,147,483,648: the counter went past the top and came out at the bottom, like a car's odometer going from 999999 to 000000. That wrapped value is what this CPU happened to do today. It is not what the language promised, because the language promised nothing.

Undefined behaviour

Undefined behaviour (often shortened to UB) means the C++ language gives no promise at all about what a program does from that point on. Not "the result is unspecified", but "anything may happen". The obvious wrapped number is one possibility. So is a crash. So is a wrong answer somewhere else in the program, far from the line that broke the rule. So is a program that appears to work perfectly today and fails next month after a compiler update.

You will meet three kinds of UB in Week 1: signed overflow, reading an uninitialised variable, and indexing outside a std::vector (chapter 6). You cannot test for UB after the fact, because what you observe is not reliable. The wrapped number above is what happened this time; it is not a result you may build on.

What you can do is compile with sanitizers. They insert checks at the risky operations they know about and print a message at the exact line the moment a rule is broken. The UndefinedBehaviorSanitizer catches signed overflow and division by zero. The AddressSanitizer catches most out-of-range memory access, including the vector case in chapter 6. Neither catches a read of an uninitialised variable. (The tool for that, MemorySanitizer, is not available on macOS.) For that one bug, the compiler warning from the previous section is the whole defence.

This is why tools/run.sh and the project's Debug build always pass -fsanitize=address,undefined. It is also why you develop with the sanitizers on and switch them off only to measure speed (chapter 13), and why you never leave a warning unread.

Why not just define it?

Other languages do define overflow (Python grows the number; Java wraps). C++ leaves it undefined so the compiler may assume it never happens, which lets it produce faster code for loops over indices. You are learning C++ for speed, so you inherit that bargain. The sanitizers are the safety rail that makes the bargain survivable.

Integer division and remainder

Dividing one int by another gives an int. There is no box for the fraction, so the fraction is thrown away. 7 / 2 is not 3.5. It is 3. The part that was thrown away is available from a second operator, %, read as "remainder" or "modulo": 7 % 2 is 1, because 7 is 3 twos plus 1 left over.

#include <print>

int main() {
    std::println("7 / 2 = {}", 7 / 2);
    std::println("7 % 2 = {}", 7 % 2);
    std::println("23 / 10 = {}", 23 / 10);
    std::println("23 % 10 = {}", 23 % 10);
    std::println("9 / 3 = {}, 9 % 3 = {}", 9 / 3, 9 % 3);
    std::println("(23 / 10) * 10 + 23 % 10 = {}", (23 / 10) * 10 + 23 % 10);
    return 0;
}

7 / 2 = 3
7 % 2 = 1
23 / 10 = 2
23 % 10 = 3
9 / 3 = 3, 9 % 3 = 0
(23 / 10) * 10 + 23 % 10 = 23

Together the two operators split a number: 23 / 10 tells you how many whole tens (2), 23 % 10 tells you what is left (3). The two pieces always fit back together, as the last line shows: the quotient times the divisor, plus the remainder, is the original number (2 × 10 + 3 = 23). That holds for every pair of ints, negative ones included. Keep that pair in mind; it is exactly how a position in a flat list turns back into a row and a column in chapter 7, and the remainder is also how a value that has run off one edge of a grid comes back in on the other side.

Negative numbers divide toward zero

Here is the part most people get wrong the first time. In C++, integer division rounds toward zero, not downward. So -7 / 2 is −3 (not −4), and to keep the equation above true the remainder has to be -7 % 2 == -1. The remainder takes the sign of the left operand.

#include <print>

int main() {
    std::println(" 7 / 2 = {},   7 % 2 = {}", 7 / 2, 7 % 2);
    std::println("-7 / 2 = {},  -7 % 2 = {}", -7 / 2, -7 % 2);
    std::println("-1 / 10 = {},  -1 % 10 = {}", -1 / 10, -1 % 10);
    return 0;
}

 7 / 2 = 3,   7 % 2 = 1
-7 / 2 = -3,  -7 % 2 = -1
-1 / 10 = 0,  -1 % 10 = -1
Trap

Look at the last line. If you want "the hour before midnight on a 10-hour clock", you want 9. C++ gives you -1 % 10 == -1. The remainder operator alone does not wrap negative numbers round to the top. This single fact is behind the comment "careful with negative numbers" next to wrap in phase1-terminal/01-life/src/life.cpp. Chapter 7 shows the fix; for now just remember that % of a negative number is negative or zero, never positive.

Dividing by zero

7 / 0 and 7 % 0 are undefined behaviour, the same category as overflow. The sanitizer reports them as "division by zero". Never divide by a value you have not checked.

Try it

Before you run anything, write down on paper what these eight expressions give: 17 / 5, 17 % 5, -17 / 5, -17 % 5, 5 / 17, 5 % 17, -3 % 10, 10 % 10. Then write a program that prints all eight and compare. Each one you got wrong points at a rule you have not absorbed yet; re-read the paragraph for that case.

Show the answers

3, 2, −3, −2, 0, 5, −3, 0. Division rounds toward zero; the remainder has the sign of the left operand; and when the left number is smaller than the right one, the quotient is 0 and the remainder is the whole left number. The last one, 10 % 10, is 0: landing exactly on the divisor leaves nothing over, which is why the top of a wrapping range comes back to position 0.

double and float: numbers with a decimal point

When you need fractions you use a floating-point type. The name means the decimal point is not nailed to one position: the type stores a fixed number of significant digits and, separately, where the point goes, so the same box can hold 0.000035 or 35000000.0. double is the default: 8 bytes, written with a decimal point. In Week 1 you use a double for exactly one thing, the fill probability passed to random_cells ("each cell is alive with probability 0.35").

#include <print>

int main() {
    double half = 7.0 / 2.0;
    std::println("7.0 / 2.0 = {}", half);

    double fill = 0.35;                 // probability that a cell starts alive
    std::println("fill = {}", fill);

    double sum = 0.1 + 0.2;
    std::println("0.1 + 0.2 = {}", sum);
    std::println("0.1 + 0.2 = {:.20f}", sum);
    std::println("0.3       = {:.20f}", 0.3);
    return 0;
}

7.0 / 2.0 = 3.5
fill = 0.35
0.1 + 0.2 = 0.30000000000000004
0.1 + 0.2 = 0.30000000000000004441
0.3       = 0.29999999999999998890

The first line settles something from the previous section: 7.0 / 2.0 is 3.5, because both operands are doubles and the result has room for the half. The decimal point in 7.0 is what makes it a double instead of an int.

The last three lines show the catch. A double is approximate. It stores a number as a binary fraction with 53 significant bits, and most decimal fractions cannot be written exactly in binary, just as 1/3 cannot be written exactly in decimal (0.333…). So 0.1 is stored as the nearest representable value, 0.2 likewise, their sum lands on a value just above 0.3, and the nearest representable value to 0.3 itself is just below. The formatting code {:.20f} (twenty digits after the point; the full table is at the end of the chapter) exposes the digits that the default printing politely hides.

The practical rules: use double for measurements and probabilities, never for counting; never test two doubles for exact equality (ask whether their difference is tiny instead); and do not be alarmed when the sixteenth or seventeenth significant digit is not what you typed. That is the approximation showing, not a bug in your program.

float: the same idea in four bytes

float is a floating-point number in 4 bytes instead of 8. It has about 7 significant decimal digits where double has about 16. A literal with an f on the end, 0.1f, is a float.

#include <print>

int main() {
    float  weight_f = 0.1f;            // 4 bytes
    double weight_d = 0.1;             // 8 bytes

    std::println("float:  {:.20f}", weight_f);
    std::println("double: {:.20f}", weight_d);
    std::println("sizeof(float) = {}, sizeof(double) = {}", sizeof(float), sizeof(double));
    return 0;
}

float:  0.10000000149011611938
double: 0.10000000000000000555
sizeof(float) = 4, sizeof(double) = 8

Both are "0.1", and both are wrong, but the float agrees with 0.1 for only 8 decimal places (count the zeros) and the double for 17. You pay for precision with bytes. Week 1 does not need float; you meet it now because it is the single most common type in the field you are heading for.

Inference twin

The weights of a neural network are stored as floating-point numbers, and float (called fp32 in that world, "32-bit floating point") is the default dtype (data type, the same idea as a C++ type) in PyTorch, the Python library most models are trained with. A GPT-2 weight file is mostly a long row of fp32 values. When people say a model has been "quantized to int8" or "to 4-bit", they mean the same tensor (a grid of numbers; in Week 1 terms, a flat list plus a width and a height) has been re-encoded into a different type: one byte per weight, or half a byte, plus a scale factor per block, instead of four bytes. Same meaning, fewer bytes, less precision, exactly the float-versus-double trade above pushed further. Everything in this chapter about "bytes plus a type" is the vocabulary of quantization; in week 9 you will write the int8 and Q4 encodings yourself.

bool: yes or no

bool is the type with exactly two values, true and false. It takes one byte (a single bit would do, but memory is addressed by the byte, so one byte is the smallest box). You will mostly meet bools as the result of a comparison: == (equal), != (not equal), <, >, <=, >=. Comparisons get their proper treatment in chapter 3; take them on trust until then. For now all you need is this: a comparison is an expression that produces a bool, and you can store that bool in a variable like any other value.

#include <print>

int main() {
    bool alive = true;
    bool dead = false;
    std::println("alive = {}, dead = {}", alive, dead);

    int neighbours = 3;
    bool is_three = neighbours == 3;    // == asks "are these equal?"
    bool is_two   = neighbours == 2;
    bool at_least_two = neighbours >= 2;
    std::println("is_three = {}, is_two = {}, at_least_two = {}", is_three, is_two, at_least_two);

    std::println("sizeof(bool) = {}", sizeof(bool));
    return 0;
}

alive = true, dead = false
is_three = true, is_two = false, at_least_two = true
sizeof(bool) = 1

Notice that = and == are different operators. One = stores. Two == compare. The line bool is_three = neighbours == 3; uses both: compare first (giving true), then store the result. In chapter 3 you will put comparisons directly into if to make the program choose a path; the rules of Life ("a dead cell with exactly 3 live neighbours becomes alive") are comparisons like these.

Trap

Writing = where you meant == is the most common typo in C++, and the compiler accepts it, because neighbours = 3 is a valid expression: it stores 3 and then has the value 3, which counts as true. -Wall warns about one form only, a lone = inside the condition of an if (chapter 3). Everywhere else you are on your own. When a comparison "does not work", count the equals signs first.

char: one byte holding a character code

A char is a 1-byte box whose contents are interpreted as a character. "Interpreted" is doing real work in that sentence. The byte holds a number from the ASCII table, a 1960s agreement that assigns a code to every English letter, digit and punctuation mark: 'A' is 65, 'a' is 97, '0' is 48, '#' is 35. A character written between single quotes, '#', is a character literal and its value is simply that code.

Because a char is really a small number, you can ask to see the number. The way to do that is static_cast<int>(c): "give me this value, re-labelled as an int". The full story of static_cast comes a few sections down; here it just reveals the code.

#include <print>

int main() {
    char alive = '#';
    char dead = '.';
    std::println("alive: {}  dead: {}", alive, dead);

    std::println("the code of '#' is {}", static_cast<int>(alive));
    std::println("the code of '.' is {}", static_cast<int>(dead));
    std::println("the code of 'A' is {}", static_cast<int>('A'));
    std::println("the code of '\\n' is {}", static_cast<int>('\n'));

    char from_code = 72;                // 72 is the code of 'H'
    std::println("code 72 is the character {}", from_code);
    std::println("sizeof(char) = {}", sizeof(char));
    return 0;
}

alive: #  dead: .
the code of '#' is 35
the code of '.' is 46
the code of 'A' is 65
the code of '\n' is 10
code 72 is the character H
sizeof(char) = 1

Two things to notice. First, '\n' is a character too: the newline, code 10. The backslash is an escape that lets you write a character you cannot type directly; '\t' is a tab and '\\' is a single backslash. In the text of the fourth println, '\\n' is used so that the output shows a backslash and an n rather than breaking the line. Second, render in the Week 1 contract builds its output from exactly three characters: '#', '.' and '\n' after every row. You now know what all three are.

Trap

A char is one byte, and one byte holds one ASCII code. The Danish letters æ, ø and å are not in ASCII. Your Mac stores source files as UTF-8, in which each of those letters takes two bytes, so none of them fits in a char. The compiler refuses:

#include <print>

int main() {
    char letter = 'æ';             // the Danish ae, two bytes in UTF-8
    std::println("{}", letter);
    return 0;
}

danish_char.cpp:4:19: error: character too large for enclosing character literal type
    4 |     char letter = 'æ';             // the Danish ae, two bytes in UTF-8
      |                   ^
1 error generated.

Inside double quotes the same letters are fine: std::println("blåbærgrød"); prints blåbærgrød, because a string literal is a row of bytes and the terminal reassembles the pairs. For Week 1, keep every char inside ASCII; '#', '.' and '\n' all qualify. Text beyond ASCII is a week 29 topic (the optional tokeniser).

std::size_t: the type for sizes and counts

How many cells does a grid have? How long is a list? Those numbers are never negative, and on a machine with lots of memory they can be bigger than 2.1 billion. The standard library has a type made for exactly this job: std::size_t. It is unsigned, meaning it has no sign bit and spends all its patterns on non-negative numbers, and on your Mac it is 8 bytes, so it reaches up to about 18 billion billion. It comes from the header <cstddef>, although nearly every standard header brings it along anyway.

Every size in the standard library is a std::size_t. sizeof gives one. In chapter 6, vector.size() gives one, and the index you write between square brackets is one. This is why the type matters this week even though you only have a few variables so far: you will be mixing your own int coordinates with the library's std::size_t sizes, and the mixing has rules.

#include <cstddef>
#include <print>

int main() {
    std::size_t width = 80;
    std::size_t height = 24;
    std::size_t cell_count = width * height;
    std::println("cells: {}", cell_count);
    std::println("sizeof(std::size_t) = {} bytes", sizeof(std::size_t));

    std::size_t zero = 0;
    std::size_t wrapped = zero - 1;     // cannot be -1: there is no sign bit
    std::println("0 - 1 as std::size_t = {}", wrapped);
    return 0;
}

cells: 1920
sizeof(std::size_t) = 8 bytes
0 - 1 as std::size_t = 18446744073709551615
Trap

Zero minus one, in a type that cannot hold negative numbers, is the largest value the type has: 18,446,744,073,709,551,615. Unlike signed overflow this is not undefined behaviour; unsigned arithmetic is defined to wrap, so the sanitizer stays silent. It is still almost certainly not what you wanted. The classic form is "the last index is size - 1" when the size is zero, or counting down with an unsigned variable until it is "below zero", which never happens. When you need to subtract, or to represent "one step to the left of position 0", use a signed type. That is why the Week 1 contract passes x, y, width and height as int: the neighbour of column 0 is column −1 before wrapping, and int can say −1.

std::uint8_t: exactly one byte

The int type is "at least 16 bits, 32 on every machine you will touch", and std::size_t is "whatever fits a size". Sometimes you want to say exactly how many bytes. The header <cstdint> provides types with the size in the name: std::uint8_t is an unsigned whole number in exactly 8 bits, so its values run from 0 to 255. (There are also std::int32_t, std::uint64_t and so on; the pattern is int or uint, a bit count, _t.)

This is the cell type of Week 1. Look at the top of phase1-terminal/01-life/src/life.hpp: using Cells = std::vector<std::uint8_t>;. A Life cell is either 1 (alive) or 0 (dead); it would be silly to spend 4 bytes on it when 1 will do, and a 1000 by 1000 grid at one byte per cell is one megabyte, which fits comfortably in the CPU's cache, the small, very fast memory that sits next to the processor (you measure what that is worth in chapter 13 and study it in week 6). (std::vector and using are chapters 6 and 7; for now just see the element type.)

#include <cstdint>
#include <print>

int main() {
    std::uint8_t alive = 1;
    std::uint8_t dead = 0;
    std::println("alive = {}, dead = {}", alive, dead);
    std::println("sizeof(std::uint8_t) = {}", sizeof(std::uint8_t));

    std::uint8_t largest = 255;
    std::println("largest = {}", largest);

    std::uint8_t code = 35;             // 35 is the code of '#' ...
    std::println("as uint8_t: {}", code);          // ... but this prints 35
    std::println("as char:    {}", static_cast<char>(code));

    top = top + 1;                      // 256 has no pattern in one byte
    std::println("255 + 1 as uint8_t = {}", top);
    return 0;

A byte that prints as a number

char and std::uint8_t are both one byte, and under the hood std::uint8_t is usually an alias of unsigned char. std::println nevertheless prints a std::uint8_t as a number and a char as a character, which is what you want: a cell with value 1 should show as 1, not as the invisible control character with code 1. When you write render you will turn each cell into '#' or '.' yourself; you never print a cell directly.

Small boxes overflow soon

The last line shows it: 255 is the top of a std::uint8_t, and adding one wraps to 0. Nothing complained. The compiler gave no warning with -Wall -Wextra, and the sanitizer stayed silent, because unsigned wrap-around is defined behaviour, by the same rule as std::size_t. Choose the type to fit the largest value it must ever hold, not the typical one. A Life cell is 0 or 1, so one byte is safe; a neighbour count that could reach 8 would also fit, but the contract uses int for counts, which keeps every arithmetic step in the chapter's "big, signed" type.

Conversions between types

You will constantly have a value of one type and need it as another: an int coordinate where a std::size_t index is wanted, two int counts whose ratio should be a double. C++ converts between the built-in number types for you in many places, but the conversions are not all equal. Some lose nothing, some lose information quietly.

Widening conversions are safe: int to double always works, because every int fits exactly in a double. The compiler does these silently. Narrowing conversions can lose information: double to int drops everything after the decimal point (it truncates, toward zero, like integer division), and a big int into a std::uint8_t keeps only the lowest byte. When you use plain =, the compiler does these silently as well; even -Wall -Wextra says nothing when a double is stored into an int. That silence is the problem.

The explicit way to convert is static_cast<T>(value): "convert value to the type T". It does the same conversion the compiler would have done, but it says so in the source. Two advantages: a reader (including you in six months) sees that a conversion happens there on purpose, and you can search a whole project for static_cast to find every place where information might be lost. The project's stubs already use it: look at random_cells in life.cpp, which casts width and height to std::size_t before multiplying them.

#include <cstdint>
#include <print>

int main() {
    int whole = 7;
    double widened = whole;              // int -> double: nothing lost
    std::println("widened = {}", widened);

    double fraction = 3.99;
    int silent = fraction;               // double -> int: cuts off the decimals, no warning
    int narrowed = static_cast<int>(fraction);     // the same cut, but now the source says so
    std::println("silent = {}, narrowed = {}", silent, narrowed);

    double negative = -3.99;
    std::println("static_cast<int>(-3.99) = {}", static_cast<int>(negative));

    std::println("static_cast<std::uint8_t>(300) = {}", static_cast<std::uint8_t>(300));

    int alive_cells = 350;
    int total_cells = 1000;
    std::println("integer ratio: {}", alive_cells / total_cells);
    std::println("double ratio:  {}", static_cast<double>(alive_cells) / total_cells);
    return 0;
}

widened = 7
silent = 3, narrowed = 3
static_cast<int>(-3.99) = -3
static_cast<std::uint8_t>(300) = 44
integer ratio: 0
double ratio:  0.35

Line by line. silent and narrowed hold the same 3; the only difference is that one line admits a conversion happened and the other hides it. 3.99 became 3, not 4: truncation is not rounding. Then 300 into one byte gives 44, because 300 = 256 + 44: the byte keeps the part below 256 and the rest is dropped. (Wrapping at 256 is the same rule you saw with 255 + 1 above.) The last two lines are the pattern to remember. 350 / 1000 with two ints is integer division: 0. Convert one operand to double first and the other is widened to match, so the division happens in double and gives 0.35.

Signed meets unsigned

The most dangerous automatic conversion is the one between signed and unsigned integers, and you will meet it the moment an int coordinate stands next to a std::size_t size. When the two are compared, the int is converted to unsigned first. A −1 becomes 18,446,744,073,709,551,615, and the comparison gives the wrong answer. The compiler knows this is a trap and, with -Wall -Wextra, warns you. The following complete program compiles, but with a warning:

#include <cstddef>
#include <print>

int main() {
    int offset = -1;
    std::size_t count = 3;
    bool smaller = offset < count;      // mixing signed and unsigned
    std::println("is -1 smaller than 3? {}", smaller);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra sign_compare.cpp -o sign_compare

    7 |     bool smaller = offset < count;      // mixing signed and unsigned
      |                    ~~~~~~ ^ ~~~~~
1 warning generated.

$ ./sign_compare
is -1 smaller than 3? false

Minus one is not smaller than three, says the program, because by the time the comparison ran the minus one had become an enormous positive number. The warning text is worth memorising: "comparison of integers of different signs". When you see it, decide which type the comparison should happen in and static_cast the other operand to match. Here the values are small and might be negative, so compare as int:

#include <cstddef>
#include <print>

int main() {
    int offset = -1;
    std::size_t count = 3;
    bool smaller = offset < static_cast<int>(count);   // compare two ints
    std::println("is -1 smaller than 3? {}", smaller);
    return 0;
}

is -1 smaller than 3? true

The other direction comes up just as often: you hold an int coordinate and the library wants a std::size_t index. Then you first make sure the int is not negative and write static_cast<std::size_t>(x). That is exactly what the random_cells stub in life.cpp does with width and height before multiplying them. Chapter 6 turns this into a habit.

First principle

A warning is the compiler telling you it did something you probably did not mean. The project's build turns on -Wall -Wextra -Wpedantic, and the book's own checker refuses any example that warns. Hold yourself to the same standard: a program that compiles with warnings is not finished.

const: a promise not to change

Many values never change after they are set: the width of the grid, the number of warm-up steps, the fill probability. Putting const in front of the declaration tells the compiler "this box is written once, at initialisation, and never again". The compiler then refuses to compile any later assignment. Here is what breaking the promise looks like:

#include <print>

int main() {
    const int width = 10;
    width = 20;                          // breaking the promise
    std::println("width = {}", width);
    return 0;
}

const_error.cpp:5:11: error: cannot assign to variable 'width' with const-qualified type 'const int'
    5 |     width = 20;                          // breaking the promise
      |     ~~~~~ ^
const_error.cpp:4:15: note: variable 'width' declared const here
    4 |     const int width = 10;
      |     ~~~~~~~~~~^~~~~~~~~~
1 error generated.

This is an error you want. The compiler found, before the program ever ran, a line that contradicts your stated intent; compare the uninitialised-variable example, where the mistake only showed up as a random number at run time. Everything you can move from "wrong at run time" to "refused at compile time" is a win, and const is the cheapest such move. So: make everything const unless it needs to change, and let the compiler tell you when you were wrong. The benchmark file phase1-terminal/01-life/bench/bench_life.cpp follows this rule; count how many of its variables are const.

#include <print>

int main() {
    const int width = 10;
    const int height = 4;
    const int cell_count = width * height;
    int alive = 0;                       // this one will change, so no const

    std::println("{} x {} grid has {} cells", width, height, cell_count);
    alive = alive + 3;
    std::println("alive now: {}", alive);
    return 0;
}

alive now: 3

Notice that a const can be computed from other values (width * height); "const" means "not changed after this line", not "known before the program runs". In chapter 5 const gets a second, bigger job: marking which function parameters a function promises not to modify. The const Cells& in the step declaration in life.hpp is that promise.

auto: let the compiler write the type

Every initialisation has a value on the right, and the value has a type. If you write auto instead of a type name, the compiler gives the variable the type of the initialiser. auto count = 10; is exactly int count = 10;, because 10 is an int.

#include <print>

int main() {
    auto count = 10;                     // int, because 10 is an int literal
    auto ratio = 0.35;                   // double, because 0.35 is a double literal
    auto alive = true;                   // bool
    auto mark = '#';                     // char
    auto size = sizeof(int);             // std::size_t, because sizeof gives one

    std::println("{} {} {} {} {}", count, ratio, alive, mark, size);

    auto total = 0;                      // int, maybe not what you meant...
    total = total + 2.5;                 // ...the .5 is lost on the way back into an int
    std::println("total = {}", total);
    return 0;
}

10 0.35 true # 4
total = 2

When auto helps: the type is obvious from the right side and tedious to spell, such as auto size = sizeof(int); or, from chapter 13 on, auto start = clock::now();. When auto hides: the type is not obvious and it matters. auto total = 0; makes an int; adding 2.5 produces a double, which is narrowed back into the int box, dropping the half. double total = 0; would have made the intent visible and the answer 2.5. A fair rule for Week 1: write the type for numbers you declare yourself; use auto when the right side already names the type or is a library call.

Literals and names

A literal is a value written directly in the source. Its spelling decides its type, which is why the previous sections kept pointing at decimal points and quote marks:

#include <print>

int main() {
    std::println("{}", 3);               // int literal
    std::println("{}", 3.0);             // double literal
    std::println("{}", 3.0f);            // float literal
    std::println("{}", 'c');             // char literal: single quotes
    std::println("{}", "text");          // string literal: double quotes
    std::println("{}", true);            // bool literal

Naming

A name can use letters, digits and underscores, cannot start with a digit, and is case-sensitive (width and Width are different variables). The conventions in this project, matching life.hpp:

  • snake_case: lower-case words joined by underscores. cell_count, count_neighbours, random_cells.
  • Descriptive. alive_cells, not ac; neighbours, not n. The name should say what the box holds without a comment.
  • No single letters, with two exceptions that are so universal they count as words: loop counters (i, j, chapter 3) and coordinates (x, y). The contract uses x and y for column and row, and so should you.
  • British spelling, because the contract says count_neighbours and a test that calls count_neighbors will not compile.
  • Not a keyword. Words the language owns, such as int, return, const, auto, true and false, cannot name a variable; int int = 3; is refused. There are a little over 90 of them, and your editor colours them differently, so you will rarely collide with one by accident.

Formatting output

You have seen {} print whatever it is given in a default style. Between the braces you can put a colon and a format specification that controls width, alignment, padding and the number of decimals. The benchmark prints ms per step: {:.3f}, and your Life main will want to line up a status line, so here are the codes you need:

#include <print>

int main() {
    double ms = 3.14159;
    std::println("[{:.2f}]", ms);        // 2 digits after the point
    std::println("[{:.0f}]", ms);        // no decimals (rounded)
    std::println("[{:>5}]", 42);         // right-align in a field 5 wide
    std::println("[{:<5}]", 42);         // left-align in a field 5 wide
    std::println("[{:^5}]", 42);         // centre in a field 5 wide
    std::println("[{:03}]", 7);          // pad with zeros to width 3
    std::println("[{:>8.3f}]", ms);      // width 8, 3 decimals
    std::println("[{:+}]", 5);           // always show the sign
    std::println("[{:>+8.1f}]", ms);     // align, sign, width, precision, type
    std::println("[{:.0f}] [{:.0f}]", 2.5, 3.5);   // rounding a tie
    std::println("[{}] [{}]", 1000000, 2.5e-5);
    return 0;
}

The order inside the braces is fixed: first the alignment (<, > or ^), then a sign flag such as +, then a 0 if you want zero padding, then the width, then a dot and the precision, then the type letter (f for fixed-point). You may leave any part out, but you may not reorder the parts; {:>+8.1f} in the program uses five of them in that order. The square brackets in the program are ordinary text, there only to make the padding spaces visible. Rounding with .0f is honest rounding, with one wrinkle shown on the [2] [4] line: a value exactly halfway between two whole numbers goes to the even one, so 2.5 prints as 2 and 3.5 as 4. One more detail from the last line: a very small or very large double printed with plain {} may come out in scientific notation (2.5e-05 means 2.5 × 10−5). If you want a fixed number of decimals regardless, say so with f.

Check yourself

What does std::println("{}", 7 / 2); print, and why? What would you change to get 3.5?

Answer

It prints 3. Both operands are int literals, so the division is integer division and the fraction is thrown away. Make either operand a double: 7.0 / 2, 7 / 2.0, or static_cast<double>(7) / 2.

What does -7 % 2 give, and what does -1 % 10 give? Why does this matter for a wrap-around grid?

Answer

-7 % 2 is -1 and -1 % 10 is -1. Integer division rounds toward zero and the remainder takes the sign of the left operand. On a wrapping grid the cell to the left of column 0 should be the last column (9 on a width-10 grid), but % alone gives −1, which is not a valid position. Chapter 7 shows how to fix it.

What does sizeof(int) print on your Mac? And sizeof(std::size_t), sizeof(char), sizeof(std::uint8_t)?

Answer

4, 8, 1 and 1. sizeof gives the number of bytes a type occupies, as a std::size_t.

Why does the standard library use std::size_t for sizes rather than int? What is the one thing you must never do with a std::size_t?

Answer

A size is never negative and may exceed 2.1 billion, so an unsigned 8-byte type fits the job and wastes no patterns on negatives. The thing to never do is subtract below zero: 0 - 1 as a std::size_t is 18,446,744,073,709,551,615, silently, with no sanitizer message. Use int for anything that might need to be −1.

What is undefined behaviour? Name two examples from this chapter and say how you would catch them.

Answer

Undefined behaviour is any situation where the C++ language makes no promise about what the program does: anything may happen, including seeming to work. Examples from this chapter: signed integer overflow (2147483647 + 1) and reading an uninitialised variable (int x; ... x * 2). Division by zero is a third. Overflow and division by zero are caught by compiling with -fsanitize=address,undefined (what tools/run.sh and the Debug build do), which prints the file and line the moment the rule is broken. The uninitialised read is not caught by those sanitizers; it is caught only by the compiler's -Wuninitialized warning, so you read every warning.

Is 0.1 + 0.2 == 0.3 true in C++? What does this tell you about using double?

Answer

No. 0.1 + 0.2 is stored as 0.30000000000000004441… and 0.3 as 0.29999999999999998890…; they are different bit patterns. A double is an approximation with about 16 significant digits. Use it for measurements and probabilities, never for exact counting, and never compare two doubles with ==.

Both char and std::uint8_t are one byte. What is the difference when you print one holding the value 35?

Answer

The bytes are identical; the type differs. std::println prints a char as the character with that code, #, and a std::uint8_t as the number 35. This is the whole chapter in one example: the type, not the byte, decides the meaning.

What does the compiler say about const int w = 10; w = 20;, and why is that message good news?

Answer

It refuses to compile: "cannot assign to variable 'w' with const-qualified type 'const int'". It is good news because a contradiction in your intent was caught before the program ran, instead of becoming a silent wrong value at run time. Make things const by default so the compiler can catch more of these.
