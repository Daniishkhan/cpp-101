Chapter 08

Strings, program arguments, randomness

At the end of this chapter you will be able to build a piece of text one character at a time, read the options a user types after your program's name (--width 80 --seed 7), turn that text into numbers, and ask the machine for a stream of "random" numbers that comes out identical every time you ask with the same seed. Those are the three things the Game of Life still needs that no earlier chapter gave you.

In this chapter

  • Reading a string one character at a time, and why 'a' and "a" are different things.
  • Building a whole picture into one string and printing it once.
  • Program arguments: what the operating system hands to main, and how to walk through it.

Three things Life still cannot do

Look at the contract in phase1-terminal/01-life/src/life.hpp. By now you can read most of it. index_of and wrap take ints and return an int. count_neighbours and step take a const Cells&, which chapter 5 taught you to read as "look, don't copy, don't change". Three pieces are still foreign:

  • std::string render(const Cells& cells, int width, int height); returns a std::string. You have not met that type properly. The comment says the string holds one row per line, '#' for alive and '.' for dead.
  • Cells random_cells(int width, int height, unsigned int seed, double fill); wants a seed and a fill, and promises that "the same seed must always give the same grid". That is randomness, but a controlled kind.
  • The stub main.cpp says the finished program is run as ./build/life --width 80 --height 24 --seed 7. Nothing you have written so far can see what the user typed after the program's name.

This chapter closes those three gaps: strings first, then program arguments, then randomness. Each is taught on a problem one step away from Life, so that the Life code stays yours to write.

std::string: a vector of characters with extras

You know std::vector<int> from chapter 6: a row of boxes in memory, with a .size(), an index operator [], and push_back to grow it. Nothing stops you writing std::vector<char>: the same row of boxes, each one byte. A string is text, and text is a row of characters. So a type for text could simply be a vector of char. The standard library gives you something very close to that, called std::string. On top of the vector behaviour it adds the conveniences that text needs all the time. You can write one in double quotes. You can append with +=, join two with +, and compare two with ==. And std::println prints one with a plain {}.

Here is the smallest program that does something with one. You need #include <string> the same way you need #include <vector> for vectors.

#include <print>
#include <string>

int main() {
    std::string greeting = "Hello";
    std::println("{}", greeting);
    std::println("size: {}", greeting.size());

    greeting += ", world";          // append more text to the end
    std::println("{}", greeting);
    std::println("size: {}", greeting.size());

    greeting += '!';                // append ONE character
    std::println("{}", greeting);
    std::println("size: {}", greeting.size());

    std::string empty;              // no characters at all
    std::println("empty has size {}", empty.size());
    return 0;
}

Hello
size: 5
Hello, world
size: 12
Hello, world!
size: 13
empty has size 0

Read the sizes. "Hello" is 5 characters. After += ", world" it is 12: seven characters were added. After += '!' it is 13. The += from chapter 2 ("add this to what is there") means for a string "put these characters after what is there", and it works both with text in double quotes and with a single character in single quotes. A string declared with no value, std::string empty;, has zero characters. That is unlike int x;, which chapter 2 warned you holds whatever bytes happened to be there (reading it is undefined behaviour): a string is always in a sensible state.

.size() is the same as for a vector: the number of elements, here characters, as a std::size_t. Behind the scenes a std::string really is a block of bytes in memory plus a count, exactly like a std::vector<char>. When you append and the block is full, the string finds a bigger block and moves the bytes across, just as push_back does.

Analogy

A string is a line of letter tiles on a rack, like in a word game. You can count the tiles, look at the tile in position 3, and push more tiles on at the right-hand end. Two racks spell the same word if they have the same tiles in the same order.

Where it breaks: a rack has a fixed number of slots. A std::string grows as far as memory allows; a million characters is nothing to it (chapter 5 made one). And tiles are letters, while a string's elements are char values: any byte, including a newline '\n', a space, or the digit '7', which is a character and not the number seven.

Joining and comparing

Where += changes a string in place, + makes a brand new string out of two pieces and leaves both pieces alone. And == asks "same characters in the same order?", which is what you mean by "same text". It is case-sensitive: an upper-case L is a different byte from a lower-case l.

#include <print>
#include <string>

int main() {
    std::string first = "Game";
    std::string second = "Life";
    std::string title = first + " of " + second;   // + makes a NEW string
    std::println("{}", title);
    std::println("first is still: {}", first);

    std::string a = "life";
    std::string b = "life";
    std::string c = "Life";
    std::println("a == b: {}", a == b);
    std::println("a == c: {}", a == c);
    std::println("a != c: {}", a != c);
    return 0;
}

Game of Life
first is still: Game
a == b: true
a == c: false
a != c: true

Notice that a == b is true even though a and b are two separate variables, two separate blocks of bytes. The comparison looks at the contents, not at where they live. This will matter in a moment, when you compare what the user typed against "--width".

A number is not text

The characters '4' and '2' next to each other in a string are two bytes with the codes for those digits. The int 42 is four bytes holding the binary pattern for forty-two. They look alike on your screen and have nothing to do with each other in memory. The compiler will not quietly turn one into the other:

#include <print>
#include <string>

int main() {
    std::string s = 42;     // a number is not text
    std::println("{}", s);
    return 0;
}

      |                 ^   ~~
1 error generated.

(Clang follows that error with several note: lines listing every way a string can be made, none of which take an int. You can ignore them; the first line is the message.) "No viable conversion" means: I know how to make a string from text in quotes, from another string, and from a few other things, but not from an int. When you want the digits of a number as text, you must ask for the conversion by name. The function is std::to_string:

#include <print>
#include <string>

int main() {
    int width = 80;
    int height = 24;
    std::string label = "grid: " + std::to_string(width) + "x" + std::to_string(height);
    std::println("{}", label);
    std::println("label has {} characters", label.size());

    double fill = 0.35;
    std::string f = std::to_string(fill);
    std::println("to_string(0.35) gives \"{}\"", f);
    return 0;
}

grid: 80x24
label has 11 characters
to_string(0.35) gives "0.350000"

std::to_string(80) produces the two-character string "80", and + then joins the pieces. For a double it always writes six digits after the point, which is why you see 0.350000. To merely print a number, std::println("{}", width) is simpler; std::to_string is for when the digits must end up inside a string.

Trap

"Score: " + 42 compiles, and it is wrong. The left side is not yet a std::string; it is the raw quoted text, which C++ inherited from the C language, and adding an int to raw quoted text means "start 42 characters further along", which here is far past the end of the seven characters you wrote. Clang does warn you. This is the whole program and the exact message it produces with -Wall -Wextra:

#include <print>
#include <string>

int main() {
    std::string s = "Score: " + 42;     // compiles, with a warning; does NOT make "Score: 42"
    std::println("{}", s);
    return 0;
}

plus_int.cpp:5:31: warning: adding 'int' to a string does not append to the string [-Wstring-plus-int]
    5 |     std::string s = "Score: " + 42;     // compiles, with a warning; does NOT make "Score: 42"
      |                     ~~~~~~~~~~^~~~
1 warning generated.

(The program is kept out of the book's automatic checks because it is not warning-free; do not run it. Reading 42 bytes past the end of your seven characters is undefined behaviour, the same category as chapter 2's overflow.) Treat that warning as an error. The fix is always std::to_string(42), or make the left side a std::string first. Once either side of + is a std::string, + means "join".

First principle

A std::string is a count plus a block of bytes, one byte per character, exactly like a std::vector<char>. Everything it does (append, index, compare, measure) is a loop over those bytes that somebody has already written for you. Nothing in it understands words or meaning; "42" is just the bytes 52 and 50 sitting next to each other.

Reading a string one character at a time

Because a string is a row of boxes, you reach any one box with [] and a position counted from zero, and you can walk the whole row with a range-for, exactly as you did with vectors in chapter 6. Each element is a char.

#include <print>
#include <string>

int main() {
    std::string row = "#..#.#";

    // Read one character at a time by position.
    for (std::size_t i = 0; i < row.size(); ++i) {
        std::println("position {}: '{}'", i, row[i]);
    }

    // Or let the loop hand you each character in turn.
    int hashes = 0;
    for (char ch : row) {
        if (ch == '#') {
            hashes += 1;
        }
    }
    std::println("{} of {} characters are '#'", hashes, row.size());
    return 0;
}

position 0: '#'
position 1: '.'
position 2: '.'
position 3: '#'
position 4: '.'
position 5: '#'
3 of 6 characters are '#'

Both loops are the vector loops from chapter 6 with the word string in place of vector. The index loop uses std::size_t because that is what .size() returns. The comparison ch == '#' compares two char values, two single bytes. The same rule from vectors applies to []: asking for row[6] on a six-character string reads past the end, and nothing stops you. Keep the index below .size().

'a' is a char, "a" is a string

Single quotes and double quotes mean different things, and this is a mistake you will make at least once, so let the compiler show you the message now. 'a' is a character literal: a single char, one byte. "a" is a string literal: a piece of text that happens to be one character long, plus an invisible terminator, a byte with the value 0 that the compiler adds after the last character to mark where the text ends. (That is how quoted text, which carries no count with it, knows its own length: something walks the bytes until it meets the 0. A std::string stores a count instead and does not need the trick.) They are not interchangeable:

#include <string>

int main() {
    char c = "a";           // "a" is a string, not a single character
    std::string s = c;
    return 0;
}

char_vs_string.cpp:4:10: error: cannot initialize a variable of type 'char' with an lvalue of type 'const char[2]'
    4 |     char c = "a";           // "a" is a string, not a single character
      |          ^   ~~~
char_vs_string.cpp:5:17: error: no viable conversion from 'char' to 'std::string' (aka 'basic_string<char>')
    5 |     std::string s = c;
      |                 ^   ~
2 errors generated.

The first message names the type of "a": const char[2], an array of two characters, the a and the terminator. (The word lvalue in front of it is compiler jargon for "a thing that has a place in memory"; you can ignore it this week.) You cannot put two bytes into a one-byte box. The second message is the mirror image: you cannot initialise a string from a single char either, though you can append one with +=, as greeting += '!' showed.

The rules you need: 'x' with single quotes is a char. "x" with double quotes is text. A char goes into s += ch or s[i] or a comparison with another char. Text goes into a std::string.

A char is a small number

Chapter 2 showed that a char is a one-byte ASCII code ('#' is 35, '.' is 46, 'A' is 65); a string is a row of those bytes, so ch == '#' is an ordinary integer comparison, and static_cast<int>(ch) shows the number behind any character.

Trap

Because a char is a number, this compiles without a word of complaint:

#include <print>
#include <string>

int main() {
    std::string s = "abc";
    s = 65;                 // compiles! but means: the single character with code 65
    std::println("{}", s);
    return 0;
}

A

Assigning an int to an existing string is allowed, because assigning a char is allowed and 65 fits in a char. The string becomes the one-character text "A", not "65". If you meant the digits, you wanted std::to_string(65). If you ever see a single strange letter where a number should be, this is why.

Building a picture row by row

Now the problem that render solves, on a different picture. You want a 4-wide, 3-high checkerboard as text: '#' where x + y is even, '.' where it is odd, and a line break after each row. The shape of the solution is the nested loop from chapter 3 (rows outside, columns inside) with one new habit: instead of printing each character as you decide it, you append it to a string, and you print the string once at the very end.

#include <print>
#include <string>

int main() {
    const int width = 4;
    const int height = 3;

    std::string frame;                       // starts empty
    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            if ((x + y) % 2 == 0) {
                frame += '#';
            } else {
                frame += '.';
            }
        }
        frame += '\n';                       // end of this row
    }

    std::print("{}", frame);                 // ONE print for the whole picture
    std::println("the frame holds {} characters", frame.size());
    return 0;
}

#.#.
.#.#
#.#.
the frame holds 15 characters

Walk through the size. Three rows of four characters is 12. Each row ends with a '\n', the newline character, which is a char like any other (its code is 10) and takes one byte; three of them make 15. When the terminal receives a byte 10 it moves to the start of the next line, which is how one flat string becomes three visible rows. Note that the last row also ends in '\n', so the string is printed with std::print, not std::println: the line break is already inside the text, and println would add a second, empty line.

Here is the same idea as a function, which is the form you will actually want. It takes the dimensions and returns the text; the caller decides what to do with it.

#include <print>
#include <string>

// The picture as text: '#' where x + y is even, '.' elsewhere,
// and a '\n' after every row.
std::string checkerboard(int width, int height) {
    std::string out;
    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            if ((x + y) % 2 == 0) {
                out += '#';
            } else {
                out += '.';
            }
        }
        out += '\n';
    }
    return out;
}

int main() {
    std::print("{}", checkerboard(4, 3));
    std::println("---");
    std::print("{}", checkerboard(8, 2));
    return 0;
}

#.#.
.#.#

---
#.#.#.#.
.#.#.#.#

Returning a string from a function is fine and cheap in modern C++: the characters are not copied twice, the string that out built simply becomes the caller's. (The mechanism behind that, "move", is a week 4 topic. For now: return strings and vectors from functions freely.)

Why build the whole picture before printing any of it? Two reasons. First, a function that returns text can be tested. The test for render in tests/life_test.cpp is CHECK(render(g, 3, 2) == "#..\n..#\n");, which is only possible because render hands back a string instead of printing; printed output cannot be compared with ==. Second, the terminal draws bytes as they arrive. If you print an 80×24 Life grid as 1,920 separate one-character prints (80 × 24 = 1,920), the terminal may show a half-drawn frame between any two of them, and when you redraw thirty times a second that is visible as flicker. One string, handed over in a single print, arrives as one block. Chapter 9 builds on exactly this.

Not render, but its shape

Your render in life.cpp is not the checkerboard. It takes a const Cells& and decides '#' or '.' from the value stored at each cell, using the flat index from chapter 7 to find it. But the skeleton is this one: an empty string, rows outside, columns inside, one += per cell, one += '\n' per row, return. Chapter 14 reminds you of this when you reach milestone 2.

Program arguments: what the OS hands to main

Every program you have written so far started with int main(), empty brackets, and ignored the outside world. But when you type ./life --width 80 --height 24 --seed 7 in the terminal, the shell splits that line on spaces into seven words (the program name counts), starts your program, and hands it the list. C++ lets main receive it by declaring two parameters:

int main(int argc, char* argv[])

argc is the argument count: how many words there are, as an int. argv is the argument vector: the words themselves, numbered from 0, so argv[0] is the first word and argv[argc - 1] is the last. You could name them anything, but every C and C++ programmer recognises these two, so keep them.

The type char* argv[] contains a *, which you have not met. It is a pointer, and pointers are the subject of week 7. For this week take argv[i] on trust as "a C-style text": a row of bytes that ends at a terminator byte 0, the same raw quoted-text form you glimpsed in the "Score: " + 42 trap above, with no count and no .size() of its own. Convert it to a std::string the moment you touch it:

std::string arg = argv[i];   // from C-style text to a real std::string, immediately

After that line, arg is an ordinary string with .size() and == and everything else from this chapter, and you never have to think about what argv[i] really is. Here is a program that prints every argument it is given. It cannot be a "run" block in this book because its output depends on what you type, so the block below is followed by a real terminal session instead.

#include <print>
#include <string>

int main(int argc, char* argv[]) {
    std::println("argc = {}", argc);
    for (int i = 0; i < argc; ++i) {
        std::string arg = argv[i];     // convert the C-style text to a std::string at once
        std::println("argv[{}] = \"{}\"  ({} characters)", i, arg, arg.size());
    }
    return 0;
}

Three things to take from the session. First, argv[0] is the name the program was started with, so the user's own words start at argv[1], and a program run with no arguments still has argc == 1. Second, every argument is text: "80" is the two characters 8 and 0, not the number eighty, and converting it is your job (the next section). Third, the splitting is done by the shell, not your program: shell quotes keep "two words" as one argument, and the quotes themselves are removed before your program sees anything.

Analogy

The command line is an order slip handed through a kitchen hatch. The customer (you, at the shell) writes words on it; the waiter (the operating system) carries it to the kitchen (your program) without reading it. The kitchen gets a count of words and the words, and must decide for itself what "80" means.

Where it breaks: a real waiter would notice that "--widht" is a spelling mistake. The operating system notices nothing. Every check, every default and every error message is yours to write.

First principle

When your program starts, the operating system has already copied the command-line words into your program's memory and placed their count in argc. main is just a function being called with those two values. Nothing happens by magic between the shell and your first line.

Parsing a flag and its value

A flag is an argument that names a setting, by convention beginning with two dashes: --width. In the style this book uses, the flag is followed by its value as the next argument: --width 80. To find the width, you walk the arguments from 1, and whenever you see "--width", the value is the next one, argv[i + 1].

That i + 1 is where the first bug hides. If --width is the last argument, there is no next one. The slot argv[argc], one past the last word, does not hold text at all: the operating system puts a special "nothing here" marker in it (a null pointer, week 7). Turn that marker into a std::string, or hand it to std::stoi, and the program dies on the spot. Here is the naive version, so that you have seen the crash once on purpose rather than by surprise at midnight:

#include <print>
#include <string>

int main(int argc, char* argv[]) {
    int width = 60;
    for (int i = 1; i < argc; ++i) {
        std::string arg = argv[i];
        if (arg == "--width") {
            width = std::stoi(argv[i + 1]);      // BUG: nobody checked that argv[i + 1] exists
            i += 1;
        }
    }
    std::println("width = {}", width);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra parse_width_unguarded.cpp -o parse_width_unguarded
$ ./parse_width_unguarded --width 80
width = 80
$ ./parse_width_unguarded --width
zsh: segmentation fault  ./parse_width_unguarded --width
$ echo $?
139

With a value it works. Without one, std::stoi starts reading bytes at the "nothing here" marker, the operating system stops the program, and the shell reports zsh: segmentation fault with exit code 139. There is no hint of which line was at fault. (Compile with -fsanitize=address,undefined, as chapter 2 suggested, and you get a report that at least names strlen, the library's "walk to the terminator" routine, and says the address was zero. Better, but still not a line number in your code.)

The fix has three parts, and the program below does them in order. First, before you read argv[i + 1], check that i + 1 < argc. Second, convert the text to a number with std::stoi, "string to int", which lives in <string>. Third, because the value was consumed, add one to i so the loop does not look at "80" on the next round as if it were a flag.

#include <print>
#include <string>

int main(int argc, char* argv[]) {
    int width = 60;                              // the default, used when --width is absent

    for (int i = 1; i < argc; ++i) {             // start at 1: argv[0] is the program name
        std::string arg = argv[i];
        if (arg == "--width" && i + 1 < argc) {  // is there a value after the flag?
            width = std::stoi(argv[i + 1]);      // text -> int
            i += 1;                              // skip the value on the next round
        }
    }

    std::println("width = {}", width);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra parse_width.cpp -o parse_width
$ ./parse_width
width = 60
$ ./parse_width --width 80
width = 80
$ ./parse_width --width
width = 60

The default is simply the value the variable starts with. If the loop never finds --width, nothing changes it, and 60 is what you get. The third run shows the guard working: --width with nothing after it is silently ignored and the default stands. Silently is not ideal, and the full parser below complains instead, but it does not crash, which is the important part.

The && from chapter 3 checks its left side first and only evaluates the right side if the left was true, so argv[i + 1] is only ever read after i + 1 < argc has been confirmed.

What std::stoi accepts

std::stoi reads digits from the front of the text and stops at the first character that is not part of a number. Its sibling std::stod, "string to double", does the same for numbers with a decimal point. Here are the edges you should know about:

#include <print>
#include <string>

int main() {
    std::println("{}", std::stoi("42"));
    std::println("{}", std::stoi("-7"));
    std::println("{}", std::stoi("  12"));     // leading spaces are skipped
    std::println("{}", std::stoi("80x24"));    // stops at the first non-digit
    std::println("{}", std::stod("0.35"));
    std::println("{}", std::stod("1e3"));
    return 0;
}

42
-7
12
80
0.35
1000

Negative numbers work and leading spaces are skipped. "80x24" gives 80 and the x24 is thrown away without complaint, which can hide a typo. std::stod understands 1e3: that is scientific notation, "1 times 10 to the power 3", so 1000. You will rarely type it, but std::println may print very large or very small doubles this way, so recognise it.

What happens with bad text

What if there are no digits at all, say the user typed --width eighty? std::stoi cannot return a number, because there is none, and it cannot return "no number" either, since every int value is a possible answer. What it does instead is stop the program with an error message. Watch:

#include <print>
#include <string>

int main() {
    std::println("about to convert \"abc\"...");
    int n = std::stoi("abc");
    std::println("n = {}", n);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra stoi_bad.cpp -o stoi_bad
$ ./stoi_bad
about to convert "abc"...
libc++abi: terminating due to uncaught exception of type std::invalid_argument: stoi: no conversion
zsh: abort      ./stoi_bad
$ echo $?
134

The first line printed. The line n = ... never did: the program ended inside std::stoi. The message says what went wrong, stoi: no conversion, and the shell reports abort with exit code 134 instead of the 0 you are used to. (libc++abi at the front of the message is the name of the piece of Apple's C++ library that printed it; it is not part of your program's text.) Note the difference from the segmentation fault above: there you got no message at all, here you get a readable one, because std::stoi noticed the problem itself before any bad memory was touched. The mechanism behind this, an exception, is how a library function says "I cannot do this" when it has no sensible value to return. Exceptions are deliberately left out of this curriculum's early weeks; what you need now is the behaviour: bad text to std::stoi stops the program with a readable message. For a Life program run by hand, that is acceptable. The usage message you write next makes the common mistakes (an unknown flag, a missing value) friendlier; a non-number is left to this message.

Trap

Three ways an argument parser goes wrong, in the order you will meet them: starting the loop at i = 0 and treating the program name as a flag; reading argv[i + 1] without checking i + 1 < argc; and forgetting i += 1 after using the value, so that "80" is examined as a flag on the next round and, once you report unknown flags, becomes an "unknown flag 80".

A complete argument parser with a usage message

Now the full shape, for four of the six settings the Life program needs: --width, --height, --seed, --fill (--fps and --steps are yours to add in milestone 5). The defaults are Life's own, from README.md: width 60, height 20, seed 1, fill 0.3. Two new behaviours make it a proper tool. A usage message tells the user what the program accepts, and is printed whenever the arguments make no sense. And return 1 from main tells the shell the program failed. Chapter 1 told you return 0 means success; any other number means a problem, and 1 is the usual choice when there is nothing more specific to say. Scripts and build tools check this number, so it is not decoration.

One new type appears, because life.hpp uses it: unsigned int is an int that cannot be negative. It uses the same four bytes but spends them all on magnitude, so it runs from 0 to 4,294,967,295 (232 − 1, about 4.29 billion). It behaves like the std::size_t of chapter 2, only four bytes wide instead of eight: going below zero wraps round to the top, and that wrap is defined behaviour, not UB. See it:

#include <print>
#include <string>

int main() {

    unsigned int zero = 0;
    unsigned int wrapped = zero - 1;                 // no sign bit: wraps to the top
    std::println("0 - 1 as unsigned int = {}", wrapped);
    unsigned int seed = static_cast<unsigned int>(std::stoi("-1"));
    std::println("--seed -1 would become {}", seed);
    return 0;
}

void print_usage(const std::string& program) {

    std::println("  --height N  rows (default 20)");

    std::println("  --fill F    chance that a cell starts alive, 0.0 to 1.0 (default 0.3)");

int main(int argc, char* argv[]) {

    int height = 20;
    unsigned int seed = 1;
    double fill = 0.3;

        std::string arg = argv[i];

        // Every flag this program knows needs a value after it. Refuse if there is none.
        bool has_value = (i + 1 < argc);
        if (!has_value) {
            std::println("error: {} needs a value", arg);
            print_usage(argv[0]);
            return 1;
        }
        std::string value = argv[i + 1];

        if (arg == "--width") {
            width = std::stoi(value);
        } else if (arg == "--height") {
            height = std::stoi(value);
        } else if (arg == "--seed") {
            seed = static_cast<unsigned int>(std::stoi(value));
        } else if (arg == "--fill") {

        } else {

            print_usage(argv[0]);

    }

    std::println("height = {}", height);
    std::println("seed   = {}", seed);
    std::println("fill   = {}", fill);

Read the loop body as a checklist that every argument goes through. Is there a value after this flag? If not, complain and stop. Which flag is it? Convert the value into the right variable. None of the known ones? Complain and stop. Finally skip past the value. The if / else if / else chain from chapter 3 is the natural shape: exactly one branch runs for each flag.

print_usage takes the program name by const std::string&, which chapter 5 taught: look, do not copy. It is given argv[0], and the C-style text becomes a std::string on the way in, the same conversion as std::string arg = argv[i]. Two design choices are worth noticing. Every flag here takes a value; a flag that stands alone, like --help, would need checking before the "needs a value" test. And flags may come in any order and be repeated; the last one wins, because each assignment overwrites the previous. Most command-line tools, llama.cpp included, follow the same conventions.

Randomness: a computer cannot roll dice

random_cells must make each cell alive "with probability fill". That needs something unpredictable, and a processor is the least unpredictable machine ever built: given the same instructions and the same starting bytes it does exactly the same thing every time. There is no dice inside. What there is instead is a pseudo-random number generator: a formula that takes a number, produces the next number, and keeps going. The sequence looks random, with no visible pattern, but it is entirely determined by the first number, the seed.

You can write one in three lines, and you should see one before using the library's, so that nothing about it is mysterious:

#include <print>

// A deliberately simple "random" formula: each number is made from the last one.
unsigned int next_number(unsigned int previous) {
    return previous * 1103515245u + 12345u;     // wraps around at 2^32, on purpose
}

int main() {
    unsigned int x = 7;                          // the seed
    for (int i = 0; i < 8; ++i) {
        x = next_number(x);
        std::print("{} ", x % 10);               // keep just the last digit
    }
    std::println("");

    x = 7;                                       // same seed again...
    for (int i = 0; i < 8; ++i) {
        x = next_number(x);
        std::print("{} ", x % 10);
    }
    std::println("  <- the same digits");
    return 0;
}

4 3 8 1 0 9 2 7
4 3 8 1 0 9 2 7   <- the same digits

Read the formula. Multiply the previous number by a large odd constant, add another constant, and let the result wrap around when it exceeds what four bytes can hold. The u after each constant marks it as unsigned too, so the whole calculation happens in unsigned int, where wrapping is defined behaviour (you saw 0 - 1 wrap a few pages ago). That wrap is what keeps the numbers inside four bytes forever, and it is also what scrambles them: the high digits of the product are thrown away each round.

Analogy

An unsigned int wrapping is like a car's distance counter rolling from 999999 back to 000000 and carrying on.

Where it breaks: the car counter is a nuisance when it rolls over; here the roll-over is the point, and the language guarantees it. The guarantee holds for unsigned types only. Write the same formula with plain int and the very first multiplication, 7 × 1103515245, overflows a signed type, which chapter 2 showed is undefined behaviour. Compiled with -fsanitize=undefined it prints runtime error: signed integer overflow: 7 * 1103515245 cannot be represented in type 'int' at that line; without the sanitizer it silently produces garbage, and the first "digit" printed is -2, because % of a negative number is negative (chapter 2's trap).

The digits that come out, 4 3 8 1 0 9 2 7, have no obvious order. Yet starting again from 7 produces exactly the same digits, because the formula and the input are the same. This formula is a real one that C libraries used for decades, and a poor one by today's standards: statistical tests find patterns in it. The library generator you are about to use is the same idea with a far better formula.

First principle

A pseudo-random generator is a variable holding a fixed number of bytes (4 in the homemade one above; 2,504 in the library's, as you will see shortly), a function that scrambles those bytes to produce the next value, and nothing else. "Random" describes how the output looks, not how it is made. Same seed, same formula, same sequence, every time, on every machine that uses the same formula.

That determinism is not a weakness to apologise for. It is the feature you will lean on hardest this week and for the rest of this curriculum. Reproducible bugs: when your Life grid does something strange at generation 212 with seed 7, you run it again with seed 7 and it does the same strange thing at generation 212, every time, until you have fixed it. Reproducible tests: life_test.cpp checks random_cells(8, 4, 42, 0.5) twice and demands the two grids are equal. Reproducible benchmarks: bench_life.cpp starts from seed 12345 so that every run times the same grid and a faster number means your code got faster, not your luck.

std::mt19937: the library's generator

The standard library's generators live in <random>. The one most code uses is std::mt19937, named after the Mersenne Twister formula and the number 19937: its sequence only starts repeating after 219937 − 1 numbers, which is more than you could draw in the lifetime of the universe (the homemade formula above repeats after at most 232). You create one with a seed and then call it like a function, with empty brackets, to get the next raw number:

#include <print>
#include <random>

int main() {
    std::mt19937 rng(42);                 // a generator, started from seed 42
    for (int i = 0; i < 3; ++i) {
        std::println("{}", rng());        // call it like a function: one raw number
    }
    std::println("the generator itself takes {} bytes", sizeof(rng));
    return 0;
}

1608637542
3421126067
4083286876
the generator itself takes 2504 bytes

Three large whole numbers, each between 0 and 4,294,967,295 (the full range of 32 bits, the same range as unsigned int). std::mt19937 rng(42) is a declaration like std::vector<int> v(10, 0): a variable called rng of type std::mt19937, initialised from 42. The last line shows it is a big variable: 2,504 bytes, which is 624 four-byte numbers (2,496 bytes) plus a counter saying which of them is next. The homemade generator kept one unsigned int of state; this one keeps 624, and each call to rng() stirs that state and returns one slice of it. Make a second std::mt19937 with seed 42 on any machine and its first number is 1608637542 too: the standard pins the formula down exactly.

A distribution shapes the raw numbers

Raw numbers up to four billion are rarely what you want. For Life you want a value between 0.0 and 1.0 to compare with fill. A distribution is a second variable, sitting next to the generator, whose job is to reshape raw generator output into the range and kind of number you asked for. std::uniform_real_distribution<double> gives a double where every value in a range is equally likely ("uniform"). You make one with the range, then hand it the generator each time you want a number:

#include <print>
#include <random>

void print_five(unsigned int seed) {
    std::mt19937 rng(seed);
    std::uniform_real_distribution<double> dist(0.0, 1.0);
    std::print("seed {}:", seed);
    for (int i = 0; i < 5; ++i) {
        double r = dist(rng);
        std::print(" {:.4f}", r);      // {:.4f} = show 4 digits after the point
    }
    std::println("");
}

int main() {
    print_five(42);
    print_five(42);
    print_five(43);
    return 0;
}

seed 42: 0.7965 0.1834 0.7797 0.5969 0.4458
seed 42: 0.7965 0.1834 0.7797 0.5969 0.4458
seed 43: 0.4969 0.1029 0.1488 0.1721 0.8110

The pattern to memorise is three lines: make the generator from the seed, make the distribution with the range, and call dist(rng) for every number. The distribution takes the generator by reference (chapter 5 again: it must advance your generator, not a copy), pulls raw numbers from it and scales them into [0.0, 1.0), meaning 0.0 is possible and 1.0 is just excluded. Seed 42 twice gives the identical five numbers. Seed 43, one away, gives numbers that share nothing with them. A good generator makes neighbouring seeds unrelated.

One honest footnote. The standard pins down std::mt19937 bit for bit, so its raw numbers are the same everywhere. It does not pin down how a distribution turns raw numbers into a double; that recipe is left to each standard library. Apple's library (libc++) and the GNU library on Linux (libstdc++) use different recipes, so the five numbers above are guaranteed only on the same compiler and library. That is all this week needs: the tests and the benchmark compare runs of the same program on the same machine.

The {:.4f} inside the braces is a formatting instruction: show four digits after the decimal point. Plain {} prints as many digits as it takes to pin the double down exactly, no more and no fewer: for these numbers that is fifteen to seventeen digits (the first one above comes out as 0.796542984287846), which is correct but hard to read. Chapter 2 has the table of formatting codes.

Trap

Create the generator once. The generator should be made once and then used for every number. A beginner's mistake is to put std::mt19937 rng(seed); inside the loop: then every round starts from the same seed and every "random" number is the same one. In a function like random_cells the generator is a local variable created at the top, used by the loops, and gone when the function returns. One seed in, one grid out.

"Alive with probability fill" means r < fill

Here is the one idea that turns a number in [0.0, 1.0) into a yes-or-no decision with a chosen likelihood. If r is uniform between 0 and 1, then the chance that r lands below some value p is exactly p: below 0.5 half the time, below 0.3 three times in ten, below 1.0 always, below 0.0 never. So "do this with probability p" is written if (r < p). On a non-Life problem, flipping a coin twenty times:

#include <print>
#include <random>
#include <string>

int main() {
    const int flips = 20;
    const double chance_of_heads = 0.5;

    std::mt19937 rng(2024);
    std::uniform_real_distribution<double> dist(0.0, 1.0);

    std::string picture;
    int heads = 0;
    for (int i = 0; i < flips; ++i) {
        double r = dist(rng);
        if (r < chance_of_heads) {
            picture += 'H';
            heads += 1;
        } else {
            picture += 'T';
        }
    }
    std::println("{}", picture);
    std::println("{} heads out of {}", heads, flips);
    return 0;
}

TTTTTHTTTHHTHTHHHTHH
9 heads out of 20

One loop, one draw per flip: when the number is below the chance the flip is heads, so an H goes on the end of the string and the count goes up by one; otherwise a T. The picture is built as the decisions are made, with no vector in between. Nine heads of twenty: close to half, not exactly half, which is what randomness looks like.

Is it really the right probability? Measure it. The next program flips ten thousand times at five different chances:

#include <print>
#include <random>

int heads_out_of(int flips, double chance, unsigned int seed) {
    std::mt19937 rng(seed);
    std::uniform_real_distribution<double> dist(0.0, 1.0);
    int heads = 0;
    for (int i = 0; i < flips; ++i) {
        if (dist(rng) < chance) {
            heads += 1;
        }
    }
    return heads;
}

int main() {
    std::println("chance 0.0 -> {} heads of 10000", heads_out_of(10000, 0.0, 1));
    std::println("chance 0.1 -> {} heads of 10000", heads_out_of(10000, 0.1, 1));
    std::println("chance 0.5 -> {} heads of 10000", heads_out_of(10000, 0.5, 1));
    std::println("chance 0.9 -> {} heads of 10000", heads_out_of(10000, 0.9, 1));
    std::println("chance 1.0 -> {} heads of 10000", heads_out_of(10000, 1.0, 1));
    return 0;
}

chance 0.0 -> 0 heads of 10000
chance 0.1 -> 1020 heads of 10000
chance 0.5 -> 4951 heads of 10000
chance 0.9 -> 8961 heads of 10000
chance 1.0 -> 10000 heads of 10000

Chance 0.0 gives exactly zero heads, because no number in [0.0, 1.0) is below 0.0. Chance 1.0 gives exactly all of them, because every number in that range is below 1.0; this is why the range excludes 1.0 itself. In between, the counts sit close to the chance times ten thousand but not on it: 1,020 where 1,000 was expected, 4,951 for 5,000, 8,961 for 9,000. Each is within 50 of the target, half a percent of the ten thousand flips. Now reread the random_cells test in life_test.cpp: fill 0.0 must give zero live cells, fill 1.0 all of them, and fill 0.5 on a 100×100 grid between 4,000 and 6,000. Those are this table's rows, with "heads" renamed "alive".

Stuck? First nudge

Chance 0.0 and 1.0 cannot change with the seed, because no value in [0.0, 1.0) is below 0.0 and every value is below 1.0; the seed only decides which values appear. For chance 0.3, expect roughly 3,000. With a million flips the count drifts further from the target in absolute terms but closer as a fraction: this is why the random_cells test accepts anything between 4,000 and 6,000 on 10,000 cells rather than demanding exactly 5,000.

Check yourself

After std::string s = "ab"; s += 'c'; s += "de";, what is s.size(), and what is s[2]?

Answer

s.size() is 5 and s is "abcde". s[2] is the char 'c', because positions count from 0.

What is the difference between '#' and "#"? Which one can you append to a string with +=?

Answer

'#' is a single char, one byte with the value 35. "#" is a string literal: text one character long (two bytes in memory, counting the terminator). Both can be appended with +=; but only '#' can be compared with ch == '#' when ch is a char, and only "#" can initialise a std::string.

A program is started as ./life --seed 7. What are argc, argv[0] and argv[2]? Is argv[2] the number seven?

Answer

argc is 3. argv[0] is "./life", the program name. argv[2] is the text "7", a single character with the code 55, not the number seven. You get the number with std::stoi(argv[2]).

Why must you check i + 1 < argc before reading argv[i + 1]? What happens if you do not and the user types ./life --width?

Answer

With ./life --width, argc is 2 and --width is at argv[1], so argv[2] is the slot one past the last word. It holds no text, only the "nothing here" marker, and making a std::string from it (or passing it to std::stoi) crashes the program with zsh: segmentation fault and no useful message. The check makes the program refuse cleanly instead.

What does std::stoi("12abc") return, and what does std::stoi("abc") do?

Answer

std::stoi("12abc") returns 12: it reads digits from the front and stops at the first non-digit. std::stoi("abc") finds no digits at all and stops the program with the message stoi: no conversion; the shell reports an abort.

You print three raw numbers from std::mt19937 rng(42), then run the same program again tomorrow, and then on a friend's Mac. Do you get the same three numbers each time? Why is that useful for this week's tests and benchmark?

Answer

Yes, all three times. The formula and the seed fully determine the sequence, and the standard fixes the formula for std::mt19937, so every machine agrees on the raw numbers. (Only the distribution step is left to the library, so numbers that went through uniform_real_distribution are guaranteed identical on the same compiler and library, which is what you have.) life_test.cpp relies on this to check that random_cells gives the same grid twice for the same seed, and bench_life.cpp relies on it so that every timed run works on the identical grid.

r is a double drawn uniformly from [0.0, 1.0). How do you make a decision that comes out true 30% of the time? What happens for a chance of exactly 1.0, and why does the range exclude 1.0?

Answer

if (r < 0.3): the chance that a uniform number lands below 0.3 is 0.3. With a chance of 1.0, r < 1.0 is true for every value the distribution can produce, so the decision is always true. If 1.0 were a possible value of r, it would occasionally fail, and "fill 1.0 = all alive" could not be guaranteed.

Why does a function that returns a string of the grid beat one that prints the grid directly? Give one reason for testing and one for the terminal.

Answer

Testing: a returned string can be compared with == against the expected text, as CHECK(render(g, 3, 2) == "#..\n..#\n") does; printed output cannot be checked that way. Terminal: one string printed once reaches the terminal as a single block, so no partially drawn frame is ever visible; many small prints can flicker when redrawn quickly (chapter 9).
