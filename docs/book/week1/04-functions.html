The problem: the same code three times

In chapter 3 you printed a rectangle of dots with two nested loops. Suppose a program needs three rectangles of # characters, all of different sizes. The obvious thing is to copy the loops three times and change the numbers. Here is exactly that, and it contains a bug. Try to find it before reading the output.

#include <print>

int main() {
    // A 5 by 2 rectangle of '#'
    for (int y = 0; y < 2; ++y) {
        for (int x = 0; x < 5; ++x) {
            std::print("#");
        }
        std::println("");
    }
    std::println("");

    // A 3 by 3 rectangle of '#'
    for (int y = 0; y < 3; ++y) {
        for (int x = 0; x < 3; ++x) {
            std::print("#");
        }
        std::println("");
    }
    std::println("");

    // A 7 by 1 rectangle of '#'
    for (int y = 0; y < 1; ++y) {
        for (int x = 0; x <= 7; ++x) {   // bug: one '#' too many
            std::print("#");
        }
        std::println("");
    }
    return 0;
}

The third rectangle is eight wide, not seven. Somebody typed <= instead of < in one copy. The first two copies are correct, which makes the bug harder to see: your eye reads "the same loop, three times" and stops checking. This is what copy-paste does to code. Every copy is a place where a typo can hide, and every fix must be made in every copy. Miss one and you have fixed the bug in two places and kept it in the third.

The deeper problem is that the three blocks are not really different. They are the same idea, "print a rectangle", with different numbers plugged in. C++ lets you write the idea once, give it a name, and leave holes for the numbers. That is a function: a named block of code that takes zero or more inputs and hands back at most one result. Here is the same program with the idea written once.

#include <print>

// Print a rectangle of '#' that is `width` wide and `height` tall.
void print_rect(int width, int height) {
    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            std::print("#");
        }
        std::println("");
    }
}

int main() {
    print_rect(5, 2);
    std::println("");
    print_rect(3, 3);
    std::println("");
    print_rect(7, 1);
    return 0;
}

The loops exist exactly once, in print_rect. The bug cannot hide in a third copy because there is no third copy. And main now reads like a description of what the program does, "print a 5 by 2, print a 3 by 3, print a 7 by 1", instead of a wall of loop machinery. You have been using functions since chapter 1: std::println is one, and so is main. Now you get to write your own.

One word in that program is new: the void at the front of print_rect. Take it on trust for a few paragraphs; it means "this function hands nothing back". The section void: a function with no result below explains it properly.

First principle

A function separates what from how. The name and the inputs say what it does; the body says how. Whoever calls the function only needs the "what". This is the single most important tool for keeping a program understandable as it grows, and the rest of this book, and llama.cpp, is built from it.

Anatomy of a function

Here is the smallest useful function with a result, plus a main that uses it four ways.

#include <print>

// Return x multiplied by itself.
int square(int x) {
    return x * x;
}

int main() {
    int a = square(4);
    std::println("square(4) = {}", a);
    std::println("square(12) = {}", square(12));
    std::println("square(-3) = {}", square(-3));
    std::println("square(square(2)) = {}", square(square(2)));
    return 0;
}

square(4) = 16
square(12) = 144
square(-3) = 9
square(square(2)) = 16

The five parts

Read the first line, int square(int x) {, left to right. Every function has these parts, in this order.

  1. Return type: int. The type of the one value the function hands back. This is a promise: whatever happens inside, the caller will receive an int.
  2. Name: square. Same rules as variable names: letters, digits, underscores, cannot start with a digit. This book uses lower case words joined by underscores, which is also what life.hpp uses.
  3. Parameter list: (int x). In parentheses, a comma-separated list of the inputs. Each one is a type followed by a name, exactly like declaring a variable. A parameter is a variable that is born when the function starts, filled in by the caller. A function can have zero parameters, written (), or several, like print_rect(int width, int height).
  4. Body: everything between { and }. Ordinary statements, the same ones you wrote in main.
  5. return: the statement that ends the function and sends a value back. return x * x; computes the product and hands it to whoever called. The expression after return must have the return type, or something the compiler can convert to it.

The first line without the body, int square(int x), is called the function's signature. You will hear "signature" constantly; it means "the return type, the name, and the parameter types". It is the part a caller needs to know. (Strictly, the C++ standard leaves the return type out of the word "signature"; everyday usage, and this book, put it in.)

Calling a function

To call a function you write its name followed by parentheses containing the arguments: the actual values to use this time. square(4) is a call with the argument 4. Two words that sound alike and are worth keeping apart: a parameter is the name inside the function (x); an argument is the value you pass in from outside (4). When the call happens, the argument is copied into the parameter, so inside this call x holds 4.

A call to a function with a return type is an expression, exactly like 3 + 4. It has a value and a type, and you can put it anywhere a value of that type is allowed. The program above shows three places: stored in a variable (int a = square(4);), used directly as an argument to std::println, and used as the argument to another call (square(square(2)), which is square(4), which is 16). The inner call finishes first, then its result becomes the argument of the outer call.

What does the machine do at a call? The CPU is executing the instructions of main, one after another. When it reaches square(4), it notes where it is, copies the value 4 into the place that square's x will live, and jumps to the first instruction of square. It runs the body. At return, it puts the result where main expects it and jumps back to the noted place. Nothing mysterious: a jump out, some work, a jump back carrying one value.

void: a function with no result

print_rect from the first example started with void instead of int. void is a type that means "nothing". A void function does something (prints, mostly, at this point in the book) but hands back no value. Its body needs no return; the function ends when it reaches the closing brace. You may still write a bare return;, with no value after it, to leave early. Here is a void function that uses it to refuse an input that makes no sense.

#include <print>

// Print `count` stars on one line. A negative count makes no sense: say so and stop.
void print_stars(int count) {
    if (count < 0) {
        std::println("(cannot print {} stars)", count);
        return;                       // leave the function here; nothing below runs
    }
    for (int i = 0; i < count; ++i) {
        std::print("*");
    }
    std::println("");
}

int main() {
    print_stars(3);
    print_stars(-2);
    print_stars(0);
    print_stars(5);
    return 0;
}

***
(cannot print -2 stars)

*****

For -2 the if fires, the message is printed, and return; ends the call before the loop is reached: no stars, and no empty line either, because the std::println("") at the bottom was never run. For 0 the if does not fire, the loop runs zero times, and the final std::println("") gives the empty line you see. The other two calls behave as you would expect.

Because a void function has no value, you cannot use a call to it where a value is needed. The compiler says so clearly.

#include <print>

void greet() {
    std::println("hello");
}

int main() {
    int x = greet();
    std::println("{}", x);
    return 0;
}

void_return_value.cpp:8:9: error: cannot initialize a variable of type 'int' with an rvalue of type 'void'
    8 |     int x = greet();
      |         ^   ~~~~~~~
1 error generated.

"rvalue" is the compiler's word for a temporary value, such as the result of a call or of 3 + 4; the name comes from "the right-hand side of an assignment". It is saying: you tried to store a nothing in an int. A void function is called on a line by itself, as a statement: greet();.

The compiler also checks that you pass the right number of arguments. Passing two to a function that takes one is an error, and the message tells you both what you did and what the function wanted.

#include <print>

int square(int x) {
    return x * x;
}

int main() {
    std::println("{}", square(3, 4));
    return 0;
}

wrong_arg_count.cpp:8:24: error: no matching function for call to 'square'
    8 |     std::println("{}", square(3, 4));
      |                        ^~~~~~
wrong_arg_count.cpp:3:5: note: candidate function not viable: requires single argument 'x', but 2 arguments were provided
    3 | int square(int x) {
      |     ^      ~~~~~
1 error generated.

Lines marked note: are the compiler explaining its reasoning: it found a square, considered it, and says why it does not fit. Misuse a life.hpp function this week and you will get this exact shape of message, with the note pointing at the declaration in the header.

Arguments are copied

This is the most important fact in the chapter, and the one beginners trip on most. When you call a function, each argument is copied into the corresponding parameter. The parameter is a brand-new variable, a separate box in memory, holding a copy of the value. Whatever the function does to its parameter happens to the copy. The caller's variable is untouched. This is called passing by value. Watch it happen.

#include <print>

void try_to_double(int n) {
    n = n * 2;                             // changes THIS function's n
    std::println("inside try_to_double: n = {}", n);
}

int main() {
    int count = 21;
    std::println("before the call: count = {}", count);
    try_to_double(count);
    std::println("after the call:  count = {}", count);
    return 0;
}

before the call: count = 21
inside try_to_double: n = 42
after the call:  count = 21

Inside the function, n really did become 42. But n is not count. It is a copy that was made at the moment of the call. When the function ended, its n was thrown away, and count had never been anything but 21.

Analogy

Calling a function is like handing a colleague a photocopy of a document. They can scribble on their copy all they like; your original on your desk does not change. If you want a result back, they have to hand you a new sheet, which is what return does.

Where it breaks: in chapter 5 you will meet references, which are a way to hand over the original instead of a copy, so the function can change your variable. The contract in life.hpp uses them, which is why step can fill in the next grid you give it. For now, every parameter you write is a copy.

So how do you get a changed value out of a function? For now, the answer is always the same: the function returns the new value, and the caller stores it wherever it likes, including back into the variable it came from.

#include <print>

// Give back twice n. The caller decides what to do with the result.
int doubled(int n) {
    return n * 2;
}

int main() {
    int count = 21;
    count = doubled(count);                // store the result back into count
    std::println("count = {}", count);
    return 0;
}

count = 42

Read count = doubled(count); from the right: first the call runs, with a copy of 21 as its n, and produces 42. Then the assignment stores 42 into count. The function never touched count; main did, using the function's answer.

Try it

Without running it, write down the three lines this program prints. Then run it and compare.

#include <print>

int add_ten(int n) {
    n = n + 10;
    std::println("inside: n = {}", n);
    return n;
}

int main() {
    int score = 5;
    int bigger = add_ten(score);
    std::println("score = {}", score);
    std::println("bigger = {}", bigger);
    return 0;
}
Show the answer

inside: n = 15, then score = 5, then bigger = 15. The parameter n is a copy of score, so changing it leaves score at 5. The changed value reaches main only because add_ten returns it and main stores it in bigger.

Passing by value is not a limitation to work around; it is a guarantee to rely on. When you read int clamp(int v, int lo, int hi) (a function you will write later in this chapter) you know, without reading the body, that calling it cannot disturb any of your variables; its only effect is its return value.

Declaration before use

The compiler reads your file from the first line to the last, once, and it must understand every name the moment it meets it. When it sees cube(3) it needs to know already that cube is a function, what it returns, and what it takes. If the function is written below the call, the compiler has not got there yet. Here is the error you get.

#include <print>

int main() {
    std::println("{}", cube(3));
    return 0;
}

int cube(int x) {
    return x * x * x;
}

before_decl.cpp:4:24: error: use of undeclared identifier 'cube'
    4 |     std::println("{}", cube(3));
      |                        ^~~~
1 error generated.

"Undeclared identifier" means "I have met a name I know nothing about". Every program so far avoided this by putting functions above main. That works, but in a real program you cannot always order things so that every function appears before every call: two functions might call each other, and you will often want main at the top so that a reader sees the big picture first. The proper fix is to tell the compiler about the function before showing it the body.

The prototype

A declaration (also called a prototype) is the signature followed by a semicolon: int cube(int x);. It says "a function named cube exists, takes one int, and returns an int; the body is elsewhere". A definition is the signature followed by the body: the whole thing. The compiler needs the declaration before any call. It needs the definition somewhere, once, in the whole program.

#include <print>

int cube(int x);              // declaration: "cube exists and looks like this"

int main() {
    std::println("{}", cube(3));
    return 0;
}

int cube(int x) {             // definition: what cube actually does
    return x * x * x;
}

27

A few details that matter:

  • You may declare a function as many times as you like, but define it exactly once. Two definitions of the same function is an error.
  • The declaration and definition must agree on the return type and the parameter types. The parameter names are allowed to differ, and may even be left out of the declaration: int cube(int); is legal. Keep the names; they are documentation.
  • Calling a declared-but-never-defined function compiles, and then fails at the link step. Recall from chapter 1 that the linker is the program that glues your compiled code to the standard library; it is also the one that finds each function's body. If no body exists anywhere, it is the linker that complains, not the compiler. On your Mac the message begins Undefined symbols for architecture arm64: and names the missing function, here "cube(int)", referenced from: _main. You will meet that step properly in chapter 10.
Where this is going

Look at phase1-terminal/01-life/src/life.hpp. It is nothing but declarations with comments. A header file is a file of declarations that other files include so they can call the functions, while the definitions live in a separate file (life.cpp). That is why the header is called the contract: it is the list of promises, and life.cpp is where you keep them. Chapter 10 explains the mechanics; for now, know that a header is a stack of prototypes.

Scope: where a name is visible

A variable declared inside a function exists only inside that function. Its scope, the region of the program where its name means something, runs from the line of its declaration to the closing brace of the block it is in. Outside that region the name is simply unknown. The compiler enforces this with the same "undeclared identifier" error you just saw.

#include <print>

void make_a_number() {
    int secret = 42;
    std::println("inside: secret = {}", secret);
}

int main() {
    make_a_number();
    std::println("outside: secret = {}", secret);
    return 0;
}

scope_error.cpp:10:42: error: use of undeclared identifier 'secret'
   10 |     std::println("outside: secret = {}", secret);
      |                                          ^~~~~~
1 error generated.

secret belongs to make_a_number. From main's point of view it does not exist, and never did, even after the call. If main wants the number, make_a_number has to return it. Variables that live inside a function are called local variables; parameters are local variables too, filled in at the call.

The same name in two functions

Because each function's locals are private to it, two functions can both have a variable named x with no conflict. They are two different boxes that happen to carry the same label.

#include <print>

int first() {
    int x = 10;
    std::println("first:  x = {}", x);
    return x;
}

int second() {
    int x = 99;                       // a different box that happens to share the name
    std::println("second: x = {}", x);
    return x;
}

int main() {
    int x = 1;
    std::println("main:   x = {}", x);
    first();
    second();
    std::println("main:   x = {} (still)", x);
    return 0;
}

main:   x = 1
first:  x = 10
second: x = 99
main:   x = 1 (still)

Three functions, three xs, three separate places in memory. main's x is still 1 at the end because nothing that happened in first or second had anything to do with it. This is why you can name a parameter width in six different functions this week and never worry about them colliding.

Blocks inside functions

Scope is about braces, not only about functions. Any { ... } block, such as the body of a loop or an if, is a scope. A variable declared inside a loop body is created afresh on every pass and vanishes at the closing brace. You saw this in chapter 3 with the loop counter; it is the same rule.

#include <print>

int main() {
    int total = 0;
    for (int i = 1; i <= 3; ++i) {
        int doubled = i * 2;          // born here, on every pass
        total = total + doubled;
    }                                 // doubled dies here; total lives on
    std::println("total = {}", total);
    return 0;
}

total = 12

A good habit that follows from this: declare each variable in the smallest scope that works, as close to its first use as possible. The less of the program a name is visible in, the less of the program you need to read to understand it.

The call stack

Where do all those local variables live? Each call to a function gets a fresh patch of memory for its parameters and locals, called a stack frame (or just a frame). When the function returns, its frame is released and the memory is reused by the next call. Frames are stacked. main's frame is at the bottom. When main calls a, a's frame goes on top. When a calls b, b's frame goes on top of that. Only the top frame is active. When b returns, its frame is removed and a carries on exactly where it stopped. This whole structure is the call stack.

Analogy

Think of sticky notes on a desk. You are working on a task (main) and write your working on a note. Someone asks you to do a sub-task: you put a new note on top, do the sub-task on that note, and when it is finished you throw the note away and continue with the note underneath, which still says exactly what it said before. Notes only ever go on and off the top.

Where it breaks: a frame is not just scribbles. It also records where to jump back to when the function returns, and its size is fixed by the compiler from the function's variables. And the stack has a limit. A function is allowed to call itself (this is called recursion; you will not need it this week). One that calls itself forever stacks frames until the memory runs out, and the program crashes with a stack overflow. A plain build on your Mac just dies with "segmentation fault"; built with the tools/run.sh flags, the report says ERROR: AddressSanitizer: stack-overflow and names the function.

Here is a chain main → a → b, with prints at every step so you can watch the stack grow and shrink.

#include <print>

int b(int n) {
    std::println("  b starts with n = {}", n);
    int result = n + 100;
    std::println("  b is about to return {}", result);
    return result;
}

int a(int n) {
    std::println(" a starts with n = {}", n);
    int from_b = b(n * 2);
    std::println(" a got {} back from b", from_b);
    return from_b + 1;
}

int main() {
    std::println("main starts");
    int answer = a(5);
    std::println("main got {} back from a", answer);
    std::println("main ends");
    return 0;
}

main starts
 a starts with n = 5
  b starts with n = 10
  b is about to return 110
 a got 110 back from b
main got 111 back from a
main ends

Follow the indentation: one space per frame. At the deepest point there are three frames on the stack: main (holding answer, not yet filled in), a (holding its n = 5 and from_b, not yet filled in), and b (holding its n = 10 and result = 110). Note that a and b both have an n, with different values, at the same time. That is only possible because they are in different frames. As b returns, its frame disappears, and a resumes on the line int from_b = b(n * 2); with 110 in hand.

This picture matters beyond this chapter. When a program crashes, the debugger shows you the call stack, the list of frames at that moment, which tells you not just where it crashed but how it got there.

main is a function too

You have written int main() { ... return 0; } since chapter 1, told to take it on trust. Now you can read it: a function named main, no parameters, returning an int. The only special thing about main is who calls it: the operating system does, when you run the program. And the int that main returns goes back to the operating system as the program's exit code, the number chapter 1 read with echo $?. By convention 0 means "everything went fine" and any other number means "something went wrong". The shell keeps the exit code of the last program in the variable $?.

#include <print>

int main() {
    std::println("something went wrong, exiting with code 3");
    return 3;
}

$ clang++ -std=c++23 -Wall -Wextra exit_code.cpp -o exit_code
$ ./exit_code
something went wrong, exiting with code 3
$ echo $?
3

This is how tools talk to each other: the doctest test program in chapter 12 returns 0 if every check passed and non-zero otherwise, and the test runner you meet in chapter 11 (ctest) reads that number to print "Passed" or "Failed". In chapter 8, main grows parameters too (int main(int argc, char* argv[])): the words you typed on the command line, delivered as arguments by the same mechanism you learned a few paragraphs ago. The * and [] in that line are chapter 8's business; take them on trust until then.

Designing small functions

Knowing the syntax is a third of it. The rest is judgement: what should be a function, and what should it be called? Three rules carry you a long way.

  • One job. A function does one thing. If you need the word "and" to describe it ("computes the area and prints it"), it is probably two functions.
  • A name that says the job. Verbs for actions (print_row), nouns for values (area), is_ prefix for yes/no questions (is_even). If the name is right, the caller never needs to read the body.
  • Short. Roughly 5 to 15 lines. Not a law, but a smell test: a 60-line function is almost always three functions wearing a trench coat.

Here are six functions that follow these rules, each in a complete program. Every one is a shape you will use this week.

is_even: a yes/no question

A function that returns bool is a question. Its body is usually a single comparison, and the return hands back the true or false that the comparison produced. You do not need an if to return a boolean; the comparison already is one.

#include <print>

// True when n divides by 2 with nothing left over.
bool is_even(int n) {
    return n % 2 == 0;
}

int main() {
    for (int n = 0; n < 6; ++n) {
        if (is_even(n)) {
            std::println("{} is even", n);
        } else {
            std::println("{} is odd", n);
        }
    }
    std::println("is_even(-4) = {}", is_even(-4));
    return 0;
}

0 is even
1 is odd
2 is even
3 is odd
4 is even
5 is odd
is_even(-4) = true

Notice if (is_even(n)): because the call produces a bool, it slots straight into the condition. Reading it aloud gives a sentence, "if n is even", which is the test of a good name.

Notice also that the body tests n % 2 == 0 and not n % 2 == 1. The two look interchangeable, but chapter 2 showed that the remainder of a negative number is negative: -3 % 2 is -1. A function written as return n % 2 == 1; would answer "false" for -3 and call it even. Comparing with 0 is correct for every int, which is why the last line of the output is right for -4.

clamp: several returns

clamp(v, lo, hi) pushes a value back inside a range: if v is below lo you get lo, above hi you get hi, otherwise v unchanged. It has three parameters and three return statements. A function may contain any number of returns; the first one reached ends the function on the spot.

The comment below writes the range as [lo, hi]. This is a notation you will see in life.hpp too, so learn it now. A square bracket means "this end is included"; a round bracket means "this end is excluded". [0, 10] is the eleven numbers 0 to 10. [0, 10) is the ten numbers 0 to 9, which is exactly the set of valid indexes for a row of 10 cells, and exactly the range that a for (int x = 0; x < 10; ++x) loop visits.

#include <print>

// Push v back inside the range [lo, hi] if it fell outside.
int clamp(int v, int lo, int hi) {
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

int main() {
    std::println("clamp(5, 0, 10)   = {}", clamp(5, 0, 10));
    std::println("clamp(-7, 0, 10)  = {}", clamp(-7, 0, 10));
    std::println("clamp(123, 0, 10) = {}", clamp(123, 0, 10));
    std::println("clamp(0, 0, 10)   = {}", clamp(0, 0, 10));
    std::println("clamp(10, 0, 10)  = {}", clamp(10, 0, 10));
    return 0;
}

clamp(5, 0, 10)   = 5
clamp(-7, 0, 10)  = 0
clamp(123, 0, 10) = 10
clamp(0, 0, 10)   = 0
clamp(10, 0, 10)  = 10

The second if does not need an else, because if the first condition had been true the function would already have returned. Code after a return that fires is never reached. This "check the odd cases first and return early, then handle the normal case at the bottom" layout is extremely common and is worth copying.

Arguments are matched to parameters by position: in clamp(123, 0, 10) the first argument goes to v, the second to lo, the third to hi. The names you gave the parameters play no part in the matching.

Trap

The compiler checks the number and types of the arguments, not their meaning. Swap two arguments of the same type and you get a quietly wrong answer, not an error. Here is clamp called correctly and then with lo and hi swapped.

#include <print>

int clamp(int v, int lo, int hi) {
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

int main() {
    std::println("clamp(5, 0, 10)  = {}", clamp(5, 0, 10));    // lo and hi in the right order
    std::println("clamp(5, 10, 0)  = {}", clamp(5, 10, 0));    // lo and hi swapped by mistake
    return 0;
}

clamp(5, 0, 10)  = 5
clamp(5, 10, 0)  = 10

In the second call lo is 10, so 5 < 10 is true and the function returns 10. Nothing warned you. index_of(int x, int y, int width) in life.hpp takes three ints, and swapping x and y in a call is the single most common Week 1 bug. When a function takes several parameters of the same type, read your calls twice, and read the declaration to confirm the order.

celsius_to_fahrenheit: doubles in, double out

The return type and the parameter types need not be int. Here everything is double, and the name says both what goes in and what comes out.

#include <print>

// Convert a temperature in degrees Celsius to degrees Fahrenheit.
double celsius_to_fahrenheit(double c) {
    return c * 9.0 / 5.0 + 32.0;
}

int main() {
    std::println("{} C = {} F", 0.0, celsius_to_fahrenheit(0.0));
    std::println("{} C = {} F", 100.0, celsius_to_fahrenheit(100.0));
    std::println("{} C = {} F", 37.0, celsius_to_fahrenheit(37.0));
    std::println("{} C = {} F", -40.0, celsius_to_fahrenheit(-40.0));
    return 0;
}

0 C = 32 F
100 C = 212 F
37 C = 98.6 F
-40 C = -40 F

The constants are written 9.0 and 5.0, not 9 and 5, for the reason you learned in chapter 2: 9 / 5 is integer division and gives 1. Inside a function the arithmetic rules are exactly the same as outside; a function is not a different language, only a named piece of the same one.

print_row: a loop inside a void function

This one prints width copies of a character on one line. It is one step away from what render in life.hpp does for each row of the grid (render builds text instead of printing, but the loop is the same). It takes two parameters of different types, an int and a char, and returns nothing.

#include <print>

// Print `width` copies of `ch` on one line, then end the line.
void print_row(int width, char ch) {
    for (int i = 0; i < width; ++i) {
        std::print("{}", ch);
    }
    std::println("");
}

int main() {
    print_row(10, '#');
    print_row(10, '.');
    print_row(3, '*');
    print_row(0, '!');          // zero copies: just an empty line
    print_row(10, '#');
    return 0;
}

max_of: two inputs, pick one

A function that chooses between its inputs. The if handles one case and returns; the normal case is the last line, the same early-return layout as clamp. Watch the last call in main: it feeds the result of one max_of into another, just as square(square(2)) did.

#include <print>

// The larger of a and b. (If they are equal, either one.)
int max_of(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}

int main() {
    std::println("max_of(3, 8)   = {}", max_of(3, 8));
    std::println("max_of(8, 3)   = {}", max_of(8, 3));
    std::println("max_of(-2, -9) = {}", max_of(-2, -9));
    std::println("max_of(5, 5)   = {}", max_of(5, 5));
    std::println("largest of three: {}", max_of(max_of(4, 11), 7));
    return 0;
}

max_of(3, 8)   = 8
max_of(8, 3)   = 8
max_of(-2, -9) = -2
max_of(5, 5)   = 5
largest of three: 11

The last line shows a two-input function stretched to three inputs by nesting the calls: the largest of three is the largest of (the largest of two) and the third. The comment on the function says what happens when a == b. Comments on a function should state the cases the name does not make obvious; that is what the comments in life.hpp do.

area: counting with std::size_t

Not every quantity is an int. A count of things, such as the number of cells in a grid, can never be negative, and chapter 2 introduced std::size_t as the type for exactly that: an unsigned integer big enough to count every byte of memory. When a function's inputs and output are counts, say so in the signature.

#include <cstddef>
#include <print>

// Number of cells in a w-by-h grid. A count can never be negative,
// so the inputs and the result are std::size_t.
std::size_t area(std::size_t w, std::size_t h) {
    return w * h;
}

int main() {
    std::println("area(3, 2)       = {}", area(3, 2));
    std::println("area(80, 24)     = {}", area(80, 24));
    std::println("area(1000, 1000) = {}", area(1000, 1000));
    std::println("sizeof(std::size_t) = {} bytes", sizeof(std::size_t));
    return 0;
}

area(3, 2)       = 6
area(80, 24)     = 1920
area(1000, 1000) = 1000000
sizeof(std::size_t) = 8 bytes

The literal 3 in area(3, 2) is an int, and the parameter is a std::size_t. The compiler converts the argument to the parameter type at the call, the same way it converts when you write double d = 3;. For small positive literals that is harmless. The trap is a negative int variable: passed to a std::size_t parameter it silently turns into an enormous positive count, as chapter 2 showed with -1 becoming 18 billion billion. That is why the life.hpp contract keeps width and height as int. It converts them with static_cast<std::size_t> only at the one place where a size is actually needed. You will see that line in life.cpp's stub for random_cells, and chapter 6 explains the rest of it.

Functions built from functions

Once a function exists, other functions can call it. This is how small functions stay small: a bigger job is written as a few calls to smaller jobs. Here is_odd is defined in terms of is_even, and print_rect is now just "print height rows", using print_row.

#include <print>

bool is_even(int n) {
    return n % 2 == 0;
}

// Built out of is_even instead of repeating the arithmetic.
bool is_odd(int n) {
    return !is_even(n);
}

void print_row(int width, char ch) {
    for (int i = 0; i < width; ++i) {
        std::print("{}", ch);
    }
    std::println("");
}

// A rectangle is just `height` rows.
void print_rect(int width, int height, char ch) {
    for (int y = 0; y < height; ++y) {
        print_row(width, ch);
    }
}

int main() {
    std::println("is_odd(7) = {}", is_odd(7));
    std::println("is_odd(8) = {}", is_odd(8));
    print_rect(6, 2, '#');
    print_rect(4, 1, '=');
    return 0;
}

is_odd(7) = true
is_odd(8) = false

Compare this print_rect with the one at the start of the chapter. The nested loop is gone; the inner loop lives in print_row, and print_rect has one loop that reads as English. Each function trusts the one below it to do its one job.

return ends the function immediately

A return inside a loop stops the loop and the function in one go. This is useful for searches: as soon as you find what you want, hand it back and stop looking.

#include <print>

// The smallest number from 2 upwards that divides n. (n must be at least 2.)
int smallest_divisor(int n) {
    for (int d = 2; d < n; ++d) {
        if (n % d == 0) {
            return d;                 // found one: leave immediately
        }
    }
    return n;                         // nothing divided it: n is prime
}

int main() {
    std::println("smallest_divisor(15) = {}", smallest_divisor(15));
    std::println("smallest_divisor(49) = {}", smallest_divisor(49));
    std::println("smallest_divisor(13) = {}", smallest_divisor(13));
    return 0;
}

smallest_divisor(15) = 3
smallest_divisor(49) = 7
smallest_divisor(13) = 13

For 15 the loop runs with d = 2 (no), then d = 3 (yes) and returns 3 without ever trying 4 to 14. Compare with chapter 3's break, which only leaves the loop and then continues with whatever comes after it inside the function. return leaves everything.

Two warnings you will meet

Two mistakes with functions do not stop the compiler, but -Wall -Wextra flags them, and you should treat both as errors. You will meet the first one on day one of the challenge, because the stubs in life.cpp are written to avoid it.

Unused parameter

If a function takes a parameter and never uses it, the compiler suspects you forgot something. This program compiles, but with a warning:

#include <print>

int always_zero(int x) {
    return 0;
}

int main() {
    std::println("{}", always_zero(5));
    return 0;
}

unused_param.cpp:3:21: warning: unused parameter 'x' [-Wunused-parameter]
    3 | int always_zero(int x) {
      |                     ^
1 warning generated.

Usually the fix is to use the parameter, because you did forget something. But sometimes a function genuinely does not need one of its inputs yet, for example a stub you have not written. The idiom for "I know, this is deliberate" is (void)x;: an expression that evaluates x and throws the result away as a nothing. It generates no machine code; it exists only to silence the warning. Now open phase1-terminal/01-life/src/life.cpp and look at any stub, for instance:

int wrap(int v, int n) {
    // TODO(you): milestone 3 — careful with negative numbers
    (void)v;
    (void)n;
    return 0;
}

That is why the stubs compile cleanly before you have written anything. When you fill in the body and start using v and n, delete the (void) lines; they were scaffolding.

Missing return

A function with a non-void return type promises to return a value on every path through its body. Forget one path and the compiler warns:

#include <print>

int sign(int n) {
    if (n > 0) {
        return 1;
    }
    if (n < 0) {
        return -1;
    }
    // what if n is exactly 0?
}

int main() {
    std::println("{}", sign(7));
    return 0;
}

missing_return.cpp:11:1: warning: non-void function does not return a value in all control paths [-Wreturn-type]
   11 | }
      | ^
1 warning generated.
Trap

This warning is the most dangerous kind: the program compiles and may even appear to work. But calling sign(0) reaches the closing brace with no value to return, and that is undefined behaviour: the C++ rules say nothing about what happens next. The caller receives whatever garbage happens to be in the place where the result should have been. It might be 0 by luck today and 7 million tomorrow. With the sanitizer flags that tools/run.sh uses, calling sign(0) stops the program instead with runtime error: execution reached the end of a value-returning function without returning a value, which is the whole point of those flags. Fix the function, never the warning: add the missing return.

#include <print>

int sign(int n) {
    if (n > 0) {
        return 1;
    }
    if (n < 0) {
        return -1;
    }
    return 0;                         // the path that was missing
}

int main() {
    std::println("sign(7) = {}, sign(-2) = {}, sign(0) = {}", sign(7), sign(-2), sign(0));
    return 0;
}

sign(7) = 1, sign(-2) = -1, sign(0) = 0

Testing a function by hand

A function with a clear signature has a wonderful property: you can check it in isolation. Pick inputs whose correct answer you know, call the function, compare. You do not need the rest of the program to exist. For clamp you know by hand that clamp(-7, 0, 10) must be 0, so write that down as a check, and let the program tell you PASS or FAIL.

#include <print>

int clamp(int v, int lo, int hi) {
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

// Compare what clamp gave with what it should have given.
void check_clamp(int v, int lo, int hi, int expected) {
    int got = clamp(v, lo, hi);
    if (got == expected) {
        std::println("PASS  clamp({}, {}, {}) == {}", v, lo, hi, expected);
    } else {
        std::println("FAIL  clamp({}, {}, {}) gave {}, expected {}", v, lo, hi, got, expected);
    }
}

int main() {
    check_clamp(5, 0, 10, 5);        // inside the range: unchanged
    check_clamp(-7, 0, 10, 0);       // below: pushed up to lo
    check_clamp(123, 0, 10, 10);     // above: pushed down to hi
    check_clamp(0, 0, 10, 0);        // exactly on the edge
    check_clamp(10, 0, 10, 10);      // exactly on the other edge
    check_clamp(10, 0, 10, 9);       // a deliberately wrong expectation
    return 0;
}

PASS  clamp(5, 0, 10) == 5
PASS  clamp(-7, 0, 10) == 0
PASS  clamp(123, 0, 10) == 10
PASS  clamp(0, 0, 10) == 0
PASS  clamp(10, 0, 10) == 10
FAIL  clamp(10, 0, 10) gave 10, expected 9

The last check is wrong on purpose so you can see what a failure looks like: it names the call, the answer it got, and the answer it wanted. That is all the information needed to start debugging. Notice the choice of inputs: one ordinary case, one below, one above, and both edges exactly. Edges are where bugs live (remember <= versus < in the first program), so a good set of checks always includes them.

The checking itself is a function, check_clamp, so that the six checks are six readable lines rather than six copies of an if. This is the seed of chapter 12. The doctest library gives you a CHECK(clamp(-7, 0, 10) == 0) that does the comparing and the printing for you, for any function, and tests/life_test.cpp is a file of exactly such lines. You have just built the idea yourself, so the library will hold no surprises.

A habit to start today

Whenever you write a function, write three checks for it before you move on: a normal case, a zero or empty case, and an edge. It takes a minute and it catches most bugs while the function is still fresh in your mind. In chapter 14 the milestones are ordered so that you can do this for every contract function, one at a time.

Reading the Week 1 contract

You can now read phase1-terminal/01-life/src/life.hpp. Here are its declarations, with their comments, exactly as they appear in the file. This is a fragment, not a program, and it is not something to implement here; it is something to read. The implementing is the challenge itself, in your own life.cpp. Four things in it are ahead of you, so take them on trust: & until chapter 5, std::vector until chapter 6, using until chapter 7, and std::string until chapter 8. Everything else you can already read.

// A flat list of cells. (`using` gives a long type a short name.)
using Cells = std::vector<std::uint8_t>;

// The position in the flat vector of the cell at column x, row y.
//   index_of(0, 0, 10) == 0,  index_of(3, 2, 10) == 23
int index_of(int x, int y, int width);

// Wrap v into the range [0, n), like the hands of a clock.
//   wrap(-1, 10) == 9,  wrap(10, 10) == 0,  wrap(7, 10) == 7
int wrap(int v, int n);

// How many of the 8 neighbours of (x, y) are alive. The grid is a torus:
// the left edge touches the right edge, the top touches the bottom.
int count_neighbours(const Cells& cells, int width, int height, int x, int y);

// One generation of Life. Reads `current`, writes the result into `next`.
// Both vectors already have width*height cells. `current` is never modified.
//   Rules: a live cell with 2 or 3 live neighbours stays alive;
//          a dead cell with exactly 3 live neighbours becomes alive;
//          every other cell is dead in the next generation.
void step(const Cells& current, Cells& next, int width, int height);

// A random starting grid. Each cell is alive with probability `fill`
// (0.0 = all dead, 1.0 = all alive). The same seed must always give
// the same grid.
Cells random_cells(int width, int height, unsigned int seed, double fill);

// The grid as text, one row per line: '#' for alive, '.' for dead,
// and a '\n' after every row (including the last).
std::string render(const Cells& cells, int width, int height);

Take each signature as a sentence. Read the return type as "gives back a ...", the name as the verb or noun, and each parameter as "given a ...".

  • int index_of(int x, int y, int width); — Given a column, a row, and the grid width, all int, gives back an int: a position in the flat list. Three inputs of the same type, so order matters: x first, then y, then width. The comment's examples are the first checks you should write. Just like clamp and area, this is plain arithmetic in, arithmetic out, with no other effect; it is milestone 1 for a reason.

  • int wrap(int v, int n); — Given a value and a size, gives back the value folded into the range [0, n), that is 0 to n−1 inclusive. Same shape as clamp: a small int function with a few cases, one of which (negative v) is the trap the comment hints at. Chapter 7 teaches the arithmetic on a clock face.

  • int count_neighbours(const Cells& cells, int width, int height, int x, int y); — Gives back an int, a count from 0 to 8. The first parameter is new: const Cells&. Cells is the short name the using line gives to "a std::vector of bytes", a list of cells you will meet in chapter 6. The & makes it a reference, and the const says the function promises not to change it. Read const Cells& cells as "look at the caller's cells without copying them and without modifying them". Chapter 5 is entirely about these two words; for today, the promise is what matters: this function only reads the grid.

  • void step(const Cells& current, Cells& next, int width, int height); — Returns nothing, so its whole effect must be through its parameters, and the signature tells you which one. current is const Cells&: read only. next is Cells&, without const: a reference the function is allowed to write through. So step reads one grid and fills in the other. This is the one place in the contract where a function changes something that belongs to the caller, and it is the mechanism this chapter said pass-by-value could not do. Chapter 5 shows how. The comment also states the Life rules in words; chapter 7 and chapter 14 give you everything else you need.

  • Cells random_cells(int width, int height, unsigned int seed, double fill); — Gives back a whole Cells: this function creates a grid and returns it, the way square creates and returns a number. Four inputs of three different types: two ints for the shape, an unsigned int (an integer that cannot be negative) for the random seed, and a double between 0 and 1 for how full the grid should be. The comment's last sentence, "the same seed must always give the same grid", is a promise you will test. Randomness arrives in chapter 8.

  • std::string render(const Cells& cells, int width, int height); — Reads a grid (const, read-only again) and gives back a std::string: text, one character per cell plus a newline per row. Chapter 8 introduces std::string. The signature already tells you two things: render does not print (it returns the text, and main decides what to do with it), and it cannot alter the grid.

Six declarations, and you could read every one: what goes in, what comes out, which inputs may be changed. Two types (Cells, std::string) and one piece of syntax (&) are still ahead of you, but the shape of each promise is already clear.

First principle

A function's signature is a promise. The return type promises what comes back; each parameter type promises what is needed and, with const, whether it will be touched; the comment promises what the result means. The tests in tests/life_test.cpp are those promises written down as checks: CHECK(wrap(-1, 10) == 9) is the comment on wrap turned into a line the computer can verify. When your definitions keep every promise, every test is green. That is the whole of Week 1.

Inference twin

In an inference engine, a tensor is a grid of numbers (one, two or more dimensions), and a kernel is a function applied to every element of a tensor, or to every small neighbourhood of elements. step applies count_neighbours plus the Life rule to every cell of the grid; a convolution kernel applies a weighted sum to every 3×3 patch of an image; a GELU kernel applies one formula to every number in a layer. Same shape: a small, pure function with a clear signature, run across a flat array. ggml, the library under llama.cpp, is a few hundred such functions, each with a signature you can read exactly the way you just read life.hpp. Being able to read "takes a const view of the input, writes into the output, returns nothing" is being able to read ggml.

Check yourself

In int max_of(int a, int b), which parts are the return type, the name, and the parameter list? What is the signature?

Answer

Return type int; name max_of; parameter list (int a, int b), two int parameters named a and b. The signature is the whole line without a body: int max_of(int a, int b), meaning "takes two ints, returns an int".

A function void reset(int n) { n = 0; } is called as reset(lives); where lives is 3. What is lives afterwards, and why?

Answer

Still 3. The argument lives is copied into the parameter n; the function sets its own copy to 0 and then that copy is destroyed. Passing by value means the caller's variable cannot be changed. Chapter 5's references are the tool for changing it.

What is the difference between int cube(int x); and int cube(int x) { return x * x * x; }? How many of each may a program contain?

Answer

The first is a declaration (prototype): it tells the compiler the function exists and its signature. The second is a definition: it also provides the body. A program may contain as many identical declarations as it likes but exactly one definition. A declaration must appear before the first call; the definition can be anywhere, even in another file.

Why does this fail to compile, and what is the one-line fix without moving any code?

int main() {
    return twice(4);
}
int twice(int n) { return 2 * n; }
Answer

The compiler reads top to bottom and meets twice in main before it has seen any declaration of it: "use of undeclared identifier 'twice'". Add the prototype int twice(int n); above main. (The return value 8 would also become the program's exit code, which is legal but odd.)

Functions a and b each declare a local variable called total. a calls b. While b is running, how many variables called total exist, and where do they live?

Answer

Two, one in each stack frame: a's frame (paused, underneath) and b's frame (active, on top). They are different boxes with the same label and do not interfere. When b returns, its frame and its total disappear; a's is unchanged.

What does return 0; at the end of main actually do, and who reads the value?

Answer

It ends main, so the program, and hands the int 0 to the operating system as the exit code. 0 means success by convention; any other value means failure. The shell exposes it as $?, and tools such as ctest read it to decide whether a test program passed.

Read this declaration from life.hpp as a sentence: void step(const Cells& current, Cells& next, int width, int height);. Which parameter can the function change?

Answer

"step returns nothing; it is given read-only access to current, writable access to next, and the two int dimensions." Only next can be changed: it is a reference (&) without const. current is const, so the function promises not to modify it, and the ints are copies anyway. The test "step: does not modify current" checks exactly this promise.

The compiler says warning: non-void function does not return a value in all control paths. Why is this more serious than a typical warning?

Answer

Because reaching the end of a non-void function without a return is undefined behaviour: the caller receives an unpredictable value and the program may seem to work until it does not. The fix is to add the missing return for the forgotten path (often the "otherwise" case at the bottom), never to silence the warning.
