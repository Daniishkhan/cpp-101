How to read any error message

Before the tables, one skill that makes every row of them easier. A program can fail in four different places, and the first thing to decide when something goes wrong is which place you are in. Each place has its own voice.

StageWho speaksWhat the message looks likeWhen

The messages in the first row have a fixed shape, and once you can read it you can read all of them. Here is a complete program with one character missing, and what clang says about it.

#include <print>

int main() {
    int count = 3
    std::println("{}", count);
    return 0;
}

missing_semicolon.cpp:4:18: error: expected ';' at end of declaration
    4 |     int count = 3
      |                  ^
      |                  ;
1 error generated.

Read it piece by piece. missing_semicolon.cpp is the file. 4 is the line, 18 is the column (the character position on that line, counting from 1). error is the severity: an error stops the compiler from producing a program, a warning does not stop it but tells you something looks wrong. After the colon comes the message itself. Then clang reprints the line, puts a caret ^ under the place it was looking at when it gave up, and, when it can, suggests the fix on the line below: here, a ;. Finally it counts: 1 error generated.

Some messages are followed by lines that begin with note:. A note is not a second problem. It is extra information about the first one: "the previous definition is here", "candidate function not viable because...", "to match this {". Read the error, then read its notes, then stop. The second error in a list is often a consequence of the first (a missing brace confuses everything after it), so fix the first, recompile, and look again.

First principle

The compiler reads your file from top to bottom and reports the first place where what it read could not be C++. The location it gives is where it noticed, which is at or just after where you made the mistake. When a message points at a line that looks fine, look at the line above it.

Analogy

A compiler error is a proofreader's mark in the margin: page, line, what is wrong, and often the correction. The analogy breaks in one way that matters. A human proofreader marks every mistake on the page; the compiler, after the first real mistake, is guessing about what you meant, and its later marks can be wrong. Trust the first mark fully, the rest only after you have fixed the first.

Warnings deserve one more word, because this book compiles everything with -Wall -Wextra and asks you to keep the output empty. A warning means "this is legal C++ and I will build it, but programs that look like this are usually wrong". The sign-comparison warning and the uninitialised-variable warning in the tables below have each caused real bugs in real programs. Treat a warning as an error you are allowed to fix tomorrow, and then fix it today.

In square brackets at the end of a warning you will see the flag that turned it on, such as [-Wsign-compare]. You never need to type these; they tell you which family the warning belongs to, and they are what to search for if the message itself is unclear.

Try it

Take any working program from chapter 3 and break it on purpose, one change at a time: delete a semicolon, delete a closing brace, delete a closing quote, misspell a variable, remove an #include. Compile after each change and find the message in the tables below before you fix it. Ten minutes of deliberate breakage now saves an hour of panic later, because every message will already be one you have met.

Trap

A program with warnings still builds and runs, so it is tempting to ignore them. The three warnings most likely to be real bugs are the uninitialised variable, the missing return path and the assignment-in-condition: all three produce a program that seems to work on some runs. Keep the warning count at zero and these bugs cannot hide.

Linker errors

These appear after every file compiled cleanly. The linker's job (chapter 10) is to find, for every function that is called, exactly one definition. Here is the smallest program that fails at this stage: a function that is declared and called but never defined.

#include <print>

int twice(int n);   // a promise...

int main() {
    std::println("{}", twice(4));   // ...that nobody keeps
    return 0;
}

Undefined symbols for architecture arm64:
  "twice(int)", referenced from:
      _main in declared_not_defined-ed7dd2.o
ld: symbol(s) not found for architecture arm64
clang++: error: linker command failed with exit code 1 (use -v to see invocation)

Three things to notice. There is no file and line number, because the linker works on compiled object files, not source. The quoted name "twice(int)" is a symbol: the linker's word for a named function (or variable) that one object file needs and another must provide (chapter 10). It includes the parameter types, so a function with the same name but different parameters is a different symbol. And the referenced from: _main line tells you who was calling it. The random-looking letters and digits after declared_not_defined- in the .o name are a temporary tag that changes on every compile; ignore them.

Runtime: sanitizers and terminations

Everything in this table happens after a successful build, while the program runs. The Debug build of the Life project, and tools/run.sh, compile with -fsanitize=address,undefined, which adds two watchdogs to your program: AddressSanitizer (ASan), which checks every memory access against what was actually allocated, and UndefinedBehaviorSanitizer (UBSan), which checks arithmetic and a few other things the language leaves undefined. Without them the same bugs produce wrong numbers or random crashes with no explanation at all.

Analogy

The sanitizers are watchdogs: they sit beside your program and bark the moment it touches memory it does not own. The analogy breaks in two places. A watchdog is free; these are not: a Debug build with the sanitizers on runs several times slower (the timing section below shows a thirty-fold gap), which is why benchmarks are built without them. And they only bark at memory and arithmetic crimes. A step that applies the Life rules wrongly but stays inside the vector is perfectly legal C++, and no sanitizer will ever complain; that is what the doctest cases are for.

The ASan report is long; you only need its first three lines. Here is a program that reads one element past the end of a vector (the loop uses <= where it should use <), built with the sanitizers on. It is marked compile-only in the book because it deliberately fails when run.

#include <print>
#include <vector>

int main() {
    std::vector<int> v(4, 1);
    int sum = 0;
    for (std::size_t i = 0; i <= v.size(); ++i) {   // <= is the bug
        sum += v[i];
    }
    std::println("{}", sum);
    return 0;
}

Line one names the kind of bug: heap-buffer-overflow, an access outside a block of heap memory (a vector's cells live on the heap, chapter 6). Line two says what kind of access and how big: a READ of size 4, one int. Line three is the one you want: #0 ... in main overflow.cpp:8, the first line of the call stack, which is the line of your code that did it. The block after that says where the memory was allocated (overflow.cpp:5, the vector's construction) and how far outside it you were (0 bytes after 16-byte region: exactly one element past the end of a four-int vector, since 4 ints of 4 bytes make 16). After the summary comes a table of "shadow bytes" that you can ignore.

Two more details of that run. The sanitizer stops the program by aborting it: it asks the operating system to kill the process at once, and the operating system does so by sending it a signal, a one-number message that means "stop now". Abort is signal number 6. zsh reports a killed program as zsh: abort and gives it exit code 128 + 6 = 134; you will see the same 134 for the library termination further down, because that also aborts. And the -g flag is what puts file names and line numbers into the report. Without it the #0 line says only in main+0x258: a position inside the function, counted in bytes of machine code, with no file and no line number. tools/run.sh and the Debug build both pass -g for you.

Try it

Type overflow.cpp into scratch/ and run it three ways. First exactly as shown, with -g and the sanitizers: find the #0 line and the bytes after line. Second, drop -g but keep -fsanitize=...: the #0 line loses its file and line. Third, drop the sanitizer flags entirely: clang++ -std=c++23 -Wall -Wextra overflow.cpp -o overflow. On this Mac that build printed 7, three runs in a row, and exited 0 as if nothing were wrong: the four real ones plus a 3 that happened to be stored in the memory just past the vector. Built once more with -O2, the same file printed 0. Neither number is a bug in the compiler; reading past the end is undefined behaviour, so any answer is permitted, and the optimiser took the liberty. That silent wrong number is what every out-of-bounds read looks like in a Release build, and it is the reason the Life project's Debug build keeps the sanitizers on.

UBSan reports are one line, and they point directly at the expression.

#include <print>
#include <vector>

int main() {
    std::vector<int> v(2, 2147483647);   // the largest int, twice
    int total = v[0] + v[1];              // does not fit in an int
    std::println("{}", total);
    return 0;
}

$ tools/run.sh signed_overflow.cpp

Inference twin

Every one of these runtime messages will reappear in week 15, when the vector of cells becomes a tensor of floats. An out-of-bounds read in a matrix multiply is the same heap-buffer-overflow with a different file name, and a stride computed in the wrong order is the same swapped x * width + y. Learn to read the #0 line now and you will never fear the long version.

CMake, Ninja and ctest

Build-system messages come from three programs: cmake when you configure, ninja when you build (even when you type cmake --build, it is Ninja doing the work), and ctest when you run tests. Two words from chapter 11 appear in several rows. The generator is the build tool CMake writes its files for; -G Ninja picks Ninja. The cache is the file build/CMakeCache.txt, where CMake remembers every choice it made while configuring: which compiler, which generator, which build type, and the absolute path of the folder it was in. Most of the confusing rows below are the cache remembering something that is no longer true.

The universal CMake fix

Nearly every confusing CMake state is cured by rm -rf build followed by the configure command. The build folder contains nothing you wrote; it is entirely regenerated from CMakeLists.txt and your sources. If you are unsure whether a problem is a stale cache, delete the folder first and see whether the message survives.

Every term the book has bolded, in alphabetical order, one sentence each. Chapter numbers in brackets say where the term is taught properly.

A short sequence of bytes starting with \x1b[ that a terminal reads as a command (clear the screen, move the cursor) instead of printing it. (9)

A keyword that asks the compiler to work out a variable's type from its initialiser; the type is still fixed, you just did not have to write it. (2)

A program that times one operation on a fixed input so you can compare numbers before and after a change. (13)
bool
The type with exactly two values, true and false; conditions in if and loops are bools. (2)

The tool that reads CMakeLists.txt and generates a build for Ninja; you run it once to configure, then cmake --build as often as you like. (11)

The program (clang here) that translates one C++ source file into machine code for the CPU, producing an object file. (1)
const
A promise, checked by the compiler, that a variable or a reference will not be used to change the value. (2, 5)

Stored in one unbroken run of memory with no gaps, as the elements of a std::vector are; this is why v[i] is one multiplication and one addition. (6)

A line that introduces a name and its type without giving the body or the value, such as int wrap(int v, int n);. (4, 10)

The 8-byte floating-point type for numbers with a fractional part, such as 0.35. (2)

How a library function such as std::stoi reports "I cannot do this" when it has no sensible value to return; unhandled, it ends the program with a libc++abi: terminating message. Taken on trust this week; taught in a later week. (8)

The whole number a program hands back to the shell when it ends: return 0; from main means success, anything else means failure, and echo $? shows the last one. (1, 8)

To push buffered output to its destination now rather than waiting for a newline or program exit; std::fflush(stdout). (9)

One complete picture of the grid drawn to the terminal; the game loop draws one frame per generation. (9)

The block of memory a function gets for its local variables while it runs; it is released when the function returns. (4)

A named block of code with parameters and a return type that you can call from elsewhere; the unit of reuse. (4)

A .hpp file containing declarations, pasted into each source file that #includes it. (10)

The large pool of memory a program asks for while running, where a vector keeps its elements; its size is decided at run time. (6)

A name you chose: a variable, a function, a type alias. (1)

A line that tells the compiler to paste another file here before compiling. (1, 10)

Giving a variable its first value at the moment it is created; an uninitialised int holds garbage. (2)
int
The 4-byte signed whole-number type, holding roughly -2.1 billion to +2.1 billion. (2)
kernel
In inference, a small function applied at every position of a tensor; the Life step is a 3 by 3 kernel. (4, 7, goal.md)
linker
The program that joins object files into one executable, matching every call to exactly one definition. (10)
literal
A value written directly in the code: 42, 0.5, '#', "hello", true. (2)

A statement that repeats a block: for when you know how many times, while when you know the stopping condition. (3)

The function where every program starts; it returns an int that becomes the exit code. (1)

The middle value of a sorted list of measurements; more honest than the mean when one run was disturbed. (13)

The remainder operator %; in C++ the result takes the sign of the left operand, so -1 % 10 is -1, not 9. (2, 7)

A named group of names; everything from the standard library lives in std, hence std::vector. (1)
Ninja
The fast build tool that actually runs the compiler commands CMake generated. (11)
object file
The .o output of compiling one source file: machine code plus a list of names it defines and names it needs. (10)
optimisation
The compiler rewriting your program to run faster without changing what it computes; -O2 or -O3 (CMake's Release type uses -O3), off in Debug. (11, 13)
parameter
A variable in a function's declaration that receives an argument when the function is called. (4)
#pragma once
The first line of every header; it makes a second #include of the same header in one file do nothing. (10)
PRNG
Pseudo-random number generator: a formula that produces a sequence that looks random but is completely determined by its seed; std::mt19937. (8)
range-for
for (int x : v): a loop over every element of a container without an index. (6)
reference
Another name for an existing variable, written T&; passing by reference avoids copying and lets a function change the caller's variable. (5)
row-major
Laying a grid out row after row in memory, so moving one step right is one element and one step down is width elements. (7)
sanitizer
A checker compiled into your program by -fsanitize=... that turns memory errors and undefined behaviour into readable reports. (11)
scope
The region of code where a name is visible, bounded by braces; a variable is destroyed at the end of its scope. (4)
seed
The starting number of a PRNG; the same seed always gives the same sequence, which is what makes a random grid reproducible. (8)
signal
A one-number message the operating system sends a running program, such as "stop now"; Ctrl+C sends one, and abort is number 6, which is why an aborted program exits with 128 + 6 = 134. (15)
signed / unsigned
Whether a whole-number type can be negative (int) or not (std::size_t, unsigned int); mixing them is the source of the sign-compare warning. (2)
std::size_t
The unsigned type used for sizes and indexes; v.size() returns it. (2, 6)
stack
The region of memory where local variables and function frames live; fast, automatic, and small. (4)
statement
One complete instruction, ending in ; or a brace block. (1)
std::string
A growable sequence of characters you can append to with +=, index with [] and compare with ==. (8)
stdout
Standard output: the byte stream your program writes to, normally connected to the terminal. (9)
stencil
A fixed pattern of neighbouring positions that an operation reads for each cell; Life's is the 3 by 3 square minus the centre. (7)
stride
How many elements you skip in memory to move one step along a dimension; in a row-major grid the row stride is width. (7)
symbol
The linker's word for a named function or variable that one object file needs and another must define; "twice(int)" in an Undefined symbols message is one. (10)
template
The mechanism that lets one recipe such as std::vector work for any element type (std::vector<int>, std::vector<std::uint8_t>); you use it this week and learn how it works in week 8. (6, week 8)
tensor
A flat array plus a shape (and strides) that describes how to read it as multi-dimensional; a Life grid is a 2D tensor of bytes. (7, goal.md)
TEST_CASE
The doctest macro that defines one named test; the tests in life_test.cpp are thirteen of these. (12)
torus
A grid whose left edge touches its right edge and whose top touches its bottom, so every cell has exactly eight neighbours. (7)
translation unit
One .cpp file after all its #includes have been pasted in: the thing the compiler actually compiles. (10)
type
What kind of value a variable holds and how many bytes it takes; the compiler uses it to decide what every operation means. (2)
std::uint8_t
An unsigned 1-byte whole number, 0 to 255; the Life grid uses it for cells so a million cells are a million bytes. (2)
undefined behaviour
Anything the C++ standard says a program must not do, with no promise about what happens if it does: out-of-range index, signed overflow, reading an uninitialised variable. (2, 6)
variable
A named piece of memory of a known type that holds a value. (2)
std::vector
The growable, contiguous array of the standard library; std::vector<int> v(n, 0) makes n zeros. (6)
warm-up
Running the operation a few times before timing it so that caches are filled and the measurement reflects steady state. (13)
warning
A compiler message about legal but suspicious code; this book keeps the count at zero. (1)
wrap
Bringing a coordinate back into range on a torus: -1 becomes width - 1, width becomes 0. (7)
zero-based
Counting positions from 0, so a vector of 10 elements has indexes 0 to 9 and v[10] is outside it. (6)

Command-line arguments

The pattern chapter 8 taught, as a complete program: flags come in pairs, the loop steps by two, and a wrong flag ends the program with a non-zero exit code.

#include <print>
#include <string>

int main(int argc, char* argv[]) {
    int width = 80;
    int height = 24;
    unsigned int seed = 1;

    for (int i = 1; i + 1 < argc; i += 2) {         // argv[0] is the program name
        std::string flag = argv[i];
        std::string value = argv[i + 1];
        if (flag == "--width") {
            width = std::stoi(value);
        } else if (flag == "--height") {
            height = std::stoi(value);
        } else if (flag == "--seed") {
            seed = static_cast<unsigned int>(std::stoi(value));
        } else {
            std::println("unknown option: {}", flag);
            return 1;
        }
    }
    std::println("width={} height={} seed={}", width, height, seed);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra args.cpp -o args
$ ./args
width=80 height=24 seed=1
$ ./args --width 40 --seed 7
width=40 height=24 seed=7
$ ./args --wdith 40

$ echo $?

Read the loop condition before you copy it. i + 1 < argc means "there is a flag at i and a value after it". That protects argv[i + 1] from reading past the end of the argument list, which would be the same out-of-bounds bug as reading past a vector.

Trap

Two inputs that this program handles in ways you may not want. Run ./args --width with no value: the loop condition is false on the first round, so the flag is silently ignored and the program prints the defaults and exits 0. Run ./args --width eighty: std::stoi cannot convert it and the program aborts with libc++abi: terminating due to uncaught exception of type std::invalid_argument: stoi: no conversion (exit code 134). Both are real outputs from this machine. Neither is a crash of your making, but neither is a friendly message either. Chapter 14 asks you to decide, in milestone 5, what your main should do about a lone flag and about a width of 0.

Timing with chrono

The complete pattern from chapter 13, timing a loop over a million cells. Your number will differ; that is the point of measuring.

#include <chrono>
#include <print>
#include <vector>

int main() {
    std::vector<int> cells(1000 * 1000, 1);

    const auto start = std::chrono::steady_clock::now();
    long long sum = 0;
    for (std::size_t i = 0; i < cells.size(); ++i) {
        sum += cells[i];
    }
    const auto end = std::chrono::steady_clock::now();

    const double ms = std::chrono::duration<double, std::milli>(end - start).count();
    std::println("sum = {}", sum);
    std::println("took {:.3f} ms", ms);
    return 0;
}

$ tools/run.sh scratch/timing.cpp                              # Debug flags: sanitizers on, no optimisation
sum = 1000000
took 7.858 ms
$ clang++ -std=c++23 -Wall -Wextra -O2 scratch/timing.cpp -o timing && ./timing   # Release flags
sum = 1000000
took 0.240 ms

Those two runs are the same program on the same machine, about thirty times apart (another run of the same pair gave 8.1 ms and 0.15 ms, fifty times apart; the gap is large and it is not a constant). The first number is what a Debug build costs: no optimisation, plus the sanitizers checking every cells[i]. That is why life_bench is built from build-release.

Three habits from chapter 13 go with it. Build in Release before you believe a number: -O2 by hand, or CMake's Release type, which uses -O3; either way, no sanitizers. Run a few warm-up iterations first, as bench_life.cpp does with its 3 warm-up steps. And time many repetitions and divide (bench_life.cpp times 20 steps), or take the median of several runs, rather than trusting one measurement.

Further reading

Short on purpose. Each of these is worth your time this week or next; everything else can wait until the book asks for it.

cppreference.com

cppreference.com is the reference every C++ programmer has open. It is written for people who already know C++, so here is how to read a page without drowning. Search for the name (for example std::vector::at). At the top is the signature: the function's declaration, often in several numbered versions; you want the simplest one. Below it, Parameters says what each argument means, Return value says what you get back, and Exceptions says how it fails (this is where "std::out_of_range" for .at() comes from). The small grey labels need decoding. "(since C++11)" or "(since C++20)" means the feature was added in that version; your compiler is C++23, so everything marked "since" applies to you and you can ignore the label. "(until C++20)" or "(deprecated)" means the opposite: that version of the feature was removed or is on its way out, so skip those lines. Scroll to the bottom: nearly every page ends with a complete Example program and its output, which is often the fastest way to understand the function. Pages you will actually use this week: std::vector, std::string, std::stoi, std::mt19937, std::uniform_real_distribution, std::chrono::steady_clock, std::println.

learncpp.com

learncpp.com is a free, careful, very long tutorial, and a good second explanation when one of this book's chapters did not land. It is organised in numbered chapters whose numbers shift between revisions, so look for titles: "C++ Basics" and "Fundamental Data Types" cover chapter 2; "Control Flow" covers chapter 3; "Functions" and "Scope, Duration, and Linkage" cover chapter 4 and chapter 10; "Compound Types: References and Pointers" (read only the reference lessons) covers chapter 5; "Dynamic arrays: std::vector" covers chapter 6. Its sections on std::cout use an older printing style than std::println; the ideas are the same. Skip its pointer and class lessons for now.

A Tour of C++, Bjarne Stroustrup

Written by the language's designer, the third edition (C++20) is short and dense. Read chapter 1, "The Basics", and chapter 2, "User-Defined Types", at the end of this week: the first will feel like a brisk review, the second is a preview of weeks 3 and 4. Chapter 12, "Containers", explains std::vector and its relatives (including the std::deque you meet next week) with exactly the right amount of detail. Do not try to read the whole book now; it is a tour, meant to be returned to.

CppCon "Back to Basics" talks

CppCon is the largest C++ conference and every talk is free on its YouTube channel. Its "Back to Basics" track is made for exactly your position: an hour on one fundamental, by a good explainer. Search the channel for "Back to Basics" plus a topic. Good ones for this week: The Structure of a Program (Bob Steagall, 2020) on declarations, definitions and translation units; Compiling and Linking (Ben Saks, 2021) for everything in chapter 10; and Debugging Techniques (Mike Shah, 2021) for sanitizers and the debugger you pick up in week 3. One talk per evening is plenty.

LifeWiki

conwaylife.com/wiki catalogues thousands of Game of Life patterns with animations. Once your step is green, look up the Glider (five cells that walk diagonally forever), the R-pentomino (five cells that take 1103 generations to settle), and the Gosper glider gun (the first pattern proved to grow without bound). The Block and Blinker your tests use are there too. Typing a pattern into your grid by hand and watching it behave as the wiki says is a better acceptance test than any CHECK.

What week 3 brings (Snake)

The row for week 3 in goal.md lists the C++ you learn next. Each item below is one paragraph of preview, not teaching; the point is that you recognise the names when the week-3 book uses them, and see that each one fixes a limitation you felt this week.

struct. This week every function took cells, width, height as three separate parameters, and you had to keep them consistent by hand. A struct bundles related variables into one new type with named parts: a Grid with .cells, .width and .height, or a Point with .x and .y. The snake's body is a list of Points. You will pass one thing instead of three, and the compiler will stop you mixing up a width with a height.

enum class. The snake moves Up, Down, Left or Right. You could use the numbers 0 to 3, but then direction = 7 compiles and means nothing. An enum class is a type whose only values are the names you list, so Direction::Up is legal and 7 is not. It is the tool for "one of a fixed set of choices", and it goes with switch, a cleaner if/else if chain for exactly that situation.

std::deque. A snake grows at the head and shrinks at the tail. With std::vector, removing the first element means shifting every other element down by one, every tick. std::deque (double-ended queue) is a container that is cheap at both ends: push_front, pop_back, still indexable with []. Same vocabulary as vector, different costs: what is cheap in one is expensive in the other. Choosing a container by what it makes cheap is a skill the whole curriculum builds.

RAII and the terminal guard. You saw this week that an interrupted animation leaves the cursor hidden. Next week the program also switches the terminal into raw mode (keys arrive instantly, without waiting for return), and leaving the terminal in that state is much worse than a hidden cursor. RAII (resource acquisition is initialisation) is the C++ idea that cleanup belongs in a type: a RawTerminal object switches the mode on when it is created and switches it back in its destructor, a function that runs automatically when the object goes out of scope, however the scope is left. It is the first thing in C++ that will feel like it is looking after you.

Raw-mode input. Reading a key press in a normal terminal is impossible: the terminal collects a whole line and hands it over only when you press return. Raw mode turns that off. It is switched on with a few system calls, which are requests your program makes directly to the operating system, the same way std::println ultimately asks the operating system to write bytes. A non-blocking read then lets the game loop ask "was a key pressed?" and get an immediate answer, yes or no, instead of waiting until one is. This is the week you learn what a terminal is on the input side, having learned the output side in chapter 9.

std::optional. "Was a key pressed?" has two kinds of answer: a key, or no key. Returning a special value such as -1 works until -1 is a real answer. std::optional<char> is a type that holds either a char or nothing, and makes you check which before you use it. It is the honest return type for every "maybe" function, and it reappears in week 5 and again in the inference engine.

Inference twin

goal.md gives week 3 its twin: the game loop is a decode loop. One update per tick with a fixed time budget, and a tick that overruns is a dropped frame, exactly as a token that takes too long is a latency spike. The frame-timing code from chapter 9 is the piece you carry forward unchanged.

Check yourself

A message begins Undefined symbols for architecture arm64:. Which of the four stages failed, and what does that tell you about your source files?

Answer

The linker (stage 2). Every file compiled, so the syntax and the types are fine; a function that is called somewhere has no definition in any of the files that were compiled. Either you have not written it yet, or the file that contains it was not passed to the compiler or listed in add_executable.

clang reports error: expected ';' at end of declaration on line 12, but line 12 looks correct. Where is the mistake?

Answer

On line 11 (or the nearest non-empty line above). The compiler notices a missing semicolon only when it reads the next token, which is on the following line. The caret is placed where it noticed, not where you forgot.

An AddressSanitizer report is forty lines long. Which single line do you read first, and what does 0 bytes after 16-byte region mean for a std::vector<int>?

Answer

The #0 ... in main file.cpp:LINE line under READ of or WRITE of: it is the line of your code that touched the bad address. A 16-byte region is four ints, and "0 bytes after" means you used index 4 in a vector of size 4: exactly one past the end.

Your program ends with libc++abi: terminating due to uncaught exception of type std::invalid_argument: stoi: no conversion. Name two ways that happens in a program that parses --width 80 --seed 7.

Answer

Either the user typed a non-number (--width eighty), or your loop is off by one and you called std::stoi on a flag such as "--seed" instead of on the value after it. Printing argv[i] before converting shows which.

Why does the warning comparison of integers of different signs deserve a fix rather than a shrug?

Answer

Because a signed int that is negative is converted to unsigned before the comparison and becomes an enormous positive number, so i < v.size() is false when you expected it to be true (or the other way round). The loop then does the wrong number of iterations silently. Use std::size_t for the counter.

CMake says The current CMakeCache.txt directory ... is different than the directory ... where CMakeCache.txt was created. What did you do, and what is the fix?

Answer

You moved or copied the project (or the build folder) after configuring; the cache stores absolute paths. Delete the build folder and run the configure command again. Nothing you wrote lives in the build folder.

You run ./args --width (from the command-line cheat sheet) with no value after the flag. What is printed, what is the exit code, and why?

Answer

width=80 height=24 seed=1 and exit code 0. The loop condition i + 1 < argc is 2 < 2, which is false, so the body never runs and the lone flag is silently skipped. Nothing crashed, but nothing told you either; your own main should probably print a message and return 1 in that case.

Without looking: in the glossary sense, what is the difference between a declaration and a definition, and which one belongs in a header?

Answer

A declaration introduces the name and its type (int wrap(int v, int n);); a definition also provides the body or the storage. Headers hold declarations, so that many files can include them; each definition lives in exactly one .cpp, or the linker reports a duplicate symbol.
