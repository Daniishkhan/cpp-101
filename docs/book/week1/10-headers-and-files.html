The problem: four programs, one set of functions

Every program you have written so far was one file. It had a main, some functions above it, and you compiled it with one command. For a program that fits on two screens that is exactly right. Week 1's challenge does not fit that shape, and it is worth seeing precisely why before learning the tools that fix it.

Look at the challenge folder, phase1-terminal/01-life/. Near the bottom of its CMakeLists.txt are three lines (chapter 11 explains the whole file; for now read only these three, which name the programs and the files each one is made from):

add_executable(life       src/main.cpp        src/life.cpp)
add_executable(life_tests tests/life_test.cpp src/life.cpp)
add_executable(life_bench bench/bench_life.cpp src/life.cpp)

Three programs are built from this one folder: life, the game you watch; life_tests, which checks your six functions against 13 test cases; and life_bench, which times step on a 1000 by 1000 grid. All three need the same functions: index_of, wrap, count_neighbours, step, random_cells, render. If each program were a single file, those six functions would exist in three copies, and you already know from chapter 4 what three copies do: a fix in one copy is a bug kept in the other two. The tests would be testing a different step from the one the game runs.

There is a second problem. Each of the three programs has its own main: the game's main runs the animation, the test program's main runs the tests, the benchmark's main runs the stopwatch. A program may have exactly one main. So the test program cannot simply swallow the game's file whole; it needs the six functions without the game's main. The functions and the main have to live in different files.

And a third, quieter problem. Compiling is not free. Here are real timings from this machine for the small two-file project you will build later in this chapter. The shell's time command runs whatever follows it and then prints how long it took; the number to read is the last one, total, in seconds. The -c flag and the .o files are explained in the section on object files below; for now, each command compiles one file.

$ time clang++ -std=c++23 -Wall -Wextra -c main.cpp -o main.o
clang++ -std=c++23 -Wall -Wextra -c main.cpp -o main.o  0.23s user 0.02s system 98% cpu 0.255 total
$ time clang++ -std=c++23 -Wall -Wextra -c shapes.cpp -o shapes.o
clang++ -std=c++23 -Wall -Wextra -c shapes.cpp -o shapes.o  0.01s user 0.01s system 85% cpu 0.017 total

A quarter of a second for a nine-line main.cpp, against two hundredths of a second for shapes.cpp. The difference is that main.cpp pulls in <print>, which is enormous (you will measure it in a moment), and shapes.cpp does not. Real projects have hundreds of files and take minutes to compile from scratch. If you change one line in one file, you want to recompile that file and nothing else. That is only possible if the program is split into pieces that are compiled separately and joined afterwards.

So the shape you need is: the six functions in one file, compiled once; three different main files; and a way for each main to call functions that live in a file it cannot see. The rest of this chapter is that machinery.

What #include really does

You have typed #include <print> at the top of every program since chapter 1, on trust. Time to cash the trust in. Make a folder for this chapter's experiments, scratch/ch10, and put two files in it. First a header file, greet.hpp: a file meant to be included by other files, never compiled on its own. It holds one declaration of the kind you wrote in chapter 4. Take its first line, #pragma once, on trust until the section with that name below; every header starts with it.

#pragma once
// greet.hpp — one declaration.

int twice(int x);

Then main.cpp, which includes it with quotes instead of angle brackets (the difference is explained shortly). Its main returns twice(2) instead of 0 only so that the file contains a call to look at; nobody is going to run it.

#include "greet.hpp"

int main() {
    return twice(2);
}

Do not build it. There is no body for twice anywhere, so building would fail with an error you meet later in this chapter. Instead, ask the compiler to stop early and show you what it would compile. The flag -E runs only the first stage of compilation and prints the result. Without -P that result begins with a dozen lines like # 1 "main.cpp", markers that record which file each line came from; -P leaves them out so the result is readable:

$ clang++ -std=c++23 -E -P main.cpp
int twice(int x);

int main() {
    return twice(2);
}

The line #include "greet.hpp" is gone, and in its place is the text of greet.hpp (minus its comments, which are thrown away at this stage, and minus the #pragma once line, which has done its job). That is the whole truth about #include: it is copy and paste. The compiler has a first stage called the preprocessor, which reads your file top to bottom and, every time it meets #include, opens the named file and pastes its contents right there. Lines that start with # are instructions to this first stage, not C++ at all. The C++ compiler proper never sees #include; it only ever sees one long pasted-together text.

That long text has a name: a translation unit. It is one .cpp file plus everything it includes, after pasting, and it is the thing the compiler actually compiles. One .cpp file in, one translation unit out.

Now see how big the paste can get. Copy the six-line hello program from chapter 1 into scratch/ch10/hello.cpp, run the same command on it, and count the lines. wc -l counts the lines it is given; the | hands the compiler's output to it instead of printing it on screen.

$ clang++ -std=c++23 -E hello.cpp | wc -l
   44451
$ clang++ -std=c++23 -fsyntax-only -H hello.cpp 2>&1 | grep -c '^\.'
728

Your six-line program became 44,451 lines. The second command counts files instead of lines: -H makes the preprocessor print the name of every file it opens, one per line, each starting with a dot; -fsyntax-only says "check the code but do not produce a program"; grep -c '^\.' counts the lines that start with a dot. (The 2>&1 is shell plumbing: the compiler prints that list on its error channel, and this sends the error channel to the same place as normal output so that grep can read it. Take it on trust.) The answer: the single #include <print> opened 728 files. That is where the quarter of a second goes, and that is why compiling shapes.cpp, which includes only a short header of its own, takes almost no time. Every .cpp file pays for its own includes.

First principle

A header is not a separate thing the compiler "knows about". It is text that gets pasted into every file that includes it. Anything you can conclude about pasting, you can conclude about headers: paste the same text twice and you get it twice; paste it into five files and each of the five contains it; change the header and every file that includes it has changed, so every one of them must be recompiled.

Declaration and definition, now across files

In chapter 4 you learned the difference between a declaration and a definition. A declaration, int twice(int x);, tells the compiler the function exists and what its signature is (the return type, the name, and the parameter types). A definition, int twice(int x) { return 2 * x; }, also supplies the body. The rule was: the compiler reads top to bottom, and a call must come after a declaration. You used that to put main first and the definitions below it.

Now notice what the compiler needs to compile the call twice(2) in main. It needs to know that twice takes one int and returns an int, so it can check the argument and the result. That is all. It does not need the body. It translates the call into machine code that says "put 2 in the usual place, jump to wherever twice is, use whatever comes back", and leaves a note: "the address of twice goes here, to be filled in later".

That is the trick that lets a program live in several files. The declaration is enough to compile a call. The definition is only needed to run it, and it can sit in a different translation unit, compiled separately, as long as somebody eventually fills in the note. The somebody is the linker, and you will watch it work in a few pages.

So a C++ project splits each piece of functionality into two files with two jobs:

  • A header file, ending in .hpp, holds the declarations and the comments that say what each function promises. It is pasted into every file that wants to call those functions. It is the promise.
  • A source file, ending in .cpp, holds the definitions: the bodies. It is compiled exactly once. It is the work.
Analogy

A header is a restaurant menu; the source file is the kitchen. Any number of customers can read the menu, and a customer can order "twice of 2" without ever seeing how it is cooked. There is one kitchen, and if the recipe changes the menu does not have to. The analogy breaks in one place: a menu is read by people who can cope with a missing dish, but the compiler is not forgiving. If a function is on the menu (declared), somebody orders it (calls it), and no kitchen (definition) exists anywhere, the program cannot be built at all, and the error comes from the linker, not the compiler, with a message you will learn to read below.

The file ending is a convention, not a rule the compiler enforces. You will see .h for headers in C and older C++ (ggml uses ggml.h), and .cc or .cxx for sources. This book uses .hpp and .cpp, like the Life project. What matters is the job: a header is included, a source is compiled.

Quotes versus angle brackets

You have now seen both #include <print> and #include "greet.hpp". The two spellings tell the preprocessor where to look for the file.

  • #include "name": look first in the folder of the file doing the including. If it is not there, look in any folders given on the command line with -I (you will meet that flag below), and finally in the system folders. Use this for your files.
  • #include <name>: skip the including file's folder and go straight to the -I folders and the system folders where the toolchain keeps the standard library. Use this for the toolchain's files: <print>, <vector>, <string>, <chrono>.

The convention is simple to remember: quotes for headers you wrote, angle brackets for headers you installed. The compiler will tell you if you get it backwards. Copy main.cpp to angle.cpp in the same folder and change its first line to #include <greet.hpp>, so that it asks for a header sitting right next to it with the wrong brackets:

$ clang++ -std=c++23 -Wall -Wextra angle.cpp -o angle
angle.cpp:1:10: error: 'greet.hpp' file not found with <angled> include; use "quotes" instead
    1 | #include <greet.hpp>
      |          ^~~~~~~~~~~
      |          "greet.hpp"
1 error generated.

The compiler found the file after all, in the including file's folder, and tells you exactly which spelling would have found it: the last line of the message, "greet.hpp", is the suggested replacement. Now the plain typo. Copy main.cpp to typo.cpp and misspell the header as "gret.hpp":

$ clang++ -std=c++23 -Wall -Wextra typo.cpp -o typo
typo.cpp:1:10: fatal error: 'gret.hpp' file not found
    1 | #include "gret.hpp"
      |          ^~~~~~~~~~
1 error generated.

Note the word fatal, which the first message did not have. The first time, the preprocessor knew what you meant and carried on. This time no such file exists anywhere, the paste cannot happen, and the preprocessor stops on the spot. A fatal error is therefore always the first and only error you see, no matter what else is wrong in the file; fix it, compile again, and only then will you learn about anything else.

#pragma once

Pasting has a consequence that bites every beginner once. Headers include other headers: main.cpp includes a.hpp and b.hpp, and b.hpp itself includes a.hpp because it needs something from it. Pasting is literal, so a.hpp lands twice in the same translation unit. Whether that matters depends on what is in a.hpp. Build the case where it matters, in a new folder scratch/ch10/banner.

A header holding two named constants (chapter 2's const int), deliberately without the #pragma once line that would protect it:

// grid_size.hpp — the default grid size, shared by several files.
// (No #pragma once yet. Watch what happens.)

const int default_width = 60;
const int default_height = 20;

A second header that needs those constants, and so includes the first:

// banner.hpp — needs the grid size, so it includes grid_size.hpp itself.
#include "grid_size.hpp"

// Print a line like "grid: 60 x 20".
void print_banner(int width, int height);

And a main.cpp that, quite reasonably, includes both: it uses the constants directly and calls print_banner. (To keep this experiment to one translation unit, the definition of print_banner is here too.)

#include "grid_size.hpp"
#include "banner.hpp"
#include <print>

void print_banner(int width, int height) {
    std::println("grid: {} x {}", width, height);
}

int main() {
    print_banner(default_width, default_height);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra main.cpp -o main

In file included from ./banner.hpp:2:

main.cpp:1:10: note: './grid_size.hpp' included multiple times, additional include site here
    1 | #include "grid_size.hpp"
      |          ^

./grid_size.hpp:4:11: note: unguarded header; consider using #ifdef guards or #pragma once
    4 | const int default_width = 60;

(The same four messages repeat for default_height; they are cut here.) "In file included from main.cpp:2, in file included from banner.hpp:2" is the paste trail: main.cpp line 2 pasted banner.hpp, whose line 2 pasted grid_size.hpp. Then the error: default_width is being defined a second time. Then two notes pointing at both include sites, and a final note that names the fix.

To see why the compiler complains, look at what it saw. Run -E -P on this main.cpp, this time writing the result to a file with -o, and look at the first few lines:

$ clang++ -std=c++23 -E -P main.cpp -o pasted.cpp
$ head -6 pasted.cpp
const int default_width = 60;
const int default_height = 20;

const int default_width = 60;
const int default_height = 20;
void print_banner(int width, int height);
$ wc -l pasted.cpp
   30364 pasted.cpp

(Why a file and not | head? Because <print> makes the pasted text thirty thousand lines long, and if head closes the pipe after three of them, clang++ stops with a "Broken pipe" complaint and a long crash report. Writing to a file avoids the noise.) There they are: the two constants, twice. Put the rest of main.cpp under them and you have this complete single-file program, which fails the same way:

#include <print>

// What the compiler saw after pasting grid_size.hpp twice:
const int default_width = 60;
const int default_height = 20;
const int default_width = 60;
const int default_height = 20;

int main() {
    std::println("grid: {} x {}", default_width, default_height);
    return 0;
}

twice_defined.cpp:6:11: error: redefinition of 'default_width'
    6 | const int default_width = 60;
      |           ^
twice_defined.cpp:4:11: note: previous definition is here
    4 | const int default_width = 60;
      |           ^
twice_defined.cpp:7:11: error: redefinition of 'default_height'
    7 | const int default_height = 20;
      |           ^
twice_defined.cpp:5:11: note: previous definition is here
    5 | const int default_height = 20;
      |           ^
2 errors generated.

Nothing mysterious: two lines each create a constant called default_width, and a name can only be created once. The header did nothing wrong on its own; it was pasted twice, and that is what the compiler received.

The fix is one line at the top of the header:

#pragma once
// grid_size.hpp — the default grid size, shared by several files.

const int default_width = 60;
const int default_height = 20;

#pragma once is an instruction to the preprocessor: "if you have already pasted this file into the current translation unit, skip it this time." The second #include of the same file does nothing. Confirm it the same way you found the problem:

$ clang++ -std=c++23 -E -P main.cpp -o pasted.cpp
$ head -3 pasted.cpp
const int default_width = 60;
const int default_height = 20;
void print_banner(int width, int height);
$ clang++ -std=c++23 -Wall -Wextra main.cpp -o main
$ ./main
grid: 60 x 20

One pair of constants, one declaration, and the program compiles and runs. The rule is absolute: every header file starts with #pragma once as its first line. Not "headers that need it"; every header, always. It costs nothing and you never have to work out whether a particular header happens to be safe.

Why "happens to be safe"? Because some repetition is legal. A declaration may be repeated as often as you like; chapter 4 said so, and this complete program proves it:

#include <print>

int area(int w, int h);
int area(int w, int h);
int area(int w, int h);

int area(int w, int h) {
    return w * h;
}

int main() {
    std::println("{}", area(3, 3));
    return 0;
}

9

So a header that holds only function declarations survives being pasted twice by luck. The moment anything in it is a definition, a constant like default_width, or in week 3 a struct, the luck runs out. #pragma once means you never depend on luck.

Try it

Prove both halves of that claim in scratch/ch10/banner. First, take the #pragma once line out of grid_size.hpp again and replace its two constants with a single declaration, int default_width();. Change the call in main.cpp to print_banner(60, 20); so that it no longer needs the constants. Then run clang++ -std=c++23 -E -P main.cpp -o pasted.cpp and look at head -5 pasted.cpp: the declaration appears twice. Does clang++ -std=c++23 -fsyntax-only main.cpp (check the code, build nothing) accept it? Now add const int default_height = 20; under the declaration and check again. Finally put #pragma once back, because that is how the file should have been from the start.

Show the answer

With only the declaration, -fsyntax-only prints nothing at all: a repeated declaration is legal, exactly like twice_declared.cpp. With the constant added, you get error: redefinition of 'default_height', with the same "included multiple times" notes as before. The header went from "fine" to "broken" by one ordinary-looking line; that is why the rule is "every header, always" and not "headers that need it".

The older spelling

Open third_party/doctest/doctest.h and the first real line is #ifndef DOCTEST_LIBRARY_INCLUDED. That is the pre-#pragma once way to do the same thing, called an include guard: "if the name DOCTEST_LIBRARY_INCLUDED is not yet defined, define it and read the rest; otherwise skip to the matching #endif at the bottom." The lines #ifndef, #define and #endif are three more instructions to the preprocessor; you do not need to be able to write them this week, only to recognise the pattern. It works everywhere and does exactly what #pragma once does, at the cost of three lines and a name you must keep unique. Every compiler you will use understands #pragma once, so write that in your own headers and simply recognise the guard when you meet it in other people's code.

A three-file project

Now the real thing: a small program split the way Life is split. It is deliberately not Life. Make a folder scratch/ch10/shapes with three files.

The header. Declarations and comments only, and #pragma once first:

#pragma once
// shapes.hpp — what the shape functions promise. No bodies here.

// The area of a w-by-h rectangle, in cells.
int area(int w, int h);

// The distance around a w-by-h rectangle.
int perimeter(int w, int h);

The source file with the definitions. Its first include is its own header, for a reason explained at the end of the chapter:

// shapes.cpp — how the shape functions keep their promise.
#include "shapes.hpp"

int area(int w, int h) {
    return w * h;
}

int perimeter(int w, int h) {
    return 2 * (w + h);
}

And the program. It includes the header, so it knows the promises, and it never sees the bodies:

// main.cpp — the program. It only needs the promises.
#include "shapes.hpp"
#include <print>

int main() {
    std::println("a 4 by 3 rectangle: area {}, perimeter {}", area(4, 3), perimeter(4, 3));
    std::println("a 10 by 10 square:  area {}, perimeter {}", area(10, 10), perimeter(10, 10));
    return 0;
}

Building in one go

Give clang++ both source files. Not the header: headers are never on the command line, because they get pasted into the sources that include them.

$ clang++ -std=c++23 -Wall -Wextra main.cpp shapes.cpp -o shapes
$ ./shapes
a 4 by 3 rectangle: area 12, perimeter 14
a 10 by 10 square:  area 100, perimeter 40

From the outside it looks like chapter 1's compile with one more filename. Inside, clang++ did three jobs: compiled main.cpp into machine code with "fill in later" notes for area and perimeter; compiled shapes.cpp into machine code containing those two functions; and joined the two, filling in the notes. The joining is the link step. The next section does it by hand so it stops being hidden.

Building in two steps: object files, then link

The flag -c means "compile this one file to machine code and stop; do not try to make a program". The result is an object file, ending in .o: the machine code for one translation unit, plus a list of the names it defines and the names it still needs. These are the two commands you saw timed at the start of the chapter. Two more shell tools follow them: wc -c counts the bytes in each file, and file says what kind of file something is.

$ clang++ -std=c++23 -Wall -Wextra -c main.cpp -o main.o
$ clang++ -std=c++23 -Wall -Wextra -c shapes.cpp -o shapes.o
$ wc -c main.o shapes.o
  337856 main.o
     648 shapes.o
$ file shapes.o
shapes.o: Mach-O 64-bit object arm64

Look at the sizes. shapes.o is 648 bytes: two tiny functions. main.o is 337,856 bytes, because the formatting code behind std::println was pasted in from <print> and compiled along with your nine lines. Neither is a program yet; file says "object", not "executable", and if you try ./shapes.o the shell refuses to run it.

Now you can look inside. The tool nm lists the names, called symbols, that an object file defines or needs. A symbol is a name the linker can look up: every function you define becomes one. The -C flag prints them in C++ spelling:

$ nm -C shapes.o
0000000000000000 T area(int, int)
0000000000000020 T perimeter(int, int)
0000000000000000 t ltmp0
0000000000000048 s ltmp1
$ nm -C main.o | grep -E 'area|perimeter|_main'
                 U area(int, int)
                 U perimeter(int, int)
0000000000000000 T _main

Two letters carry the whole story. T means "defined here, in this file's machine code": the number in front is how many bytes from the start of that code the function begins. shapes.o defines area(int, int) at byte 0 and perimeter(int, int) at byte 32. (The number is printed in base 16, where 20 means 2×16+0=32; take that on trust, nothing in Week 1 needs it.) U means undefined: "I call this, but I do not have it; somebody else must". main.o defines _main and needs area and perimeter. Those U lines are the "fill in later" notes made real. (The two lowercase lines, ltmp0 and ltmp1, are internal labels the compiler made for itself; ignore them.)

Notice that the symbol is area(int, int), with the parameter types, not just area. The compiler bakes the types into the name, a step called name mangling. Run nm shapes.o without -C and you see the mangled form, __Z4areaii: 4area is the four-letter name and ii is the two ints. That is why the declaration and the definition must agree exactly on parameter types: a definition of area(long, long) produces a different symbol, __Z4areall, and a call compiled against area(int, int) will never find it.

The last step joins them:

$ clang++ main.o shapes.o -o shapes
$ ./shapes
a 4 by 3 rectangle: area 12, perimeter 14
a 10 by 10 square:  area 100, perimeter 40

No -std, no -Wall: there is no C++ left to compile. Given .o files, clang++ only runs the linker. The linker (on the Mac the program is called ld, and you will see that name in its error messages) does five things, in order:

  1. Collect every object file named on the command line.
  2. Make one list of every T symbol across all of them: every name that somebody defines.
  3. For every U symbol in any file, find the matching T and write its final address into the machine code where the "fill in later" note was.
  4. Add the standard library's own object code, such as the machinery behind std::println, and fill in those notes too.
  5. Write out one executable file.

Step 3 can fail in two ways. If a U has no T anywhere, or if one name has two Ts, the linker stops with an error. Those two errors are the next section.

First principle

Compiling and linking are different jobs with different knowledge. The compiler sees one translation unit at a time and knows types, signatures and bodies, but nothing about other files. The linker sees every object file at once and knows names and addresses, but nothing about types or bodies. An error message tells you which one is speaking: a compiler error names a file, a line and a column (main.cpp:4:24:); a linker error talks about symbols and architectures and has a line that begins with ld:, followed by clang++: error: linker command failed.

Compile only what changed

Here is the payoff for the two-step way. Change the body of perimeter in shapes.cpp (say, to return w + h + w + h;). main.cpp has not changed and main.o is still correct, so recompile only the file you touched and link again:

$ clang++ -std=c++23 -Wall -Wextra -c shapes.cpp -o shapes.o
$ clang++ main.o shapes.o -o shapes
$ ./shapes
a 4 by 3 rectangle: area 12, perimeter 14
a 10 by 10 square:  area 100, perimeter 40

Two hundredths of a second instead of a quarter, and in a project with four hundred files the saving is minutes. A rule comes with it: if you change a header, every source file that includes it has changed, because the header is pasted into each of them, so all of those must be recompiled. Tracking which .o is out of date, and which headers each .cpp pulls in, is tedious bookkeeping you will not do by hand. It is exactly what CMake and Ninja do in chapter 11: Ninja remembers the dependencies and recompiles precisely the object files whose inputs changed. Now you know what it is doing.

Try it

Add a third function to the shapes project, int diagonal_cells(int w, int h), that returns the number of cells on the diagonal of a w by h rectangle (the smaller of the two). Which files must change? Which object files must be rebuilt? Run nm -C on each .o before linking and find your new symbol with its T and its U.

Stuck? First nudge

The declaration goes in shapes.hpp, the body in shapes.cpp, and a call in main.cpp. All three files change, so both object files must be rebuilt. If you only call it from main.cpp and forget the body, the compiler is perfectly happy and the linker is not; the next section shows you what it says.

Reading linker errors

There are two, and you will meet both this week. The text below is real output from this machine; learn its shape so that you recognise it in a hurry.

Undefined symbols: you forgot a source file

Compile the shapes program but leave shapes.cpp off the command line:

$ clang++ -std=c++23 -Wall -Wextra main.cpp -o shapes
Undefined symbols for architecture arm64:
  "area(int, int)", referenced from:
      _main in main-9d6099.o
      _main in main-9d6099.o
  "perimeter(int, int)", referenced from:
      _main in main-9d6099.o
      _main in main-9d6099.o
ld: symbol(s) not found for architecture arm64
clang++: error: linker command failed with exit code 1 (use -v to see invocation)

Line by line: "Undefined symbols" is the U from nm that never found its T. "for architecture arm64" is just the CPU family; it is not the problem. Then each missing symbol with its full signature, area(int, int), and who wanted it: _main, twice, because main calls area twice. The object file has a random suffix, main-9d6099.o (yours will differ), because in a one-go build clang++ writes temporary object files with made-up names; in the two-step build it would simply say main.o. Finally ld: summarises and clang++ reports that the linker, not the compiler, failed.

Notice what did not happen: main.cpp compiled without complaint. The compiler had the declarations from shapes.hpp, which is all it needs; only the linker noticed the bodies were nowhere. The fix is to add the file that defines the symbol, shapes.cpp, to the command. The same message with a different name means the same thing: find which .cpp defines that name and make sure it is on the command line, or that you actually wrote the definition. (Declared in the header, called from main, body never written: exactly this message.)

Duplicate symbol: a body in a header

The opposite mistake. Suppose someone puts a function body in a header, thinking it saves a file:

#pragma once
// shapes.hpp — WRONG: a function body in a header.

int area(int w, int h) {
    return w * h;
}

A second header uses it, and a source file defines the function the second header declares. Put the four files in scratch/ch10/report:

#pragma once
#include "shapes.hpp"

void print_area(int w, int h);

#include "report.hpp"
#include <print>

void print_area(int w, int h) {
    std::println("area {}", area(w, h));
}

#include "report.hpp"

int main() {
    print_area(4, 3);
    return 0;
}

#pragma once is present everywhere, so inside each translation unit shapes.hpp is pasted once, and each file compiles on its own without a word of complaint. But there are two translation units, and the body of area got pasted into both:

$ clang++ -std=c++23 -Wall -Wextra -c main.cpp -o main.o
$ clang++ -std=c++23 -Wall -Wextra -c report.cpp -o report.o
$ nm -C main.o | grep area
0000000000000000 T area(int, int)
$ nm -C report.o | grep area
0000000000000000 T area(int, int)
$ clang++ main.o report.o -o report
duplicate symbol 'area(int, int)' in:
    /Users/dan/Desktop/projects/cpp-101/scratch/ch10/report/main.o
    /Users/dan/Desktop/projects/cpp-101/scratch/ch10/report/report.o
ld: 1 duplicate symbols
clang++: error: linker command failed with exit code 1 (use -v to see invocation)

Two Ts for one name. The linker cannot know they are the same code and refuses to guess. The message names the symbol and the two object files that define it (the linker prints their full paths; yours will start with your own folder); that is all you need. The fix is the discipline this chapter is about: the body moves to shapes.cpp, the header keeps only int area(int w, int h);, and shapes.cpp joins the command line.

#pragma once did not help here, and it is important to see why: it stops a header being pasted twice into one translation unit. It cannot stop a header being pasted into two different translation units; that is the whole purpose of a header. Only the rule "no bodies in headers" prevents this error.

Duplicate symbol '_main': two programs in one

The same error has a second face you will see the moment you build tests. Make a folder scratch/ch10/layout and lay the shapes project out like Life: the correct shapes.hpp, shapes.cpp and main.cpp from the three-file project go in layout/src/, and a new file goes in layout/tests/. It includes shapes.hpp, checks one fact about area, and has a main of its own. (Chapter 12's doctest will write a test main for you; this hand-written one uses only chapter 3's if and shows the same error.)

// tests/shapes_test.cpp — a hand-written test with its own main.
#include "shapes.hpp"
#include <print>

int main() {
    if (area(2, 3) == 6) {
        std::println("area(2, 3) == 6: pass");
        return 0;
    }
    std::println("area(2, 3) == 6: FAIL, got {}", area(2, 3));
    return 1;
}

From inside layout/, first try to build the test the obvious way, naming it together with shapes.cpp:

$ clang++ -std=c++23 -Wall -Wextra tests/shapes_test.cpp src/shapes.cpp -o shapes_test
tests/shapes_test.cpp:2:10: fatal error: 'shapes.hpp' file not found
    2 | #include "shapes.hpp"
      |          ^~~~~~~~~~~~
1 error generated.

The fatal error from earlier, for a new reason: shapes.hpp is spelt right but lives in src/, and quoted includes look in the including file's own folder, tests/, where it is not. The flag -I followed by a folder name (no space: -Isrc) adds that folder to the list of places the preprocessor searches. This is the flag the quotes-versus-brackets section promised. Now add it, and at the same time make the mistake this section is about: give the linker src/main.cpp as well, so that two files each define main:

$ clang++ -std=c++23 -Wall -Wextra -Isrc tests/shapes_test.cpp src/main.cpp src/shapes.cpp -o shapes_test
duplicate symbol '_main' in:
    /private/var/folders/nb/6p990kd50v1gk55h9g11s6pc0000gn/T/main-659a98.o
    /private/var/folders/nb/6p990kd50v1gk55h9g11s6pc0000gn/T/shapes_test-ab6fa5.o
ld: 1 duplicate symbols
clang++: error: linker command failed with exit code 1 (use -v to see invocation)

(The long /private/var/folders/... paths are the temporary folder where a one-go build keeps its object files; yours will differ.) Leave src/main.cpp out and the test program builds and runs:

$ clang++ -std=c++23 -Wall -Wextra -Isrc tests/shapes_test.cpp src/shapes.cpp -o shapes_test
$ ./shapes_test
area(2, 3) == 6: pass

This is the reason the test program must not be built from main.cpp: the tests have their own main, and a program may have only one. It is also the reason CMakeLists.txt lists src/life.cpp in all three programs but src/main.cpp in only one.

Compiler error or linker error?

For contrast, here is the compiler refusing. This complete program calls area without including any header that declares it:

#include <print>

int main() {
    std::println("{}", area(4, 3));
    return 0;
}

noinc.cpp:4:24: error: use of undeclared identifier 'area'
    4 |     std::println("{}", area(4, 3));
      |                        ^~~~
1 error generated.

File, line 4, column 24, a caret under the offending name: the compiler is speaking, and it never got as far as the linker. Adding shapes.cpp to the command line would not help; the compiler cannot see other files. The fix is #include "shapes.hpp". Here is the whole family in one table.

Symptom (what the message says)Who says itCauseFix
fatal error: 'x.hpp' file not foundpreprocessorMisspelt name, wrong folder, or the folder is not given with -ICheck the spelling and the path; add -Ifolder if the header lives elsewhere
file not found with <angled> include; use "quotes" insteadpreprocessorYour own header included with <>Use "x.hpp" for your files
error: use of undeclared identifier 'f'compilerNo declaration of f was seen before the callInclude the header that declares it (or, in a one-file program, write the declaration above the call as in chapter 4)

Trap

The parameter types in the definition must match the declaration exactly. If shapes.hpp says int area(int w, int h); and shapes.cpp writes int area(long w, long h) { ... }, both files compile cleanly, each one sensible on its own, and the linker then reports Undefined symbols: "area(int, int)". The message names the signature the caller wanted. When you see an undefined symbol for a function you are sure you wrote, compare the two signatures character by character. This is also why the Life tests insist you keep life.hpp's signatures unchanged.

Try it

Make the trap happen on purpose, so that you recognise it later. In scratch/ch10/shapes, change the first line of the area definition in shapes.cpp to int area(long w, long h) { and leave the header alone. Compile shapes.cpp with -c: does it complain? Run nm -C shapes.o: what symbol does it define now? Then build the whole program in one go and read the error. Put int back afterwards.

Show the answer

The compile is clean; the file is perfectly sensible on its own. nm -C shapes.o now shows T area(long, long). The one-go build ends with Undefined symbols for architecture arm64: "area(int, int)", referenced from: _main: the caller wants area(int, int), nobody defines that exact name, and the area(long, long) that does exist is a stranger to the linker. The message does not mention long at all, which is what makes this one hard to spot without nm.

The one definition rule

Everything above is one rule seen from different angles. C++ calls it the one definition rule, and in words it is:

  • A function may be declared as many times as you like, in as many files as you like. Every translation unit that calls it must see a declaration first, and they must all agree on the signature.
  • A function must be defined exactly once in the whole program: exactly one body, in exactly one translation unit, in exactly one object file. Zero definitions is "undefined symbol". Two is "duplicate symbol".

Headers are the mechanism for the first half: because a header holds declarations and is pasted into every file that includes it, every file gets the same declaration, and a repeated declaration is harmless. Source files are the mechanism for the second half: a body written in one .cpp is compiled into exactly one object file. Keep bodies out of headers and the rule keeps itself. (Chapter 11's CMakeLists.txt keeps the other half of the rule for you: each add_executable line lists every .cpp that program needs, once.)

Later you will meet two legitimate exceptions whose bodies do live in headers and for which the compiler and linker have special arrangements: functions marked inline (week 4) and templates (week 8). Until then, treat the rule as having no exceptions.

Why main.cpp must stay thin

A rule for the whole week follows directly from the layout. Anything in main.cpp cannot be tested and cannot be benchmarked. The test program is not linked with main.cpp (it cannot be: two mains), so a function written in main.cpp is invisible to life_tests and life_bench. The moment you catch yourself writing a loop in main.cpp that computes something you might want to check, stop and ask: should this be a function in life.cpp, declared in life.hpp? For the six contract functions the answer is decided for you. Helpers you invent, such as one that reads a --width 80 pair out of argv, may stay in main.cpp this week, but notice the cost: nothing checks them. From week 3 the habit is: main.cpp reads arguments, makes the vectors, runs the loop, and does no arithmetic of its own.

Where to put what

The rules for a header, this week and for the rest of Phase 1. A header:

  • Starts with #pragma once. Always, first line.
  • Includes what it needs. life.hpp mentions std::vector, std::string and std::uint8_t in its declarations, so it includes <vector>, <string> and <cstdint> itself. A header must never rely on whoever includes it having included something first; pasting order is not a contract.
  • Holds declarations with comments, using aliases, and named constants (const int). Each declaration's comment says what the function promises, in words a caller can rely on.
  • Never holds a function body. (Until week 4's inline and week 8's templates, no exceptions.)
  • Never contains using namespace std;. You have not used that line in this book and you will not; in a header it is especially harmful because it is pasted into every file that includes the header, silently changing what names mean there.
  • Never defines a variable that is not const. A plain int counter = 0; in a header is a definition pasted into every translation unit: duplicate symbol. (Why is const int default_width = 60; allowed, then? Because C++ treats a const at file level as private to its own translation unit, so the copies never meet at link time; a non-const one is shared by name across the whole program, so two copies collide. Take the why on trust; the rule is what matters this week.)

And a source file:

  • Includes its own header first, before <print> or anything else. This is a free test: if shapes.hpp forgot an include it needs, compiling shapes.cpp fails immediately instead of working by accident because some other include happened to come earlier. life.cpp follows this rule.
  • Then includes the standard headers it needs for its bodies. life.cpp will need <random> for random_cells once you write it; that include belongs in life.cpp, not in life.hpp, because the declaration of random_cells does not mention anything from <random>. Callers should not pay to paste in a library only the body uses.
  • Holds the definitions, each matching its declaration exactly.
  • Contains exactly one main if it is a program's entry file, and none otherwise.
  • May mark a helper that only this file uses as static, which keeps its name private to this translation unit, so no other file can call it and no other file's helper of the same name can collide with it. The test file does this with its grid_with helper (chapter 12); linkage, the rule behind it, is week 4 material.
Inference twin

Open the ggml repository and the first two files you should look at are ggml.h and ggml.c. ggml.h is the header the whole world includes: a few thousand lines of declarations and comments, the tensor functions, the graph functions, every operation, each one a promise with no body. ggml.c is the definitions. llama.cpp itself is llama.h and llama.cpp, and around them a few hundred such pairs: ggml-quants.h and .c, ggml-backend.h and .cpp, and so on. When you read llama.cpp in weeks 27 and 28 you will open the .h to learn what a part promises and only open the .c or .cpp when you need to know how. That reading strategy is exactly the one you used on life.hpp, and it works because of the one definition rule you learned today: the header is the complete list of what exists, and every body is in exactly one place.

Check yourself

What does the line #include "shapes.hpp" do, mechanically, and which part of the toolchain does it?

Answer

The preprocessor, the first stage of compilation, replaces the line with the full text of shapes.hpp, copy-and-paste style, before the C++ compiler proper sees anything. The compiler then compiles one long text, the translation unit, and never knows a header was involved. You can see the pasted result with clang++ -E -P file.cpp.

Why do you write #include <print> with angle brackets but #include "life.hpp" with quotes?

Answer

Quotes search the including file's own folder first, then -I folders, then the system folders; angle brackets skip the file's own folder. So quotes are for your headers and angle brackets for the toolchain's. Writing <life.hpp> fails with "file not found with <angled> include; use "quotes" instead".

A header contains only int wrap(int v, int n); and is included twice into one .cpp file, with no #pragma once. Does it compile? Now the header contains const int default_width = 60;. Does it compile?

Answer

The first compiles: a declaration may be repeated. The second fails with "redefinition of 'default_width'" because a constant is a definition and pasting it twice defines it twice. The lesson is that only some headers survive double inclusion by luck, so every header gets #pragma once regardless.

You compile with clang++ -std=c++23 -Wall -Wextra main.cpp -o game and get Undefined symbols for architecture arm64: "step(...)". Who is complaining, what went wrong, and what is the fix?

Answer

The linker (ld). main.cpp compiled fine because it saw the declaration of step in life.hpp, but no object file on the command line defines step. Add src/life.cpp to the command. If it is already there, check that you wrote the body and that its parameter types match the declaration exactly.

Someone writes the body of wrap directly in life.hpp, with #pragma once at the top. life.cpp and main.cpp both compile cleanly. What happens at link time, and why did #pragma once not prevent it?

Answer

duplicate symbol 'wrap(int, int)': the body was pasted into two translation units, so two object files each define it. #pragma once only stops a header being pasted twice into the same translation unit; it cannot and should not stop a header being included from two different .cpp files. Only the rule "no function bodies in headers" prevents this.

Why does CMakeLists.txt list src/life.cpp in all three add_executable lines but src/main.cpp in only one?

Answer

life.cpp defines the six functions that all three programs call, so each program needs it linked in (one definition per program). main.cpp defines the game's main; the tests and the benchmark each have their own main, and linking two would give duplicate symbol '_main'.

State the one definition rule in your own words, and name the error you get for breaking each half.

Answer

Declare as often as you like, define exactly once per program. Zero definitions: the linker says "Undefined symbols". Two definitions: the linker says "duplicate symbol". Inside one translation unit, two definitions are caught earlier by the compiler as "redefinition".

You write a helper function in main.cpp that converts an argv string to an int with a sensible default. Why can life_tests not test it, and what would you have to do to make it testable?

Answer

life_tests is linked with life.cpp, not main.cpp (two mains), so nothing in main.cpp is visible to it. To test the helper, move its body into a .cpp that is linked into both programs (life.cpp, or a new args.cpp added to both add_executable lines) and put its declaration in a header both include.
