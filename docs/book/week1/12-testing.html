Chapter 12

Testing with doctest

By the end of this chapter you will be able to write a test for any function in one line, read a failing test the way you read a sentence, and run the thirteen Life tests one at a time. You will also understand what every one of those thirteen tests is claiming about your code, and why.

In this chapter

  • What a test is: a program that calls your function and compares. You already wrote one in chapter 4.
  • doctest: one header file, one #define, TEST_CASE, CHECK, REQUIRE, SUBCASE.
  • A complete test program with one deliberate failure, and every line of its output explained.
  • Running the tests: all of them, one of them, listing them, seeing the passing ones, and through ctest.
  • The thirteen test cases in phase1-terminal/01-life/tests/life_test.cpp, one by one.
  • The red-to-green rhythm for the rest of the week, and how to write a test for an edge you worry about.

Why you want tests

Once the thirteen tests are green you will want a smaller number. In chapter 13 you time one call of step() on a 1000 by 1000 grid and write the number down; then you will try things: a different loop order, fewer calls to wrap, a different way of counting neighbours. Every one of those changes could break the rules of Life in a way that looks fine on screen. A blinker (three cells in a row that flip to a column and back, from chapter 0) that oscillates slightly wrong still looks like a blinker at ten frames per second. A grid where the left edge does not quite see the right edge still looks like a grid.

A test is a program that answers the question "does it still work?" in about one second, every time, without you looking at anything. You change step(), you type one command, you read one word: SUCCESS or FAILURE. That is what makes change cheap. Without tests, every improvement is a gamble and you end up not improving anything because you are afraid to.

There is a second reason, and for this week it matters more. A test is the specification written as code. The file phase1-terminal/01-life/src/life.hpp says in a comment that wrap(-1, 10) must be 9. A comment can be misread. The test file says CHECK(wrap(-1, 10) == 9), and the computer reads that for you, and tells you whether your function agrees. When you are not sure what a function is supposed to do, read its tests. They are the most precise description you will get.

The third reason is about how you work. With tests you can work in small steps: pick one failing test, make it pass, run the tests again, move to the next one. Each step is small enough to hold in your head. Each step ends with a visible result. This rhythm has a name, red to green: a failing test is red, a passing one is green, and your job is to turn one red thing green at a time. Twelve of the thirteen Life tests start red on purpose (you will see below which one does not, and why). Chapter 14 is you turning them green.

First principle

A test does nothing clever. It is an ordinary program that calls your function with an input whose correct answer you already know, and compares the function's answer with yours. The whole value lies in two facts: the computer does the comparing (so it never gets bored or sloppy), and the comparison is written down (so it runs again tomorrow, unchanged, after you have forgotten why it mattered).

You have already written a test

At the end of chapter 4 you tested clamp by hand: a function check_clamp that called clamp, compared the result with the expected value, and printed PASS or FAIL. Here is a slightly more general version of the same idea. It counts failures instead of only printing them, so that at the end there is one number to look at.

// hand_test.cpp — a hand-made checker: it compares for you, but says little.
#include <print>

// Keep v inside [lo, hi]: too small becomes lo, too big becomes hi.
int clamp(int v, int lo, int hi) {
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

// Prints PASS or FAIL for one comparison and returns the new failure count.
int check_equal(int got, int want, int failures_so_far) {
    if (got == want) {
        std::println("PASS");
        return failures_so_far;
    }
    std::println("FAIL: got {}, wanted {}", got, want);
    return failures_so_far + 1;
}

int main() {
    int failures = 0;
    failures = check_equal(clamp(5, 0, 10), 5, failures);
    failures = check_equal(clamp(-3, 0, 10), 0, failures);
    failures = check_equal(clamp(42, 0, 10), 9, failures);   // wrong expectation on purpose
    std::println("{} failure(s)", failures);
    return 0;
}

PASS
PASS
FAIL: got 10, wanted 9
1 failure(s)

This works, and you should feel free to test this way whenever you have a single file and five minutes. But look at what is missing:

  • The failure says got 10, wanted 9. It does not say which check failed. You have to count lines. With fifty checks that is hopeless.
  • check_equal only compares two ints. For a std::vector or a std::string you need another function. For a < b instead of a == b, another one.
  • The program exits with 0 even when a check failed, so no other tool (a build system, a script) can tell whether the tests passed.
  • Every test file has to repeat the main, the counting, and the printing.

A test framework is a library that fixes exactly these four things and nothing else. It gives you a way to name a group of checks, a CHECK that works for any comparison and prints both sides when it fails, a main that runs every group and counts, and an exit code that other tools can read. doctest is such a library, and it is small enough that the whole thing is one file.

doctest: one header file

doctest lives in this repository at third_party/doctest/doctest.h. It is a single header of about nine thousand lines, version 2.5.3, copied in (the word for this is vendored) so that you do not have to install anything. The Life CMakeLists.txt already tells the compiler where to find it; chapter 11 showed the line: include_directories(src ${CMAKE_CURRENT_SOURCE_DIR}/../../third_party/doctest). When you compile a test file by hand in scratch/, you pass the same folder with -I (capital i, for "include path"), which tells the compiler one more folder to search when it sees #include "doctest.h".

There are four things to learn. The first complete program below uses the first three (the define, TEST_CASE, CHECK); REQUIRE gets its own program right after.

The define, exactly once

A test program needs a main: something has to find all the tests, run them, count, and print the summary. doctest has one ready. You ask for it with a line before the include:

#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

#define NAME creates a macro: a name that the preprocessor (the part of the compiler that handles #include, from chapter 10) knows about from that line on. doctest.h contains, roughly, "if DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN is defined, also include the code of the test runner and a main". Without the define you get only the declarations: enough to write tests, not enough to run them.

The rule is: in each test program, exactly one .cpp file has this define. If none has it, there is no main and the linker complains (you will see the message below). If two have it, there are two copies of everything and the linker complains about that instead. tests/life_test.cpp is the one file in the Life project that has it.

TEST_CASE: a named group of checks

TEST_CASE("a short sentence saying what this group claims") {
    // checks go here
}

A test case is a block of code with a name. The name is any text in quotes; it is printed when a check inside fails, so make it a sentence a stranger could understand. doctest finds every TEST_CASE in the program and runs them one after another. You do not call them, and you do not list them anywhere; take it on trust that the library collects them before main starts (the mechanism uses language features from week 4).

CHECK: one claim

CHECK(clamp(42, 0, 10) == 10);

CHECK takes one expression that is either true or false. If it is true, nothing happens (the check is counted as passed). If it is false, doctest prints the file and line, the expression exactly as you wrote it, and the values of both sides. Then it continues with the next line. A test case with five CHECKs reports all five results, not only the first failure.

REQUIRE: a claim the rest depends on

REQUIRE(v.size() == 3);

REQUIRE is the same as CHECK except that on failure it stops the current test case. Use it when the lines after it would be meaningless or dangerous if it failed, for example reading v[2] when v might have two elements. Other test cases still run.

A complete test program, with one mistake

Here is a whole doctest program testing clamp. The last check is wrong on purpose, so that you can see what a failure looks like before you meet one that is not on purpose. Type it into scratch/clamp_test.cpp.

// clamp_test.cpp — a complete doctest program with one deliberate mistake.
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

// Keep v inside [lo, hi]: too small becomes lo, too big becomes hi.
int clamp(int v, int lo, int hi) {
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

TEST_CASE("clamp: values inside the range are unchanged") {
    CHECK(clamp(5, 0, 10) == 5);
    CHECK(clamp(0, 0, 10) == 0);
    CHECK(clamp(10, 0, 10) == 10);
}

TEST_CASE("clamp: values outside the range are pulled to the edge") {
    CHECK(clamp(-3, 0, 10) == 0);
    CHECK(clamp(42, 0, 10) == 10);
    CHECK(clamp(42, 0, 10) == 9);   // wrong on purpose: the answer is 10
}

There is no main in the file; the define provides it. Compile from inside scratch/, telling the compiler where doctest.h is, and run:

$ cd scratch
$ clang++ -std=c++23 -Wall -Wextra -I ../third_party/doctest clamp_test.cpp -o clamp_test
$ ./clamp_test

Read it from the top. Every line is there for a reason.

  • [doctest] doctest version is "2.5.3": the library announcing itself. Two lines of this, always.
  • clamp_test.cpp:22: followed by TEST CASE: clamp: values outside ...: the test case that contains the failure, with the file and the line where the TEST_CASE begins. Test cases with no failures print nothing at all; that is why the first one is absent.
  • clamp_test.cpp:25: ERROR: CHECK( clamp(42, 0, 10) == 9 ) is NOT correct!: the exact line of the failing check, and the expression as you typed it. You can jump straight to line 25.
  • values: CHECK( 10 == 9 ): the same expression with each side replaced by its value. The left side, clamp(42, 0, 10), evaluated to 10. The right side was 9. This one line usually tells you whether the function is wrong or the test is wrong. Here the function is right and the test is wrong.
  • test cases: 2 | 1 passed | 1 failed | 0 skipped: the count of test cases. A test case counts as failed if any check in it failed.
  • assertions: 6 | 5 passed | 1 failed: the count of individual CHECKs and REQUIREs. (Assertion is the general word for "a claim that is checked at run time".)
  • Status: FAILURE!: the one word you look at first. The program also exits with code 1 instead of 0, which is how ctest and scripts know.
First principle

How can CHECK print 10 == 9 when you wrote clamp(42, 0, 10) == 9? Because CHECK is a macro, not a function. The preprocessor replaces the text CHECK(a == b), before the compiler proper sees it, with a longer piece of code that evaluates a on its own, then b on its own, compares them, and keeps both values for the message. It also pastes in the text of the expression as a string, plus __FILE__ and __LINE__, two built-in names the preprocessor fills with the current file and line. Nothing in C++ is doing anything magical: it is text substitution followed by ordinary code.

Now fix the mistake. Change the 9 on line 25 to 10, recompile, run. (If your run says a different line number, you typed one blank line more or fewer than the listing; nothing is wrong. Always follow the numbers your run prints.)

$ ./clamp_test

[doctest] test cases: 2 | 2 passed | 0 failed | 0 skipped
[doctest] assertions: 6 | 6 passed | 0 failed |

Try it

Two small experiments on clamp_test.cpp, in this order. First, add a third test case at the bottom of the file, named "clamp: a range of one value, and negative bounds", with CHECK(clamp(7, 7, 7) == 7) and CHECK(clamp(-100, -10, 10) == -10). That is a lesson in itself: a bug can hide behind seven passing checks, and it was the plain, boring, middle-of-the-range input that caught it. Put hi back.

CHECK keeps going; REQUIRE stops

The difference between the two matters most when a later line would misbehave if an earlier claim is false. The function below is deliberately wrong: it is supposed to return the first n even numbers but returns one too few. Watch what the two test cases do with the same wrong function.

// require_vs_check.cpp — CHECK keeps going, REQUIRE stops the test case.
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

#include <vector>

// Returns the first n even numbers, starting at 0. (Deliberately wrong: it
// returns one too few.)
std::vector<int> first_evens(int n) {
    std::vector<int> out;
    for (int i = 0; i < n - 1; ++i) {
        out.push_back(2 * i);
    }
    return out;
}

TEST_CASE("first_evens with CHECK: every failure is reported") {
    std::vector<int> v = first_evens(3);
    CHECK(v.size() == 3);
    CHECK(v[0] == 0);
    CHECK(v[1] == 2);
    CHECK(v.at(2) == 4);   // .at() on a 2-element vector: not safe!
}

TEST_CASE("first_evens with REQUIRE: stop before touching missing cells") {
    std::vector<int> v = first_evens(3);
    REQUIRE(v.size() == 3);   // if this fails, the lines below never run
    CHECK(v[0] == 0);
    CHECK(v[1] == 2);
    CHECK(v[2] == 4);
}

In the first test case, the size check fails and doctest carries on. v[0] and v[1] pass (the two values that exist are right). Then v.at(2) asks for a third element that is not there. You met .at() in chapter 6: unlike [], it refuses loudly. doctest catches the refusal, reports it as THREW exception, and keeps the program alive. (The mechanism, exceptions, is a later-week topic. For now: .at() out of range is an error that doctest can report; [] out of range is the silent kind that the sanitizers from chapter 11 exist to catch.)

In the second test case, REQUIRE fails, is reported as FATAL ERROR, and the three lines after it never run. The assertion count confirms it: five assertions in total, not eight. The last three were never reached. This is what you want when a later line reads memory that only exists if the earlier claim holds.

Rule of thumb for the week: use CHECK by default, because more information per run is better. Use REQUIRE for a claim that the later lines cannot do without, most often a size: if the vector does not have three elements, there is no point reading the third one.

SUBCASE: one setup, several continuations

You will not need this for the Life tests, but you will see it in other people's test files and it is worth one program. A SUBCASE is a block inside a test case. doctest runs the test case once per subcase, executing the shared code at the top each time and then one subcase. So each subcase starts from a fresh copy of the setup.

// subcase_demo.cpp — SUBCASE: shared setup, several continuations.
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

#include <vector>

TEST_CASE("a vector of three zeros") {
    std::vector<int> v(3, 0);
    REQUIRE(v.size() == 3);

    SUBCASE("push_back makes it longer") {
        v.push_back(7);
        CHECK(v.size() == 4);
        CHECK(v[3] == 7);
    }
    SUBCASE("resize to zero empties it") {
        v.resize(0);
        CHECK(v.size() == 0);
    }
    SUBCASE("the setup is fresh in every subcase") {
        CHECK(v.size() == 3);   // the push_back and resize above never happened here
    }
}

Analogy

A test case is a recipe card with a title and a list of things that must be true at the end: "the cake is golden", "the centre is set". CHECK is ticking a line and moving on. REQUIRE is "if the oven did not reach temperature, do not bother checking the cake". SUBCASE is baking the batter three times to try three toppings, starting from fresh batter each time. Where the analogy breaks: real recipes are followed by a cook who notices things that are not on the list. A test checks exactly what you wrote and nothing else. If you forgot to check the edge, the edge is not checked.

One test case at a time

Fifty-one failures at once is noise. While you work on wrap, you only care about the wrap test. The -tc flag (test case) takes a pattern: a piece of text in which * stands for "any characters, including none". The quotes around the pattern are for the shell, not for doctest: without them the shell would try to replace wrap* with the names of files that start with wrap, and doctest would never see the *.

Twelve skipped, one run. And look: three of the seven wrap checks pass with a stub that always returns 0, because wrap(0, 10), wrap(10, 10) and wrap(-10, 10) really are 0. This is why the test has seven checks and not one. A single check can be passed by accident; seven well-chosen ones cannot.

The pattern is matched against the whole name, ignoring the difference between upper and lower case. So -tc="wrap*" means "names starting with wrap", -tc="*torus*" means "names containing torus", and -tc="wrap*,index*" runs two groups. But -tc="wrap", without the *, matches only a test named exactly wrap, and there is none. If nothing matches you get test cases: 0 | 0 passed | 0 failed | 13 skipped and, confusingly, Status: SUCCESS!: no tests ran, so none failed. Check the count.

The helper: grid_with

// Small helper used by the tests only: a grid with a list of live (x, y) cells.
static Cells grid_with(int width, int height, std::initializer_list<std::pair<int, int>> alive) {
    Cells cells(static_cast<std::size_t>(width) * static_cast<std::size_t>(height), 0);
    for (auto [x, y] : alive) {
        cells[static_cast<std::size_t>(y * width + x)] = 1;
    }
    return cells;
}

grid_with(5, 5, {{2, 2}}) makes a 5 by 5 grid of dead cells and sets the cell at column 2, row 2 alive. grid_with(3, 2, {{0, 0}, {2, 1}}) makes a 3 by 2 grid with two live cells. It is a convenience so that each test can describe a picture in one line instead of twenty.

Its signature uses three things you have not met. static in front of a function means "this function is private to this file"; that is chapter 10 territory, take it on trust for now. std::initializer_list<std::pair<int, int>> is "a list of pairs of two ints", which is what {{0, 0}, {2, 1}} is. auto [x, y] unpacks one pair into two named variables, so that inside the loop x is the column and y the row. The last two are week-4 topics. Take the helper on trust; what it does is exactly what the comment says, and it uses y * width + x, the formula from chapter 7, to find each cell. Notice that it deliberately does not call your index_of. If it did, a bug in index_of would corrupt every test grid, and every test would fail for a reason that has nothing to do with the function it is testing. Tests should depend on as little of your code as possible.

Milestone 1: index_of

TEST_CASE("index_of: row-major flat index") {
    CHECK(index_of(0, 0, 10) == 0);
    CHECK(index_of(9, 0, 10) == 9);
    CHECK(index_of(0, 1, 10) == 10);
    CHECK(index_of(3, 2, 10) == 23);
    CHECK(index_of(4, 4, 5) == 24);
}

Claim: the cell at column x, row y of a grid width columns wide lives at position y * width + x in the flat vector. Why it matters: everything else in the project reads and writes cells through this formula. The five checks are chosen to catch the common mistakes: the first cell (0), the end of the first row (9, so x is not being dropped), the start of the second row (10, so the row stride is width, not 1), a general interior cell, and the last cell of a different-sized grid (so width is really being used and not a hard-coded 10). If you swapped x and y, the third check would say 1 == 10.

Milestone 2: random_cells and render

TEST_CASE("random_cells: size, determinism and fill extremes") {
    Cells a = random_cells(8, 4, 42, 0.5);
    CHECK(a.size() == 32);

    Cells b = random_cells(8, 4, 42, 0.5);
    CHECK(a == b);  // same seed, same grid

    Cells dead = random_cells(8, 4, 1, 0.0);
    int live = 0;
    for (std::uint8_t c : dead) live += c;
    CHECK(live == 0);

    Cells full = random_cells(8, 4, 1, 1.0);
    live = 0;
    for (std::uint8_t c : full) live += c;
    CHECK(live == 32);

    Cells half = random_cells(100, 100, 7, 0.5);
    live = 0;
    for (std::uint8_t c : half) {
        CHECK((c == 0 || c == 1));
        live += c;
    }
    CHECK(live > 4000);
    CHECK(live < 6000);
}

Claims: the grid has width * height cells; the same seed gives the same grid twice (chapter 8 explained why a seeded generator does this); a fill of 0.0 gives no live cells and 1.0 gives all live; every cell is exactly 0 or 1 and nothing else; and a fill of 0.5 on ten thousand cells gives roughly half alive. Why it matters: determinism is what makes a bug reproducible: "seed 7 looks wrong" is a report you can act on. The extremes pin down the meaning of fill without depending on any particular random numbers. The 4000 to 6000 window is wide on purpose. Ten thousand honest coin flips give 5000 heads give or take about 50 (that "about 50" is the typical wobble; 4000 or 6000 would be twenty times the typical wobble away, which does not happen in practice). So a correct random_cells always lands inside the window, while a function that compared against the wrong threshold, or produced mostly 1s, would miss it.

Two small things about how the test is written. CHECK(a == b) compares two whole vectors with ==, the element-by-element comparison from chapter 6, so one == checks all 32 cells. And for (std::uint8_t c : dead) live += c; is a range-for from chapter 6 whose body is a single statement written on the same line without braces. The language allows that; chapter 3 told you to always write the braces anyway, and that advice stands for your own code. The test file is someone else's code, and you only need to read it. Finally, notice the double parentheses in CHECK((c == 0 || c == 1)): the macro wants one expression, and the inner pair keeps || from confusing it.

TEST_CASE("render: '#' alive, '.' dead, newline after every row") {

Milestone 3: wrap and count_neighbours

TEST_CASE("wrap: like a clock face") {
    CHECK(wrap(0, 10) == 0);
    CHECK(wrap(7, 10) == 7);
    CHECK(wrap(10, 10) == 0);
    CHECK(wrap(11, 10) == 1);
    CHECK(wrap(-1, 10) == 9);
    CHECK(wrap(-10, 10) == 0);
    CHECK(wrap(-11, 10) == 9);
}

Claim: wrap(v, n) brings any integer into the range 0 to n - 1 the way a clock brings any hour into 0 to 11. Why it matters: this is the function that makes the grid a torus, and chapter 7 showed you the trap: in C++, -1 % 10 is -1, not 9. The last three checks exist for that trap alone: minus one, exactly minus n, and one past minus n. Milestone 4: step

TEST_CASE("step: a lone cell dies") {
    Cells cur = grid_with(5, 5, {{2, 2}});
    Cells next(25, 1);  // deliberately dirty: step must overwrite every cell
    step(cur, next, 5, 5);
    for (std::uint8_t c : next) CHECK(c == 0);
}

Claim: a cell with no neighbours dies, no cell is born anywhere, and step writes every cell of next. Why it matters: the dirty next, filled with 1s, is the important part. A step that only writes cells that change, or only writes the live ones, would leave 1s behind and fail 24 of the 25 checks. The contract says "writes the result into next"; the test makes "the whole result" explicit. This is a habit worth stealing: when a function fills a buffer, test it with a buffer full of wrong values, never with a clean one.

First principle

Notice what the thirteen tests never do: they never look inside your implementation. They call the six functions through the signatures in life.hpp and judge only the answers. This means you can rewrite step any way you like in chapter 13 and later, and the same thirteen tests still say whether it is correct. Tests that depend on how a function works break every time you improve it; tests that depend on what it returns are the ones worth having.

The rhythm for the rest of the week

You now know what every red line means. Here is the loop you will run in chapter 14, in order:

  1. Build. cmake --build build. If it does not compile, nothing else matters; read the first error, fix it, build again.
  2. Run the test for the function you are on. ./build/life_tests -tc="index_of*". Read the first failing CHECK: the expression, then the values: line. Decide whether you believe the test (you should; but reading it carefully is how you find out what the function is meant to do).
  3. Change one thing in src/life.cpp. One function, or one line of one function.
  4. Build and run again. Did the number of failures go down? If it went up, you know exactly which edit did it, because you made only one.
  5. When the test case is green, commit. git add -A && git commit -m "M1: index_of green". A commit per green test case gives you a trail you can always return to, and a sense of progress that is real rather than felt.
  6. Run all thirteen before moving to the next milestone, to be sure the new function did not break an old one. This week that is unlikely, because each new function only calls the ones that are already green (step will call count_neighbours, which calls wrap, never the other way round), but the habit is the point. And it does catch one real mistake: going back to "improve" wrap while working on step.
$ cmake --build build && ./build/life_tests -tc="index_of*"

The && between the two commands means "and then, only if the first succeeded". If the build fails, the tests do not run, and you are not confused by stale results from the previous binary. This one line is your most-typed command this week.

Trap

Running ./build/life_tests without rebuilding first. The executable in build/ is whatever you last compiled; editing life.cpp changes the source file and nothing else. If a test keeps failing in a way that makes no sense given what you just wrote, check that you rebuilt. The && form above makes this mistake impossible.

Try it

Before you implement anything, make the index_of stub return x instead of 0, rebuild, and run -tc="index_of*". Two checks will pass and three will fail. Read the three values: lines and say out loud, for each one, what the stub got wrong. Then put the 0 back. Being able to read a failure as a sentence is the skill; the implementing comes in chapter 14.

Writing a test of your own

The thirteen tests are the acceptance criteria: the list of things that must be true for the week's work to count as done. But they are not everything you might worry about. When you find yourself thinking "what happens if the grid is tiny?", the answer is not to think harder; it is to write the question down as a test and let the computer answer. You add a TEST_CASE to tests/life_test.cpp, anywhere after grid_with, rebuild, and run it with -tc.

Here is a worry worth having. On a grid that is only 2 columns wide, what is the left neighbour of a cell in column 0? Column -1, which wraps to column 1. And its right neighbour? Column 1. The same cell, twice. Here is the ring of columns for width 2:

width 5:   ... 3 4 | 0 1 2 3 4 | 0 1 ...     left of 0 is 4, right of 0 is 1: different cells
width 2:   ... 0 1 | 0 1 | 0 1 ...           left of 0 is 1, right of 0 is 1: the SAME cell

So on a 2-wide grid, a live cell in column 1 is seen from column 0 as both a left neighbour and a right neighbour, and contributes 2 to the count. Is that correct? The contract in life.hpp says "how many of the 8 neighbours of (x, y) are alive", and defines neighbours by position on a torus. On a torus of width 2 the eight positions around a cell are not eight distinct cells, so counting positions gives 2 and counting distinct cells gives 1. Both readings are defensible. What is not defensible is not knowing which one your code does. So you decide, and you write the decision down as a test. The eight-positions reading is the one that falls out of the straightforward stencil and the one the rest of this book assumes:

TEST_CASE("count_neighbours: on a 2-wide grid the other column is seen twice") {
    // 2 columns, 3 rows; one live cell at (1, 1), the middle of the right column.
    Cells g = grid_with(2, 3, {{1, 1}});
    // From (0, 1): the left neighbour is column -1, which wraps to column 1.
    // The right neighbour is column 1. Same cell, seen from both sides.
    CHECK(count_neighbours(g, 2, 3, 0, 1) == 2);
    // From (0, 0): the two lower diagonals (-1,+1) and (+1,+1) both land on (1, 1).
    CHECK(count_neighbours(g, 2, 3, 0, 0) == 2);
    // The live cell itself still does not count itself.
    CHECK(count_neighbours(g, 2, 3, 1, 1) == 0);
}

Push the same idea to the limit: a 1 by 1 grid. Every one of the eight neighbour positions wraps to the single cell. A live cell on a 1 by 1 torus therefore has eight live neighbours, all of them itself, and dies of overcrowding in the next generation. A dead one has zero and stays dead. Strange, but consistent with the rules as written, and a very good test of whether your wrap handles n == 1 and offsets of both signs:

TEST_CASE("1x1 grid: every neighbour position is the cell itself") {
    Cells alive = grid_with(1, 1, {{0, 0}});
    CHECK(count_neighbours(alive, 1, 1, 0, 0) == 8);

    Cells dead(1, 0);
    CHECK(count_neighbours(dead, 1, 1, 0, 0) == 0);

    Cells next(1, 1);
    step(alive, next, 1, 1);
    CHECK(next[0] == 0);   // eight neighbours: dies
}

Why bother with grids nobody will ever run? Because the edge cases are where the formula and your intuition disagree, and a test is the cheapest way to find out which one your code followed. A wrap that works for n = 10 and breaks for n = 1 (dividing by 1 is fine; but did you write n - 1 somewhere?) is a real class of bug. And in week 13 you will run a cellular automaton over a 400 by 200 grid on several threads, each thread handling a strip a few rows tall, and a strip two rows tall has exactly this "my neighbour above and my neighbour below are the same row" property. The tiny grid is not a toy; it is the small version of a real situation.

Tests the main program cannot have

You will notice there is no test for main: argument parsing, the animated loop, the screen clearing. That is deliberate. main talks to a terminal and sleeps between frames, which a test cannot easily observe, and a test program already has a main (doctest's). This is the practical reason the contract puts all the logic in six free functions and leaves main thin: everything that can be wrong in an interesting way lives in a function that a test can call. Keep that shape in every project.

Numbers that are nearly equal

One more thing before the twin, because it will bite you the first time you test anything with a double. Two doubles that should be equal often are not, by a hair, because the machine stores them in binary and most decimal fractions have no exact binary form (chapter 2). Watch:

// approx.cpp — comparing numbers that are only "nearly" equal.
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"

#include <cmath>

TEST_CASE("0.1 + 0.2 is not exactly 0.3 in a double") {
    double a = 0.1 + 0.2;
    double b = 0.3;
    CHECK(a == b);                        // fails: the two doubles differ in the last bits
    CHECK(std::abs(a - b) < 1e-9);        // passes: close enough for any purpose here
    CHECK(a == doctest::Approx(b));       // doctest's built-in way of saying the same thing
}

$ clang++ -std=c++23 -Wall -Wextra -I ../third_party/doctest approx.cpp -o approx
$ ./approx
[doctest] doctest version is "2.5.3"
[doctest] run with "--help" for options
===============================================================================
approx.cpp:7:
TEST CASE:  0.1 + 0.2 is not exactly 0.3 in a double

approx.cpp:10: ERROR: CHECK( a == b ) is NOT correct!
  values: CHECK( 0.3 == 0.3 )

===============================================================================
[doctest] test cases: 1 | 0 passed | 1 failed | 0 skipped
[doctest] assertions: 3 | 2 passed | 1 failed |
[doctest] Status: FAILURE!

values: CHECK( 0.3 == 0.3 ) looks absurd until you remember that doctest prints a double rounded to six significant digits, which is the default of C++'s older printing machinery. The two numbers differ around the seventeenth significant digit: 0.1 + 0.2 is stored as 0.30000000000000004, and 0.3 as 0.29999999999999999, exactly as chapter 2 showed with {:.20f}. The fix is never to compare floating-point numbers with ==. Instead check that the difference is smaller than a tolerance, a small number you choose: std::abs (from <cmath>; take it on trust) gives the absolute value, so std::abs(a - b) is the distance between the two, and 1e-9 is the number 0.000000001. doctest::Approx(b) is doctest's own way of saying "anything within a tiny fraction of b": the comparison a == doctest::Approx(b) is true when a and b differ by less than about one part in a hundred thousand of their size, and when it fails the message shows both numbers. Integers, which is all Life uses, never have this problem; 0 and 1 are exact.

Inference twin

In week 15 you will write a matrix multiply and need to know it is correct. The reference answer will come from PyTorch: a Python script dumps a tensor to a file, your C++ reads it, and your test says CHECK(std::abs(mine[i] - reference[i]) < 1e-5) for every element. Same header, same TEST_CASE, same CHECK, same red-to-green loop; only the tolerance is new, because two correct matrix multiplies that add numbers in a different order produce answers that differ in the last bits. Every optimisation you make to that matmul over the following weeks (blocking, SIMD, quantisation, your own CUDA kernel) is accepted or rejected by exactly this test. The habit you build on Life this week, "change it, run the tests, read the first red line", is the habit you will use on a SmolLM2-135M forward pass.

Check yourself

A test file compiles cleanly but linking fails with a long list of Undefined symbols including "_main". What did you forget?

Answer

The line #define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN before #include "doctest.h". Without it the header provides only declarations, so there is no test runner and no main for the linker to find. Exactly one file in the test program must have the define.

A test case has five CHECKs. The second one fails. How many of the five run, and how many would run if the second were a REQUIRE?

Answer

All five run with CHECK; doctest reports the failure and continues. With REQUIRE, only two run: the first (passes) and the second (fails, reported as FATAL ERROR), and the test case stops there. Other test cases still run either way.

You run ./build/life_tests -tc="wrap" and get test cases: 0 | 0 passed | 0 failed | 13 skipped and Status: SUCCESS!. Did the wrap tests pass?

Answer

No. Nothing ran: the pattern is matched against the whole name, and no test is named exactly wrap; the one you wanted is wrap: like a clock face, which only -tc="wrap*" matches. Zero tests ran, so zero failed, and doctest calls that success. Always read the counts, not only the status word. Use -ltc to see the exact names.

Why does the test "step: a lone cell dies" fill next with 1s before calling step, when a vector of 0s would be the natural choice?

Answer

To prove that step writes every cell of next. If next started as all 0s, a step that only wrote live cells, or only wrote cells that changed, would pass by accident. Starting from the wrong value everywhere means every correct 0 in the result had to be written by step.

The failure message says CHECK( wrap(-1, 10) == 9 ) is NOT correct! and values: CHECK( -1 == 9 ). Is the function wrong or the test wrong, and what is the likely bug?

Answer

The function. wrap(-1, 10) should be 9 (one step back from 0 on a 10-hour clock). The left side evaluated to -1, which is exactly what -1 % 10 gives in C++: the remainder keeps the sign of the dividend. The function is using % without correcting negative results. Chapter 7 showed the trap and how to think about it.

Which of the thirteen test cases passes before you have written any code, and why?

Answer

"step: does not modify current". The stub step does nothing, and a function that does nothing certainly leaves current unchanged. It is still a valuable test: it guards against a future step that writes into the vector it reads from, which would break double buffering.

On a 2-wide grid, a live cell at (1, 1) is the only live cell. What does count_neighbours(g, 2, 3, 0, 1) return under the "eight positions" reading, and why?

Answer

2. From (0, 1) the left neighbour is column -1, which wraps to column 1, and the right neighbour is column 1. Both positions are the same cell, (1, 1), and it is counted once for each position. The up-left, up-right, down-left and down-right positions land on (1, 0) and (1, 2), which are dead.

Why is CHECK(0.1 + 0.2 == 0.3) a bad test, and what should you write instead?

Answer

Because doubles store most decimal fractions inexactly; 0.1 + 0.2 and 0.3 differ in the last bits and the == fails even though both are "right". Compare with a tolerance instead: CHECK(std::abs(a - b) < 1e-9) or CHECK(a == doctest::Approx(b)). Integer comparisons do not have this problem.

What you can do now

  • Explain why a test suite is the specification written as code, and why it makes changing step() safe next chapter.
  • Write a complete doctest program from an empty file: the define, the include, TEST_CASE, CHECK, compiled with -I ../third_party/doctest.
  • Read a failing check as a sentence: which file and line, which expression, what each side evaluated to, and whether the function or the test is wrong.
  • Choose between CHECK and REQUIRE, and recognise SUBCASE when you see it.
  • Run the Life tests all at once, one test case at a time with -tc, list them with -ltc, see passes with -s, and run them through ctest --test-dir build --output-on-failure.
  • State, for each of the thirteen test cases in tests/life_test.cpp, what it claims and what mistake it would catch.
  • Work in the red-to-green rhythm: build, run one test case, change one thing, rerun, commit on green.
  • Turn a worry about an edge case (a 1 by 1 grid, a 2-wide grid) into a TEST_CASE of your own, and explain why wrapping on a 2-wide grid counts the same cell twice.
  • Compare floating-point results with a tolerance instead of ==, which is how you will test a matrix multiply against PyTorch in week 15.
