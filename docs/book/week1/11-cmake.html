The problem: three programs and one very long line

In chapter 10 you split a program across several files and compiled them together by naming every .cpp on the command line. That works. Now look at what the Life project actually asks for. The folder phase1-terminal/01-life holds four source files and wants three programs out of them:

  • life, the game: src/main.cpp plus src/life.cpp.
  • life_tests, the tests: tests/life_test.cpp plus src/life.cpp.
  • life_bench, the benchmark: bench/bench_life.cpp plus src/life.cpp.

Each one needs the same flags: the C++ standard, the warnings, the sanitizers, and two -I options (the "look in this folder for headers" flag from chapter 10) so the compiler can find life.hpp in src/ and doctest.h in the repo's third_party/doctest folder, two levels up from the project. By hand, that is this, typed three times with small differences:

$ cd phase1-terminal/01-life
$ clang++ -std=c++23 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined -fno-omit-frame-pointer -Isrc -I../../third_party/doctest src/main.cpp src/life.cpp -o life
$ clang++ -std=c++23 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined -fno-omit-frame-pointer -Isrc -I../../third_party/doctest tests/life_test.cpp src/life.cpp -o life_tests
$ clang++ -std=c++23 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined -fno-omit-frame-pointer -Isrc -I../../third_party/doctest bench/bench_life.cpp src/life.cpp -o life_bench

Those three lines take about two and a half seconds on your Mac (measured: 2.5 s). Now think about the week. You change one line in life.cpp and want to run the tests. You fish the second line out of your shell history (the list of past commands the up-arrow key walks through), and the compiler translates everything again: life_test.cpp, which did not change and which pulls in the 360 KB doctest.h, as well as life.cpp. If you also want the game and the benchmark, life.cpp is compiled a third and fourth time. You will do this hundreds of times, and each time there is a chance of a typo, a forgotten flag, or a test binary secretly older than the code it claims to test.

There are three separate annoyances here:

  1. The recipe is not written down. The flags live in your memory and your shell history.
  2. Everything is rebuilt every time. The compiler has no memory of what it did last time, so it cannot skip the files that did not change.
  3. Nothing runs in parallel. A core is one complete processor inside the chip, able to run one program at a time; your M5 has ten of them (sysctl -n hw.ncpu prints 10). Compiling four files one after the other uses one core and leaves nine idle.

A build system solves all three: it reads a file that records the recipe, rebuilds only the outputs that are older than their inputs, and runs independent compilations at the same time. The one this curriculum uses, and the one llama.cpp and most of the C++ world use, is CMake together with Ninja.

Two tools, two jobs

It surprises people that "the build system" is two programs, so be precise about who does what.

CMake reads a file named exactly CMakeLists.txt, which you write, and generates a second file: a detailed, machine-oriented plan that lists every compiler command, every output file, and which outputs depend on which inputs. CMake does not compile anything itself. It is a translator from your short recipe into that long plan.

Ninja reads the plan (a file named build.ninja) and executes it. It checks the timestamp of every input and output (the date and time a file was last saved, which the operating system records for every file), decides which commands actually need to run, and runs them, as many at once as you have cores. Ninja never reads CMakeLists.txt; it does not even know what CMake is. It only knows how to run commands in the right order, fast.

Analogy

CMake is the architect; Ninja is the builder. You tell the architect what you want in a few sentences ("three programs, from these files, with these flags"). The architect produces detailed drawings for every wall and wire. The builder works only from the drawings and never speaks to you; if you change your mind, you go back to the architect, who redraws, and the builder reads the new drawings. Where the analogy breaks: a real builder cannot tell which walls are already standing. Ninja can. It compares dates on files, so if only one source file changed it rebuilds only the pieces that depend on it, in well under a second.

Why two tools? Because the plan Ninja wants is tedious and platform-specific: which compiler is installed, where it lives, which flags it needs on macOS versus Linux. CMake deals with all of that once, when it generates the plan, so your CMakeLists.txt stays short and identical on every machine. That matters in week 6 when you build the same projects inside a Linux container.

You will also hear of Make, a much older builder that reads Makefiles. CMake can generate those too, and many projects still use them. Ninja does the same job but was designed for speed and for being generated rather than hand-written. This book uses Ninja everywhere; nothing in the recipe would change if you switched.

The smallest recipe

Before the real recipe, build a toy one, so you can see every moving part with nothing else in the way. Make a folder scratch/ch11/hello_cmake with one source file and one CMakeLists.txt.

#include <print>

int main() {
    std::println("Built by CMake and Ninja.");
    std::println("The compiler flags came from CMakeLists.txt, not from me.");
    return 0;
}

Built by CMake and Ninja.
The compiler flags came from CMakeLists.txt, not from me.

cmake_minimum_required(VERSION 3.25)
project(hello_cmake LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)
add_executable(hello_cmake hello_cmake.cpp)

Four lines, each a command: a name followed by arguments in round brackets. That is the whole of the CMake language you need this week. Read them as English: "I need CMake 3.25 or newer. This project is called hello_cmake and is written in C++ (CXX is CMake's spelling of C++). Use the C++23 standard. Make a program called hello_cmake out of the file hello_cmake.cpp." Take the set(...) line on trust for a moment; the Life recipe below explains what set does and why the real file has three of them.

Now the two steps. The first is called configuring: CMake reads the recipe and writes the plan into a folder you name.

$ cd scratch/ch11/hello_cmake
$ cmake -S . -B build -G Ninja
-- The CXX compiler identification is AppleClang 21.0.0.21000101
-- Detecting CXX compiler ABI info
-- Detecting CXX compiler ABI info - done
-- Check for working CXX compiler: /usr/bin/c++ - skipped
-- Detecting CXX compile features
-- Detecting CXX compile features - done
-- Configuring done (0.2s)
-- Generating done (0.0s)
-- Build files have been written to: /Users/dan/Desktop/projects/cpp-101/scratch/ch11/hello_cmake/build

Notice that CMake went looking for a compiler and found Apple clang 21 at /usr/bin/c++, which on your Mac is the same program as clang++. It checked that the compiler works and asked it which C++ features it supports. The two lines about "ABI info" are CMake asking how this compiler lays out compiled code; take them on trust, they never matter this year. Then "Configuring done" means the recipe was read without errors, and "Generating done" means the plan was written. The last line tells you where.

The second step is building: Ninja carries out the plan.

$ cmake --build build
[1/2] Building CXX object CMakeFiles/hello_cmake.dir/hello_cmake.cpp.o
[2/2] Linking CXX executable hello_cmake
$ ./build/hello_cmake
Built by CMake and Ninja.
The compiler flags came from CMakeLists.txt, not from me.

Two steps, exactly as in chapter 10: compile the source into an object file, then link the object file into a program. The difference is that you did not type either command. Look inside the build folder to see what CMake made.

$ ls build
CMakeCache.txt
CMakeFiles
build.ninja
cmake_install.cmake
compile_commands.json
hello_cmake

build.ninja is the plan (about 145 lines for this four-line recipe). CMakeCache.txt is CMake's memory of the choices it made while configuring: which compiler, which generator, which build type. CMakeFiles/ holds the object files. compile_commands.json is a list of the compile commands for your editor. The recipe did not ask for it; your shell did. An environment variable is a named setting that the shell hands to every program it starts, and ~/.zshrc, the file your shell runs each time a terminal opens, contains the line export CMAKE_EXPORT_COMPILE_COMMANDS=ON. CMake reads that variable and writes the file. It gets its own section further down. And hello_cmake is your program. Every one of these can be regenerated from the recipe, which leads to the most useful habit in this chapter.

First principle

Everything inside build/ is derived: made by a tool from your source files and your recipe. Nothing you wrote lives there. So build/ is disposable. When a build behaves strangely, rm -rf build and configure again. You lose nothing but a few seconds of compile time, and you gain a clean start. The same is true of every build-* folder you will make. (They are git-ignored for exactly this reason.)

What Ninja actually ran

There is no magic in the plan. You can ask Ninja to print the exact commands it would run for a target, and you will recognise them. In the line below, -C build means "change into the folder build first" (Ninja always works from inside the build folder), and -t commands picks Ninja's built-in tool named commands, which prints instead of running.

$ ninja -C build -t commands hello_cmake
ccache /usr/bin/c++   -std=gnu++23 -arch arm64 -MD -MT CMakeFiles/hello_cmake.dir/hello_cmake.cpp.o -MF CMakeFiles/hello_cmake.dir/hello_cmake.cpp.o.d -o CMakeFiles/hello_cmake.dir/hello_cmake.cpp.o -c /Users/dan/Desktop/projects/cpp-101/scratch/ch11/hello_cmake/hello_cmake.cpp
: && /usr/bin/c++ -arch arm64 -Wl,-search_paths_first -Wl,-headerpad_max_install_names CMakeFiles/hello_cmake.dir/hello_cmake.cpp.o -o hello_cmake   && :

Line one is the compile step: -c compiles one file into an object. The -MD -MT -MF options ask the compiler to also write down which headers the file included, so Ninja can rebuild it when a header changes. Line two is the link step (the : && and && : around it are shell padding that does nothing). Two kinds of flag here are new and can be taken on trust: -arch arm64 names the kind of chip the program is for (Apple Silicon), and the -Wl,... flags are settings CMake passes through to the linker on macOS. Neither changes what your program does. Note one oddity: the standard is -std=gnu++23, not -std=c++23. The real recipe fixes that, and you will see why.

Note

The word ccache in front of the compiler is not CMake's doing either. Your ~/.zshrc exports CMAKE_CXX_COMPILER_LAUNCHER=ccache, and CMake obeys it by putting that program in front of every compile command. ccache is a compiler cache: it remembers the object file produced for a given source text and flags, and hands it back instantly if you ask for the same compile again (after an rm -rf build, say). It never changes what the compiler produces. Read past it; the real command starts at /usr/bin/c++. If you unset the variable, the word disappears and nothing else changes.

Try it

Run cmake --build build a second time without changing anything. Ninja prints ninja: no work to do. Then open hello_cmake.cpp, change the text, save, and build again: one compile and one link, nothing else. That is annoyance number two solved: Ninja compares the date on hello_cmake.cpp with the date on hello_cmake.cpp.o and only runs the command when the source is newer.

Configure, then build: the flags

You will type the configure line many times this week, so know what each piece means rather than copying it.

  • cmake with -S .: the source folder is ., the current one. This is where CMakeLists.txt must be.
  • -B build: the binary (output) folder is build. CMake creates it if needed. You may call it anything, and you may have several.
  • -G Ninja: the generator, meaning "plans for which builder?" Run cmake --help and the end of the output lists the choices on your machine: Unix Makefiles, Ninja, Xcode and more. The one marked with * is the default. On a fresh Mac the default is Unix Makefiles. On this machine the star sits on Ninja only because ~/.zshrc also exports the environment variable CMAKE_GENERATOR=Ninja. Do not rely on that: always say -G Ninja explicitly. It costs nothing when it is already the default, and it saves you from a Makefile build on a machine without that setting.
  • -DCMAKE_BUILD_TYPE=Debug: -D defines a variable before the recipe is read. Here it sets the build type, which the recipe uses to decide on sanitizers and optimisation. You will see -D used for other variables later in the curriculum; the shape is always -DNAME=value, no spaces.

And the build line: cmake --build build means "run the builder in the folder build". CMake looks in CMakeCache.txt to see that the builder is Ninja and simply runs ninja there for you. Typing ninja -C build does the same thing directly (-C means "change into this folder first"). Use whichever you like; the book uses cmake --build because it works for any generator.

The two steps are separate for a reason. Configuring only needs to happen when the recipe or the machine changes; building happens every time you save a file. If you edit CMakeLists.txt, you do not reconfigure by hand: Ninja notices the recipe is newer than the plan and reruns CMake first, printing Re-running CMake... at the top of the build output.

Trap

Configure and build take different folder arguments. Configure wants -S (source) and -B (build). Build wants only the build folder, with no -B: cmake --build build. People type cmake --build . from inside the project folder, where there is no plan, and get Error: not a CMake build directory (missing CMakeCache.txt). Stay in the project folder and name the build folder.

The Life recipe, line by line

Here is the real file, phase1-terminal/01-life/CMakeLists.txt, reproduced in full. Lines starting with # are comments. Read it once now; the rest of this section walks through it group by group.

# CMakeLists.txt — the recipe that turns the source files in this folder into
# three programs: `life` (the game), `life_tests` (the tests), `life_bench`.
#
# Configure once, then build as often as you like:
#   cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
#   cmake --build build
#   ./build/life_tests
#
# Book chapter 11 explains every line below.

cmake_minimum_required(VERSION 3.25)
project(life LANGUAGES CXX)

# Which C++ we speak: C++23, and nothing vendor-specific.
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# Writes build/compile_commands.json so editors (VS Code, clangd) understand the project.
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

# Default to a Debug build if nobody said otherwise.
if(NOT CMAKE_BUILD_TYPE)
  set(CMAKE_BUILD_TYPE Debug)
endif()

# Warnings are free bug reports: turn them all on.
add_compile_options(-Wall -Wextra -Wpedantic)

# In Debug builds, the sanitizers turn memory bugs into readable error messages.
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
  add_link_options(-fsanitize=address,undefined)
endif()

# Every program here can #include "life.hpp" and "doctest.h".
include_directories(src ${CMAKE_CURRENT_SOURCE_DIR}/../../third_party/doctest)

# The three programs. Each one is made from the listed source files.
add_executable(life       src/main.cpp        src/life.cpp)
add_executable(life_tests tests/life_test.cpp src/life.cpp)
add_executable(life_bench bench/bench_life.cpp src/life.cpp)

# Lets `ctest --test-dir build` run the tests too.
enable_testing()
add_test(NAME life_tests COMMAND life_tests)

Version and project

cmake_minimum_required(VERSION 3.25) must be the first command. CMake has changed its behaviour in small ways over the years, and this line says "interpret this file the way CMake 3.25 would"; anyone with an older CMake gets a clear error instead of a mysterious one. Your Mac has CMake 4.4, so the line is satisfied.

project(life LANGUAGES CXX) names the project and declares the languages; CXX is C++. This is the command that makes CMake go and look for a C++ compiler. Without LANGUAGES CXX it would also look for a C compiler you do not need.

Which C++

Three set commands follow. set(NAME value) gives a variable a value. A CMake variable is simpler than a C++ one: it has no type and no size in bytes, it holds nothing but a piece of text, and it exists only while CMake is reading the recipe. The names that begin with CMAKE_ are variables CMake itself reads when it writes the plan; set on one of those is how you change CMake's behaviour.

CMAKE_CXX_STANDARD 23 says which edition of the language you are writing. This is what puts -std=...23 on every compile command, instead of you remembering it.

CMAKE_CXX_STANDARD_REQUIRED ON says "and if the compiler cannot do C++23, stop with an error". Without it, CMake would quietly fall back to an older standard, and you would get baffling errors about std::println not existing.

CMAKE_CXX_EXTENSIONS OFF fixes the oddity from the toy project. Compilers offer small non-standard extras on top of the standard; clang signals "standard plus extras" with -std=gnu++23, and CMake asks for the extras by default. Turning extensions OFF gives plain -std=c++23, the flag you have used since chapter 1. The point is portability: code that relies on one compiler's extras may not compile on another, and in week 6 you move to a second compiler on Linux.

Try it

In the toy project, add the line set(CMAKE_CXX_EXTENSIONS OFF) after the set(CMAKE_CXX_STANDARD 23) line, run cmake --build build (watch it print Re-running CMake... first), then ninja -C build -t commands hello_cmake | head -1. The flag is now -std=c++23. Remove the line, build, and look again: -std=gnu++23 is back. One recipe line, one compiler flag; that is the whole relationship between the two files.

A map for your editor

set(CMAKE_EXPORT_COMPILE_COMMANDS ON) asks CMake to write one more file into the build folder, compile_commands.json, listing the exact compile command for every source file. The compiler never reads it. Your editor does, so it can show you errors as you type. This gets its own section further down.

A default build type

if(NOT CMAKE_BUILD_TYPE)
  set(CMAKE_BUILD_TYPE Debug)
endif()

CMake has if, written as if(...), a body, and endif(). CMAKE_BUILD_TYPE chooses between a Debug build (no optimisation, debugging information, and in this recipe the sanitizers) and a Release build (full optimisation, nothing else). If you passed -DCMAKE_BUILD_TYPE=Debug on the configure line, the variable already has a value and the if does nothing. If you passed nothing, CMake leaves it empty, which means "neither": no -g, no -O, no sanitizers. (-g and -O are the compiler's flags for debugging information and for optimisation; the section "Debug and Release: two folders" below shows both on real command lines.) Empty is a poor default for a learner, so this block fills in Debug. So cmake -S . -B build -G Ninja on its own gives a Debug build, and you only need -D for something else.

Warnings for every file

add_compile_options(-Wall -Wextra -Wpedantic) appends flags to every compile command in the project. You know -Wall and -Wextra from the first chapter. -Wpedantic adds warnings about anything that is not strictly standard C++, the same portability idea as CMAKE_CXX_EXTENSIONS OFF from the other side: extensions are off, and if you accidentally use one anyway, the compiler tells you.

Sanitizers in Debug only

if(CMAKE_BUILD_TYPE STREQUAL "Debug")
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
  add_link_options(-fsanitize=address,undefined)
endif()

STREQUAL compares two strings for equality, so this block runs only when the build type is Debug. Inside, three flags you have met through tools/run.sh since chapter 0; chapters 2 and 6 showed what the sanitizers catch, so here is only what each flag asks the compiler to do:

  • -fsanitize=address is AddressSanitizer (ASan): a check in front of every memory read and write, which is what catches a read past the end of a vector and produces the report chapter 6 decoded.
  • -fsanitize=undefined is UndefinedBehaviorSanitizer (UBSan): checks at the operations the standard leaves undefined, such as the signed overflow you watched in chapter 2. The two sanitizers are listed together, separated by a comma.
  • -fno-omit-frame-pointer asks the compiler to keep a small piece of bookkeeping that records how functions called each other. It lives in a register, one of the few dozen storage slots built into the CPU itself, far faster than memory and therefore precious. Normally an optimiser may reuse that slot for something else to save an instruction or two. The sanitizers use it to print the chain of calls (main called step called count_neighbours) that led to the error, which is what makes the report readable.

The sanitizers must be present both when compiling (to insert the checks) and when linking (to pull in the library that prints the reports), which is why -fsanitize appears in add_compile_options and again in add_link_options. Forget the second and you get a long linker error about missing __asan_ symbols.

Why Debug only? Because the checks are not free: a sanitized program is typically two to three times slower and uses more memory. For finding bugs that is a bargain; for the benchmark number this week ends with, it would make the number meaningless. Debug for correctness, Release for speed, and the recipe remembers the flags for you.

Here is the difference made visible. Put this file and recipe in scratch/ch11/oops. The program writes one position past the end of a four-element vector, the bug the sanitizers exist for.

#include <print>
#include <vector>

int main() {
    std::vector<int> scores(4, 0);   // positions 0, 1, 2, 3
    int position = 4;                // one past the end
    scores[position] = 99;           // writes outside the vector
    std::println("wrote 99 to position {}", position);
    return 0;
}

cmake_minimum_required(VERSION 3.25)
project(oops LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

if(NOT CMAKE_BUILD_TYPE)
  set(CMAKE_BUILD_TYPE Debug)
endif()

add_compile_options(-Wall -Wextra -Wpedantic)

if(CMAKE_BUILD_TYPE STREQUAL "Debug")
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
  add_link_options(-fsanitize=address,undefined)
endif()

add_executable(oops oops.cpp)

Configure and build it twice, into two folders, with two build types. As in chapter 6, the long numbers starting with 0x are memory addresses and the ==63167== is a process id; both differ on every run. The words are what you read.

$ cd scratch/ch11/oops
$ cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
...
$ cmake --build build
[1/2] Building CXX object CMakeFiles/oops.dir/oops.cpp.o
[2/2] Linking CXX executable oops
$ ./build/oops
=================================================================
==63167==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x6020000000e0 at pc 0x000100d01718 bp 0x00016f0fdc30 sp 0x00016f0fdc28
WRITE of size 4 at 0x6020000000e0 thread T0
    #0 0x000100d01714 in main oops.cpp:7
    #1 0x000186c214e0 in start+0x1b4c (dyld:arm64e+0x204e0)

0x6020000000e0 is located 0 bytes after 16-byte region [0x6020000000d0,0x6020000000e0)
...
$ cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
...
$ cmake --build build-release
[1/2] Building CXX object CMakeFiles/oops.dir/oops.cpp.o
[2/2] Linking CXX executable oops
$ ./build-release/oops
wrote 99 to position 4

Same source, same recipe. The Debug build stops at line 7 and says it wrote 4 bytes just after a 16-byte region (four ints of 4 bytes each). It does not reach the println, and it exits with a non-zero status so that anything waiting on it, such as ctest, knows it failed. The Release build writes 99 somewhere it does not own, prints a cheerful message, and exits with status 0. The program has no defined meaning. Today it happened to look fine; tomorrow, with a bigger vector, it corrupts something and crashes far from the real cause. This is why every test run this week happens in the Debug build.

One more thing to notice: the compiler never warned, in either build, even though position is plainly 4. scores[position] is a call to a function inside std::vector, and the compiler does not check what a function will do with its argument. A vector's bounds are checked only while the program runs, and only if something like ASan is watching.

Where the headers are

include_directories(src ${CMAKE_CURRENT_SOURCE_DIR}/../../third_party/doctest) adds -I options to every compile command. Each argument is a folder in which the compiler should look when it meets #include "something.h".

The first, src, is relative to the project folder, so #include "life.hpp" works from tests/life_test.cpp and bench/bench_life.cpp even though they live elsewhere. The second uses a variable reference: ${CMAKE_CURRENT_SOURCE_DIR} is replaced by the absolute path of the folder holding this CMakeLists.txt, so the whole thing reads "from this folder, go up two levels to the repo root and into third_party/doctest". That is where doctest.h, the single-file test framework for chapter 12, is kept. A copy is checked into the repo, so nothing needs installing. The path is written relative to the recipe, not as an absolute /Users/dan/.... That is what lets the same file work on any machine, including the Linux container in week 6.

Three programs from four files

add_executable(life       src/main.cpp        src/life.cpp)
add_executable(life_tests tests/life_test.cpp src/life.cpp)
add_executable(life_bench bench/bench_life.cpp src/life.cpp)

This is the heart of the recipe. add_executable(name sources...) declares a target: a program to be built, with the list of .cpp files that make it. Headers are not listed; the compiler finds them through #include and the -I folders, and Ninja learns about them from the dependency files you saw earlier.

Each line is one program, and the sources after the name are exactly the files you would have typed on the clang++ line. Read down the second column: main.cpp, life_test.cpp, bench_life.cpp. Each contains a main function, and a program may have only one, which is why they cannot be combined. Read down the third column: life.cpp three times. That file holds the functions all three programs need, and the only way a program can call step is to have life.cpp compiled into it.

Is compiling life.cpp three times wasteful? A little; you can see life.cpp.o produced once per target in the build output below. It is also completely fine: the three compiles run in parallel, take a fraction of a second, and keep the recipe at three readable lines. CMake has a tidier way (compile life.cpp once into a library, then link it into each program), and you will meet it in week 3.

Telling CMake about the tests

enable_testing() switches on CMake's test runner support for this folder, and add_test(NAME life_tests COMMAND life_tests) registers one test named life_tests whose command is the life_tests program. The convention is simple: the test passes if the program exits with 0, fails otherwise. doctest, which you meet in chapter 12, exits with 1 when any check fails, so the two agree. These two lines are what make ctest work, shown below.

Everything from the recipe is in both: the two -I folders, -std=c++23, the three warning flags. The Debug line adds -g, which stores debugging information (variable names, line numbers) so that error reports and, from week 3, the debugger can point at your source, plus the sanitizer flags from the if block. The Release line has neither and instead has -O3 -DNDEBUG. Careful with that -D: it is the compiler's -D, not CMake's. Two different programs happen to use the same letter. CMake's -DNAME=value on the configure line sets a CMake variable; the compiler's -DNAME defines a name for the #include machinery from chapter 10, as if the file began with #define NAME. NDEBUG ("no debug") switches off assert checks, a self-check mechanism you have not used yet. -O3 is the optimiser, and it deserves a paragraph.

An optimiser is the part of the compiler that rewrites your program into a faster one with the same visible behaviour. -O0, the default when no -O is given, does almost none of this: every variable gets a slot in memory, every statement becomes machine code in the order you wrote it, every function call is a real call. That is easy to debug and slow. At -O2 and -O3 the compiler does four big things. It keeps values in the CPU's registers (the fast built-in slots mentioned above) instead of memory. It removes computations whose result is never used. It reorders instructions so the CPU is never waiting. And it inlines small functions: it pastes the body of index_of into the place that called it instead of jumping there and back. For a loop over a million cells that calls index_of and wrap many times per cell, the difference is typically five to thirty times. CMake's Release type picks -O3, the most aggressive level; -O2 is a common conservative choice, and in week 6 you will measure them against each other.

So: Debug for correctness, Release for numbers. Never report a benchmark from a Debug build, and never trust a Release build that has not passed the tests in Debug. Chapter 13 builds life_bench both ways on the 1000 by 1000 grid and puts the two numbers side by side in BENCH.md; the ratio is your first concrete measurement of what the optimiser is worth.

First principle

One source tree, many build folders. Debug, Release, a build with a different compiler, a build for Linux: each is one more -B folder with its own CMakeCache.txt. They never interfere, because nothing in them is shared, and any of them can be deleted and remade. The sources are the truth; the builds are views of it.

Trap

The folder name means nothing to CMake. If you type cmake -S . -B build-release -G Ninja and forget -DCMAKE_BUILD_TYPE=Release, the if(NOT CMAKE_BUILD_TYPE) block fills in Debug, and you have a folder called build-release full of sanitized, unoptimised programs. Your benchmark number will be somewhere between ten and a hundred times too slow (the missing optimiser and the extra sanitizer checks multiply) and you will not know why. Check what a folder really is with grep CMAKE_BUILD_TYPE build-release/CMakeCache.txt; it prints CMAKE_BUILD_TYPE:STRING=Release when all is well and CMAKE_BUILD_TYPE:STRING= (empty) when you forgot. The fix is to run the configure line again with the -D; CMake updates the cache in place, and the next build recompiles everything with the new flags.

compile_commands.json and your editor

Because the recipe set CMAKE_EXPORT_COMPILE_COMMANDS ON (and your shell asks for the same thing, which is why the toy project had one too), the build folder contains a file your editor can use. It is plain text in JSON format (a widely used way of writing lists and name/value pairs so that programs can read them: square brackets for a list, curly brackets for one entry, "name": value inside), one entry per source file. It looks like this (shortened; notice that the ccache prefix is left out here, because the editor wants the compiler, not the cache):

[
{
  "directory": "/Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/build",
  "command": "/usr/bin/c++ -I/Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/src -I/Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/../../third_party/doctest -g -std=c++23 -arch arm64 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -fno-omit-frame-pointer -o CMakeFiles/life.dir/src/main.cpp.o -c /Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/src/main.cpp",
  "file": "/Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/src/main.cpp",
  "output": "/Users/dan/Desktop/projects/cpp-101/phase1-terminal/01-life/build/CMakeFiles/life.dir/src/main.cpp.o"
},
...
]

Why does an editor need this? When your editor underlines a mistake before you compile, it is running the front half of a real compiler on your file as you type. The program that does this is called a language server; for C++ it is clangd, a helper built from the same code as clang++. Zed, the editor from chapter 0's machine table, uses clangd out of the box; VS Code gets it through the clangd extension; CLion has it built in. To do that correctly it must know what the build knows: which standard, which -I folders, which flags. Without them, every #include "doctest.h" is a false error and std::println is "not found". compile_commands.json is how CMake hands those facts to the editor, per file.

clangd looks for the file in the folder of the source you have open, then in each parent folder. In each of those it also peeks into a sub-folder named exactly build/. So for the Life project, with its Debug build in build/, it finds the file on its own. The lookup breaks as soon as your build folder has another name (build-release/, or build-asan/ later in the curriculum). And clang-tidy, the checker from goal.md's formatting row that you set up in week 3, does not peek into build/ at all; it wants the file beside the sources. The convention in this repo is therefore to make a link from the project folder, once:

$ cd phase1-terminal/01-life
$ ln -s build/compile_commands.json compile_commands.json

A symbolic link is a small file that points at another file; the editor follows it and sees the real one. Because CMake rewrites the real file every time it configures, the link never goes stale, and compile_commands.json is in .gitignore so the link is never committed. If your editor insists on the repository root instead, make the link there, pointing at phase1-terminal/01-life/build/compile_commands.json. Reload the editor window afterwards and the red underlines should match what cmake --build would say.

Adding a new source file

Week 1 does not need a new source file, but the stretch goals and every later week will, so here is the procedure on a toy. Suppose you have a two-file greeting program in scratch/ch11/greet:

#pragma once
#include <string>

// Builds a greeting for one person.
std::string greeting_for(const std::string& name);

#include "greet.hpp"

std::string greeting_for(const std::string& name) {
    return "Hello, " + name + "!";
}

cmake_minimum_required(VERSION 3.25)
project(greet LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 23)
add_executable(greet main.cpp greet.cpp)

Configure and build it once, so there is a plan and a working program to start from:

$ cd scratch/ch11/greet
$ cmake -S . -B build -G Ninja
...

Then main.cpp calls both:

#include <print>
#include "greet.hpp"
#include "farewell.hpp"

int main() {
    std::println("{}", greeting_for("Danish"));
    std::println("{}", farewell_for("Danish"));
    return 0;
}

Build without touching the recipe and you get the third failure from the previous section, because CMake does not scan folders for .cpp files; it builds exactly what you list:

$ cmake --build build
[1/2] Building CXX object CMakeFiles/greet.dir/main.cpp.o
[2/2] Linking CXX executable greet
FAILED: [code=1] greet

Undefined symbols for architecture arm64:
  "farewell_for(std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&)", referenced from:
      _main in main.cpp.o
ld: symbol(s) not found for architecture arm64
clang++: error: linker command failed with exit code 1 (use -v to see invocation)
ninja: build stopped: subcommand failed.

(The long std::__1::basic_string<...> is the linker's full name for std::string. Read it as "farewell_for taking a const std::string&".) The fix is the one line: add the new file to the target.

add_executable(greet main.cpp greet.cpp farewell.cpp)

$ cmake --build build

See the first line: Ninja saw that CMakeLists.txt was newer than the plan, reran CMake, then built with the new file included. Only farewell.cpp was compiled; main.cpp.o and greet.cpp.o from the failed attempt were still good and were reused. (The counter says /3 but you see only two numbered lines because the CMake re-run was the third step; Ninja printed it as [0/1] before it knew the total.) The rule: new .cpp file, one more word on the add_executable line. New header: nothing to do, as long as it sits in a folder the compiler already searches.

Try it

What comes later

Other projects' recipes use commands this chapter did not, and it helps to know they exist. add_library(name sources...) compiles a set of files once into a library, and target_link_libraries(program library) attaches it to each program that needs it; that is how a grown-up version of this recipe would avoid compiling life.cpp three times. target_include_directories(name PUBLIC folder) and target_compile_options(name PRIVATE flags) attach include folders and flags to one target rather than to every file in the folder as include_directories and add_compile_options do. These target-scoped commands are the modern style and scale to hundreds of targets; you switch to them in week 3 when the shared common/ headers appear. For a four-file project, the directory-scoped commands are shorter and say the same thing.

Inference twin

llama.cpp is built with exactly the two commands you learned today: cmake -B build (with no -S, CMake takes the current folder as the source folder) and cmake --build build. Its recipe has the same if(NOT CMAKE_BUILD_TYPE) block as yours, except that it fills in Release, because its users want speed; and with no -G it takes your machine's default generator, which on your Mac is Ninja. Its top-level CMakeLists.txt is about three hundred lines and pulls in the ggml/ and src/ recipes with add_subdirectory, yet it is made of the same ideas: project, set(CMAKE_CXX_STANDARD 17) (in ggml/), if(...) blocks that turn features on and off, add_library for ggml and for llama itself, add_executable for the tools, and -D options such as -DGGML_CUDA=ON that you pass on the configure line. When you open it in week 27 you will skim it rather than study it, because every command will be one you have met.

Check yourself

CMake and Ninja: which one reads CMakeLists.txt, which one runs the compiler, and what file passes between them?

Answer

CMake reads CMakeLists.txt and generates build.ninja in the build folder. Ninja reads build.ninja and runs the compiler and linker commands listed there, in parallel, skipping the ones whose outputs are already up to date. Ninja never reads CMakeLists.txt.

You run cmake -S . -B build -G Ninja on the Life project with no -D. Which build type do you get, and which line of the recipe decides it?

Answer

Debug. CMake leaves CMAKE_BUILD_TYPE empty when you pass nothing, and the block if(NOT CMAKE_BUILD_TYPE) set(CMAKE_BUILD_TYPE Debug) endif() fills in Debug. Empty on its own would mean no -g, no -O and no sanitizers.

Why does src/life.cpp appear in all three add_executable lines, and why can the three programs not be merged into one?

Answer

Each program calls functions defined in life.cpp, and the only way a program gets a definition is by having that file compiled and linked into it. They cannot be merged because main.cpp, life_test.cpp and bench_life.cpp each contain a main, and a program may have exactly one.

The sanitizers are enabled only when CMAKE_BUILD_TYPE STREQUAL "Debug". Give one reason for having them on and one for having them off.

Answer

On: they catch memory errors and undefined behaviour at the moment they happen, with a file and line, instead of letting the program silently corrupt memory. Off: they make the program two to three times slower and heavier, which would make the Release benchmark number meaningless.

You rename the folder 01-life to life-game and run cmake --build build. What happens and what do you do?

Answer

CMake reports that the CMakeCache.txt directory differs from the one it was created in, then fails to find the old source folder. The build folder stores absolute paths. Delete it (rm -rf build) and configure again; nothing you wrote lives in there.

Compilation succeeds for every file, then the link step prints Undefined symbols ... "wrap(int, int)", referenced from: ... in life_test.cpp.o. Which file is probably wrong, and which line do you check?

Answer

Not life_test.cpp; it only calls wrap. The file that defines wrap (src/life.cpp) is missing from the add_executable(life_tests ...) line in CMakeLists.txt. Add it there.

What is compile_commands.json for, and who reads it?

Answer

It lists the exact compile command for every source file (standard, include folders, flags). Your editor's language server (clangd, which Zed uses out of the box, VS Code via the clangd extension, and CLion built in) reads it so that the errors it shows as you type match what the real build would say. The compiler and Ninja do not use it.

In one sentence each: what does -O0 do, and what does -O3 do?

Answer

-O0 translates the program almost literally: every variable in memory, every statement in order, every call a real call, which is slow but easy to debug. -O3 rewrites it for speed with the same visible behaviour: values kept in registers, dead computations removed, instructions reordered, small functions inlined into their callers.
