The problem: a queue at a counter

A post office counter has a queue. People take a ticket and join at the back; the clerk serves the person at the front, who leaves. Two ends, two jobs. Store the tickets in a std::vector<int> and the back is easy: push_back, which you have used since Week 1. The front is another story. A vector has no push_front, and no cheap way to remove its first element, because its elements must stay in one unbroken block in order: element 0 first, then element 1, and so on. Change who is first and everyone's position changes.

Here is what that means, done by hand with index loops. Someone with an appointment goes to the front, and then the first person is served:

#include <cstddef>
#include <print>
#include <vector>

void print_queue(const std::vector<int>& queue) {
    std::print("queue:");
    for (int ticket : queue) {
        std::print(" {}", ticket);
    }
    std::println("");
}

// Put a ticket at the front: every ticket already waiting moves one place back.
int insert_at_front(std::vector<int>& queue, int ticket) {
    queue.push_back(0);                       // one more place, at the back
    int moves = 0;
    for (std::size_t i = queue.size() - 1; i > 0; --i) {
        queue[i] = queue[i - 1];              // from the back: each ticket steps back one place
        ++moves;
    }
    queue[0] = ticket;
    return moves;
}

// Serve the first ticket: every ticket behind it moves one place forward.
int serve_front(std::vector<int>& queue) {
    int moves = 0;
    for (std::size_t i = 0; i + 1 < queue.size(); ++i) {
        queue[i] = queue[i + 1];
        ++moves;
    }
    queue.resize(queue.size() - 1);           // the last place is now a duplicate: drop it
    return moves;
}

int main() {
    std::vector<int> queue = {41, 42, 43, 44, 45};
    print_queue(queue);

    int moves = insert_at_front(queue, 40);   // ticket 40 has an appointment
    print_queue(queue);
    std::println("moves to put one ticket at the front: {}", moves);

    moves = serve_front(queue);
    print_queue(queue);
    std::println("moves to serve the first ticket:      {}", moves);
    return 0;
}

queue: 41 42 43 44 45
queue: 40 41 42 43 44 45
moves to put one ticket at the front: 5
queue: 41 42 43 44 45
moves to serve the first ticket:      5

insert_at_front makes room at the back with a push_back, then walks from the back to the front, copying each ticket one place back, and only then writes the new ticket into place 0. It must walk from the back: walk from the front and you would copy ticket 41 over 42, then that 41 over 43, and so on down the line. serve_front is the mirror image: everyone steps forward one place, and resize drops the last place, which now holds a duplicate. Each operation moved all five waiting tickets. With a thousand people in the queue, it is a thousand moves to serve one person.

(A vector does have a function, insert, that puts an element anywhere, including the front. It takes an iterator, a way of naming a position that this course meets later, and inside it does the same shifting. It is shorter to write, not faster to run.)

First principle

A vector promises one unbroken block with element 0 at its start. That promise is what makes v[i] one multiplication and one addition, and it is also why the front is expensive: anything that changes which element is first must move every element. A container that wants a cheap front has to give up that promise.

Timing it

The C++ library has a container that gave up the promise: std::deque, from the header <deque>. Its name is short for double-ended queue and is pronounced "deck". Before learning its interface, measure it against the vector on the one operation that matters here, putting a value at the front, with the steady_clock pattern from Week 1's chapter 9:

#include <chrono>
#include <cstddef>
#include <deque>
#include <print>
#include <vector>

// Put value at the front of v by hand: every element moves one place towards the back.
void shift_in_front(std::vector<int>& v, int value) {
    v.push_back(0);
    for (std::size_t i = v.size() - 1; i > 0; --i) {
        v[i] = v[i - 1];
    }
    v[0] = value;
}

int main() {
    using clock = std::chrono::steady_clock;
    using std::chrono::duration_cast;
    using std::chrono::microseconds;

    const std::vector<int> sizes = {25000, 50000, 100000};
    for (int n : sizes) {
        std::vector<int> v;
        const auto t0 = clock::now();
        for (int i = 0; i < n; ++i) {
            shift_in_front(v, i);
        }
        const auto t1 = clock::now();

        std::deque<int> d;
        const auto t2 = clock::now();
        for (int i = 0; i < n; ++i) {
            d.push_front(i);
        }
        const auto t3 = clock::now();

        // Print the front of each, so that the compiler cannot skip the work.
        std::println("{:6} at the front: vector {:8} us, deque {:4} us  (front: {} and {})", n,
                     duration_cast<microseconds>(t1 - t0).count(),
                     duration_cast<microseconds>(t3 - t2).count(), v[0], d[0]);
    }
    return 0;
}

(The first run of the program gave 30 ms instead of 12 for the smallest vector case, the first-run effect chapter 13 warned about, which is why you run a measurement more than once.) Under two tenths of a millisecond for the deque, more than a quarter of a second for the vector: about 1,600 times. In a Debug build with the sanitizers, as tools/run.sh makes, the same program took 40 seconds for the vector at 100,000 and 10 ms for the deque, so build this one with -O2.

The ratio is not a constant, and that is the real lesson. Look at how each column grows as n doubles. The deque goes 47, 86, 172: twice the work, twice the time. The vector goes 12, 60, 272 ms: four to five times for each doubling. Count the moves to see why. The first insertion moves 0 elements, the second 1, the third 2, and the last one n - 1. The total is 0 + 1 + 2 + ... + (n - 1), which is n × (n - 1) / 2: for 100,000 insertions, almost 5 billion moves. Double n and that total roughly quadruples. A cost that grows with the square of the size is called quadratic; one that grows in proportion to the size, like the deque's, is linear. At 10 elements nobody can tell them apart. At 100,000 one of them is unusable.

Analogy

A deque is a train. You can couple a carriage at the front or at the back, and the carriages already in the train do not move. A vector is a row of cinema seats bolted to the floor: someone arriving for seat 1 means everyone gets up and moves along. Where it breaks: a train's carriages are all the same size and hold one passenger list each. A deque's "carriages" are blocks of memory that each hold many elements, and a train has no index: you cannot ask a train for carriage 7 without walking along it, whereas a deque can find element 7 directly, with a little arithmetic. The layout section below shows both.

The deque's interface

A deque does everything a vector does with its back, the same things at its front, and keeps []:

#include <deque>
#include <print>

void show(const std::deque<int>& waiting) {
    std::print("waiting ({}):", waiting.size());
    for (int ticket : waiting) {
        std::print(" {}", ticket);
    }
    std::println("");
}

int main() {
    std::deque<int> waiting;                 // empty at opening time
    std::println("empty: {}", waiting.empty());

    waiting.push_back(41);                   // people join at the back
    waiting.push_back(42);
    waiting.push_back(43);
    show(waiting);

    waiting.push_front(40);                  // an appointment goes straight to the front
    show(waiting);

    std::println("first: {}, last: {}, second: {}", waiting.front(), waiting.back(), waiting[1]);

    waiting.pop_front();                     // 40 is served and leaves from the front
    show(waiting);

    waiting.pop_back();                      // 43 gives up and leaves from the back
    show(waiting);

    waiting[0] = 99;                         // [] can change an element, as in a vector
    show(waiting);

    waiting.clear();                         // closing time: everyone goes home
    std::println("size: {}, empty: {}", waiting.size(), waiting.empty());
    return 0;
}

waiting (3): 41 42 43
waiting (4): 40 41 42 43
first: 40, last: 43, second: 41
waiting (3): 41 42 43
waiting (2): 41 42
waiting (2): 99 42
size: 0, empty: true
OperationWhat it does
d.push_back(x), d.push_front(x)Add x at the back, or at the front. Nothing already in the deque moves.
d.pop_back(), d.pop_front()Remove the last, or the first, element. They return nothing: read the element first if you need it.
d.front(), d.back()The first and the last element, by reference: you can read them or assign to them.
d[i]Element i, counted from the front, from 0, like a vector. After a push_front, every element's number goes up by one.
d.size(), d.empty()How many elements (a std::size_t), and whether there are none.
d.clear()Remove every element. The size becomes 0.
for (int x : d)Every element, front to back. By const& for big elements, as with a vector.

A deque can also be built from a list in braces, std::deque<int> waiting = {41, 42, 43};, and compared with == against another deque of the same type: equal when the sizes and every element match, as for vectors. Notice that the two pops return nothing. To serve the first person you read front() and then pop_front(), two steps, and that order matters, because of the rule in the next section.

Never ask an empty deque

What is the first element of an empty queue? There is none, and C++ does not check for you: front(), back(), pop_front() and pop_back() on an empty deque are undefined behaviour. Here is the version that does the most damage, a queue that has just been emptied by serving everyone:

#include <deque>
#include <print>

int main() {
    std::deque<int> waiting;
    waiting.push_back(41);
    waiting.push_back(42);
    waiting.pop_front();                // 41 served
    waiting.pop_front();                // 42 served: nobody is waiting now
    std::println("empty: {}", waiting.empty());
    std::println("serving ticket {}", waiting.front());   // undefined behaviour
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra emptied_front.cpp -o emptied_front && ./emptied_front
empty: true
serving ticket 0

The deque says it is empty, and then front() serves ticket 0, a ticket nobody ever took, and the program ends normally. The deque's memory is still there after the last pop_front, so front() read a place that held no element and returned whatever it contained. On a deque that had never held anything, the same call crashed here instead, with a segmentation fault: undefined behaviour does not promise to be consistent. Trap

Check empty() before every front(), back(), pop_front() or pop_back(), unless the line just above it guarantees an element. Without the sanitizers this mistake can return a believable number, and the program carries on with a ticket that never existed.

The safe shape asks first and has an answer for "nobody":

#include <deque>
#include <print>

// Serve the next person, if there is one. Returns the ticket, or 0 when nobody is waiting.
int serve_next(std::deque<int>& waiting) {
    if (waiting.empty()) {
        return 0;                            // ask first: front() on an empty deque is undefined
    }
    const int ticket = waiting.front();
    waiting.pop_front();
    return ticket;
}

int main() {
    std::deque<int> waiting = {41, 42};
    for (int call = 0; call < 3; ++call) {
        const int ticket = serve_next(waiting);
        if (ticket == 0) {
            std::println("nobody is waiting");
        } else {
            std::println("now serving {}", ticket);
        }
    }
    return 0;
}

now serving 41
now serving 42
nobody is waiting

Returning 0 for "nobody" works only because no ticket is numbered 0, and the caller has to know that agreement, the same weakness as the traffic light stored in an int in chapter 2. Chapter 5 gives C++'s proper way to say "maybe a value, maybe nothing".

How a deque is laid out

How can a deque add at the front without moving anything? It does not keep one block. It keeps its elements in several blocks of the same fixed size, plus a small table, often called the map, that lists where each block is, in order. On your Mac (libc++, Apple's C++ library) a block is 4,096 bytes: 1,024 ints or 512 doubles. The figure uses blocks of four to fit on the page:

               the table: where each block is, in order
               +---------+---------+---------+
               | block 0 | block 1 | block 2 |
               +----+----+----+----+----+----+
                    |         |         |
        +-----------+         |         +-----------+
        v                     v                     v
  +----+----+----+----+ +----+----+----+----+ +----+----+----+----+
  |    |    | 40 | 41 | | 42 | 43 | 44 | 45 | | 46 | 47 |    |    |
  +----+----+----+----+ +----+----+----+----+ +----+----+----+----+
              ^ front                                   ^ back
   free places for push_front              free places for push_back

The deque itself, the variable, remembers where the table is, where in the first block the front element sits, and how many elements there are. push_front(39) writes 39 into the free place just before 40: nothing moves. When the first block has no free place left, the deque allocates a new block, writes 39 into its last place, and adds the new block's address at the front of the table. The table may itself have to grow now and then, but it is tiny (one entry per 1,024 ints), so copying it is cheap. The back works the same way. No element ever moves when you push or pop at either end. That is the trade the deque makes: it gives up "one unbroken block" and gets two cheap ends.

#include <deque>
#include <print>
#include <vector>

int main() {
    std::vector<int> v;
    std::deque<int> d;
    std::println("sizeof(std::vector<int>) = {}", sizeof(v));
    std::println("sizeof(std::deque<int>)  = {}", sizeof(d));
    for (int i = 0; i < 100000; ++i) {
        v.push_back(i);
        d.push_back(i);
    }
    std::println("with 100000 ints each: {} and {}", sizeof(v), sizeof(d));
    return 0;
}

sizeof(std::vector<int>) = 24
sizeof(std::deque<int>)  = 48
with 100000 ints each: 24 and 48

Like a vector, the variable is a fixed-size handle with the elements elsewhere: 48 bytes here against the vector's 24, because it records more (the table's extent, the position of the front and the size), and it stays 48 bytes with 100,000 elements.

Why its [] is slower

The price of the blocks is paid in []. For a vector, v[i] is "the start, plus i elements": one address calculation and one read. For a deque, d[i] first adds the position of the front element within its block, then splits the result with / and % into a block number and a place in that block, exactly the inverse of Week 1's flat index, reads the block's address from the table, and only then reads the element. In the figure, d[3]: the front sits at place 2 of block 0, so 2 + 3 = 5, block 5 / 4 = 1, place 5 % 4 = 1: block 1, place 1, which holds 43. Because 1,024 is a power of two, the compiler turns the division and remainder into cheap bit operations, but the extra read of the table remains. How much does it cost? Sum ten million ints each way:

#include <chrono>
#include <cstddef>
#include <deque>
#include <print>
#include <vector>

int main() {
    using clock = std::chrono::steady_clock;
    using std::chrono::duration_cast;
    using std::chrono::microseconds;

    const int n = 10000000;
    std::vector<int> v;
    std::deque<int> d;
    for (int i = 0; i < n; ++i) {
        v.push_back(i % 7);
        d.push_back(i % 7);
    }

    long long a = 0;
    const auto t0 = clock::now();
    for (std::size_t i = 0; i < v.size(); ++i) {
        a += v[i];
    }
    const auto t1 = clock::now();

    long long b = 0;
    for (std::size_t i = 0; i < d.size(); ++i) {
        b += d[i];
    }
    const auto t2 = clock::now();

    long long c = 0;
    for (int x : d) {
        c += x;
    }
    const auto t3 = clock::now();

    std::println("vector [] : {:6} us  (sum {})", duration_cast<microseconds>(t1 - t0).count(), a);
    std::println("deque  [] : {:6} us  (sum {})", duration_cast<microseconds>(t2 - t1).count(), b);
    std::println("deque for : {:6} us  (sum {})", duration_cast<microseconds>(t3 - t2).count(), c);
    return 0;
}

The other part is that the elements of a vector are one unbroken block, and the compiler used that: the assembly of the vector loop contains the processor's vector instructions, which add several numbers in one go (week 12 is about them), and neither deque loop does. For a queue, where you mostly touch the two ends, none of this matters. For a big array you read again and again, it does: that is still a vector's job.

A sliding window: the moving average

A weather station sends a temperature every hour. A single reading jumps about; the average of the last five is steadier, and it is the number you would put on a display. Keep the last five readings in a deque: each new reading joins at the back, and once there are more than five, the oldest leaves from the front. The readings inside are a sliding window: a fixed-length view that slides along the stream one value at a time.

#include <cstddef>
#include <deque>
#include <print>
#include <vector>

double mean_of(const std::deque<double>& window) {
    double sum = 0.0;
    for (double t : window) {
        sum += t;
    }
    return sum / static_cast<double>(window.size());
}

int main() {
    const std::vector<double> hourly = {3.5, 4.0, 5.5, 7.0, 8.5, 9.0, 8.0, 6.5, 5.0, 4.5};
    const std::size_t window_size = 5;

    std::deque<double> window;              // the last few readings, oldest at the front
    for (double t : hourly) {
        window.push_back(t);                // the newest reading joins at the back
        if (window.size() > window_size) {
            window.pop_front();             // the oldest one leaves from the front
        }
        std::println("new {:4.1f}   {} in the window   moving average {:5.2f}", t,
                     window.size(), mean_of(window));
    }
    return 0;
}

For the first four readings the window is still filling; from the fifth on it always holds five, and each line's average covers the five most recent hours. ({:4.1f} combines Week 1's width and decimals codes: four characters wide, one decimal.) Notice what each new reading costs: one push_back, at most one pop_front and a sum of five numbers. The work per reading never grows, however long the station runs: the window keeps the memory and the time of each step fixed. Keep that sentence for the inference twin at the end.

Searching a deque

A customer at the back of the queue asks the clerk: "Is ticket 42 still waiting, or have I missed my friend?" A deque has no built-in answer, so you write one with range-for: look at every ticket, and stop at the first that matches.

#include <deque>
#include <print>

// Is this ticket still in the queue? Compare it with every ticket until one matches.
bool is_waiting(const std::deque<int>& waiting, int ticket) {
    for (int t : waiting) {
        if (t == ticket) {
            return true;
        }
    }
    return false;
}

int main() {
    std::deque<int> waiting = {39, 40, 41, 42, 43};
    std::println("is 42 waiting? {}", is_waiting(waiting, 42));

    for (int served = 0; served < 4; ++served) {   // 39, 40, 41 and 42 are served
        waiting.pop_front();
    }
    std::println("is 42 waiting? {}", is_waiting(waiting, 42));
    std::println("is 43 waiting? {}", is_waiting(waiting, 43));
    return 0;
}

is 42 waiting? true
is 42 waiting? false
is 43 waiting? true

The return true inside the loop leaves the function at the first match; only if the loop finishes without one does the function reach return false. That makes the cost uneven. Finding a ticket near the front is quick. "No, it is not here" is the slowest answer of all, because it can only be given after comparing with every ticket: a queue of a thousand people means a thousand comparisons for every "no". The cost of a search grows linearly with the length of what you search, and if you search once for every new arrival, the total grows with the square, the vector's problem from the start of this chapter in a new place.

Passing a deque to a function

is_waiting takes its deque by const&, the same choice as for a vector in Week 1's chapter 5, for the same two reasons: no copy is made, and the compiler stops the function from changing the queue. Here are the three choices side by side:

#include <cstddef>
#include <deque>
#include <print>

// Only looks: const&, no copy, and the compiler stops it from changing the queue.
std::size_t length_of(const std::deque<int>& waiting) {
    return waiting.size();
}

// Changes the caller's queue: a plain &.
void serve(std::deque<int>& waiting) {
    if (!waiting.empty()) {
        waiting.pop_front();
    }
}

// By value: the function gets a whole copy of the queue and serves the copy.
void serve_a_copy(std::deque<int> waiting) {
    if (!waiting.empty()) {
        waiting.pop_front();
    }
    std::println("  inside serve_a_copy: {} waiting", waiting.size());
}

int main() {
    std::deque<int> waiting = {41, 42, 43};
    serve(waiting);
    std::println("after serve:        {} waiting", length_of(waiting));
    serve_a_copy(waiting);
    std::println("after serve_a_copy: {} waiting", length_of(waiting));
    return 0;
}

after serve:        2 waiting
  inside serve_a_copy: 1 waiting
after serve_a_copy: 2 waiting

serve takes a plain & and really serves someone. serve_a_copy takes the deque by value: it receives a complete copy, every block and the table included, serves the copy, and the copy is destroyed when the function ends, so the real queue still has two people. That is rarely what you want, and for a long queue the copy is expensive. How expensive, and when a copy is exactly right, is the subject of chapter 6, which times a big deque passed both ways.

Inference twin

When a language model writes a word, it looks back at every earlier word through attention. To avoid recomputing the past, it keeps two vectors of numbers per earlier token, its key and its value: the KV cache, which week 18 builds. With full attention the cache grows by one entry per token and every step reads all of it, so the attention in step 4,000 does about 4,000 times the work it did in step 1: a growing context makes each step cost more, like the search above. Sliding-window attention keeps only the last W tokens (Mistral 7B used W = 4,096): the newest token's key and value join at one end, the oldest leave at the other, and every step costs the same, exactly moving_average.cpp with bigger numbers. Engines do not use std::deque for it: the cache is large, often lives on a GPU, and must be one block, so they keep W fixed slots and wrap the position with %, Week 1's clock face. The shape is the deque's; the storage is the ring's.

Check yourself

Why does putting one element at the front of a vector of n elements move n elements, while a deque moves none?

Answer

A vector keeps its elements in one unbroken block starting with element 0, so a new first element means every existing element must shift one place back. A deque keeps fixed-size blocks and a table of where they are; the first block has free places before the front element, so push_front writes into one, or into a new block whose address is added to the table. Nothing that is already stored moves.

Putting 25,000 values at the front of a vector took 12 ms. Roughly how long would 100,000 take, and why not 48 ms?

Answer

Around 200 ms (the measured value was 272 ms). The total number of moves is n × (n - 1) / 2, which grows with the square of n: four times as many insertions means about sixteen times as many moves. That is quadratic growth; 48 ms would be linear.

What happens when you call front() on an empty deque?

Answer

Undefined behaviour. On this Mac it returned 0 for a deque that had been emptied by popping, and crashed for one that had never held anything; the sanitizers report container-overflow for the first. Check empty() first.

Explain, with the figure's blocks of four, how a deque whose front element sits at place 2 of block 0 finds d[6].

Answer

Add the front's position: 2 + 6 = 8. Block 8 / 4 = 2, place 8 % 4 = 0. Read the address of block 2 from the table, then place 0 of that block (in the figure, 46). A vector would need only "start plus 6".

In moving_average.cpp, why do the work and the memory per reading stay the same however many readings arrive?

Answer

The window never holds more than five readings: each new one is pushed at the back and, once there are more than five, the oldest is popped from the front. So each step does one push, at most one pop and a sum of at most five numbers.

Why is "ticket 50 is not waiting" the slowest answer is_waiting can give?

Answer

The search returns at the first match, so it can say "yes" early, but it can only say "no" after comparing with every ticket in the queue. The cost of a "no" is the length of the queue.

A function only needs to read a big deque. Which parameter type do you give it, and what would by value cost?

Answer

const std::deque<T>&: no copy, and the compiler stops the function from changing it. By value would copy every element, block by block, plus the table, on every call; chapter 6 measures that.

What you can do now

  • Explain why the front of a vector is expensive, and shift elements by hand to prove it.
  • Measure a vector against a deque with steady_clock, and tell quadratic from linear growth by doubling the size.
  • Use a deque's two ends, front, back, [], size, empty, clear and range-for.
  • Guard every front, back and pop with empty(), and recognise container-overflow.
  • Draw a deque's blocks and table, and say why its [] costs more than a vector's.
  • Keep a sliding window over a stream with push_back and pop_front.
  • Search a deque with range-for, and pass it by const& or & on purpose.
