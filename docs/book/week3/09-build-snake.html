Chapter 09

Build Snake

This is the chapter you work from in every Code block this week. It tells you what to build, in which order, which tests prove it, and where to look when you are stuck. By the end of it you will have written nine game functions, a terminal guard, a key reader and a main by hand, turned 26 tests green, played your own game, and measured what one tick costs. It never shows you the answer.

First principle

Hints, not solutions, exactly as in Week 1's chapter 14. The ladders below go close: they say what to compute, which statement goes where and what to test first, in words. They stop before the code. Climb one rung at a time, after you have re-read the failing test and the comment above the function in snake.hpp, and after you have tried the smallest version of the problem in scratch/.

The spec, restated

The full spec is phase1-terminal/02-snake/README.md, frozen by you in the spec ritual on Friday 20 November. If the ritual changed a rule, the README and the tests say so; where this chapter and the README disagree, the README wins. In one place:

The board. width columns by height rows, the wall outside them. Column x counts from 0 at the left, row y from 0 at the top, so up makes y smaller. The snake is a Body, a deque of Points, head first.

A tick. The heading becomes the wanted direction, unless no direction key was pressed or the wanted direction is the reverse of the heading. The head moves one cell. Into the wall or onto the body: the game is lost and the snake does not move (the cell the tail is leaving is not body, unless the snake is eating). Onto the food: the score goes up, the snake grows by one (its tail stays put), new food appears on a free cell, and if there is none the game is won. Otherwise the tail follows and the length stays the same.

The program. --width (default 30, 8 to 200), --height (15, 5 to 100), --seed (0, meaning "from the clock"). Bad arguments: one line, exit status 2, terminal untouched. A tick lasts tick_ms(score): 150 ms, 10 ms less per 5 points, never below 60. Arrows or wasd steer, p pauses, q quits; one key per tick, the first one read. Each tick one whole frame: the board from render, then a status line. Raw mode and a hidden cursor while it runs, and everything back to normal however it ends (lost, won, q, Ctrl-C), before the last line: score, length, ticks, late ticks, seed.

Setup, and how to use the milestones

Chapter 0 built the folder and read the red: 23 cases fail, 3 pass by accident. Keep a second terminal tab in phase1-terminal/02-snake with the build-and-test command ready:

$ cmake --build build && ./build/snake_tests
$ cmake --build build && ./build/snake_tests -tc="tick*"

The second form runs only the cases whose names start with tick; the * matches anything. Each milestone lists the cases it turns green. After each one, run the whole test binary to check nothing that was green turned red, commit with the suggested message, and ask for a review (the ritual is near the end of this chapter).

Each milestone's hint ladder has four rungs, the same four the tutor gives (CLAUDE.md): where to look, the idea in words, the shape (which statement goes where, still no code), and a worked example on a different problem, which is always one of the book's own programs. On this page the tutor adds a button after each ladder that asks for the next rung; it gives one rung per request and there is no rung 5.

Milestone 1: next_head and tick_ms

Goal. The two smallest functions of the game: where the head goes, and how long a tick lasts. Re-read: chapter 1 (making and returning a struct), chapter 2 (switch over an enum class). Turns green: next_head: one step in each direction (y grows downwards), next_head: knows nothing about the board and can step outside it, tick_ms: 150 ms then 10 ms faster every 5 points (never below 60 ms). Commit: M1: next_head and tick_ms green.

Rung 1: where to look

The comments above both functions in snake.hpp give the answers for several inputs, and the tests add more. For next_head: which of the two coordinates changes when the head moves up, and does it get bigger or smaller? Check your answer against the first test before you write a line. For tick_ms: what does the test expect at 4 points, and at 5? What does that tell you about when the speed changes?

Rung 2: the idea in words

next_head: start from the head's position. Moving up takes one off the row, down adds one to the row, left takes one off the column, right adds one to the column; the other coordinate stays as it is. The board is never consulted, so a step off the edge simply gives a coordinate of -1 or one past the last column or row. tick_ms: count how many complete groups of five points the score contains; each group takes ten milliseconds off one hundred and fifty; if what is left is below sixty, the answer is sixty.

Rung 3: the shape

next_head is one switch on the heading with a case per enumerator, and no default, so that -Wswitch tells you if a case is missing (chapter 2). Each case can return a Point straight away, built from the head's coordinates with one of them changed. Clang is satisfied when a switch returns from a case for every enumerator; decide anyway what your function does if control ever gets past the switch (it cannot with a valid Direction), and look at the printers at the top of the test file for one way to say it. tick_ms is three lines: an integer division (it rounds down, which is exactly "complete groups"), a multiplication and subtraction, and a comparison with the floor. Test the edges first: 0, 4, 5, 45 and 50.

Rung 4: the same mechanism on a different problem

Chapter 2's traffic light is a function that takes one enumerator and returns a value for each case of a switch; next_head is that shape with a Point as the answer. For tick_ms, Week 1's chapter 2 showed that integer division throws the remainder away: 12 / 5 is 2.

Common bugs. Up adds one instead of subtracting (the y axis points down here; it is the most common bug in every grid game). Swapping x and y. A missing case: -Wswitch names it ("enumeration value 'Left' not handled in switch"), and if nothing comes after the switch, -Wreturn-type adds "non-void function does not return a value in all control paths"; at run time UBSan reports the same thing the moment the missing case is used. In tick_ms, dividing after multiplying (score * 10 / 5 is not score / 5 * 10 for score 4).

Done when the three cases pass, the whole binary shows no new failures, and you can say why next_head({0, 0}, Direction::Left) must be allowed to return {-1, 0}.

Milestone 2: render

Goal. The board as text, wall included, in one string. Re-read: chapter 1 (reading a struct's members through const&), chapter 3 (you will want the debugger here), and Week 1's chapter 9 on why a frame is built as one string. Turns green: render: the wall and every kind of cell, render: height + 2 lines of width + 2 characters (snake drawn over food). Commit: M2: render green.

Rung 1: where to look

The comment above render draws a 4 by 2 board in full, and the first test is that same board. Count its characters on paper: how many lines, how many characters in each, where the newlines are. The second test checks the size of the whole string and three of its lines by position. Which cell of the board is the first character of the second line?

Rung 2: the idea in words

There are two ways to fill the picture. You can visit every cell and ask what is there (the head? some other part of the body? the food? nothing?), which means searching the body for every cell of the board. Or you can draw in layers, the way a painter does: first the wall and empty insides, then the food on top, then every part of the body, then the head last, so that later layers cover earlier ones. The second way never searches, and its order is the spec: the snake covers the food, and the head covers the body.

Rung 3: the shape

Build the whole frame first: a string of the right length, or one string per line that you join at the end. Work out on paper where the cell at column x, row y lands in the string: every line is width + 3 characters long counting its newline, and the first line and the first character of every line are wall. That position is the only arithmetic in the function; put it in one place and check it with the 4 by 2 example by hand. Then one assignment for the food, a range-for over game.body that writes 'o', and one more assignment that writes '@' at the head.

Rung 4: the same mechanism on a different problem

Week 1's chapter 7 turned a grid position into a position in one flat row of memory; the frame string is a flat grid whose rows are width + 3 long. Chapter 1 of this book walks a vector of structs with a range-for by const&, which is how you visit the body here.

Common bugs. Forgetting the newline in the line length, so every line after the first is shifted by one. Drawing the head before the body, so the head is overwritten with 'o'. Indexing a Body cell that is outside the board (a test never does that, but a buggy tick might later): the sanitizer will tell you, and lldb's frame variable shows which cell.

Done when both cases pass, and std::print("{}", render(g)) in a scratch program draws a board you recognise.

Milestone 3: on_body, steer and parse_key

Goal. Three small functions about the snake and the keyboard. Re-read: chapter 4 (searching a deque), chapter 5 (optional parameters and results), chapter 2 (several case labels sharing one statement). Turns green: on_body: ..., both steer: ... cases (one of them was green by accident; keep it green), and the four parse_key: ... cases. Commit: M3: on_body, steer and parse_key green.

Rung 1: where to look

on_body's test includes the head, the tail, and a cell whose coordinates are those of a body cell swapped: what is it guarding against? steer's two tests: which one passed before you wrote anything, and what will make it fail if you get the reversal rule wrong? parse_key: the comment lists every input; the third test lists the inputs that must give nothing, including two that look like the start of an arrow key. What happens in your function when the string is only one byte long and that byte is Escape?

Rung 2: the idea in words

on_body: look at every cell of the body; the answer is yes as soon as one of them is the point, and no if none is. steer: if no direction was wanted, keep the heading. If the wanted direction is the opposite of the heading (up and down are opposites, left and right are opposites), keep the heading. Otherwise take the wanted one. parse_key: decide from the first byte alone, except for Escape. Each letter, in either case, names one key; byte 3 is Quit. Byte 27 is the start of an arrow only if there are at least three bytes and the second is '['; then the third byte names the arrow (A up, B down, C right, D left). Every other byte, and every other situation, means nothing, and bytes after the first key are never looked at.

Rung 3: the shape

on_body: a range-for over the body that returns true from inside the loop, and false after it. steer: check has_value() first and return early; then compare the wanted direction with the heading's opposite. A tiny helper of your own that answers "what is the opposite of this direction?" is a switch like milestone 1's; keep it in snake.cpp (it is not in the header, so nothing outside can call it). parse_key: an empty string returns nothing before anything else is read; then one switch on the first byte, with the upper- and lower-case letters as two case labels on one return; the Escape case checks the size before it reads the second and third bytes, and has its own small switch on the third. Test the lone Escape first: it is the input that reads past the end if the size check is missing.

Rung 4: the same mechanism on a different problem

Chapter 4's "is ticket 42 still waiting?" search is on_body's loop over a different list. Chapter 5's thermostat keeps its previous value when no reading arrived, which is steer's first rule. Chapter 8's key logger shows the exact bytes each key sends, and chapter 2's vending machine shows several case labels sharing one statement.

Common bugs. In parse_key, reading bytes[1] or bytes[2] without checking the size: with the sanitizers on, the test parse_key: no key or a key the game does not use stops with a report naming your line, and the arrow test passes, which makes it confusing until you read the report. In steer, comparing wanted with the heading itself instead of with its opposite. In on_body, taking the body by value (it compiles; chapter 6 says why it is wrong).

Done when all seven cases pass with no sanitizer report, and you can say why a lone Escape byte must mean nothing.

Milestone 4: place_food, new_game and tick

Goal. The game itself. This is the longest milestone of the week; give it the whole Code block. Re-read: chapter 6 (the engine by reference, the dice trap, std::uniform_int_distribution), chapter 5 (returning nothing), chapter 4 (adding at one end, removing at the other). Turns green: the four place_food: ..., the two new_game: ... and the eight tick: ... cases; all 26 pass. Commit: M4: place_food, new_game and tick green; 26 of 26.

Rung 1: where to look

tick's comment in snake.hpp is five numbered steps: that is the algorithm, in order. Do the cases in the order the test file gives them; each one adds one rule. For place_food, the test every free cell about equally often explains in its comment which unfair method it is built to catch. For new_game, which cell is the head on a 10 by 6 board, and on an 11 by 7 one?

Rung 2: the idea in words

place_food: if the snake covers the whole board there is nowhere to put food: say so first. Otherwise there are two fair methods. Keep choosing a random cell of the whole board until you find one that is not on the body (every choice is equally likely, so the first free one you hit is too). Or count the free cells, choose a random number below that count, and walk the board to the free cell with that number. new_game: fill in every field of a Game, the three cells in the order the comment gives (head first), then ask place_food for the food. tick: decide everything before you change anything. Work out the new heading and the new head. If the head would leave the board, the game is lost and nothing else changes. If it lands on the body, the same, except that when it is not eating the tail's cell does not count, because the tail leaves it this very tick. Only then move: the new head goes on the front, and the tail comes off the back unless the head landed on the food. Then the score, the growth and the next food, and if there is no free cell, the game is won.

Rung 3: the shape

place_food: the full-board check compares the body's size with width * height (in a real game the body never covers a cell twice); the random cell comes from two std::uniform_int_distribution<int> draws, one for the column and one for the row, both using the engine you were given, by reference; on_body from milestone 3 says whether a cell is free. tick: the first line returns at once if the game is not Playing; then steer and next_head; then two checks, each of which sets state and returns. For the tail rule, you have two choices: check against the body as it is and allow exactly the case "the new head is the tail's cell and the snake is not eating"; or take the tail off first when not eating, and then check. Both pass the tail test. Only one of them keeps the promise "the body is left exactly as it was" when the game is lost; find out which before you choose. Use lldb with a breakpoint on tick and frame variable game to watch the body change in the 2 by 2 square test.

Rung 4: the same mechanism on a different problem

Chapter 6 rolls dice with an engine passed by reference and shows what goes wrong by value. Chapter 4's moving average adds a reading at one end of a deque and drops the oldest at the other, which is the snake's movement without a board. Chapter 5 returns an empty optional when there is no answer, as place_food must on a full board.

Common bugs. Moving the snake and then discovering it died, so a lost game shows the head inside the wall (the wall test checks the body is unchanged). Forgetting the tail exception (the 2 by 2 square test). Growing on every tick after the first meal, or never (the eating test ticks twice). Placing the new food before the snake has moved, so it can land under the new head. Taking the engine by value in a helper of your own, so the food appears in the same place every time; the fairness test catches it. A place_food that loops forever on a full board: the test the last free cell and then no cell at all hangs instead of failing; press Ctrl-C and read rung 2 again.

Done when all 26 cases pass with no sanitizer report, the whole binary is green, and you can explain the tail rule with the 2 by 2 square on paper.

Milestone 5: RawTerminal and read_keys

Goal. The guard that puts the terminal in the game's mode and always gives it back, and the function that collects whatever keys are waiting. Re-read: chapter 7 (destructors, the echo-off guard, flags), chapter 8 (line mode, the VMIN and VTIME table, read). Turns green: no test; nothing that needs a keyboard can be tested automatically. The proof is by hand, below. Commit: M5: RawTerminal and read_keys.

Rung 1: where to look

terminal.hpp's comments list everything the constructor and the destructor must do. Chapter 7's password guard does a part of it; chapter 8's key logger does more. Make a list of what the game needs that the key logger does not do.

Rung 2: the idea in words

The constructor saves the terminal's settings into the guard, makes a copy, changes the copy (no echo, no line mode, and the two control values that make a read come back at once even when nothing has been typed), applies the copy, and hides the cursor. The destructor applies the saved settings and shows the cursor. Nothing else touches the settings, so whatever the program does in between, the destructor restores exactly what was there. read_keys asks for one byte at a time and keeps going while a byte comes back; in this mode, "nothing waiting" comes back at once as zero bytes, which is where it stops.

Rung 3: the shape

The guard is chapter 7's echo-off guard with one more flag turned off and two control values changed, plus the two cursor escape codes from Week 1's chapter 9; leave the signal flag alone, so Ctrl-C still sends its signal. read_keys is a while loop around read(STDIN_FILENO, &c, 1) that appends each byte to a string, and stops when read returns anything other than 1. Then write the manual check below before you touch main.

Rung 4: the same mechanism on a different problem

Chapter 7's password prompt is the guard with one flag; chapter 8's key logger is the guard with two flags and a reading loop that waits for each key. The game's version waits for nothing.

The manual check. Write a short program of your own in scratch/, built with terminal.cpp (clang++ -std=c++23 -Wall -Wextra -g -fsanitize=address,undefined scratch/keys.cpp phase1-terminal/02-snake/src/terminal.cpp -I phase1-terminal/02-snake/src -o /tmp/keys), that creates a RawTerminal and, for about five seconds, prints the number of every byte read_keys returns, sleeping 100 ms between calls. Run it as /tmp/keys; cat. Press letters and arrows: an arrow should show as three numbers. When it ends, cat starts, and it must behave normally: wait for you, show what you type, repeat the line on Enter (Ctrl-D ends it). That is the proof that your destructor restored the terminal. Looking at the prompt proves nothing: zsh switches echo and line mode back on before every prompt (chapter 0), so only a program on the same command line sees what yours left behind. If your destructor did nothing, cat finds the game's settings, sees "nothing waiting" at once and ends without letting you type. Then run /tmp/keys once more and press Ctrl-C during the five seconds: with no signal handling yet, the program is killed and its destructor does not run, and the prompt comes back without a cursor. That is expected today; type tput cnorm. Milestone 6 fixes it for good.

Common bugs. Changing the saved settings instead of a copy, so the destructor restores the changed ones. Turning off a flag with |= instead of &= ~. A read_keys that waits for a key because the control values are wrong (the game then only moves while you hold a key down). Forgetting std::fflush(stdout) after the cursor codes.

Done when the scratch check prints arrows as three bytes, and the cat after it waits for you and echoes what you type.

Milestone 6: main

Goal. The program: arguments, the game, the loop, the keys, pause, the clock, every way out. Re-read: chapter 8 (deadlines, late frames), chapter 7 (a block that ends a guard's life early; the Ctrl-C flag), your own Life main (argument parsing, the frame string, flushing). Turns green: no test; the checklist's by-hand items. Commit: M6: main, the game plays.

Rung 1: where to look

The stub main.cpp has the plan in five steps. Your Life main already parses --width and friends. The README's spec section says when the terminal may be touched (not before the arguments are known to be good) and what the last line contains. Where must that last line be printed, relative to the guard's lifetime, so that it lands on a normal terminal?

Rung 2: the idea in words

First the arguments, with every error reported before anything else happens. Then the seed (zero means take one from the clock; keep the one you used, to print at the end), the engine, the game, and the Ctrl-C arrangement. Then a block, opened only for the guard's sake: inside it the guard is created and the loop runs; when the loop ends, the block ends, the guard dies, and the terminal is normal again. Each turn of the loop: note the deadline of this tick; read the waiting keys and find out what they mean; quit, pause or remember the wanted direction; tick, unless paused; build the whole frame (cursor home, the board, the status line) and print it once, flushed; if the work so far took longer than this tick's budget, count a late tick; sleep until the deadline. The loop ends when the game is no longer playing, when quit was pressed, or when the Ctrl-C flag is set. After the block, print the last line.

Rung 3: the shape

The Ctrl-C flag is a volatile std::sig_atomic_t at namespace scope and a one-line handler, installed with std::signal before the guard is created (chapter 7). The wanted direction is a std::optional<Direction> that starts empty every tick. The key goes through a switch on the Key with one case per enumerator and no default, so -Wswitch checks you handled all six. The deadline is a steady_clock::time_point that grows by tick_ms(score) milliseconds each turn, with std::this_thread::sleep_until at the bottom (chapter 8). Clear the screen once before the loop, then send only "cursor home" each frame: the frame always has the same size, so it overwrites itself.

Rung 4: the same mechanism on a different problem

Chapter 7's countdown ends cleanly on Ctrl-C through a flag while a guard keeps the cursor safe. Chapter 8's metronome keeps time with deadlines and counts late beats. Week 1's chapter 9 builds a whole frame as one string and prints it once.

Common bugs. Printing the last line inside the guard's block: it appears, but on a terminal that is still in raw mode, and the next prompt lands in a strange place. Calling std::exit or return from inside the loop for "game over": the guard still dies on return, but the last line is skipped. Sleeping a fixed 150 ms instead of until a deadline, so the game slows down as the board gets bigger. Forgetting to flush, so frames arrive in bursts. A seed taken from the clock that you forgot to keep, so the last line cannot show it.

Done when every by-hand item of the acceptance checklist is ticked, including every way out, each run as ./build/snake; cat. Winning is proven by the test tick: eating the last free cell wins the game; winning an 8 by 5 board by hand is possible, but not required.

Saturday: the strands

Maths: 10,000 draws against the count you expect (45 minutes)

Your place_food promises that every free cell is equally likely. How would you know? Draw many times and count. But "equally likely" does not mean "equally often": with 100 cells and 10,000 draws, no cell will get exactly its share. So the real question is how far from its share a cell may land before you should be suspicious.

Take a die first. Roll it 6,000 times. Each face has a probability of one in six, so you expect 6,000 × 1/6 = 1,000 of each. The typical distance of an actual count from that expectation has a formula worth knowing, the standard deviation of a count: for n tries that each succeed with probability p, it is the square root of n × p × (1 − p). For the die: √(6,000 × 1/6 × 5/6) = √833 ≈ 28.9. About two counts in three land within one standard deviation of the expectation, and about nineteen in twenty within two. Check it:

#include <cmath>
#include <print>
#include <random>
#include <vector>

int main() {
    const int rolls = 6000;
    std::mt19937 rng(1);
    std::uniform_int_distribution<int> die(1, 6);
    std::vector<int> counts(7, 0);  // counts[1] to counts[6]; counts[0] is never used
    for (int i = 0; i < rolls; ++i) {
        counts[die(rng)] += 1;
    }
    const double expected = rolls / 6.0;
    double squares = 0.0;
    for (int face = 1; face <= 6; ++face) {
        const double off = counts[face] - expected;
        std::println("face {}: {} (off by {:+.0f})", face, counts[face], off);
        squares += off * off;
    }
    std::println("expected per face: {:.0f}", expected);
    std::println("typical distance, measured: {:.1f}", std::sqrt(squares / 6));
    std::println("typical distance, predicted: {:.1f}", std::sqrt(rolls * (1.0 / 6) * (5.0 / 6)));
    return 0;
}

face 1: 980 (off by -20)
face 2: 955 (off by -45)
face 3: 1035 (off by +35)
face 4: 1000 (off by +0)
face 5: 982 (off by -18)
face 6: 1048 (off by +48)
expected per face: 1000
typical distance, measured: 32.3
typical distance, predicted: 28.9

Measured 32.3 against a predicted 28.9: close, with only six faces to measure from. Three of the six faces are within 29 of 1,000 (you would expect about four), and all six are within 58. Now do the same for the food, on paper, before running anything: 10,000 draws over the 100 cells of an empty 10 by 10 board. What count do you expect per cell, what standard deviation, and roughly how many of the 100 cells should land more than two standard deviations away? Write the three numbers in the log. Then run ./build-release/snake_bench draws, which counts your own place_food's choices, and compare. A fair place_food matches your prediction about as well as the die matched its own; an unfair one does not, and you will see where.

The write-up (one hour)

400 to 800 words in docs/, the same three questions as in Week 1: what you built, what surprised you, what you would do differently. A good place to start: the first time your terminal was left in raw mode, and what you understood about lifetimes afterwards.

The debugging playbook

  1. Read the failing check's values line. doctest prints both sides, with your types spelled out: CHECK( [{6, 3} {5, 3} {4, 3}] == [{6, 3} {5, 3} {4, 3} {3, 3}] ) says the snake did not grow. Say the difference in words before you open any file.
  2. Run one case. ./build/snake_tests -tc="tick: eating*". Less output, faster thinking.
  3. Stop inside it. lldb ./build/snake_tests, then breakpoint set -n tick, process launch -- -tc="tick: eating*", and when it stops, frame variable game, next, frame variable game again. Watching the body before and after one line answers most tick questions (chapter 3). A conditional breakpoint, breakpoint modify -c "game.body.size() == 4", stops only at the interesting call.

The review ritual

After each milestone, with the tests green and the commit made, ask for a review naming the function (CLAUDE.md, "What a review contains"). On Friday, the review covers the whole challenge: src/, tests/, the README and BENCH.md so far. It comes back in six parts: correctness (with an input that breaks your code, if one exists), clarity and style, idioms, performance ideas phrased as experiments, the inference twin, and three questions you should be able to answer without the code. Write the three questions and your answers into the log. Do not act on the review before the next Code block; let it settle.

The inference twin, in depth

Look at the loop you wrote in milestone 6 with a language model in mind. Each turn reads the input that arrived since the last turn, updates a state with one fixed function, emits exactly one output, and waits for a deadline. An inference engine's decode loop has the same four parts: take the token just produced, run the model's forward pass once over it (updating the KV cache, its state), emit one new token, and keep up with a target rate. Your late-tick counter is the beginning of every serving dashboard: a median latency that looks fine can hide a tail of late tokens, and users feel the tail.

Now look at tick's collision check. To decide whether the head bit the body, it looks at every cell of the body: the work of one tick grows with the length of the snake. A decode step does the same with its context: attention compares the new token with the key of every earlier token, so each new token costs more than the one before, and a long conversation is slower per token than a short one. Your benchmark draws that line for the snake. Stretch goal 2 shows the escape you have here (a lookup instead of a search); attention has no exact shortcut like that, which is why so much of inference engineering (the KV cache, paged attention, sliding windows, quantised caches) is about making that line cheaper rather than flat.

And look at the body itself when the snake is not eating: one cell added at the front, one dropped at the back, the length fixed. That is a sliding window, the shape of a KV cache that keeps only the last N tokens, and the deque is the shape of its buffer. You will meet all three again in week 18, when your own engine generates text.

Check yourself

Why must tick decide whether the snake dies before it changes the body?

Answer

Because the spec says that on the losing tick the body is left exactly as it was, so that the last frame shows the snake just before the crash. If the body is changed first, undoing the change correctly in every case is harder and easier to get wrong than not making it.

Why is the cell the tail is leaving free to move into, but only when the snake is not eating?

Answer

When not eating, the tail comes off in the same tick as the head goes on, so by the end of the tick the cell is free again and nothing collides. When eating, the tail stays put to make the snake one longer, so the tail's cell is still body. (On a real board food is never on the tail, so the second case cannot even arise; the rule just says why.)

Your place_food takes a random cell, and if it is on the body, uses the next free cell in reading order. It always returns a free cell. Why does the fairness test fail?

Answer

Because the cell just after a long run of body is chosen whenever any cell in that run is drawn, so it is chosen several times as often as a cell in open space. It is never on the body, but it is not equally likely, and the test's 1,600 draws show the difference clearly.

Where must the result line be printed relative to the RawTerminal guard, and why?

Answer

After the guard has been destroyed, outside the block that holds it, so that it is printed on a terminal that is back in its normal mode, with the cursor visible.

Ctrl-C during the milestone 5 check leaves you without a cursor. After milestone 6 it no longer does. What changed?

Answer

In milestone 5 nothing handles the signal, so the program is killed on the spot and no destructor runs; zsh repairs echo and line mode for its own prompt, but nothing shows the cursor again. In milestone 6 the signal only sets a flag; the loop sees it, ends normally, the guard's block ends, and the destructor restores the settings and shows the cursor.

Why does a longer snake make every tick cost more, and what is the inference version of that sentence?

Answer

Because tick compares the new head with every cell of the body to find out whether it bit itself, so the work grows with the length. In a decode step, attention compares the new token with the key of every earlier token, so the work grows with the length of the context, and a long conversation costs more per token than a short one.
