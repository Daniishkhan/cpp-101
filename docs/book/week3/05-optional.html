The problem: an answer that may not exist

Here is a small question: what is the first even number in a list? Write it as a function, the way Week 1 chapter 4 taught. It walks the list and returns the first number whose remainder after dividing by 2 is zero. The interesting line is the last one. If the loop finishes, the list had no even number at all, and the function still has to return some int. Here it returns -1 and calls that "none".

One small thing in main is new. The calls hand the function a list written in braces, first_even({3, 8, 5, 6}), where a const std::vector<int>& is expected. The machine builds a nameless vector from the braces, lends it to the function and throws it away at the end of the statement. That is the temporary you met in Week 1 chapter 5, when a string literal was handed to a const std::string&.

#include <print>
#include <vector>

// The first even number in `numbers`, or -1 if there is none.
int first_even(const std::vector<int>& numbers) {
    for (int n : numbers) {
        if (n % 2 == 0) {
            return n;
        }
    }
    return -1;  // "none": safe here only because -1 is odd, so it is never an answer
}

int main() {
    std::println("{}", first_even({3, 8, 5, 6}));
    std::println("{}", first_even({-4, 7}));
    std::println("{}", first_even({1, 3, 5}));
    return 0;
}

8
-4
-1

It works, and the comment says why: -1 is odd, so it can never be a real answer, and a caller who sees -1 knows the list had no even number. A value with a special meaning like this is called a sentinel. Now ask the sister question, the first odd number, and keep the same trick:

#include <print>
#include <vector>

// The first odd number in `numbers`, or -1 if there is none.
int first_odd(const std::vector<int>& numbers) {
    for (int n : numbers) {
        if (n % 2 != 0) {  // not "== 1": in C++, -3 % 2 is -1
            return n;
        }
    }
    return -1;
}

int main() {
    std::println("{}", first_odd({4, -1, 6}));  // there is an answer: -1
    std::println("{}", first_odd({2, 4, 6}));   // there is no answer
    return 0;
}

-1
-1

Two different situations, one output. In the first list the answer really is -1; in the second there is no answer, and the function says -1 again. The caller cannot tell them apart. (The comment about == 1 is Week 1 chapter 2's rule: a remainder takes the sign of the number divided, so -3 % 2 is -1, and "odd" has to be written as "the remainder is not zero".)

Could you pick a better sentinel? Try. 0 is even, so it is safe for first_odd, but it breaks first_even. Any odd number breaks first_odd. Change the question to "the first number above 100" or "the first temperature below zero" and some other set of values becomes unsafe. The deep reason is a counting argument. An int has 4,294,967,296 bit patterns, and when the answer can be any int, every one of those patterns already means a number. "There is no answer" needs one more pattern, and there is none left.

First principle

When every value of a type can be a real answer, "no answer" is extra information. It needs a place of its own to live: at least one more bit, beside the value. Either the caller and the function carry that bit separately, or they use a type that carries the value and the bit together.

You already know a way to carry the bit separately. Week 1 chapter 5 wrote divide, which handed back two results through references. The same shape works here: return a bool that says whether there was an answer, and write the answer itself through an int&.

// true: there was an odd number, and it has been written into `answer`
bool first_odd(const std::vector<int>& numbers, int& answer);

int answer = 0;                       // a box that may never be filled
if (first_odd(numbers, answer)) {     // the bool says whether it was
    std::println("{}", answer);
}

That is honest, and C code is full of it. It is also clumsy: the caller must make a box first and fill it with a meaningless 0, and because the answer and the bool travel separately, nothing stops a hurried caller from printing that 0 as if it were the answer. What you want is one value that is either "here is the number" or "there is no number". The standard library has exactly that type.

std::optional: a value, or nothing

A std::optional<T> is a variable that either holds one value of type T or holds nothing. It lives in the header <optional>. std::optional<int> reads as "maybe an int". An optional that holds a value is said to have a value; one that holds nothing is empty. There is a special value, std::nullopt ("null optional"), that means "nothing": assign it, or compare with it, and you are talking about the empty state.

#include <optional>
#include <print>

int main() {
    std::optional<int> maybe;  // starts empty: no int inside
    std::println("has a value: {}", maybe.has_value());

    maybe = 42;  // now it holds 42
    std::println("has a value: {}, the value: {}", maybe.has_value(), *maybe);

    maybe = std::nullopt;  // empty again
    std::println("has a value: {}", maybe.has_value());

    std::optional<int> zero = 0;  // holds 0, which is a value, not "nothing"
    std::println("zero has a value: {}", zero.has_value());
    return 0;
}

has a value: false
has a value: true, the value: 42
has a value: false
zero has a value: true

Read it line by line. std::optional<int> maybe; makes an empty optional. A plain int n; would hold whatever bytes were in memory (Week 1 chapter 2); an optional is never uninitialised, because empty is a well-defined state of its own. has_value() asks the question and gives a bool. maybe = 42; puts an int in. *maybe, with a star in front, means the value inside: the multiplication symbol with one thing after it instead of two around it, a notation borrowed from pointers (Buffer A and week 10). maybe = std::nullopt; empties it again.

The last two lines are the point of the whole type. zero holds 0, and 0 is a value. An optional keeps "the number is zero" and "there is no number" apart, which no sentinel could.

Analogy

An optional is a box with a small lamp on the lid. The lamp is lit when there is something inside and dark when there is not. You look at the lamp first (has_value()), and only open the box (*) when it is lit.

Where it breaks: a real empty box is visibly empty. An empty optional is not. Its box still exists, full size, and still holds whatever bytes were last left in that memory; opening it when the lamp is dark gives you those leftover bytes as if they were a value, and the language makes no promise about what happens. The section on the two ways to end your program shows this happening.

Returning an optional

Now rewrite first_odd with the honest return type:

#include <optional>
#include <print>
#include <vector>

// The first odd number in `numbers`, or nothing if there is none.
std::optional<int> first_odd(const std::vector<int>& numbers) {
    for (int n : numbers) {
        if (n % 2 != 0) {
            return n;  // the int is wrapped in an optional that holds it
        }
    }
    return std::nullopt;  // the empty optional: "there is no answer"
}

int main() {
    const std::optional<int> a = first_odd({4, -1, 6});
    const std::optional<int> b = first_odd({2, 4, 6});

    if (a.has_value()) {
        std::println("a: the first odd number is {}", *a);
    } else {
        std::println("a: there is no odd number");
    }

    if (b) {  // the same question, short form
        std::println("b: the first odd number is {}", *b);
    } else {
        std::println("b: there is no odd number");
    }
    return 0;
}

a: the first odd number is -1
b: there is no odd number

Two lines changed in the function. return n; hands back an int, and the compiler wraps it in an optional that holds it. return std::nullopt; hands back the empty optional. In main, the two lists now give two clearly different results, and the caller has to ask which one it got. if (b) is short for if (b.has_value()): an optional used as a condition is true exactly when it has a value.

The biggest change is not in any line of the body. It is in the first line of the function. int first_odd(...) claims there is always an answer. std::optional<int> first_odd(...) says, to every reader and to the compiler, "sometimes there is not, and you must look". The signature tells the truth.

First principle

Use std::optional<T> as a return type when "no answer" is a normal, expected outcome: the list had no odd number, the word is not in the dictionary, nothing was typed. It is not for errors that should never happen; for those, a crash with a clear message (a sanitizer report, a failed test) is more useful than a quiet "nothing".

Reading an optional

You have seen has_value(), if (opt) and *opt. Two more ways of reading an optional come up all the time. value_or(fallback) gives the value if there is one and fallback if there is not; it is the right tool when a sensible default exists. And you can compare an optional with a plain value using == and !=, without checking first:

#include <optional>
#include <print>

int main() {
    const std::optional<int> seven = 7;
    const std::optional<int> none = std::nullopt;

    std::println("value_or(0):  {} and {}", seven.value_or(0), none.value_or(0));
    std::println("== 7:         {} and {}", seven == 7, none == 7);
    std::println("!= 7:         {} and {}", seven != 7, none != 7);
    std::println("== nullopt:   {} and {}", seven == std::nullopt, none == std::nullopt);
    return 0;
}

value_or(0):  7 and 0
== 7:         true and false
!= 7:         false and true
== nullopt:   false and true

The comparisons follow one rule: an empty optional is never equal to a value. So seven == 7 is true, none == 7 is false, and none != 7 is true, because "nothing" is indeed not 7. Comparing with std::nullopt asks "is it empty?". This is exactly the form the tests for this week use: CHECK(parse_key("w") == Key::Up) in tests/snake_test.cpp is true only when parse_key returned an optional holding Key::Up.

Trap

if (opt) asks "is there a value?", never "is the value true or non-zero?". An optional holding 0 passes the test, as you saw with zero. It bites hardest with std::optional<bool>: an optional holding false still has a value, so if (answer) runs its body. When the value matters, say so: if (answer == true), or if (answer.value_or(false)).

An optional struct, and the arrow

An optional can hold any type, including a struct of your own from chapter 1. Here is a small English to Dutch glossary, a vector of entries, and a function that looks a word up in it. When the word is there, the function returns the whole entry; when it is not, nothing.

#include <optional>
#include <print>
#include <string>
#include <vector>

struct Entry {
    std::string english;
    std::string dutch;
};

// The entry for `word`, or nothing if the glossary does not have it.
std::optional<Entry> look_up(const std::vector<Entry>& glossary, const std::string& word) {
    for (const Entry& entry : glossary) {
        if (entry.english == word) {
            return entry;
        }
    }
    return std::nullopt;
}

int main() {
    const std::vector<Entry> glossary = {
        {"cat", "kat"},
        {"house", "huis"},
        {"bicycle", "fiets"},
        {"rain", "regen"},
    };
    const std::vector<std::string> words = {"bicycle", "snow", "rain"};

    for (const std::string& word : words) {
        const std::optional<Entry> found = look_up(glossary, word);
        if (found) {
            std::println("{} is {} in Dutch", found->english, found->dutch);
        } else {
            std::println("{} is not in the glossary", word);
        }
    }
    return 0;
}

bicycle is fiets in Dutch
snow is not in the glossary
rain is regen in Dutch

found is a std::optional<Entry>. To reach a member of the Entry inside, you could write (*found).dutch: open the box, then take the member. That is common enough to have a shorter spelling, found->dutch, an arrow made of a minus sign and a greater-than sign. Read it as "the dutch of the entry inside found". The same rule applies as for the star: only use the arrow after you have checked that there is an entry inside.

One thing worth noticing in look_up: return entry; puts a copy of the entry into the optional. The optional owns its own Entry, two strings and all, independent of the glossary. For a four-word glossary that costs nothing worth measuring; chapter 6 is about when copies like this start to matter.

Two ways to end your program

An optional makes "maybe nothing" visible in the type. It does not force anyone to check. Both of the following compile without a warning.

The star on an empty optional

#include <optional>
#include <print>

int main() {
    const std::optional<int> nothing = std::nullopt;
    std::println("has a value: {}", nothing.has_value());
    std::println("*nothing = {}", *nothing);  // undefined behaviour: there is no int
    return 0;
}

$ tools/run.sh scratch/star_empty.cpp
has a value: false
*nothing = 1863539712
$ tools/run.sh scratch/star_empty.cpp
has a value: false
*nothing = 1829968896
$ clang++ -std=c++23 -Wall -Wextra scratch/star_empty.cpp -o scratch/star_empty
$ ./scratch/star_empty
has a value: false
*nothing = 0

Three runs, three different numbers, and not a word from the sanitizers in the two runs that had them. * does not check the lamp. It opens the box and reads the four bytes in the value slot, which for an empty optional are whatever happened to be in that memory. That is undefined behaviour again (Week 1 chapter 2): the language gives no rules for what happens. The sanitizers stay quiet because nothing they watch went wrong: the memory belongs to the program, it is just not a value. The plain build is the most dangerous of the three, because 0 looks like a perfectly good answer.

Trap

Never use *opt or opt->member without knowing that opt has a value: check it with if (opt) first, or use value_or. The compiler will not remind you, and the sanitizers cannot.

Try it

Apple's C++ library has a checking mode that does test the lamp. Compile star_empty.cpp with one extra flag, -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG, and run it. This time the program stops with a message: libc++ Hardening assertion this->has_value() failed: optional operator* called on a disengaged value ("disengaged" is the library's word for empty), and zsh reports abort. The flag costs speed, so it belongs in Debug builds only.

.value() on an empty optional

Optionals also have a member function .value() that does check the lamp. Here is what it does when the lamp is dark:

#include <optional>
#include <print>

int main() {
    const std::optional<int> nothing = std::nullopt;
    std::println("about to call .value() on an empty optional...");
    const int n = nothing.value();
    std::println("n = {}", n);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra value_empty.cpp -o value_empty
$ ./value_empty
about to call .value() on an empty optional...
libc++abi: terminating due to uncaught exception of type std::bad_optional_access: bad_optional_access
zsh: abort      ./value_empty
$ echo $?
134

You have seen this shape before: it is what std::stoi("abc") did in Week 1 chapter 8. .value() found no value and raised an exception, the library's way of saying "I cannot do this". Nothing in the program catches exceptions, so the program ends with a message and exit code 134. This course does not use exceptions as a mechanism (week 16 explains them, and why inference code avoids them), so for you .value() is just a slower, more verbose way to crash. Check with if, then use *.

What an optional is in memory

An optional is not magic and it does not allocate anything. It is a small fixed-size box: room for one value, plus a flag. sizeof shows it:

#include <optional>
#include <print>

int main() {
    std::println("char   {:2} bytes   std::optional<char>   {:2} bytes", sizeof(char),
                 sizeof(std::optional<char>));
    std::println("int    {:2} bytes   std::optional<int>    {:2} bytes", sizeof(int),
                 sizeof(std::optional<int>));
    std::println("double {:2} bytes   std::optional<double> {:2} bytes", sizeof(double),
                 sizeof(std::optional<double>));
    return 0;
}

char    1 bytes   std::optional<char>    2 bytes
int     4 bytes   std::optional<int>     8 bytes
double  8 bytes   std::optional<double> 16 bytes

An int is 4 bytes; an optional int is 8. Four of them are the value slot. One byte is the flag, a bool that is 1 when there is a value and 0 when there is not: the lamp. The last three are padding, the unused bytes chapter 1 showed in a struct: an int must start at a multiple of 4, and in a vector each optional starts where the previous one ends, so the size is rounded up to a multiple of 4. A double wants a multiple of 8, so its optional is 8 + 1 + 7 = 16; a char is happy anywhere, so its optional is 1 + 1 = 2.

std::optional<int> holding 42    [ 42 . . . ][ 1 ][ pad pad pad ]     8 bytes
std::optional<int> that is empty  [ ? ? ? ?  ][ 0 ][ pad pad pad ]     8 bytes
                                    value slot  flag   padding

Three facts follow from the picture. An empty optional is exactly as big as a full one, because the slot is always there. The question marks are why * on an empty optional printed a different number on every run: it read the slot without looking at the flag. And copying an optional copies its bytes, 8 for an optional int, so a small optional is as cheap to pass around as a double.

Inference twin

A request to a language-model server is full of settings that may or may not be given: a temperature, a maximum number of tokens, a seed, a stop word. Absent is not the same as zero. A temperature of 0.0 is a real setting (always pick the most likely next token), while an absent temperature means "use the default". A C++ server reads such a request into a struct of std::optional fields for exactly the reason in the first section: every double is a possible temperature, so "not given" needs its own flag. In week 17 you meet the optional's sibling, std::expected, in the weight loader: it holds either the tensor you asked for or the reason it could not be read (the file is missing, the shape is wrong), so a failure carries an explanation instead of a bare "nothing".

An optional parameter: no reading this second

Optionals are not only for answers. A function can take one as a parameter, to say "the caller may or may not have this for me". Picture a greenhouse thermostat. Its thermometer sends one reading per second over a radio link that sometimes drops a message, and the thermostat smooths the readings before it acts on them, so that one odd reading does not switch the heating on: each second, its value moves a quarter of the way from where it is towards the new reading. That is a smoothing filter. When a second passes with no reading at all, the filter has nothing to move towards, so it keeps the value it had.

#include <optional>
#include <print>
#include <vector>

// One step of a smoothing filter: move a quarter of the way from `previous`
// towards the new reading. No reading this second: keep the previous value.
double smooth(double previous, std::optional<double> reading) {
    if (!reading) {
        return previous;
    }
    return previous + 0.25 * (*reading - previous);
}

int main() {
    // One entry per second. std::nullopt is a second in which no reading arrived.
    const std::vector<std::optional<double>> readings = {
        20.0, 24.0, std::nullopt, std::nullopt, 24.0, 24.0, std::nullopt, 16.0,
    };

    double value = 20.0;
    int second = 0;
    for (std::optional<double> reading : readings) {
        value = smooth(value, reading);
        if (reading) {
            std::println("second {}: reading {:4.1f}   smoothed {:5.2f}", second, *reading, value);
        } else {
            std::println("second {}: no reading     smoothed {:5.2f}", second, value);
        }
        ++second;
    }
    return 0;
}

second 0: reading 20.0   smoothed 20.00
second 1: reading 24.0   smoothed 21.00
second 2: no reading     smoothed 21.00
second 3: no reading     smoothed 21.00
second 4: reading 24.0   smoothed 21.75
second 5: reading 24.0   smoothed 22.31
second 6: no reading     smoothed 22.31
second 7: reading 16.0   smoothed 20.73

smooth takes the previous value and a std::optional<double>. Its first line handles the empty case: !reading, "not reading", is true when the optional is empty, and the previous value goes straight back. Otherwise it moves a quarter of the way: from 20 towards 24 is a step of 4, a quarter of that is 1, so second 1 shows 21.00. Seconds 2 and 3 bring nothing and the value holds at 21.00 instead of falling to zero. The readings sit in a std::vector<std::optional<double>>, a vector of maybe-doubles, where each std::nullopt is a lost second. Without optionals you would need a sentinel temperature for "lost", and every temperature is a possible reading.

Notice the parameter type: std::optional<double> by value, not by const&. It is 16 bytes, small enough that copying it is cheaper than going through a reference. That is one of the rules of thumb from Week 1 chapter 5, and chapter 6 tests it on real types.

Text to a number, without stopping the program

Week 1 chapter 8 turned text into numbers with std::stoi. It has two habits you saw there: given "80x24" it quietly returns 80 and throws the rest away, and given "eighty" it ends the program with an exception, because an int has no spare value for "that was not a number". Now you have a type with a spare value. Here is a converter that accepts digits only and says "not a number" instead of stopping:

#include <optional>
#include <print>
#include <string>
#include <vector>

// The number written in `text`, or nothing if `text` is not 1 to 9 digits.
// Nine digits always fit in an int: 999,999,999 is less than 2,147,483,647.
std::optional<int> digits_to_int(const std::string& text) {
    if (text.empty() || text.size() > 9) {
        return std::nullopt;
    }
    int value = 0;
    for (char c : text) {
        if (c < '0' || c > '9') {
            return std::nullopt;  // one stray character spoils the whole text
        }
        value = value * 10 + (c - '0');  // '7' - '0' is 7: the digits are bytes 48 to 57
    }
    return value;
}

int main() {
    const std::vector<std::string> texts = {"42", "007", "80x24", "", "eighty", "-3", "1234567890"};
    for (const std::string& text : texts) {
        const std::optional<int> number = digits_to_int(text);
        if (number) {
            std::println("\"{}\" -> {}", text, *number);
        } else {
            std::println("\"{}\" -> not a number", text);
        }
    }
    return 0;
}

"42" -> 42
"007" -> 7
"80x24" -> not a number
"" -> not a number
"eighty" -> not a number
"-3" -> not a number
"1234567890" -> not a number

The loop is the way you read a number aloud from left to right. Start with 0. For each digit, multiply what you have by 10 and add the digit: "427" goes 0, then 4, then 42, then 427. To turn the character '7' into the number 7, the function uses the fact from Week 1 chapter 8 that a char is a small number: the digit characters '0' to '9' are the bytes 48 to 57, in order, so c - '0' is the digit's value. Any other character, and the whole text is refused.

The limit of nine digits is first principles, not fussiness. The largest int is 2,147,483,647, ten digits long. Every nine-digit number fits; not every ten-digit one does, and 9,999,999,999 would overflow, which is undefined behaviour. Refusing ten digits also refuses some numbers that would have fitted, such as 1,234,567,890, but it makes overflow impossible with one simple check. And unlike std::stoi, it refuses "80x24" outright, which for a program's arguments is friendlier: the user hears about the typo instead of silently getting 80.

The optionals in snake.hpp

Open phase1-terminal/02-snake/src/snake.hpp and look for std::optional. It appears in four declarations. Read each one aloud, the way Week 1 chapter 5 read life.hpp; do not implement anything yet.

  • std::optional<Key> parse_key(const std::string& bytes);: "give me the bytes read from the keyboard; I hand back maybe a key". Its comment lists when the answer is nothing, and the first case is the most common: no key was pressed at all.
  • std::optional<Point> place_food(const Body& body, int width, int height, std::mt19937& rng);: "maybe a free cell". Nothing means the snake fills the board.
  • Direction steer(Direction heading, std::optional<Direction> wanted);: "give me the heading, and maybe a direction the player asked for". Nothing means no direction key this tick.
  • void tick(Game& game, std::optional<Direction> wanted, std::mt19937& rng);: the same maybe-a-direction, handed on.

Each is the situation from the first section: a key, a cell and a direction have no spare value for "none". The optional parameters travel by value, like reading in smooth, because they are a few bytes. What each function does with its optional is the challenge; chapter 9 has the hint ladders.

Check yourself

A function returns the position of a word in a list as an int, and -1 when the word is missing. Why is that sentinel safe, when -1 was not safe for first_odd?

Answer

A position is never negative, so -1 can never be a real answer: the type int has values the answer never uses, and one of them can mean "none". For first_odd every odd int, including -1, is a possible answer, so no value is left over. A sentinel is safe exactly when the real answers leave some values of the type unused.

What does each optional hold after these lines: std::optional<int> a;, std::optional<int> b = 0;, std::optional<int> c = std::nullopt;? Which of if (a), if (b), if (c) run their body?

Answer

a is empty, b holds 0, c is empty. Only if (b) runs its body: the condition asks whether there is a value, and 0 is a value.

first_odd({2, 4}) returns an empty optional. What are first_odd({2, 4}) == 5, first_odd({2, 4}) != 5 and first_odd({2, 4}).value_or(5)?

Answer

false, true and 5. An empty optional is never equal to a value, so it is "not equal" to every value; value_or gives the fallback when there is nothing inside.

Why did *nothing print a different number on every run under tools/run.sh, and why did neither sanitizer report it?

Answer

* reads the value slot without looking at the flag. In an empty optional the slot holds leftover bytes, so the result is whatever those bytes were (undefined behaviour). The sanitizers did not report it because the slot is memory the program owns; reading it is not an out-of-bounds or use-after-free access, it is reading bytes that were never set to a value.

sizeof(std::optional<double>) is 16 on your Mac. Account for every byte.

Answer

8 bytes for the double value slot, 1 byte for the flag that says whether there is a value, and 7 bytes of padding so that the total is a multiple of 8, which keeps the slot of the next optional in a vector on an 8-byte boundary.

What does .value() do on an empty optional, and why does this course prefer if (opt) followed by *opt?

Answer

It throws an exception, std::bad_optional_access. Nothing catches it, so the program ends with libc++abi: terminating due to uncaught exception and exit code 134, like std::stoi("abc"). This course does not use exceptions, so the honest pattern is to check first and then read with *, or to use value_or when there is a sensible default.

What do digits_to_int("12a") and std::stoi("12a") each give? Which would you want for a --width argument, and why?

Answer

digits_to_int("12a") returns an empty optional; std::stoi("12a") returns 12 and silently ignores the a. For an argument, refusing is better: 12a is almost certainly a typo, and the user should hear about it rather than get a board 12 wide without knowing why.

  • Write a function that returns std::optional<T>, handing back a value or std::nullopt.
  • Read an optional safely with has_value() or if (opt) followed by *opt or opt->member, and with value_or; compare one with a value or with std::nullopt.
  • Recognise the two ways to end a program with an optional: * on an empty one (silent undefined behaviour) and .value() (an uncaught exception).
  • Say what an optional is in memory: a value slot, a flag and padding, and why an empty one is as big as a full one.
  • Take "maybe a value" as a parameter, by value when it is small, and keep the previous state when nothing arrived.
