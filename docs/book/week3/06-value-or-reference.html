Chapter 06

By value or by reference

At the end of this chapter you will choose between T, const T& and T& on purpose for structs, containers and random engines, and back the choice with a measurement. You will also have seen the one bug a reference makes that the compiler cannot warn about: a reference into a vector that has moved.

In this chapter

The same question, with real types

Week 1 chapter 5 gave you three ways to hand a value to a function and a table of rules for choosing. int v: a copy. int& v: the caller's own box, which the function may change. const int& v: the caller's own box, read-only. Small things by value, big read-only things by const&, things to change by &. In Week 1 the examples were ints and one big string, and the big thing in Life was a grid.

This week you own real types: structs from chapter 1, a std::deque from chapter 4, optionals from chapter 5, and a random engine. The rules do not change, but applying them now takes a judgement: is this struct small? Is this container big? Does the function change it? This chapter makes each judgement once, with numbers, so that you can make it quickly for the rest of the course.

First principle

Passing by value copies every byte of the object, and for a container that includes every element it owns. Passing by reference copies nothing but costs a detour: the function reaches the object through its address. Neither is free. Which one is cheaper depends on how many bytes the copy would move, and which one is right depends first on whether the function should be able to change the caller's object.

Small structs: by value

A struct of a few numbers is small. Copying it moves a handful of bytes, which is as cheap as anything the machine does. Here are two such structs and two functions that take them by value:

#include <print>

struct Date {
    int year = 2026;
    int month = 1;
    int day = 1;
};

struct Colour {
    int red = 0;  // each channel from 0 to 255
    int green = 0;
    int blue = 0;
};

// Small and read-only: by value. Each call copies two 12-byte Dates.
bool same_month(Date a, Date b) {
    return a.year == b.year && a.month == b.month;
}

// Small, and the function wants a changed copy anyway: by value in, by value out.
Colour inverted(Colour c) {
    c.red = 255 - c.red;
    c.green = 255 - c.green;
    c.blue = 255 - c.blue;
    return c;
}

int main() {
    std::println("sizeof(Date) = {}, sizeof(Colour) = {}", sizeof(Date), sizeof(Colour));

    const Date today{2026, 11, 26};
    const Date deadline{2026, 11, 28};
    std::println("same month: {}", same_month(today, deadline));

    const Colour orange{255, 165, 0};
    const Colour opposite = inverted(orange);
    std::println("orange {} {} {}, inverted {} {} {}", orange.red, orange.green, orange.blue,
                 opposite.red, opposite.green, opposite.blue);
    return 0;
}

sizeof(Date) = 12, sizeof(Colour) = 12
same month: true
orange 255 165 0, inverted 0 90 255

A Date is three ints, 12 bytes, and so is chapter 1's Colour. Calling same_month(today, deadline) copies 24 bytes in all.

Why not const Date&, to save the copy? Because a reference is not free either. Under the hood it is the object's address, 8 bytes on this Mac, so passing a reference to a 12-byte Date saves 4 bytes of copying and in exchange makes every use of a.month inside the function a trip to memory through that address. A small struct passed by value can travel to the function inside the processor itself, in registers: the processor's own handful of tiny storage slots, each 8 bytes, much faster than memory. On your Mac's processor a struct of up to 16 bytes is handed over in at most two of them. You will look at this in the machine code in week 4; for now take the rule of thumb: a struct of a few numbers, up to about 16 bytes, goes by value. It is also simpler to read: Date a says "a date", while const Date& a makes the reader wonder whether the function cares about which date object it was.

inverted shows the second reason to take a small struct by value: the function wants a changed copy anyway. The parameter is the copy. It turns each channel of its own c into 255 minus itself and returns it, and the caller's orange is untouched, which is why it can be const.

Analogy

Passing by value is handing someone a photocopy; passing by reference is telling them which drawer the original is in. For a postcard, the photocopy is quicker: no walking to the drawer. For a phone book, giving directions to the drawer is far quicker than copying a thousand pages.

Where it breaks: a photocopier's cost depends on the pages you can see. A C++ copy's cost depends on what the object owns, which you often cannot see from outside. The next section has an object whose box is 48 bytes and whose copy is four million.

Big containers: by const&

The program below fills a std::deque<int> with a million numbers and sums it twenty times through each of two functions. They are identical except for the parameter: one takes the deque by value, the other by const&. It times both with steady_clock, exactly as Week 1 chapter 9 timed a frame.

#include <chrono>
#include <deque>
#include <print>

long long sum_copy(std::deque<int> numbers) {  // by value: copies every element
    long long total = 0;
    for (int n : numbers) {
        total += n;
    }
    return total;
}

long long sum_view(const std::deque<int>& numbers) {  // by const&: copies nothing
    long long total = 0;
    for (int n : numbers) {
        total += n;
    }
    return total;
}

int main() {
    using clock = std::chrono::steady_clock;
    using std::chrono::duration_cast;
    using std::chrono::microseconds;

    std::deque<int> numbers;
    for (int i = 0; i < 1000000; ++i) {
        numbers.push_back(i % 100);
    }
    std::println("{} ints, sizeof(numbers) = {} bytes", numbers.size(), sizeof(numbers));

    const int calls = 20;
    long long check = 0;

    const auto copy_start = clock::now();
    for (int i = 0; i < calls; ++i) {
        check += sum_copy(numbers);
    }
    const auto copy_time = duration_cast<microseconds>(clock::now() - copy_start);

    const auto view_start = clock::now();
    for (int i = 0; i < calls; ++i) {
        check += sum_view(numbers);
    }
    const auto view_time = duration_cast<microseconds>(clock::now() - view_start);

    std::println("by value:  {:6} microseconds per call", copy_time.count() / calls);
    std::println("by const&: {:6} microseconds per call", view_time.count() / calls);
    std::println("(both sums together: {})", check);
    return 0;
}

Start with the first line, because it is the surprise. sizeof(numbers) is 48 bytes, for a deque holding four million bytes of ints. sizeof measures the variable's own box: the bookkeeping that says where the elements are and how many there are. The elements live elsewhere, on the heap, in blocks the deque owns (Week 1 chapter 6 showed the same for a vector, whose box was 24 bytes). Copying the deque copies what it owns: the copy asks the heap for new blocks and copies all four million bytes into them, and at the end of sum_copy it gives every block back.

That work is the difference between the two lines. In the Debug build the copy turned 10 milliseconds per call into 32. In the optimised build both got much faster, and the copy still more than doubled the time. Summing has to read every element anyway, so a copy "only" doubles or triples the cost here; a function that reads a single element of the deque would pay the whole four-megabyte copy to look at four bytes.

Trap

sizeof is not the cost of a copy. For a std::string, a std::vector, a std::deque, or a struct that contains any of them, sizeof counts only the box, and the copy also duplicates everything the box points at. When you judge "small or big", ask how much the object owns, not how big its box is.

Changing the caller's object, or returning a new one

The third kind of parameter, T&, is for a function whose job is to change something the caller owns. A bank account is the classic case. Here are two functions that add money: one changes the caller's account, the other leaves it alone and returns a changed copy.

#include <print>
#include <string>

struct Account {
    std::string owner;
    int balance_cents = 0;  // whole cents: a double cannot hold 0.10 exactly
};

// The function's job is to change the caller's account: by reference.
void deposit(Account& account, int cents) {
    account.balance_cents += cents;
}

// The caller wants a changed copy and keeps the original: by value, and return it.
Account with_deposit(Account account, int cents) {
    account.balance_cents += cents;
    return account;
}

int main() {
    Account mine{"Danish", 10000};
    deposit(mine, 2550);
    std::println("after deposit:     {} has {} cents", mine.owner, mine.balance_cents);

    const Account what_if = with_deposit(mine, 100000);
    std::println("what if:           {} cents", what_if.balance_cents);
    std::println("the real account:  {} cents", mine.balance_cents);
    return 0;
}

after deposit:     Danish has 12550 cents
what if:           112550 cents
the real account:  12550 cents

deposit(mine, 2550) binds account to mine itself, so the 25.50 lands in the caller's account; no copy of the struct is made. with_deposit(mine, 100000) works on a private copy, returns it, and mine is the same afterwards. Both are correct; they answer different questions. "Put this money in my account" is deposit. "What would my account look like after a big deposit?" is with_deposit, and there a copy is not a cost to avoid but the whole point.

The money is in whole cents, an int, because a double cannot hold 0.10 exactly (Week 1 chapter 2) and a bank that loses a fraction of a cent per deposit is a bank in trouble.

Notice the two signatures. void deposit(Account& account, int cents) reads aloud as "give me your account itself; I will change it". Account with_deposit(Account account, int cents) reads as "give me a copy; I hand back a new account". As Week 1 chapter 5 warned, the two calls look the same at the call site, so the signature is the only place this promise is written. That is why the declarations in snake.hpp are worth reading slowly: void tick(Game& game, ...) promises to change the game you pass it, and std::string render(const Game& game) promises only to look.

Returning a struct by value is fine

with_deposit and inverted both return a whole struct. Does that cost a second copy, from the function's variable into the caller's? Usually not. When a function returns an object by value, the caller sets aside room for the result in its own frame, and the compiler builds the result directly in that room. For a freshly made value, such as return Date{2026, 11, 26};, C++17 guarantees it, and for a named local variable compilers do it almost always. A parameter, like account in with_deposit, is the one case where it cannot happen, because the parameter already existed before the function started; there the compiler hands the result over with something cheaper than a copy, a move, which week 4 explains (for a 12-byte Colour, a move is simply a copy of its 12 bytes). So the rule from Week 1 stands: one result, return it by value; never return a reference to a local (chapter 7 shows that bug again with an object you can watch die).

The engine trap: dice that always roll a 4

You want a function that rolls a six-sided die. Week 1 chapter 8 introduced std::mt19937, the generator, and std::uniform_real_distribution<double>, which shapes its raw numbers into a real number in a range. Its integer sibling is std::uniform_int_distribution<int>: std::uniform_int_distribution<int> die(1, 6); gives whole numbers from 1 to 6 inclusive, each equally likely, every time you hand it the engine. Here is the roll with the engine taken by value, which looks harmless: the function only uses the engine, and it has no intention of changing anything the caller owns.

#include <print>
#include <random>

// The engine arrives BY VALUE: `rng` is a copy of the caller's engine.
int roll(std::mt19937 rng) {
    std::uniform_int_distribution<int> die(1, 6);
    return die(rng);
}

int main() {
    std::mt19937 rng(23);
    for (int i = 0; i < 8; ++i) {
        std::print("{} ", roll(rng));
    }
    std::println();
    return 0;
}

4 4 4 4 4 4 4 4

Eight rolls, eight 4s. Run it again and you get eight 4s again; seed it differently and you get eight of some other number. Now the same program with one character added, an &:

#include <print>
#include <random>

// The engine arrives BY REFERENCE: `rng` is another name for the caller's engine.
int roll(std::mt19937& rng) {
    std::uniform_int_distribution<int> die(1, 6);
    return die(rng);
}

int main() {
    std::mt19937 rng(23);
    for (int i = 0; i < 8; ++i) {
        std::print("{} ", roll(rng));
    }
    std::println();
    return 0;
}

4 1 2 1 6 5 4 3

Here is the mechanism. An engine is a variable full of state: 2,504 bytes, which Week 1 chapter 8 printed with sizeof. Every number it gives you stirs that state, and the next number comes from the stirred state. In dice_copy.cpp, each call to roll copies the caller's engine into the parameter, draws one number from the copy, stirring the copy, and then the copy dies at the closing brace. The caller's engine was never touched. The next call copies the same unstirred state again and draws the same first number again. The copy's state moved on; the original's did not.

In dice_ref.cpp, rng inside roll is another name for main's engine, so every draw stirs the one engine that lives on. Its first roll is the same 4 (same seed, same first draw), and from then on each call continues the sequence. As a bonus, nothing is copied: the by-value version moved 2,504 bytes per roll to produce a wrong answer.

First principle

A random engine is never read-only: giving you a number is changing it. So it can be neither a copy, which makes the change vanish, nor a const&, which forbids the change. If you try const std::mt19937&, the compiler refuses with a long message whose last note ends but method is not marked const: the function that draws a number is allowed to change the engine, so it cannot be called on a read-only one. A random engine always goes by plain &.

That is why every function in snake.hpp that draws a random number takes std::mt19937& rng, and why the comment above place_food says the reference is there on purpose. The test "place_food: the same seed gives the same food, and the engine moves on" checks both halves of this section: two engines with one seed give one sequence, and ten calls on one engine do not give the same cell ten times.

Trap

The by-value engine compiles without a warning and gives numbers that look random in any single call. It only shows itself when you look at many calls together. When a game always puts the food in the same place, or a "random" test always draws the same case, look for an engine passed by value, or for an engine created inside the function (Week 1 chapter 8's trap), which is the same mistake in another form.

A reference into a vector that moves

A reference is a second name for an existing box. All the bugs with references are one bug: the box stops existing while the name is still in use. Chapter 7 shows the version where the box is a local variable. Here is the version where the box is an element of a vector, and the vector moves.

#include <print>
#include <vector>

int main() {
    std::vector<int> scores = {7, 9, 4};
    int& best = scores[1];  // a second name for the 9
    std::println("best = {}, capacity = {}", best, scores.capacity());

    scores.push_back(10);  // no room left: the vector moves
    std::println("capacity now {}", scores.capacity());

    best += 1;  // the 9 is not where it was
    std::println("best = {}", best);
    return 0;
}

The first two lines explain everything. A vector keeps its elements in one block on the heap, and capacity() is how many elements fit in that block before it is full. This vector started with exactly 3. The call to push_back needed a fourth slot, so the vector did what a vector does: it asked the heap for a bigger block (room for 6), copied the three elements across, added the 10, and gave the old block back. best still names the slot in the old block, and line 12 reads it.

Read the report in the order Week 1 chapter 6 taught. The kind: heap-use-after-free, a heap block used after it was given back. What: READ of size 4, one int, the read half of best += 1. Where: #0 ... in main dangling_score.cpp:12. Then the two sections that make this kind of report so useful. freed by thread T0 here tells you who gave the block back: entry #9, line 9, the push_back (entries #0 to #8 are the library at work; _ZdlPv is the compiler's internal name for the function that returns memory to the heap). previously allocated by thread T0 here tells you who asked for it: line 5, where the vector was made (_Znwm is the internal name of the function that asks the heap for memory). The block was 12 bytes, three ints, and the read was 4 bytes inside it: element 1, the 9.

Without the sanitizers, compiled plainly, the same program printed best = 1 on this Mac and exited with status 0. Not 9, not 10: the heap had already reused the freed bytes for its own bookkeeping, the program added 1 to whatever was there, and the vector's real 9 was never touched. Nothing in the source looks wrong; the reference was valid when it was made.

The cure is to not hold a reference to an element across anything that can make the container move. Keep the element's position instead, and look it up again after the change:

#include <cstddef>
#include <print>
#include <vector>

int main() {
    std::vector<int> scores = {7, 9, 4};
    const std::size_t best = 1;  // a position, not a reference

    scores.push_back(10);  // the vector moves; positions do not
    scores[best] += 1;
    std::println("scores[{}] = {}", best, scores[best]);
    return 0;
}

scores[1] = 10

A position survives the move because it is just a number: element 1 is element 1 in the old block and in the new one.

A deque is different, but do not build on it

The C++ standard says that adding an element at either end of a std::deque, with push_back or push_front, keeps references to the existing elements valid: a deque grows by adding blocks, and it never moves the elements it already has. (It does invalidate iterators, which you meet in week 5.) Inserting in the middle or removing elements can break references, and the rule is different for every container. So in this course, treat every reference into a container as valid only until the container next changes, deque included. Positions and fresh look-ups are always safe.

Inference twin

An inference engine makes exactly these three choices, at a scale that turns mistakes into disasters. The weights of SmolLM2-135M, the model you run from week 17, are about 135 million numbers; at fp32, four bytes each, that is about 540 MB. Every function that computes with them takes them through a const reference or a view (a reference plus a shape, week 15), and a single by-value parameter in the wrong place would copy half a gigabyte per token. The KV cache, the memory where the model keeps what it has computed for earlier tokens (week 18), is the opposite case: it is written in place on every step, through a plain reference, exactly like deposit. And the small settings that steer generation, a temperature, a top-k, a seed, travel together in a small struct by value, like Date. Big and read-only, changed in place, small and copied: the table above is the parameter list of a decode step.

Check yourself

A struct Reading holds a double temperature and an int minute. How would you pass it to a function that only prints it, and why?

Answer

By value: void show(Reading r). It is two numbers, 16 bytes with padding, owns nothing on the heap, and the function only reads it. Copying it is as cheap as going through a reference, and it can travel in registers.

sizeof(std::deque<int>) printed 48 for a deque holding a million ints. Why does passing it by value still cost milliseconds?

Answer

sizeof counts only the deque's own box, the bookkeeping. The million elements live in heap blocks the deque owns, and a copy duplicates what it owns: it asks the heap for new blocks, copies four million bytes and gives the blocks back when the copy dies.

int roll(std::mt19937 rng) returns the same number on every call with the same engine. Explain in terms of the engine's state, and give the one-character fix.

Answer

Each call copies the caller's engine state into rng, draws from the copy (which stirs the copy) and throws the copy away. The caller's engine never changes, so every call starts from the same state and draws the same number. Add &: int roll(std::mt19937& rng), so every draw stirs the caller's engine.

Why can the engine not be passed as const std::mt19937&?

Answer

Drawing a number changes the engine's state, and const forbids changes, so the compiler refuses the draw (its message ends but method is not marked const). A random engine is never read-only.

A function takes Account& account and another takes Account account and returns an Account. At the call site both look like f(mine, 100). Which one changes mine, and where do you find out?

Answer

Only the one with Account& changes mine; the other changes a copy and returns it. The call site cannot tell you; the declaration, with or without the &, is the only place the promise is written.

After int& r = v[0]; the program calls v.push_back(5) and then reads r. Under the sanitizers it sometimes reports heap-use-after-free and sometimes does not. Why the difference, and what is the robust fix?

Answer

It depends on the capacity. If the vector was full, push_back moved the elements to a new block and freed the old one, and r names a slot in the freed block: use after free. If there was spare capacity, nothing moved and r is still fine, by luck. The fix that does not depend on luck is to keep the position, std::size_t i = 0;, and use v[i] after the change.

Fill in the parameter types for bool on_weekend(? date), double average(? readings) where readings is a std::deque<double>, void add_reading(? readings, double value), and int draw_card(? rng).

Answer

Date date (small, read-only), const std::deque<double>& readings (big, read-only), std::deque<double>& readings (changed for the caller), std::mt19937& rng (an engine, always by reference).

What you can do now

  • Judge whether a type is small or big by what it owns, not by its sizeof.
  • Pass small structs such as a Date or a Colour by value, and say why that is as cheap as a reference or cheaper.
  • Pass containers by const&, and show with steady_clock what a by-value copy of a million-element deque costs.
  • Choose between changing the caller's object through & and returning a new value, and read that choice off a signature.
  • Return structs by value without worrying about copies.
  • Roll dice with std::uniform_int_distribution<int>, and explain why an engine passed by value repeats itself while one passed by & moves on.
  • Read a heap-use-after-free report, find who freed the block and who allocated it, and avoid holding references into a container across a change.
