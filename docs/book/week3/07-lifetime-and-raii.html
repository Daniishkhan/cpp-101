Chapter 07

Scope, lifetime and RAII

At the end of this chapter you will be able to say exactly when every object in a program is born and when it dies, write a small struct that cleans up after itself however its scope is left, change one terminal setting and always put it back, and make Ctrl-C end a loop cleanly instead of killing the program. That last one keeps the promise of Week 1 chapter 9.

In this chapter
  • Scope (where a name can be used) and lifetime (when an object exists).
  • A struct whose constructor and destructor print, to watch objects live and die in blocks, loops, globals and vectors.
  • Two ways to outlive an object by mistake: a reference to a dead local, and std::exit.
  • RAII: a guard that hides the cursor and always shows it again.
  • The terminal driver's switches: flag words and the bit operators &, |, ~.
  • A second guard that turns echo off for a password prompt.
  • Ctrl-C, what it leaves behind, and the fix: a signal handler that sets a flag.

Scope and lifetime are two different questions

Week 1 chapter 4 introduced scope: the part of the program text where a name can be used. A pair of braces makes a block, and a name declared in a block can be used from its declaration to the closing brace. The braces need not belong to a function, an if or a loop; a bare pair makes a block too. The compiler checks scope:

#include <print>

int main() {
    {
        int inner = 42;
        std::println("inside the block: {}", inner);
    }
    std::println("after the block: {}", inner);  // the name ended with the block
    return 0;
}

scope_error.cpp:8:41: error: use of undeclared identifier 'inner'
    8 |     std::println("after the block: {}", inner);  // the name ended with the block
      |                                         ^~~~~
1 error generated.

Scope is about text: which lines may mention inner. Lifetime is about time: while the program runs, when does the box exist? For a local the two match: the box is made when the declaration runs and destroyed when the program leaves the block. But they are not the same thing, and this chapter's bugs live in the gap: a name still usable for an object that no longer exists. For an int you cannot watch a lifetime, because nothing visible happens when an int dies. For your own structs you can make something happen.

A struct that announces its birth and death

A struct may contain two special functions. One with the struct's own name and no return type, not even void, is the constructor: it runs automatically whenever an object of the type is created. One with the struct's name after a ~ (tilde) is the destructor: it runs automatically whenever an object of the type is destroyed. You never call either yourself. This chapter uses only the simplest form, with empty parentheses; week 4 goes deep.

#include <print>

int next_number = 1;  // a global: outside every function, alive for the whole run

struct Noisy {
    int number = 0;

    Noisy() {  // the constructor: runs when a Noisy is created
        number = next_number;
        next_number += 1;
        std::println("  Noisy {} is born", number);
    }

    ~Noisy() {  // the destructor: runs when a Noisy dies
        std::println("  Noisy {} dies", number);
    }
};

int main() {
    std::println("main starts");
    Noisy a;
    {
        std::println("inner block starts");
        Noisy b;
        Noisy c;
        std::println("inner block ends");
    }
    std::println("back in main");
    return 0;
}

main starts
  Noisy 1 is born
inner block starts
  Noisy 2 is born
  Noisy 3 is born
inner block ends
  Noisy 3 dies
  Noisy 2 dies
back in main
  Noisy 1 dies

int next_number = 1; sits outside every function, which makes it a global: its scope is the rest of the file and its lifetime is the whole run. Each Noisy takes a number from it, so you can tell them apart. Now read the output against the code. a is born when its declaration runs, b and c inside the block in the order declared. At the block's closing brace both die, in reverse order: c, then b. a dies last, after back in main: leaving main is leaving a block too.

First principle

A local object dies when the program leaves the block that holds it, and the objects of one block die in the reverse of the order they were born: last in, first out, like a stack of plates. Reverse order is what makes it safe for a later object to depend on an earlier one: the later one is taken apart while the earlier one still exists.

A loop body is a new block every time round

#include <print>

Every pass enters the loop body and leaves it again, so n is three different objects that share a name, and each is gone before the next pass begins.

Two ways to outlive an object by mistake

A reference to a dead local

Week 1 chapter 5 warned you never to return a reference to a local. Now you can watch why:

#include <print>

int next_number = 1;

struct Noisy {
    int number = 0;
    Noisy() {
        number = next_number;
        next_number += 1;
        std::println("  Noisy {} is born", number);
    }
    ~Noisy() {
        std::println("  Noisy {} dies", number);
    }
};

const Noisy& make_noisy() {
    Noisy local;
    return local;  // a name for an object that dies at the closing brace
}

int main() {
    const Noisy& r = make_noisy();
    std::println("using Noisy {}", r.number);
    return 0;
}

$ clang++ -std=c++23 -Wall -Wextra dangling_noisy.cpp -o dangling_noisy
dangling_noisy.cpp:19:12: warning: reference to stack memory associated with local variable 'local' returned [-Wreturn-stack-address]
   19 |     return local;  // a name for an object that dies at the closing brace
      |            ^~~~~
1 warning generated.

A warning, not an error, so the program is built. Run it and the lines come in this order: Noisy 1 is born, Noisy 1 dies, using Noisy .... The object died at the closing brace of make_noisy, before main used the reference. The number after "using" is not promised: 0 in a plain build on this Mac, 41448480 under tools/run.sh, and neither sanitizer said a word. The reference's scope outlived the object's lifetime, and this warning is your only guard.

std::exit skips the destructors of locals

std::exit(status), from <cstdlib>, ends the program on the spot from anywhere, with that exit status:

#include <cstdlib>
#include <print>

int next_number = 1;

struct Noisy {
    int number = 0;
    Noisy() {
        number = next_number;
        next_number += 1;
        std::println("  Noisy {} is born", number);
    }
    ~Noisy() {
        std::println("  Noisy {} dies", number);
    }
};

Noisy global_one;

int main() {
    std::println("main starts");
    Noisy local;
    std::println("calling std::exit(0)");
    std::exit(0);  // ends the program here: nothing below this line runs
}

  Noisy 1 is born
main starts
  Noisy 2 is born
calling std::exit(0)
  Noisy 1 dies

There is no Noisy 2 dies. std::exit does not leave main's block, it stops the program, so no closing brace is reached and no local destructor runs; only the globals are cleaned up. For a Noisy that costs a line of output. For the guards below it costs a terminal left in the wrong state. In this book, a program ends by returning from main.

RAII: tie the clean-up to a lifetime

Some actions come in pairs: hide the cursor and show it again; change a terminal setting and put it back; open a file and close it. The second half must happen however the code in between ends. Writing it by hand at every way out fails the day you add a way out, as Life's cursor showed.

Instead, put the first half in a constructor and the second half in a destructor, and make an object of that type a local variable. The language guarantees the destructor runs on every ordinary way out of the block: the closing brace, an early return, a break or a continue. This pattern is RAII, "resource acquisition is initialisation": the thing is acquired when the object is initialised and released when it dies. An object whose only job is that is a guard. Week 1 chapter 6 named RAII when a vector gave back its own memory; now you write your own.

Analogy

A guard is a door with a spring closer. You open it once and never have to remember to shut it: walk through, run through or turn back halfway, and the spring closes it behind you.

Where it breaks: the spring only acts when you leave through that door. Two ways out of a program climb out of the window instead: std::exit, which you have just seen, and being killed by a signal, which is what Ctrl-C does. The end of this chapter turns the second one into an ordinary way out.

Guard 1: a cursor that always comes back

Here is Week 1's hidden cursor as a guard, protecting a countdown that can give up early. The early stop is a std::optional<int> from chapter 5, so the second countdown can have none.

#include <chrono>
#include <cstdio>
#include <optional>
#include <print>
#include <thread>

// While a CursorHidden exists, the terminal's cursor is hidden.
struct CursorHidden {
    CursorHidden() {
        std::print("\x1b[?25l");  // hide the cursor (Week 1 chapter 9)
        std::fflush(stdout);
    }
    ~CursorHidden() {
        std::print("\x1b[?25h");  // show it again
        std::fflush(stdout);
    }
};

// Counts down from `from`. Gives up at `scrub_at`, if there is one. True means lift-off.
bool countdown(int from, std::optional<int> scrub_at) {
    using namespace std::chrono_literals;
    CursorHidden cursor;
    for (int seconds = from; seconds > 0; --seconds) {
        if (scrub_at == seconds) {
            std::println("\rscrubbed at {}", seconds);
            return false;  // way out 1: early return
        }
        std::print("\r{:2} ", seconds);
        std::fflush(stdout);
        std::this_thread::sleep_for(1s);
    }
    std::println("\rlift-off");
    return true;  // way out 2: the normal end
}

int main() {
    if (!countdown(5, 3)) {
        std::println("trying again");
        countdown(5, std::nullopt);
    }
    return 0;
}

Run it and watch. The first countdown shows 5 and 4, prints scrubbed at 3 and returns early; the second runs from 5 to lift-off. The cursor is hidden during each countdown and back after each, including after the early return, although no "show" line is anywhere near either return. Recorded through a terminal, the bytes say the same: \x1b[?25l before the first 5, \x1b[?25h straight after scrubbed at 3, and the same pair around the second countdown. cursor is never mentioned after its declaration; its job is to exist. (The compiler does not call it unused, because a variable whose type has a constructor or destructor is assumed to be there for them.)

Try it

Replace return false; with break;, and predict what the first countdown now prints and whether the cursor comes back. Then press Ctrl-C during the second countdown and look at your prompt: the cursor is gone (tput cnorm brings it back). The guard did not run. Why not is the rest of this chapter.

The terminal driver and its switches

Between your keyboard and your program sits a part of the operating system called the terminal driver; Week 1 chapter 9 met it adding a carriage return before every newline you print. On the input side it does three things you have relied on without noticing:

  • Line mode, officially canonical mode: it collects what you type into a line and gives your program nothing until Enter. Until then the line is the driver's, Backspace edits it, and your program never sees the mistake.
  • Echo: it sends every key you type back to the screen. Your program never printed those letters.
  • Ctrl-C as a signal: Ctrl-C does not reach your program as a byte. The driver sends a signal, a message from the operating system that arrives outside the program's normal flow. This one is SIGINT, the interrupt signal, and unless the program has made arrangements, it ends the program on the spot.

Each is a switch a program may flip: a password prompt wants echo off, and Snake wants line mode off too (chapter 8). The switches live in a struct of type termios, from the C header <termios.h>, packed as bits into a few numbers called flag words.

A flag word: one number, many switches

A number is stored as a pattern of bits (Week 1 chapter 2). A flag word uses each bit as a separate on-off switch. Each switch gets a number with exactly one bit set, a power of two: 1, 2, 4, 8, which are 0001, 0010, 0100, 1000 in binary. Such a one-bit number is a mask. Three operators, each working on every bit position separately, do the rest:

OperatorA result bit is 1 when...Used forExample
a | b (or)it is 1 in a, in b, or in bothswitching on: word |= mask1001 | 0010 is 1011
a & b (and)it is 1 in bothtesting: (word & mask) != 01011 & 1000 is 1000
~a (not)it is 0 in a: every bit flipsswitching off: word &= ~mask~0001 is 1110 (in four bits)

Here they are on four light switches. 0b in front of a number means "written in binary", and {:04b} prints a number in binary, at least four digits, with leading zeros.

#include <print>

int main() {
    // One switch per bit. In binary, 1, 2, 4 and 8 are 0001, 0010, 0100 and 1000.
    const unsigned int kitchen = 0b0001;
    const unsigned int hall = 0b0010;
    const unsigned int bedroom = 0b0100;
    const unsigned int garden = 0b1000;

    unsigned int lights = kitchen | garden;  // two lights on
    std::println("start:              {:04b}", lights);

    lights |= hall;  // switch the hall on
    std::println("hall on:            {:04b}", lights);

    lights &= ~kitchen;  // switch the kitchen off
    std::println("kitchen off:        {:04b}", lights);

    std::println("garden on?          {}", (lights & garden) != 0);
    std::println("bedroom on?         {}", (lights & bedroom) != 0);
    std::println("~kitchen, all bits: {:032b}", ~kitchen);
    return 0;
}

start:              1001
hall on:            1011
kitchen off:        1010
garden on?          true
bedroom on?         false
~kitchen, all bits: 11111111111111111111111111111110

kitchen | garden is 0001 | 1000, so 1001. lights |= hall, short for lights = lights | hall, sets one bit and leaves the rest. Switching off takes two operators: ~kitchen is every bit except the kitchen's (the last line shows all 32), and & with it keeps every bit that was on except that one. Testing is & with the mask, which gives the mask if the bit was on and 0 if not. The type is unsigned int (Week 1 chapter 8): a row of switches has no sign.

Trap

& is not &&, and | is not ||: the doubled ones treat each side as a single true or false. lights && garden compiles and only asks whether both numbers are non-zero. Keep the parentheses in (lights & garden) != 0, too: without them it means lights & (garden != 0). And note that & now has three jobs: after a type it makes a reference, between two numbers it is bitwise and, and in front of a variable handed to a C function it does the third job, next.

Reading the terminal's settings

termios has a member c_lflag, the "local flags" word, and <termios.h> provides a mask for each of its switches; the first you need is ECHO. (Names from C headers are often in capitals; your own constants stay in snake_case.) tcgetattr, "terminal control: get attributes", fills a termios variable with the current settings. Its first argument is STDIN_FILENO, from <unistd.h>: the number of your program's standard input, the keyboard. Its second is your variable, written &settings. Take that & on trust: the function is written in C, which has no references, so it must be told where your variable lives in memory, and &settings is that location, its address. Buffer A shows what an address really is.

#include <print>
#include <termios.h>
#include <unistd.h>

int main() {
    termios settings{};
    if (tcgetattr(STDIN_FILENO, &settings) != 0) {  // fill `settings` from the terminal
        std::println("standard input is not a terminal");
        return 1;
    }
    std::println("c_lflag: {:32b}", settings.c_lflag);
    std::println("ECHO:    {:32b}", ECHO);
    if ((settings.c_lflag & ECHO) != 0) {
        std::println("echo is on");
    } else {
        std::println("echo is off");
    }
    return 0;
}

ECHO:                                1000
echo is on
$ stty -echo; ./echo_flag; stty echo
c_lflag:   100000000000000000010111000011
ECHO:                                1000

$ ./echo_flag < /dev/null

(Recorded through a terminal on this Mac; the other bits depend on your terminal program.) {:32b} right-aligns the binary in 32 columns, so the mask sits under the bit it tests, the fourth from the right. In the second run the shell command stty -echo switched echo off before the program ran and stty echo switched it on again after, all on one line, and exactly one bit changed. In the third, standard input is a file, so tcgetattr has no terminal to ask and returns -1 instead of 0; a careful program checks.

Guard 2: echo off for a password prompt

To change a setting, read the settings, change a copy, and hand the copy back with tcsetattr, "set attributes"; its middle argument, TCSANOW, means "now". To put things back later, the guard keeps the original settings in a member, like any value in a struct (chapter 1). std::getline(std::cin, line), from <iostream>, reads one typed line into a string; take it on trust.

#include <cstdio>
#include <iostream>
#include <print>
#include <string>
#include <termios.h>
#include <unistd.h>

// While an EchoOff exists, the terminal does not show what you type.
// Line mode stays on: you still finish the line with Enter, and Backspace still works.
struct EchoOff {
    termios original{};  // the settings to put back

    EchoOff() {
        tcgetattr(STDIN_FILENO, &original);          // save the settings as they are
        termios changed = original;                  // change a copy...
        changed.c_lflag &= ~ECHO;                    // ...with one switch turned off
        tcsetattr(STDIN_FILENO, TCSANOW, &changed);  // and hand it to the terminal
    }

    ~EchoOff() {
        tcsetattr(STDIN_FILENO, TCSANOW, &original);  // put back exactly what was saved
    }
};

int main() {
    std::string password;
    {
        EchoOff quiet;
        std::print("password: ");
        std::fflush(stdout);
        std::getline(std::cin, password);
        std::println();  // Enter was not echoed either
    }
    std::println("you typed {} characters", password.size());
    return 0;
}

$ ./password
password:
you typed 6 characters

That is the screen after typing secret and Enter (checked by driving the program through a terminal from a script: the letters never appeared). The constructor saves the settings in original, copies them, switches exactly one bit off in the copy with &= ~ECHO, the kitchen light again, and hands the copy over. The destructor hands back original. Restoring the saved settings, rather than switching echo on, matters: if echo was off when the program started, it stays off. Line mode is untouched, so Enter still ends the line and Backspace still corrects it. The guard lives in its own block, so echo is back before anything else is printed. The prompt is flushed before reading, or it could still sit in the buffer (Week 1 chapter 9), and the program prints its own newline, because the Enter was not echoed either.

First principle

A guard saves the whole state before changing anything, and restores exactly that state when it dies. It never assumes what the state was. One guard, one job.

Ctrl-C: the way out that skips everything

Press Ctrl-C at the password prompt. The program ends at once, without even a ^C on screen, because ^C is shown by echo and echo is off. The exit status is 130 (128 plus 2, the number of SIGINT). The destructor did not run: a program killed by a signal runs none of its own code, clean-up included. At that moment the terminal still has echo off.

What happens next depends on who started the program. zsh, your Mac's shell, switches echo and line mode back on before it runs your next command, so in zsh you may notice nothing. bash restores its saved settings only after a program was killed by a signal, and keeps whatever a program that ended normally left behind. Inside a script, or when one program starts another, nothing is repaired until a shell shows its next prompt. And nothing repairs the cursor: hiding it was an escape sequence the terminal obeyed, which no shell knows to undo. You can catch the damage even in zsh. Add std::exit(0); after the std::println(); inside the guard's block (with #include <cstdlib>), build it as password_exit, and put a second command on the same line, so that it runs before zsh gets its turn:

$ ./password_exit; ./echo_flag
password:
c_lflag:                      10111000011
ECHO:                                1000
echo is off
$ ./echo_flag
c_lflag:   100000000000000000010111001011
ECHO:                                1000
echo is on

The guard restored nothing; zsh repaired it before the next prompt. In bash the same run leaves echo off: you type ls, see nothing, and the command still runs when you press Enter. Two shell commands fix a terminal in a strange state; type them even if you cannot see them, and press Enter:

  • stty sane sets the driver's switches back to sensible values: echo on, line mode on, Ctrl-C a signal.
  • reset also resets the terminal program itself: the cursor comes back, colours are cleared and the screen is wiped. It is the bigger hammer, and it takes about a second.
Trap

Do not let zsh's kindness make a guard look optional. zsh repairs only echo and line mode, and only when it gets back to its prompt. Not the cursor, not colours, not the other switches Snake changes. A program that relies on its shell to clean up works on your machine and breaks on someone else's.

The fix: turn the signal into a flag

The trouble is not the signal but its default effect: being killed mid-step. std::signal(SIGINT, on_interrupt), from <csignal>, tells the operating system: "when SIGINT arrives, do not kill me; call on_interrupt instead". Such a function is a signal handler. When it returns, the program carries on from exactly where it was interrupted.

The handler cannot do the clean-up itself. The signal can arrive between any two machine instructions: halfway through a std::println, with the output buffer half-updated, or while the heap is handing out memory. A handler that printed or built a string would walk into the half-finished operation and could corrupt it or wait for it for ever. So a handler does almost nothing. The one thing it may safely do is store a value in a variable of type volatile std::sig_atomic_t. std::sig_atomic_t is an integer type the machine writes in one step, so the program never sees half a write. volatile tells the compiler the variable can change behind the program's back, so the loop really reads it every time; otherwise the optimiser, seeing a loop that never changes the flag, may read it once and never again. And it must be a global, because the operating system calls the handler and nobody can pass it a parameter.

So: the handler sets the flag; the loop checks it every time round; when it is set, the loop ends, the block is left the ordinary way, and every guard's destructor runs. Ctrl-C has become an ordinary way out.

#include <chrono>
#include <csignal>
#include <cstdio>
#include <print>
#include <thread>

// Set by the signal handler, read by the loop. Nothing else may touch it.
volatile std::sig_atomic_t interrupted = 0;

// Runs when Ctrl-C arrives. It does one thing: set the flag.
void on_interrupt(int) {
    interrupted = 1;
}

struct CursorHidden {
    CursorHidden() {
        std::print("\x1b[?25l");
        std::fflush(stdout);
    }
    ~CursorHidden() {
        std::print("\x1b[?25h");
        std::fflush(stdout);
    }
};

int main() {
    using namespace std::chrono_literals;
    std::signal(SIGINT, on_interrupt);  // Ctrl-C: call on_interrupt instead of killing us

    CursorHidden cursor;
    for (int seconds = 10; seconds > 0 && interrupted == 0; --seconds) {
        std::print("\r{:2} ", seconds);
        std::fflush(stdout);
        std::this_thread::sleep_for(1s);
    }
    if (interrupted == 1) {
        std::println("\rstopped by Ctrl-C");
    } else {
        std::println("\rlift-off");
    }
    return 0;  // cursor's destructor runs after this line
}

$ ./countdown_ctrl_c
stopped by Ctrl-C
$ echo $?
0

That is the screen after pressing Ctrl-C at about 8 (for a moment the line reads 8 ^C, then the message overwrites it). Exit status 0, not 130, and the last bytes written are \x1b[?25h: the cursor came back. The handler's parameter has no name, void on_interrupt(int): std::signal needs a handler that takes the signal's number, this one does not use it, and leaving the name out says so on purpose (a named, unused parameter draws a -Wunused-parameter warning).

The message came 0.73 seconds after the key press in the recorded run, not at once. The signal arrived during sleep_for(1s); the handler ran, the sleep carried on to the end of its second (that is what Apple's library does with an interrupted sleep), and only then did the loop look at the flag. A flag is only as good as how often the loop looks at it. A program blocked in std::getline keeps waiting after the handler has run, because macOS quietly restarts an interrupted read. Snake's loop never waits for a key: it looks at the keyboard and at the flag on every tick.

Try it

Move the std::signal line to after the loop and press Ctrl-C during the countdown: status 130, cursor hidden. Put it back, then split each second into ten sleep_for(100ms) calls, checking the flag after each, and see how much faster Ctrl-C is answered.

Two guards: the order of destruction

A program often holds more than one guard. They follow the rule of plates. Here are two harmless ones on a trip to the garden shed, once with the ladder there and once without:

#include <print>

struct DoorOpen {
    DoorOpen() {
        std::println("  open the shed door");
    }
    ~DoorOpen() {
        std::println("  close the shed door");
    }
};

struct LightOn {
    LightOn() {
        std::println("  switch the shed light on");
    }
    ~LightOn() {
        std::println("  switch the shed light off");
    }
};

void fetch(bool ladder_is_there) {
    DoorOpen door;
    LightOn light;
    if (!ladder_is_there) {
        std::println("  no ladder: leave early");
        return;
    }
    std::println("  take the ladder");
}

int main() {
    std::println("first trip:");
    fetch(true);
    std::println("second trip:");
    fetch(false);
    return 0;
}

first trip:
  open the shed door
  switch the shed light on
  take the ladder
  switch the shed light off
  close the shed door
second trip:
  open the shed door
  switch the shed light on
  no ladder: leave early
  switch the shed light off
  close the shed door

The door was opened first, so it is closed last. The early return gives the same clean-up in the same order. A CursorHidden declared before an EchoOff would likewise restore echo first and the cursor second. For those two the order is harmless, but the rule matters whenever one guard depends on another: declare the one it depends on first, and destruction undoes them in a safe order.

Inference twin

Every resource in an inference engine that is not plain memory is held this way. In week 17 your engine maps SmolLM2's weight file into memory, so its hundreds of megabytes can be read as one long array; a guard maps it in its constructor and unmaps it in its destructor, so no error path leaks the mapping. In week 22 every buffer on the GPU belongs to an object whose destructor frees it. And a serving process stops on Ctrl-C the way your countdown does: the handler sets a flag, the loop finishes the token it is computing, and the destructors hand back the GPU memory and the files on the ordinary way out.

Check yourself

What is the difference between the scope of a local and its lifetime? Give a case where a name is usable but its object no longer exists.

Answer

Scope is the stretch of program text where the name may be used, checked by the compiler; lifetime is the stretch of time during the run when the object exists. A reference returned from a function to one of its locals: the name is in scope in the caller, but the object died when the function returned.

x, y and z are declared in that order in one block, and a Noisy is declared inside a loop that runs five times. When do the destructors run, and in what order?

Answer

z, y, x, when the program leaves the block, whichever way it leaves. The loop's Noisy is born and destroyed five times, once per pass; at most one exists at a time.

Which of these run the destructors of the current function's locals: the closing brace, return, break out of a loop that holds the object, std::exit(0), being killed by Ctrl-C?

Answer

The first three. std::exit(0) runs only the globals' destructors, and a program killed by a signal runs none of its own code.

Write one line each to switch ECHO off in settings.c_lflag, switch it on, and test it.

Answer

Off: settings.c_lflag &= ~ECHO;. On: settings.c_lflag |= ECHO;. Test: (settings.c_lflag & ECHO) != 0.

Why does the EchoOff destructor hand back the saved original instead of switching ECHO on?

Answer

The guard does not know what the state was before. If echo was already off, switching it on would leave the terminal different from how the program found it; restoring the saved settings puts back exactly what was there.

Why must a signal handler do almost nothing, and why is the flag a volatile std::sig_atomic_t?

Answer

The signal can interrupt the program between any two instructions, even in the middle of printing or of the heap's bookkeeping, and a handler doing the same kind of work could corrupt it or wait for ever. Storing one value is safe. std::sig_atomic_t is written in one step, so the loop never sees half a write; volatile makes every check in the loop really read the variable.

A program installs the Ctrl-C flag and then blocks in std::getline. You press Ctrl-C. What happens, and what does that say about where the flag must be checked?

Answer

The handler sets the flag and the read carries on waiting (macOS restarts it), so nothing visible happens until a line is typed. The flag only helps a loop that checks it regularly and never waits indefinitely, which is why Snake's loop looks at the keyboard on every tick instead of waiting for a key.

What you can do now

  • Tell scope from lifetime, and predict when locals, loop-body objects, globals and a vector's elements are born and die.
  • Write a struct with a constructor and a destructor, and use one as a guard that undoes its action on every ordinary way out.
  • Explain why a reference to a local and std::exit both leave you on the wrong side of a lifetime.
  • Read and change a flag word with &, |, ~, &= and |=, and read the terminal's settings with tcgetattr.
  • Write a guard that switches one terminal setting off and restores the saved settings.
  • Recover a terminal with stty sane or reset, and say what zsh repairs and what it does not.
  • Turn Ctrl-C into a flag with std::signal and a volatile std::sig_atomic_t, so the loop ends normally and every guard's destructor runs.
