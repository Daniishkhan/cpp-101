What you will build: Snake

A snake lives on a walled board. Every tick, a fixed slice of time, its head moves one cell forward and the rest of the body follows. You steer it with the arrow keys or w a s d; you cannot stop it. Somewhere on the board is a piece of food. When the head reaches the food, the snake grows by one cell, you score a point, new food appears on a random free cell, and every five points the ticks get shorter, so the snake moves faster. If the head runs into the wall or into the snake's own body, the game is over. Fill the whole board and you win.

Here is a 12-wide, 5-tall board, exactly as your program will draw it: a # wall around the outside, @ for the head, o for the rest of the body, * for the food, and a space for an empty cell.

##############
#            #
#   ooo@     #
#        *   #
#            #
#            #
##############
score 0   length 4   150 ms per tick

The snake is heading right. Its head is in column 6, row 1 (columns and rows count from 0, and row 0 is the top, as in Life). If nothing is pressed, the next tick moves the head to column 7 and the tail leaves column 3. Press the down arrow, and the head goes to column 6, row 2 instead; one tick after that it is next to the food, which is in column 8, row 2.

That looks like a small change from Life: another grid redrawn in place. It is not, for three reasons, and they are what this week teaches.

  • The program has to listen while it runs. Life never read the keyboard. A terminal normally holds back what you type until you press Enter, and echoes it on the screen. Snake needs every key the moment it is pressed, silently. That means changing the terminal's settings, and then, however the program ends, changing them back. Chapter 7 and chapter 8.
  • The data has shape. In Life everything was a number or a vector of numbers, and you passed cells, width, height around as three loose parameters. A snake is a list of positions; a position is two numbers that belong together; a direction is one of exactly four choices; a game is all of that plus a score. C++ lets you make these into types of your own, so the compiler can check that you never pass a width where a height belongs. Chapter 1 and chapter 2.
  • The body moves at both ends. Every tick a cell is added at the head and one is removed at the tail. A std::vector is cheap at one end only. Chapter 4 introduces the container made for this.

And one tool that is not C++ at all: the debugger. Until now, when a test failed you read the message and added std::println lines. On Tuesday you learn to stop a running program on any line and look at every variable in it. Chapter 3 is that session.

Inference twin

The Snake loop is a decode loop. A language model producing text does one step per token: read the state, compute, emit one token, go again, within a time budget per token. Snake does one step per tick: read the keys, update the game, emit one frame, wait for the next deadline. A tick whose work takes longer than its budget is a dropped frame; in a chat window the same thing is a latency spike. Your program will count them. And there is a second twin hidden in the body: to know whether the head bit the snake, every tick checks it against every cell of the body, so a longer snake costs more per tick, the way a longer context makes every decode step cost more. The benchmark measures that line on Saturday.

Setup

Let the debugger in (once, before Tuesday)

A debugger is a program that controls another program: it stops it, reads its memory, steps it one line at a time. macOS guards that power. On this Mac, as it was found on 7 November, Developer Mode is off, so the first time lldb starts a program a dialog asks for your password, and in some situations lldb simply waits until you answer. Switch it on once, in Terminal:

$ sudo DevToolsSecurity -enable
Password:
Developer mode is now enabled.
$ DevToolsSecurity -status
Developer mode is currently enabled.

sudo runs one command as the administrator, which is why it asks for your login password (nothing appears as you type it; that is deliberate). If you prefer not to change the setting, approve the dialog the first time it appears on Tuesday instead; it is remembered for a while.

The same permission matters to AddressSanitizer. When it finds a bug, it turns the raw addresses of its report into file names and line numbers by asking a helper, atos, to look inside your still-running program, and atos needs exactly the permission lldb needs. Without it, a report on this Mac printed its first lines and then hung, waiting for that dialog. Enabling Developer Mode fixes both. If you would rather not, there is a second fix for the sanitizers alone: point them at the symbolizer that came with Homebrew's LLVM, which reads the program file instead of the running program and needs no permission. Add this line to ~/.zshrc and open a new terminal window:

export ASAN_SYMBOLIZER_PATH=/opt/homebrew/opt/llvm/bin/llvm-symbolizer

lldb itself still needs Developer Mode or the dialog.

Build the Snake folder and read the red

The challenge folder is phase1-terminal/02-snake. Its CMakeLists.txt is Life's, with one new idea: the game is made from three source files, while the tests and the benchmark need only one. Configure, build, and run the tests exactly as you did for Life:

$ cd phase1-terminal/02-snake
$ cmake -S . -B build -G Ninja
$ cmake --build build
$ ./build/snake_tests
...
===============================================================================
[doctest] test cases:  26 |  3 passed |  23 failed | 0 skipped
[doctest] assertions: 224 | 93 passed | 131 failed |
[doctest] Status: FAILURE!

Twenty-six test cases, one small claim each, in milestone order. List them with ./build/snake_tests -ltc; the names are written so you can filter on any one of them with -tc="...", as in Week 1 chapter 12. Here are the first few failures, which are milestone 1's:

TEST CASE:  next_head: one step in each direction (y grows downwards)

tests/snake_test.cpp:132: ERROR: CHECK( next_head({5, 5}, Direction::Up) == Point{5, 4} ) is NOT correct!
  values: CHECK( {5, 5} == {5, 4} )

Read the values: line. The test asked where the head goes when it moves up from column 5, row 5, and expected column 5, row 4 (up makes the row number smaller). The stub answered column 5, row 5: it does not move the head at all. Notice that doctest prints a Point as {5, 4}. That is not automatic; a few lines at the top of the test file teach it how, and you may read them, but you do not need to understand them yet.

Three tests that pass by accident

Twenty-three cases fail, which is right. Three pass, which is the lesson Week 1's setup taught you with step: does not modify current, three times over. Find them before you read on: run each case on its own with -tc, or read the output for the cases that are missing from it.

Show which three, and why

steer: a request to reverse is ignored: every check in it expects steer to keep the old heading, and the stub always returns the old heading. parse_key: no key or a key the game does not use: every check expects "nothing", and the stub always returns nothing. tick: nothing changes once the game is over: the stub tick changes nothing, ever. Each of the three describes something a correct program must not do, and a program that does nothing at all never does it. Keep them in mind: when you start changing steer, parse_key and tick, these are the tests that can turn red, and that is the moment they start to mean something.

The program itself builds too. It prints one line and exits, like Life's stub did:

$ ./build/snake
snake: not implemented yet (0 arguments given)

Terminal first aid

This week, for the first time, your program changes how the terminal behaves. While Snake runs, the terminal does not echo what you type, hands over each key the moment it is pressed, and hides the cursor. If your program stops without putting that back (a crash, a sanitizer report, a bug in the guard you are writing), something is left behind.

What you see depends on the shell. zsh, the shell Terminal runs on your Mac, protects itself: before it prints its next prompt, it switches echo and line mode back on, so you can type normally again. Nothing switches the cursor back on, though: the prompt returns without one. In bash, the usual shell on Linux, nothing is repaired: you type and nothing appears, or each key acts at once.

Nothing is broken either way. tput cnorm brings the cursor back. reset puts every setting back to normal and clears the screen; if nothing echoes, type it blind and press Enter. If the window is truly stuck, close it and open a new one; settings belong to a window, not to your Mac. Chapter 7 explains what happened, and the guard you write on Friday is what makes it never happen again.

Try it

Practise now, while nothing is at stake. Type stty -echo; cat and press Enter. Type hi and press Enter: you did not see the letters as you typed them, but cat repeats the line once Enter arrives. That is echo off with line mode still on, the first part of what Snake's guard will do. Press Ctrl-D to end cat, then type anything at the prompt: your letters show again, because zsh switched echo back on before printing the prompt. That repair is why, this week, you check what a program left behind with a second program on the same command line, as cat was here.

Check yourself

The snake's head is at column 3, row 4, moving up. Where is it after one tick, if no key is pressed?

Answer

Column 3, row 3. Rows count downwards from the top, so moving up makes the row number one smaller, and with no key pressed the heading stays up.

Why can 26 tests check the whole game without anyone pressing a key?

Answer

Because the game's rules live in snake.hpp as functions that take values and return values (or change a Game they are handed), with nothing in them that reads the keyboard or the clock. The keyboard and the clock are in terminal.cpp and main.cpp, which the test program does not even link.

A test passes before you have written anything. What does that tell you about the function, and about the test?

Answer

Nothing good about the function: it is a stub. About the test: it checks something a correct function must not do (reverse, react to an unknown key, change a finished game), and a function that does nothing never does it. Such a test only starts protecting you once the function does something.

When is the Snake spec frozen, and what may change after that?

Answer

At the end of your 20-minute spec ritual on Friday 20 November 2026. After that the spec only shrinks: a requirement can move to stretch, in writing, with the date, in the README and the log. It is never quietly redefined.

Your program crashed in the middle of a game. The prompt is back and you can type, but there is no cursor. Why can you type, why is the cursor missing, and what do you type?

Answer

zsh switched echo and line mode back on before it printed the prompt. The cursor is a different kind of thing: hiding it was a message sent to the terminal window, not a setting the shell keeps, so nothing sends the message that shows it again. tput cnorm (or reset) does. In bash, echo would still be off as well, and you would type reset blind.

What do you need to do before Tuesday's lldb session, and why?

Answer

Run sudo DevToolsSecurity -enable once, or be ready to approve a password dialog the first time lldb starts a program. macOS only lets a debugger control other programs when you have allowed it, and Developer Mode is off on this Mac.
