Chapter 02

enum class and switch

At the end of this chapter you will be able to give a value a fixed list of possibilities, such as the colours of a traffic light, so that the compiler refuses anything else. You will choose between those possibilities with a switch, avoid its one famous trap, let the compiler tell you when you forgot a case, build small state machines, and look at what the processor actually does with a switch.

The problem: a traffic light as an int

A traffic light is always in one of a few states. The obvious way to store that is a number with an agreement in a comment: 0 is red, 1 is amber, 2 is green.

#include <print>
#include <string>

// 0 is red, 1 is amber, 2 is green. This comment is the only place that says so.
std::string light_name(int light) {
    if (light == 0) {
        return "red";
    } else if (light == 1) {
        return "amber";
    } else if (light == 2) {
        return "green";
    }
    return "???";
}

int main() {
    int light = 0;
    std::println("{}", light_name(light));
    light = 7;                            // compiles: 7 is an int like any other
    std::println("{}", light_name(light));
    light = light * 2;                    // what is "red times two"? it compiles too
    std::println("{}", light_name(light));

    const int wednesday = 2;              // a weekday, numbered from Monday = 0
    std::println("{}", light_name(wednesday));   // a day where a light was meant
    return 0;
}

red
???
???
green

Every line compiled. light = 7 is accepted because 7 is an int, and so is red times two. The last call hands a weekday to a function about lights, and it answers "green", because Wednesday happens to be numbered 2. The agreement "0 is red" lives in a comment, and the compiler does not read comments. This is chapter 1's problem again, in a different shape: there it was three numbers that meant one thing; here it is one number that can mean only three things, and the type says it can mean four billion.

enum class: a type with a fixed list of values

An enumeration is a type whose values are a list of names you write out. In C++ you declare one with enum class, and each name in the list is an enumerator:

#include <print>

enum class Light { Red, Amber, Green };

int main() {
    Light now = Light::Red;
    if (now == Light::Red) {
        std::println("stop");
    }

    now = Light::Green;
    if (now != Light::Red) {
        std::println("not red any more");
    }

    std::println("Red is {}, Amber is {}, Green is {}", static_cast<int>(Light::Red),
                 static_cast<int>(Light::Amber), static_cast<int>(Light::Green));
    std::println("now is {}", static_cast<int>(now));
    std::println("sizeof(Light) = {}", sizeof(Light));
    return 0;
}

stop
not red any more
Red is 0, Amber is 1, Green is 2
now is 2
sizeof(Light) = 4

enum class Light { Red, Amber, Green }; makes a new type, Light, with exactly three values (note the ; after the brace, as for a struct). You write a value with the type name in front, Light::Red: the enumerators are scoped, which means they live inside the type's name, so Red on its own means nothing and another enumeration can have its own Red without a clash. Two Lights compare with == and != straight away; unlike a struct, an enumeration needs no extra line for that.

Underneath, each enumerator is a whole number, counted from 0 in the order you wrote them: Red is 0, Amber 1, Green 2. A Light is stored as an int, 4 bytes, and costs exactly what the int version cost. What changed is what the compiler allows:

#include <print>

enum class Light { Red, Amber, Green };

int main() {
    Light a = 2;                 // an int where a Light is wanted
    int n = Light::Green;        // a Light where an int is wanted
    Light b = Red;               // the name without its type in front
    std::println("{} {}", n, static_cast<int>(a) + static_cast<int>(b));
    return 0;
}

Three errors, three holes closed. An int cannot become a Light by accident, so light = 7 is impossible. A Light cannot quietly become an int either, so it cannot be added, multiplied or passed where a number is wanted. And the bare name Red is an "undeclared identifier": only Light::Red exists. (An rvalue, in the first two messages, is a value that is not a variable, such as 2 or Light::Green; you can read it as "a value".)

When you do want the number, for printing or for an index, say so with static_cast<int>(now), the deliberate conversion from Week 1, chapter 2. You need it for printing, too: std::println("{}", now) fails with the same "not formattable" error as a struct did in chapter 1. A function that turns each value into a name is the better fix, and it is the first job for a switch.

First principle

An enum class costs nothing at run time: it is an int in memory and in the processor. All of its value is at compile time, where it turns "a number that should be 0, 1 or 2" into "one of three named values, and nothing else". Use one whenever a variable means one of a fixed list of things.

The old enum, without class

You will meet enum Light { Red, Amber, Green };, without the word class, in older C++ and in every C library. It is the original version, and it has both holes: its names are not scoped (Red alone means 0 everywhere in the file) and its values convert to int silently. C has nothing else, so ggml, the C library under llama.cpp, uses it. In your own code, write enum class.

switch: one value, many branches

With an if chain you would test light == Light::Red, then light == Light::Amber, and so on. When one value decides between many branches, C++ has a statement made for it:

#include <print>
#include <string>

enum class Light { Red, Amber, Green };

void advise(Light light) {
    switch (light) {
    case Light::Red:
        std::println("stop");
        break;
    case Light::Amber:
        std::println("stop if you safely can");
        break;
    case Light::Green:
        std::println("go if the way is clear");
        break;
    }
    std::println("(advice given)");
}

// Each case returns, so no break is needed: return leaves the whole function.
std::string light_name(Light light) {
    switch (light) {
    case Light::Red:
        return "red";
    case Light::Amber:
        return "amber";
    case Light::Green:
        return "green";
    }
    return "?";   // only reached if light holds a number that is none of the three
}

int main() {
    advise(Light::Amber);
    advise(Light::Green);
    std::println("the light is {}", light_name(Light::Red));
    return 0;
}

stop if you safely can
(advice given)
go if the way is clear
(advice given)
the light is red

switch (light) looks at one value, once. Each case Light::Red: is a case label: a marked place in the switch's body. The program jumps straight to the label that matches the value and runs the statements from there. break; means "leave the switch now", and the program carries on after its closing brace, which is why (advice given) is printed every time. A switch works on whole-number types: int, char, and enumerations. It does not work on a std::string or a double.

light_name shows the other common shape: every case ends with return. A return leaves the whole function, so it leaves the switch too, and no break is needed. Notice the return "?"; after the switch. Every enumerator is handled, so it should never run, and clang does not demand it. It is there because a Light is only an int underneath: a cast in the other direction, or a corrupted byte, can make it hold 7, and then no case matches. Without the last line the function would reach its closing brace without returning a value, which is undefined behaviour. With it, the worst case is a "?" on screen. The text_of functions at the top of tests/snake_test.cpp follow the same pattern.

Several labels, and default

Two labels can share one block, and default: is the label for "every value not listed":

#include <print>
#include <vector>

enum class Day { Monday, Tuesday, Wednesday, Thursday, Friday, Saturday, Sunday };

bool is_weekend(Day day) {
    switch (day) {
    case Day::Saturday:
    case Day::Sunday:          // two labels, one block: Saturday OR Sunday
        return true;
    default:                   // every other value
        return false;
    }
}

int main() {
    const std::vector<Day> week = {Day::Monday, Day::Tuesday, Day::Wednesday, Day::Thursday,
                                   Day::Friday, Day::Saturday, Day::Sunday};
    for (Day d : week) {
        std::println("day {}: weekend {}", static_cast<int>(d), is_weekend(d));
    }
    return 0;
}

day 1: weekend false
day 2: weekend false
day 3: weekend false
day 4: weekend false
day 5: weekend true
day 6: weekend true

case Day::Saturday: has no statements of its own, so Saturday runs on into Sunday's statements: two labels, one answer. default: catches the five weekdays without naming them. It is convenient here, because seven cases would say nothing more. Hold on to that word "convenient", because the section after next shows what it costs.

The fallthrough trap

The Saturday-and-Sunday trick works because a case label is only a marker. The program jumps to the matching label and then runs every statement below it until something leaves the switch, labels included. Usually that something is a break. Forget one and the program does not stop at the next label:

#include <print>

enum class Suit { Clubs, Diamonds, Hearts, Spades };

void describe(Suit suit) {
    switch (suit) {
    case Suit::Hearts:
        std::println("hearts are red");
    case Suit::Diamonds:
        std::println("diamonds are red");
        break;
    case Suit::Clubs:
        std::println("clubs are black");
    case Suit::Spades:
        std::println("spades are black");
        break;
    }
}

int main() {
    std::println("-- hearts:");
    describe(Suit::Hearts);
    std::println("-- diamonds:");
    describe(Suit::Diamonds);
    std::println("-- clubs:");
    describe(Suit::Clubs);
    return 0;
}

-- hearts:
hearts are red
diamonds are red
-- diamonds:
diamonds are red
-- clubs:
clubs are black
spades are black

Hearts printed two lines, one of them about diamonds; clubs printed two, one about spades. The missing break after each first line let the program fall through into the next case. It compiled without a warning: -Wall -Wextra -Wpedantic do not include the check for this. Falling through on purpose is occasionally useful, so C++ allows it, and the marker [[fallthrough]]; exists to say "I meant this" where it happens. Clang can warn about every unmarked fallthrough with -Wimplicit-fallthrough, but that flag is not in this course's CMake recipe, so the habit has to be yours.

Trap

Every case that has statements ends with break; or return. No exceptions this week. When a switch prints or does more than you expect, look for the case above the extra output: its break is missing. Empty labels stacked on top of each other, like Saturday and Sunday, are the one shape that falls through safely, because there is nothing between them to run twice.

Analogy

A switch is a corridor of doors with the case labels painted on the floor. The value tells you where to start walking; break is the exit sign. If there is no exit sign after your section, you keep walking past the next label into someone else's room. Where it breaks: in a corridor you would notice. The program does not notice anything; it only follows the instructions that are there.

Let the compiler check you: -Wswitch

A pelican crossing needs a fourth state: amber flashing, "go if the crossing is clear". Add it to the enumeration and forget to add it to the switch:

#include <print>
#include <string>

// A pelican crossing adds a fourth state: amber flashing, go if the crossing is clear.
enum class Light { Red, Amber, Green, FlashingAmber };

std::string light_name(Light light) {
    switch (light) {
    case Light::Red:
        return "red";
    case Light::Amber:
        return "amber";
    case Light::Green:
        return "green";
    }
    return "?";
}

int main() {
    std::println("{}", light_name(Light::FlashingAmber));
    return 0;
}

The compiler noticed. -Wswitch, which clang turns on even without -Wall, checks every switch over an enumeration: if an enumerator has no case, it names the enumerator and the line. In a real program the enumeration lives in a header and the switches are spread over many files; add one value and the compiler hands you the list of every switch that must learn about it. The program still builds (it is a warning), and if you ran it, it would print ?. In this course a warning counts as a bug, so you fix it.

Now the same switch with a default::

#include <print>
#include <string>

enum class Light { Red, Amber, Green, FlashingAmber };

std::string light_name(Light light) {
    switch (light) {
    case Light::Red:
        return "red";
    case Light::Amber:
        return "amber";
    case Light::Green:
        return "green";
    default:
        return "?";       // catches FlashingAmber too, so the compiler says nothing
    }
}

int main() {
    std::println("{}", light_name(Light::FlashingAmber));
    return 0;
}

?

Silence. default handles every value not listed, FlashingAmber included, so there is nothing to warn about. The program is just as wrong, it prints ? for a perfectly good state, and now nothing tells you. That is the cost of "convenient".

First principle

In a switch over an enum class, list every enumerator and write no default. Then the compiler checks your switch every time the enumeration changes. Put the fallback for impossible values after the switch, as light_name does. Keep default for switches over plain numbers and characters, where listing every value is impossible, and for the rare enum switch where "every other value" really is one answer, like the weekdays.

State machines

A traffic light does not only have a state; it moves from one state to the next in a fixed order. A program that keeps one value saying which state it is in, plus rules for which state comes next, is a state machine. An enum class holds the state; a switch holds the rules. Here is the British sequence, in which red and amber show together before green:

#include <print>
#include <string>

// The British sequence: red, red and amber together, green, amber, then red again.
enum class Light { Red, RedAmber, Green, Amber };

std::string light_name(Light light) {
    switch (light) {
    case Light::Red:
        return "red";
    case Light::RedAmber:
        return "red+amber";
    case Light::Green:
        return "green";
    case Light::Amber:
        return "amber";
    }
    return "?";
}

// The state that comes after this one.
Light next_light(Light light) {
    switch (light) {
    case Light::Red:
        return Light::RedAmber;
    case Light::RedAmber:
        return Light::Green;
    case Light::Green:
        return Light::Amber;
    case Light::Amber:
        return Light::Red;
    }
    return Light::Red;   // the safe state, if light ever held anything else
}

// How long the light stays in this state, in seconds.
int seconds_in(Light light) {
    switch (light) {
    case Light::Red:
        return 30;
    case Light::RedAmber:
        return 2;
    case Light::Green:
        return 25;
    case Light::Amber:
        return 3;
    }
    return 0;
}

int main() {
    Light light = Light::Red;
    int clock = 0;
    for (int change = 0; change < 6; ++change) {
        std::println("t = {:3} s  {}", clock, light_name(light));
        clock += seconds_in(light);
        light = next_light(light);
    }
    return 0;
}

t =   0 s  red
t =  30 s  red+amber
t =  32 s  green
t =  57 s  amber
t =  60 s  red
t =  90 s  red+amber

Three small functions, each a switch, each answering one question about a state: what is it called, what comes next, how long does it last. The loop in main asks the questions in order. Notice that next_light's fallback after the switch is Light::Red: when a traffic light does not know what state it is in, red is the safe answer, and choosing the fallback is a design decision, not an afterthought.

Some machines also take an input, and some reach a state they never leave. A washing machine runs a programme (cotton, quick), moves through its phases, and stops at Finished:

#include <print>
#include <string>

enum class Programme { Cotton, Quick };
enum class Phase { Filling, Washing, Rinsing, Spinning, Finished };

std::string phase_name(Phase phase) {
    switch (phase) {
    case Phase::Filling:
        return "filling";
    case Phase::Washing:
        return "washing";
    case Phase::Rinsing:
        return "rinsing";
    case Phase::Spinning:
        return "spinning";
    case Phase::Finished:
        return "finished";
    }
    return "?";
}

Phase after(Phase phase) {
    switch (phase) {
    case Phase::Filling:
        return Phase::Washing;
    case Phase::Washing:
        return Phase::Rinsing;
    case Phase::Rinsing:
        return Phase::Spinning;
    case Phase::Spinning:
    case Phase::Finished:
        return Phase::Finished;   // once finished, it stays finished
    }
    return Phase::Finished;
}

int minutes_in(Phase phase, Programme programme) {
    switch (phase) {
    case Phase::Filling:
        return 3;
    case Phase::Washing:
        if (programme == Programme::Cotton) {
            return 50;
        }
        return 15;
    case Phase::Rinsing:
        return 10;
    case Phase::Spinning:
        if (programme == Programme::Cotton) {
            return 12;
        }
        return 5;
    case Phase::Finished:
        return 0;
    }
    return 0;
}

void run(Programme programme) {
    Phase phase = Phase::Filling;
    int minute = 0;
    while (phase != Phase::Finished) {
        std::println("  minute {:3}: {}", minute, phase_name(phase));
        minute += minutes_in(phase, programme);
        phase = after(phase);
    }
    std::println("  minute {:3}: {}", minute, phase_name(phase));
}

int main() {
    std::println("cotton:");
    run(Programme::Cotton);
    std::println("quick:");
    run(Programme::Quick);
    return 0;
}

cotton:
  minute   0: filling
  minute   3: washing
  minute  53: rinsing
  minute  63: spinning
  minute  75: finished
quick:
  minute   0: filling
  minute   3: washing
  minute  18: rinsing
  minute  28: spinning
  minute  33: finished

Two enumerations work together: Phase is the state, Programme is a setting that changes how long some phases last. minutes_in shows that a case can contain ordinary statements, an if here, as long as every path ends in a return. after shows a final state: Finished leads to Finished, so once the loop condition phase != Phase::Finished fails, nothing can start the machine again. A Snake game has the same kind of state, State in snake.hpp: its comment says a game starts Playing and ends Lost or Won, and never goes back.

What the processor does with a switch

This section is for Saturday's measurement strand. A switch is a description of a decision; the compiler chooses the machine instructions that make it. There are three shapes you will see.

  • A compare chain: compare the value with the first case, branch there if equal; otherwise compare with the second, and so on. It is exactly the if chain you would have written. Its cost grows with the position of the matching case. A cleverer variant compares against the middle case first and halves the range each time, like looking up a word in a dictionary; that is a tree of compares.
  • A jump table: an array, built by the compiler, with one entry per possible value, each saying where that case's code starts. The processor checks the value is in range, loads the entry, and jumps to it: one jump straight to the right case however many cases there are. The price is an indirect branch, a jump to an address the processor only learns at run time, which it has to guess in advance to stay fast.
  • A lookup table: when every case only produces a value, the compiler can skip the code and store the answers themselves in an array. The switch becomes "load element number value". No compare per case and no jump at all.

You do not choose between them; the optimiser does, and you can only look. Here is a vending machine's coin switch to look at:

#include <print>

enum class Coin {
    OnePenny, TwoPence, FivePence, TenPence, TwentyPence, FiftyPence, OnePound, TwoPounds
};

int pence(Coin coin) {
    switch (coin) {
    case Coin::OnePenny:
        return 1;
    case Coin::TwoPence:
        return 2;
    case Coin::FivePence:
        return 5;
    case Coin::TenPence:
        return 10;
    case Coin::TwentyPence:
        return 20;
    case Coin::FiftyPence:
        return 50;
    case Coin::OnePound:
        return 100;
    case Coin::TwoPounds:
        return 200;
    }
    return 0;
}

int main() {
    const int price = 135;   // a sandwich, in pence
    int paid = 0;
    paid += pence(Coin::OnePound);
    paid += pence(Coin::TwentyPence);
    paid += pence(Coin::TenPence);
    paid += pence(Coin::TenPence);
    std::println("paid {}p for {}p, change {}p", paid, price, paid - price);
    return 0;
}

paid 140p for 135p, change 5p
Looking at a switch in Compiler Explorer

Compiler Explorer (godbolt.org) shows the machine instructions a compiler produces for your code, line by line. Open it, choose C++ as the language, and paste the enum class Coin and the function pence into the left pane (leave out main, which only adds noise). In the right pane, pick the compiler: type armv8-a clang and take the highest version number. Those are clang builds for AArch64, the 64-bit Arm instruction set your M5 runs. In the options box next to it, type -std=c++23 -O2. The output is assembly: one machine instruction per line, written as text. Each source line and the instructions made from it share a background colour, and hovering over either side highlights the other. You can also make the same listing on your Mac, without the colours: clang++ -std=c++23 -O2 -S -o - pence.cpp, where -S means "stop at assembly" and -o - means "print it".

What clang made of pence, on this Mac

At -O2, a lookup table. This is the listing from clang++ -std=c++23 -O2 -S on this Mac, with Apple's linker-hint lines (Lloh) and the assembler's housekeeping lines left out:

__Z5pence4Coin:
	cmp	w0, #7
	b.hi	LBB0_2
	adrp	x8, l_switch.table._Z5pence4Coin@PAGE
	add	x8, x8, l_switch.table._Z5pence4Coin@PAGEOFF
	ldr	w0, [x8, w0, uxtw #2]
	ret
LBB0_2:
	mov	w0, #0
	ret
l_switch.table._Z5pence4Coin:
	.long	1
	.long	2
	.long	5
	.long	10
	.long	20
	.long	50
	.long	100
	.long	200

Read it top to bottom. __Z5pence4Coin is the function's name as the linker sees it: the compiler encodes the parameter types into the name ("pence, taking a Coin"); Compiler Explorer turns it back into pence(Coin) for you. The coin arrives in register w0 as its number, 0 to 7. cmp w0, #7 and b.hi mean "if it is above 7, jump to LBB0_2", which returns 0: that is your return 0; after the switch, kept for impossible values. Otherwise adrp and add put the address of the table in x8, and ldr w0, [x8, w0, uxtw #2] loads entry number w0 (each entry is 4 bytes, which is what #2, "times 4", means) into w0, where an int result is returned. The table is the eight .long lines: your eight return values, in enumerator order. Eight cases became one load.

At -O0, a compare chain. The listing is three times longer; its shape is this, cut where marked:

__Z5pence4Coin:
	sub	sp, sp, #16
	str	w0, [sp, #8]
	ldr	w8, [sp, #8]
	str	w8, [sp, #4]
	cbz	w8, LBB0_8
	b	LBB0_1
LBB0_1:
	ldr	w8, [sp, #4]
	subs	w8, w8, #1
	b.eq	LBB0_9
	b	LBB0_2
LBB0_2:
	ldr	w8, [sp, #4]
	subs	w8, w8, #2
	b.eq	LBB0_10
	b	LBB0_3
...
LBB0_8:
	mov	w8, #1
	str	w8, [sp, #12]
	b	LBB0_17
...

cbz w8, LBB0_8 is "if the coin is 0, go to the code for return 1"; then "subtract 1; if the result is zero, it was coin 1, go to return 2"; then the same for 2, and so on up to 7. A Debug build translates your switch almost literally, so a two-pound coin takes eight tests. This is one reason chapter 13 of the Week 1 book never times a Debug build.

A jump table needs bigger switches whose cases do different work. A 12-case switch over the buttons of a vending machine, each case calling a different motor function, gave this at -O2 (the start only):

__Z4vend6Button:
	cmp	w0, #11
	b.hi	LBB0_15
	...
	adrp	x9, lJTI0_0@PAGE
	add	x9, x9, lJTI0_0@PAGEOFF
	adr	x10, LBB0_2
	ldrb	w11, [x9, x8]
	add	x10, x10, x11, lsl #2
	br	x10
LBB0_2:
	bl	__Z8motor_a1v
	b	LBB0_14
...
lJTI0_0:
	.byte	(LBB0_2-LBB0_2)>>2
	.byte	(LBB0_9-LBB0_2)>>2
	...

The table lJTI0_0 holds one byte per button: how far that case's code is from LBB0_2, counted in instructions. ldrb loads the byte for this button, add ... lsl #2 turns it into an address (an instruction is 4 bytes), and br x10 is the indirect branch: jump to it. The same switch with eight buttons became a tree of compares instead: on this Mac's clang, jump tables started at about a dozen cases. Another compiler version may draw that line elsewhere, which is exactly why you look instead of assuming.

Compiler Explorer runs on Linux, so its names differ a little (pence(Coin):, .LBB0_2, :lo12: in place of @PAGEOFF); the instructions are the same kind.

Inference twin

A tensor knows its element type: 32-bit floats, 16-bit floats, or one of the quantised block formats such as Q8_0 from chapter 1's twin. In ggml that type is an enumeration, enum ggml_type, with values like GGML_TYPE_F32, GGML_TYPE_F16 and GGML_TYPE_Q8_0, written as a plain C enum because ggml is C. An operation such as "add two tensors" begins with a switch on its input's type, and each case calls the kernel written for that type: the float loop for GGML_TYPE_F32, a dequantise-then-add path for the block formats. Unlike this chapter's advice, those switches end with a default that stops the program with an error, because with dozens of types and most operations supporting only a few of them, a loud failure at run time is the honest choice. For its hottest operation, the matrix multiply, ggml goes one step further and looks the type up in a table of per-type functions: the lookup-table idea of the last section, applied to code instead of numbers. You build your own op library with a kernel per type in week 16 and read ggml's in week 27.

Check yourself

With enum class Light { Red, Amber, Green };, which of these compile: Light a = Light::Amber;, Light b = 1;, int c = Light::Green;, int d = static_cast<int>(Light::Green);? What is d?

Answer

The first and the last. An int does not convert to a Light and a Light does not convert to an int without a cast. d is 2: enumerators are numbered from 0 in the order written.

What does this print for Suit::Hearts, and how do you fix it? switch (s) { case Suit::Hearts: std::println("red"); case Suit::Spades: std::println("black"); break; default: break; }

Answer

red and then black: there is no break after the hearts line, so the program falls through into the spades case. Add break; after std::println("red");.

Why can a switch over an enum class without default be safer than one with it?

Answer

Without default, -Wswitch (on by default in clang) warns about every enumerator that has no case, so when someone adds a value to the enumeration the compiler lists every switch that needs updating. A default handles the new value silently, often wrongly, and the warning never appears.

A function returns a value from every case of a switch that lists all enumerators. Why write a return after the switch as well?

Answer

Because an enumeration is an int underneath and can, through a cast or corrupted memory, hold a number that matches no case. Then the switch does nothing, and a function that reaches its closing brace without returning a value is undefined behaviour. The extra return gives that impossible case a defined, safe answer, such as "?" or Light::Red.

What is a state machine, and which two C++ tools from this chapter build one?

Answer

A program that keeps one value saying which state it is in, plus rules for which state comes next (sometimes depending on an input). The state is an enum class; the rules are switches over it, such as next_light or after.

Name the three shapes a compiler can give a switch, and say which one has no branch at all.

Answer

A compare chain (or tree of compares), a jump table, and a lookup table. The lookup table has no branch per case: when every case only produces a value, the answers are stored in an array and the switch becomes one load.

Why did pence become eight compares at -O0 and one load at -O2, though the source is identical?

Answer

-O0 asks the compiler to translate almost literally, so the debugger can follow every line; a switch becomes the chain of tests it describes. -O2 asks it to optimise, and it noticed that every case only returns a constant, so it built a table of the eight answers instead.
