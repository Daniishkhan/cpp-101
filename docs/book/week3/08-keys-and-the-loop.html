Chapter 08

Raw keys and the game loop

At the end of this chapter you will be able to switch line mode off so that every key reaches your program the moment it is pressed, see the exact bytes each key sends, ask whether a key is waiting without stopping to wait for one, and run a loop that keeps its own time with deadlines. You will also see why that loop is the same loop that streams words out of a language model.

In this chapter
  • What line mode does to your keys before your program sees them.
  • Line mode off with ICANON, and the VMIN and VTIME settings that decide how long a read waits.
  • A key logger: the bytes of letters, Enter, Backspace and the arrow keys, and the Escape problem.
  • What read returns: 1, 0 or -1.

  • Deadlines: steady_clock::time_point, sleep_until, next += period, and counting late beats.

What line mode does to your keys

Chapter 7 named the terminal driver's line mode: it collects your typing into a line and hands your program nothing until you press Enter. Here is the evidence. This program reads one line and prints the bytes it received:

#include <cstdio>
#include <iostream>
#include <print>
#include <string>

int main() {
    std::print("type a word, then Enter: ");
    std::fflush(stdout);
    std::string line;
    std::getline(std::cin, line);
    std::print("your program received {} bytes:", line.size());
    for (char c : line) {
        std::print(" {}", static_cast<int>(c));
    }
    std::println();
    return 0;
}

$ ./line_bytes
type a word, then Enter: hello
your program received 5 bytes: 104 101 108 108 111

What was typed (checked by driving the program from a script) was h e l o, then Backspace, then l o and Enter. The screen shows hello, and the program received hello: five bytes, no wrong o, no Backspace. The driver kept the line in its own buffer, let Backspace rub out the mistake, drew every change on the screen itself, and released the finished line when Enter came. Your program slept through all of it, inside std::getline.

For a form, that is perfect. For a game it is useless: nobody presses Enter after every arrow key, and a snake cannot wait while you edit your move. The game needs each key the moment it is pressed, and it needs to keep running while no key is pressed at all.

Line mode off: every byte as it is typed

Line mode is one more switch in c_lflag, called ICANON ("canonical"). Switch it off and the driver stops collecting lines: each byte goes to your program as soon as it arrives, and nothing is edited on the way, so Backspace arrives as a byte like any other. That raises a question line mode used to answer for you: when your program asks to read, and no byte has arrived, how long should the read wait? Two more settings answer it. They live in c_cc, a row of 20 small numbers inside termios that you index with [] like a vector; VMIN and VTIME are two positions in it. VMIN is the number of bytes a read waits for, and VTIME is a time limit, counted in tenths of a second. They only matter when ICANON is off.

VMINVTIMEA read of one byte...
10waits until a byte arrives, for ever if need be. "Block until a key."
00never waits. It returns at once with a byte if one is already there, and with nothing if not.
0twaits at most t tenths of a second (so 5 means half a second) for a byte, and returns with nothing if none came.

(A fourth combination, both non-zero, waits for the first byte for ever and then times the gaps between bytes; this course does not use it.) The first row is the friendliest to learn with, so the next program uses it.

A key logger

The guard below is chapter 7's EchoOff with more to do. It switches two bits off at once, ECHO | ICANON being a mask with both bits set, and puts 1 and 0 into VMIN and VTIME. Then the program reads one byte at a time with read(STDIN_FILENO, &byte, 1), from <unistd.h>: "read from standard input into byte, at most 1 byte". It is the C function underneath std::getline, so it is handed &byte, the location of the variable, as tcgetattr was. Each byte is printed as a number, and as a character if it has a visible one.

#include <cstdint>
#include <print>
#include <termios.h>
#include <unistd.h>

// While a KeyByKey exists: no echo, no line mode, and a read waits for one byte.
struct KeyByKey {
    termios original{};

    KeyByKey() {
        tcgetattr(STDIN_FILENO, &original);
        termios changed = original;
        changed.c_lflag &= ~(ECHO | ICANON);  // two switches off at once
        changed.c_cc[VMIN] = 1;               // a read returns when 1 byte has arrived...
        changed.c_cc[VTIME] = 0;              // ...and waits as long as it takes
        tcsetattr(STDIN_FILENO, TCSANOW, &changed);
    }

    ~KeyByKey() {
        tcsetattr(STDIN_FILENO, TCSANOW, &original);
    }
};

int main() {
    KeyByKey keys;
    std::println("press keys; q quits");
    while (true) {
        std::uint8_t byte = 0;
        const auto got = read(STDIN_FILENO, &byte, 1);  // 1 byte, 0 at end of input, -1 error
        if (got != 1) {
            std::println("read returned {}", got);
            break;
        }
        if (byte >= 32 && byte < 127) {
            std::println("{:3}  {}", byte, static_cast<char>(byte));
        } else {
            std::println("{:3}", byte);
        }
        if (byte == 'q') {
            break;
        }
    }
    return 0;
}

Read the bytes. Letters are their codes from Week 1 chapter 8: a is 97, A is 65. Enter arrives as 10, the newline; the key actually sends 13, carriage return, and a switch you did not touch on the driver's input side turns it into 10 on the way. Backspace is 127 now that the driver no longer handles it, and Tab is 9. Nothing was echoed: the numbers are the program's own output.

An arrow key is three bytes: 27, 91, then a letter. 27 is the escape byte and 91 is [, the same two bytes that start the escape sequences you print (Week 1 chapter 9): the keyboard talks back in the same language. Up is 27 91 65, that is \x1b[A; down is 27 91 66, right 27 91 67, left 27 91 68. The three bytes arrive together, so the three reads return one after another without waiting.

Trap

Look at the line after 68: the Escape key on its own sends a single 27. A program that has just read a 27 cannot tell from that byte whether the Escape key was pressed or an arrow key has begun. It only knows by what comes next, and maybe nothing comes next. Every terminal program faces this ambiguity; most look at what has already arrived together with the 27, or wait a few milliseconds for more. Write down now what you would want a lone 27 to mean in a game. The comment above parse_key in snake.hpp has its own answer.

Two things this guard leaves alone

Ctrl-C is still a signal, so it kills the key logger before its destructor can run: press q. (zsh then switches echo and line mode back on, as chapter 7 showed; the Try it below adds chapter 7's flag instead.) And the output side is untouched, so \n still means "start of the next line". Week 1 chapter 9 mentioned a staircase of lines that each start where the last one ended: you get that only if output processing is switched off too, a setting in a different flag word, which neither this guard nor Snake needs.

What read returns

read returns how many bytes it put into your variable, and the type of that number is ssize_t, a signed cousin of std::size_t, so that it can also be negative. With a one-byte request there are three possible answers:

  • 1: one byte arrived and is in byte.
  • 0: no byte. With a file or a pipe as standard input, it means the input has ended. With VMIN 0, it means "nothing has arrived (yet)".
  • -1: the read failed, and byte means nothing.

The key logger checks for exactly 1 before it uses the byte, and stops otherwise. You can see the 0 by giving it a file instead of a keyboard:

$ ./key_logger < /dev/null
press keys; q quits
read returned 0

/dev/null is an empty file, so the very first read reports the end of input. (The guard's two calls quietly fail, because there is no terminal to set, and nothing is harmed.) A loop that ignored the 0 would spin for ever, printing a stale byte.

First principle

A read hands back two things: some bytes, and a count of them. The bytes mean something only when the count says they do. Check the count first, every time.

Is a key waiting? poll

A game needs a third behaviour, between "wait for ever" and "do not wait": wait for a key, but only up to a time limit, and tell me which of the two happened. The function for that is poll, from <poll.h>. You describe what to watch in a small struct, a pollfd: its fd member is which input (STDIN_FILENO), and its events member is what you are waiting for, POLLIN, "there is something to read". Then poll(&keyboard, 1, 3000) means: watch this one input for at most 3000 milliseconds. (The 1 says how many pollfds you are handing it; a program can watch several inputs at once.) It returns 1 if the input became ready, 0 if the time ran out, and -1 on failure.

#include <cstdint>
#include <poll.h>
#include <print>
#include <termios.h>
#include <unistd.h>

struct KeyByKey {
    termios original{};
    KeyByKey() {
        tcgetattr(STDIN_FILENO, &original);
        termios changed = original;
        changed.c_lflag &= ~(ECHO | ICANON);
        changed.c_cc[VMIN] = 1;
        changed.c_cc[VTIME] = 0;
        tcsetattr(STDIN_FILENO, TCSANOW, &changed);
    }
    ~KeyByKey() {
        tcsetattr(STDIN_FILENO, TCSANOW, &original);
    }
};

int main() {
    KeyByKey keys;
    std::println("press any key within 3 seconds");

    pollfd keyboard{};
    keyboard.fd = STDIN_FILENO;                  // which input to watch
    keyboard.events = POLLIN;                    // what to wait for: "there is something to read"
    const int ready = poll(&keyboard, 1, 3000);  // wait at most 3000 ms

    if (ready == 1) {
        std::uint8_t byte = 0;
        if (read(STDIN_FILENO, &byte, 1) == 1) {  // will not wait: a byte is there
            std::println("in time: byte {}", byte);
        }
    } else if (ready == 0) {
        std::println("too slow: nothing in 3 seconds");
    } else {
        std::println("poll failed");
    }
    return 0;
}

$ ./wait_for_key
press any key within 3 seconds
in time: byte 120
$ ./wait_for_key
press any key within 3 seconds
too slow: nothing in 3 seconds

The first run got an x within the time; the second got nothing for three seconds. When poll returns 1, the following read does not wait, because the byte is already there. poll answers "is there something?" and read fetches it: two separate jobs. One more fact for later: if a signal handler runs while poll is waiting, poll stops at once and returns -1. Unlike std::getline, it is not quietly restarted.

Keeping time with deadlines

Week 1 chapter 9 paced a loop like this: note when the frame started, do the work, then sleep_for(budget - spent). That measured each frame from when that frame began, and the sum came out late: 30 frames took 3130 ms instead of 3000, because every sleep woke up a little after it was asked to and each frame started from wherever the last one had really ended. The errors added up.

The fix is to plan the times in advance. A deadline is a moment in time by which something should happen. std::chrono::steady_clock::time_point is the type of such a moment: clock::now() returns one, a time point plus a duration is a later time point, and the difference of two time points is a duration. std::this_thread::sleep_until(t) sleeps until the moment t, and returns at once if t has already passed. A loop that keeps its own time then has three lines at its heart: next = clock::now() once before the loop; sleep_until(next) at the top of each round; and next += period at the end. The schedule is fixed by the plan, not by how the previous round went.

Analogy

sleep_for pacing is a bus driver told "leave ten minutes after you got back"; deadline pacing is a driver with a timetable that says 9:00, 9:10, 9:20. One slow trip makes the first driver late for the rest of the day. The second is late once, then leaves at 9:20 as printed.

Where it breaks: a real timetable has slack, and a bus that is twenty minutes late simply skips a slot. A loop that falls several periods behind finds several deadlines already in the past, and with next += period it runs the missed rounds back to back to catch up, unless you write code that decides otherwise.

Here is a metronome that beats 12 times, four beats a second, and measures how late each beat started. On beat 6 something slow happens: the program sleeps 400 milliseconds, longer than a whole period.

#include <chrono>
#include <print>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    using clock = std::chrono::steady_clock;
    using std::chrono::duration_cast;
    using std::chrono::microseconds;
    using std::chrono::milliseconds;

    const milliseconds period = 250ms;    // 240 beats per minute
    const milliseconds tolerance = 20ms;  // later than this, you would hear it
    const int beats = 12;
    int late = 0;

    const clock::time_point start = clock::now();
    clock::time_point next = start;  // the deadline of the first beat
    for (int beat = 1; beat <= beats; ++beat) {
        std::this_thread::sleep_until(next);  // sleep until the deadline itself
        const microseconds lateness = duration_cast<microseconds>(clock::now() - next);
        if (lateness > tolerance) {
            ++late;
        }
        std::println("beat {:2}  {:6} microseconds late", beat, lateness.count());

        if (beat == 6) {
            std::this_thread::sleep_for(400ms);  // something slow happens during beat 6
        }
        next += period;  // the next deadline, fixed in advance
    }

    const milliseconds total = duration_cast<milliseconds>(clock::now() - start);
    std::println("{} beats in {} ms (the plan: {} ms), {} late", beats, total.count(),
                 (beats - 1) * period.count(), late);
    return 0;
}

A metronome you can play

Now put the pieces together: the key-by-key guard, a deadline, and poll. While the metronome waits for its next beat, it should also notice a key, so that + and - change the tempo by 20 beats per minute and q quits. The trick is to give poll as its time limit exactly the time left until the next beat. Then the loop sleeps inside poll until whichever comes first: a key, or the deadline.

#include <chrono>
#include <cstdint>
#include <poll.h>
#include <print>
#include <termios.h>
#include <unistd.h>

struct KeyByKey {
    termios original{};
    KeyByKey() {
        tcgetattr(STDIN_FILENO, &original);
        termios changed = original;
        changed.c_lflag &= ~(ECHO | ICANON);
        changed.c_cc[VMIN] = 1;
        changed.c_cc[VTIME] = 0;
        tcsetattr(STDIN_FILENO, TCSANOW, &changed);
    }
    ~KeyByKey() {
        tcsetattr(STDIN_FILENO, TCSANOW, &original);
    }
};

int main() {
    using namespace std::chrono_literals;
    using clock = std::chrono::steady_clock;
    using std::chrono::milliseconds;

    KeyByKey keys;
    std::println("+ faster, - slower, q quits");

    int bpm = 120;
    int beat = 0;
    int late = 0;
    bool running = true;
    clock::time_point next = clock::now();

    while (running) {
        const clock::time_point now = clock::now();
        if (now >= next) {  // the deadline has come: beat
            beat += 1;
            if (now - next > 20ms) {
                late += 1;
            }
            std::println("beat {:3}   {:3} bpm", beat, bpm);
            next += milliseconds(60000 / bpm);  // the next deadline
            continue;
        }

        // Not yet: wait for a key, but never past the deadline.
        const milliseconds left = std::chrono::ceil<milliseconds>(next - now);
        pollfd keyboard{};
        keyboard.fd = STDIN_FILENO;
        keyboard.events = POLLIN;
        if (poll(&keyboard, 1, static_cast<int>(left.count())) == 1) {
            std::uint8_t key = 0;
            if (read(STDIN_FILENO, &key, 1) == 1) {
                if (key == '+' && bpm < 240) {
                    bpm += 20;
                } else if (key == '-' && bpm > 40) {
                    bpm -= 20;
                } else if (key == 'q') {
                    running = false;
                }
            }
        }
    }
    std::println("{} beats, {} late", beat, late);
    return 0;
}

(Real output; the keys +, +, - and q were sent by a script about a second apart.) Each time round, the loop asks one question: has the deadline come? If so, it beats, moves the deadline on by one period at the current tempo, and goes round again. If not, it computes the time left and hands it to poll. std::chrono::ceil rounds that time up to whole milliseconds; rounding down would wake poll up to a millisecond early, and the loop would find the beat not yet due and go round again. When poll reports a key, the loop reads that one byte and acts on it; when it times out, the next round finds the deadline due and beats. A new tempo takes effect from the next deadline, which is why beat 3 shows 140 bpm but arrived on the old schedule.

Notice the shape. The loop does nothing at all until something happens, a key or a deadline, and then reacts. That is an event loop, and poll with a time limit is how it waits for two kinds of event at once. Snake's loop has a different shape, the one in the comment at the top of phase1-terminal/02-snake/src/main.cpp: it does the same work on every tick, whether or not a key came. Both keep time with deadlines.

The decode loop

A language model writes its answer one token at a time: a token is a word or a piece of a word, and generating one means running the whole model once. The loop that does it is called the decode loop, and it has the shape of everything in this chapter: take the input, update the state (the KV cache, chapter 6's twin), emit one token, and go round again. Two numbers describe how fast it is. Tokens per second is the rate, the number on every inference engine's README. Per-token latency is how long one token takes: your tick, your beat. They are two views of one fact, but they hide different things, and the difference is the most important idea in measuring latency.

A user reading the answer does not experience the average. They experience the stalls. Here are 1,000 token latencies, almost all between 20 and 24 ms, except that one token in 50 takes 400 ms:

#include <cstddef>
#include <print>
#include <vector>

// The latency that `percent` per cent of the tokens beat or match: count[ms] says how many
// tokens took exactly ms milliseconds; walk up from 0 ms until enough tokens are counted.
int percentile(const std::vector<int>& count, int tokens, int percent) {
    const int needed = (tokens * percent + 99) / 100;  // round up
    int seen = 0;
    for (std::size_t ms = 0; ms < count.size(); ++ms) {
        seen += count[ms];
        if (seen >= needed) {
            return static_cast<int>(ms);
        }
    }
    return static_cast<int>(count.size()) - 1;
}

int main() {
    // 1000 per-token latencies in milliseconds: 20 to 24 ms each, except that every
    // 50th token waits 400 ms, because something else needed the machine.
    std::vector<int> latency_ms;
    for (int i = 0; i < 1000; ++i) {
        if (i % 50 == 49) {
            latency_ms.push_back(400);
        } else {
            latency_ms.push_back(20 + i % 5);
        }
    }

    int total_ms = 0;
    std::vector<int> count(1001, 0);  // count[ms], for 0 to 1000 ms
    for (int ms : latency_ms) {
        total_ms += ms;
        count[static_cast<std::size_t>(ms)] += 1;
    }
    const int tokens = static_cast<int>(latency_ms.size());
    const double mean = static_cast<double>(total_ms) / tokens;

    std::println("tokens:        {}", tokens);
    std::println("total time:    {:.2f} s, so {:.1f} tokens per second", total_ms / 1000.0,
                 tokens / (total_ms / 1000.0));
    std::println("mean latency:  {:.2f} ms", mean);
    std::println("p50 (median):  {} ms", percentile(count, tokens, 50));
    std::println("p90:           {} ms", percentile(count, tokens, 90));
    std::println("p99:           {} ms", percentile(count, tokens, 99));
    return 0;
}

tokens:        1000
total time:    29.52 s, so 33.9 tokens per second
mean latency:  29.52 ms
p50 (median):  22 ms
p90:           24 ms
p99:           400 ms

The mean, 29.5 ms, and the rate, 33.9 tokens per second, both look healthy. The percentiles tell the truth. p50, the median, is the latency that half the tokens beat or match: 22 ms. p99 is the latency that 99% of tokens beat or match, and here it is 400 ms: 2% of the tokens are stalls, more than the 1% that p99 is allowed to ignore. A reader sees the text freeze for almost half a second about every two seconds. The function percentile works by counting, not sorting: count[ms] holds how many tokens took exactly that many milliseconds, and walking up from 0 ms until enough tokens have been counted finds the answer, the way you would find the median height in a class by calling out 150 cm, 151 cm, 152 cm and counting the hands until half the class has answered.

That is why serving teams quote p99 (and p99.9) and not the mean, and why Snake's last line counts late ticks rather than reporting an average. A late tick in a game, a late beat in a metronome and a late token in a chat window are the same event: work that missed its deadline, which a person notices.

Inference twin

The game loop is a decode loop: one update per tick on a fixed time budget. Snake's tick is one step of the model: read the input, update the state, emit one frame where the model emits one token, then wait for the next deadline. A tick whose work overruns its budget is a dropped frame, and in a chat window the same thing is a latency spike. In week 18 your SmolLM2-135M engine streams tokens to the terminal through this loop, and you will measure its tokens per second and its per-token latencies with the steady_clock pattern from this chapter. Report p50 and p99 there, not just the mean.

Answer

1 and 0; 0 and 0; 0 and 5 (VTIME counts tenths of a second). All three need ICANON off.

The key logger prints 27, 91, 66. Which key was it? And what do you know when it prints a 27 and nothing else arrives?

Answer

The down arrow, \x1b[B. A lone 27 is the Escape key, but at the moment the 27 is read the program cannot be sure: the same byte starts every arrow key. Only what does or does not come with it, or soon after, tells them apart.

read(STDIN_FILENO, &byte, 1) returned 0. Name two situations that produce this, and say what the program must not do next.

Answer

The input has ended (standard input is a file or a pipe, for example /dev/null), or the terminal is set to VMIN 0 and no byte has arrived. In either case byte was not filled, so the program must not use it as if a key had been pressed.

poll(&keyboard, 1, 50) returned 0. What happened, and how long did the call take?

Answer

No byte arrived on standard input within the time limit, so poll timed out; the call took about 50 milliseconds (plus however late the operating system woke the program).

A loop sleeps with sleep_for(period) each round; another sleeps with sleep_until(next) and then does next += period. Both oversleep by about 3 ms every time. After 1,000 rounds, how far behind the plan is each?

Answer

The sleep_for loop is about 3 seconds behind (1,000 times 3 ms, plus all the work time), because each round starts from where the last one really ended. The deadline loop is only about 3 ms behind, because each sleep aims at a moment fixed in advance: a late wake-up makes the next sleep shorter.

1,000 tokens: 990 take 10 ms and 10 take 1,000 ms. What are the mean, the p50 and the p99? Which one would you put in a report to a user?

Answer

Mean: (990 × 10 + 10 × 1000) / 1000 = 19.9 ms. p50: 10 ms. p99: also 10 ms, because exactly 1% of the tokens are slow and p99 is allowed to ignore the slowest 1%; the 990th smallest latency is still 10 ms. Only p99.9 (1,000 ms) or the maximum shows the stalls. So none of the first three belongs alone in a report: a one-second freeze every hundred tokens is what the user notices, and you need the tail number, p99.9 or the maximum, to see it.
