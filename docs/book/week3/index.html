C++ from Life to Snake

Ten chapters that take you from the Game of Life you finished last week to a Snake you steer from the keyboard: your own types, a body that grows at one end and shrinks at the other, a terminal you borrow and always give back, and a debugger that shows you what your program is really doing.

What this book is

This is the Week 3 book of the 30-week curriculum in goal.md. Two weeks ago you had never written C++; since then you have built Conway's Game of Life by hand, with tests, a benchmark and a CI run, using everything in the Week 1 book. This week's program is Snake: a snake that moves one cell every tick, steered with the arrow keys, growing as it eats, getting faster as you score, dying when it hits a wall or itself. The spec, the contract and the tests are in phase1-terminal/02-snake/README.md.

Life taught you to think in data and loops. Snake adds the three things every real program needs next: your own types (a Point, a Game, a Direction that can only ever be one of four values), input while the program runs (a terminal in raw mode, and a guarantee that it is put back however the program ends), and a way to look inside a running program (lldb, in a 75-minute session on Tuesday).

The rules have not changed. Every mechanism is taught on a problem one step away from Snake, a traffic light, a queue at a counter, a password prompt, a metronome, and the book never shows you a Snake function. Chapter 9 gives you the milestones and the hint ladders; the code is yours.

How to read it

As before: in order, every example typed into scratch/ and run with tools/run.sh, every output compared character by character, check-yourself questions answered before you open the answers. The coloured boxes mean what they meant in Week 1 (first principle, analogy, inference twin, trap, try it, note); the Week 1 front page shows them all. Chapters are shorter than Week 1's, because each one has a fixed Read block and you are no longer starting from zero.

Before Tuesday 24 Nov

The debugger needs permission to control your programs, and on this Mac it does not have it yet: macOS Developer Mode is off, so the first time lldb starts a program a password dialog appears. The same permission is what lets an AddressSanitizer report name your file and line; without it, a report can stop half-way and hang. Run sudo DevToolsSecurity -enable once in Terminal (it asks for your password), or approve the dialog when it appears. Chapter 0 has the details, and a way to fix the sanitizer reports without the password.
