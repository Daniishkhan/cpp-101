Chapter 03

The debugger: lldb

This chapter is a guided session of 75 minutes for Tuesday 24 November. At the end of it you will be able to stop a running program at any line, look at every variable, walk through it one line at a time, stop only when a condition is true, see the chain of calls that led somewhere, and let AddressSanitizer and the debugger together stop a program exactly where it touched memory that is not its own. First on a small toy, then on your own Life tests.

Before Tuesday

macOS does not let one program take control of another without permission, and taking control is what a debugger does. On this Mac Developer Mode is off (DevToolsSecurity -status prints Developer mode is currently disabled.), so the first time lldb starts a program, macOS shows a dialog asking for an administrator's password, and lldb waits silently until you answer. Do this once, in Terminal, before Tuesday:

$ sudo DevToolsSecurity -enable
$ DevToolsSecurity -status

The first asks for your password; the second should now say Developer mode is enabled. Or approve the dialog on Tuesday; it can hide behind other windows, so if lldb seems to hang after run, look for it. AddressSanitizer needs the same permission to turn addresses into file names and line numbers: on this Mac, with Developer mode off, a sanitizer report stopped after its READ of size ... line and hung. Enabling Developer mode fixes both. (For the sanitizers alone, chapter 0 shows a fix without the password: ASAN_SYMBOLIZER_PATH.)

Why a debugger

Until now, when a program surprised you, you had two tools: read the code again, or add a std::println, rebuild and run. Both are guesses: you choose in advance which value to print, and if you chose wrong, you start again. A debugger is a program that runs your program under its control. It can stop it at any line, show every variable at that moment, run it one line at a time, and say which function called which to get there. You stop guessing and look.

Yours is lldb, from the same Apple command line tools as clang (lldb --version prints lldb-2100.0.17.203 here). It reads the debug information that -g puts in the executable: the names of your variables and functions, and which machine instructions came from which line. -O0, no optimisation (the default when you give no -O), keeps each line as its own code in the order you wrote it, so stepping goes line by line; an optimised build merges lines and hides variables. Your CMake Debug builds have both.

First principle

A bug is a difference between what you believe the program does and what it does. Reading the code shows you the first; a debugger shows you the second, one line and one variable at a time. When they disagree, the program is right about itself, and your belief is the thing to fix.

Analogy

A debugger is a pause button and a magnifying glass: stop the film at any frame, study every detail, advance one frame at a time. Where it breaks: pausing a film changes nothing, but pausing a program changes its timing. A bug that depends on time, such as Snake's tick deadlines or week 11's threads, can vanish while you watch.

Part 0 · The toy (5 minutes)

Save this as scratch/walk.cpp. It records six temperature readings, keeps the last three, and prints the warmest reading, the average and whether it is getting colder. It has one bug. You may spot it by reading; pretend you have not, because the next one will be in a thousand lines you did not write.

// walk.cpp: a small program with one bug, for the lldb session (chapter 3).
#include <cstddef>
#include <deque>
#include <print>
#include <vector>

enum class Trend { Falling, Steady, Rising };

struct Reading {
    int hour = 0;
    double celsius = 0.0;
};

// Rising if the newest of the recent values is above the oldest, Falling if below.
Trend trend_of(const std::deque<double>& recent) {
    if (recent.back() > recent.front()) {
        return Trend::Rising;
    }
    if (recent.back() < recent.front()) {
        return Trend::Falling;
    }
    return Trend::Steady;
}

// The warmest reading of the day.
Reading warmest(const std::vector<Reading>& readings) {
    Reading best = readings[0];
    for (const Reading& r : readings) {
        if (r.celsius > best.celsius) {
            best = r;
        }
    }
    return best;
}

// The mean temperature of all the readings.
double average(const std::vector<Reading>& readings) {
    double sum = 0.0;
    for (std::size_t i = 1; i <= readings.size(); ++i) {
        sum += readings[i].celsius;
    }
    return sum / static_cast<double>(readings.size());
}

int main() {
    const std::vector<Reading> readings = {{6, 3.5}, {9, 5.0}, {12, 8.5},
                                           {15, 9.0}, {18, 6.5}, {21, 4.0}};

    std::deque<double> recent;   // the last three temperatures, oldest first
    for (const Reading& r : readings) {
        recent.push_back(r.celsius);
        if (recent.size() > 3) {
            recent.pop_front();
        }
    }

    const Trend trend = trend_of(recent);
    const Reading top = warmest(readings);
    const double mean = average(readings);
    std::println("warmest: {} degrees at {}:00", top.celsius, top.hour);
    std::println("average: {:.2f} degrees", mean);
    std::println("trend:   {}", static_cast<int>(trend));
    return 0;
}

Everything in it is from chapters 1 and 2 except std::deque<double>, from <deque>: a vector that can also grow and shrink at the front. push_back adds at the back as you know, and pop_front removes the first element, so the loop in main leaves the last three temperatures in recent. Chapter 4 explains it; today it is something to print. Build with debug information and no sanitizers, and run it. Check that your average starts on line 37 and the call to trend_of is line 57.

$ clang++ -std=c++23 -Wall -Wextra -g -O0 scratch/walk.cpp -o scratch/walk
$ scratch/walk
warmest: 9 degrees at 15:00
average: 5.50 degrees
trend:   0

By hand: 3.5 + 5 + 8.5 + 9 + 6.5 + 4 is 36.5, and 36.5 / 6 is 6.08. The program says 5.50, with no crash and no warning. (The trend prints as 0 because std::println cannot print an enum class; 0 is Falling.)

Part 1 · Stopping and stepping (15 minutes)

The first stop with sum > 20

After its report the sanitizer hands control to lldb, which stops with stop reason = Heap buffer overflow. The stop is inside the sanitizer's own code, which has no debug information, so lldb shows machine code. bt shows the way back: a few frames in libclang_rt.asan_osx_dynamic.dylib (names and count may differ on your Mac), then your average, then main. up 5 climbs five frames at once (or repeat up until the frame names walk.cpp), and you are on the faulting line, at column 28 where celsius begins, with i showing 6. quit asks first because the program is still alive.

That is the pairing to remember. The sanitizer notices the bad access the moment it happens, even when the stray bytes are harmless zeros; the debugger lets you stand on that line and ask questions. Neither needs you to suspect the right line first.

Part 5 · Your Life tests (20 minutes)

Now the same tools on code you wrote, in phase1-terminal/01-life. Its Debug build has -g, no optimisation and the sanitizers, and its test program is an ordinary executable.

Trap

Commit before you start. Part 6 · The rule and the cheat sheet (5 minutes)

This week's rule, from goal.md and the Snake README: one blocker in your log is solved with lldb, and the log names the command that solved it. Not "used the debugger": the command and what it showed, in the "Blockers and bugs I slept on" table of docs/log/2026-W48.md. Inference twin

An inference engine runs one loop thousands of times: a decode step per token, through every layer. When token 437 comes out as nonsense, printing from every step buries you. A conditional breakpoint on the step counter, today's i == 6 written as "position equals 437", stops on that token only; frame variable shows its numbers and the length of the KV cache; bt says which layer called which kernel. And a read past the end of a cache buffer is today's heap-buffer-overflow with bigger numbers. goal.md has debugger checkpoints in weeks 7, 11, 17 and 22, each worked with today's commands.

Check yourself

Why build with -g and -O0 for debugging?

Answer

-g stores the names of variables and functions and which instructions came from which line; without it lldb cannot show source or variables by name. -O0 keeps each line as its own code in source order and keeps variables where lldb can find them; optimised code merges and reorders lines.

The arrow is on line 57, const Trend trend = trend_of(recent);. What does p trend show, and why?

Answer

A meaningless value: the arrow marks the line that runs next, so trend has not been assigned. Run the line with next, then print it.

What is the difference between next, step and finish?

Answer

next runs the current line, counting each call on it as one step. step runs to the next line anywhere, so it goes into a function called on this line (not into the standard library's own). finish runs until the current function returns and prints its return value.

A loop runs 10,000 times and goes wrong on turn 9,000. How do you stop exactly there?

Answer

A conditional breakpoint on a line inside the loop: breakpoint set -f FILE -l LINE, then breakpoint modify -c 'i == 9000' N with its number, then run or continue.

You are stopped in average and want the deque recent, which lives in main. What do you type?

Answer

up, to select main's frame, then p recent or frame variable recent; down to come back. The program does not move, only your view.

Under lldb, a sanitizer report ends with stop reason = Heap buffer overflow and machine code instead of source. Where are you, and how do you reach your line?

Answer

Inside the sanitizer's runtime, which has no debug information. bt shows its frames and, below them, yours; up (or up N) until the frame names your file, then frame variable.

Why commit src/life.cpp before adding a bug on purpose?

Answer

Because git restore src/life.cpp replaces the file with its last committed version, discarding every uncommitted change, not only the deliberate bug.

The sanitizer says READ of size 8 ... 8 bytes after 96-byte region for six Readings. Explain the 96 and the 8.

Answer

A Reading is 16 bytes (int, 4 bytes of padding, double), so six take 96. readings[6] would start at the end of the block, and its celsius is 8 bytes into it, so the 8-byte read starts 8 bytes after the region.
